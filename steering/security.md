# セキュリティ標準

> このファイルは、**どの機能にも共通して適用される防御のしかた**（入力検証、出力エスケープ、攻撃対策、シークレット管理、トークンの保管と転送、機密データ、ヘッダ、ログ、脆弱性対応）と、**認証・認可の方針**（誰かを確かめてから、何をしてよいかを決めるまで）を確定させる文書である。\
> _分担_: フィーチャー固有のセキュリティ判断と権限の一覧は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。エラー応答から機密を除く扱いは `api-standards.md` の `## エラーハンドリング（API 契約）`。セキュリティ事故が起きたときの流れは `non-functional.md` の `### 障害対応フロー（プロセス骨格）`、具体的な手順は同ファイルの `### 運用手順書の正本`。

> _書き方_: 全機能に共通する方針だけを書く。特定の機能にしか当てはまらない判断は書かない。

> _出典の表記_: 「回答 N」「回答 Q-STR-xxx」とパスの意味は `tech.md` の冒頭と同じ。「非機能要求」は WTZ 共通の「非機能要求」（回答 6 で指定）。

## 基本方針

> このプロジェクトのセキュリティで何を優先するかの原則を確定させる節。後続の各節の判断軸になる。\
> _分担_: ネットワークの公開範囲・アクセス経路・接続元の制限もこの節に書く（`non-functional.md` の `## 環境` には書かない）。

> _書き方_: 1 項目 1 行で列挙する。判断が分かれたときに立ち返れる粒度で書き、個別の設定値は書かない。

- セキュリティの方針は WTZ 共通の「非機能要求」に従う（回答 6）
- 利用者ごとにログインID を発行し、共用しない（非機能要求。回答 6）
- 画面と操作へのアクセスは権限で制御する（非機能要求。回答 6、REQ-009・REQ-020・REQ-043）
- XSS と SQL インジェクションへの対策を全画面で行う（非機能要求。回答 6）
- 新しい認証・認可の仕組みを作らず、既存 wing の仕組みに乗せる（REQ-043・REQ-045）

## 入力検証 / 出力エスケープ

> 受け取った値を確かめる作業（入り口）と、外へ出す値を無害な形に直す作業（出口）を分けて確定させる節。この 2 つは別の作業であり、片方だけでは守れない。\
> _分担_: 値が正しいかどうかを止めるのは API の境界で、ここが入り口側の要となる。DB の制約はそこを通り抜けたものに対する最後の受け皿であり、`database.md` の `## 整合性` を正とする。フィーチャー固有のファイル受付ルールは `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: どの機能にも共通して適用する内容だけを書く。

### 入り口 — 入力検証

> 受け取った値をどの層で、どこまで確かめるかを確定させる節。

> _書き方_: 層には画面、API の境界、業務ロジック、DB など、値が通過する順に書く。同じ検証を複数の層で重ねる場合は、それぞれの層が何を担うかを書き分ける。詳細の列には、より詳しい規定がある場合の参照先を書く。

| 層 | この層の役割 | 実装の要点 | 詳細 |
| --- | --- | --- | --- |
| 画面 | 必須・桁数・形式の入力チェックを行い、エラー時はメッセージを表示して処理を止める（REQ-063） | Service の `checkXxx` が `BindingResult.rejectValue` にメッセージキー付きでエラーを積み、Controller が同じ画面へ戻す | `tech.md` の `### 例外処理フロー`、`wing/src/main/java/jp/co/kccs/wt/common/utils/ValidationUtils.java` |
| 取込バッチ | 取込ファイルの拡張子・空ファイル・各行の値を確かめる | 行ごとのチェックでエラーをためる（`WTX_Batch/src/jp/co/kccs/wt/wtg/wtg040/PWTGB040CheckUtils.java`） | エラー時の扱いは各 feature の requirements で定める |

### 出口 — 出力エスケープ

> 外へ出す値を、出力先ごとに無害な形へ直す方法を確定させる節。

> _書き方_: 出力先には画面（HTML）、SQL、シェル、ログ、外部 API など、値の行き先を書く。やってはいけない例には、実際に起きやすい誤った書き方を書く。

| 出力先 | 防ぐこと | やること | やってはいけない例 |
| --- | --- | --- | --- |
| 画面（HTML） | XSS（回答 6） | Thymeleaf の `th:text` で出力し、自動のエスケープを使う | `th:utext` で利用者が入力した値をそのまま出す |
| SQL | SQL インジェクション（回答 6） | MyBatis の `#{}`（画面）、VE の検索パラメータと `?` のバインド（バッチ）で値を渡す | `${}` や文字列連結で値を SQL に埋め込む |

### 共通ルール

> 入り口と出口の両方に当てはまるルールを確定させる節。

> _書き方_: どちらか一方にしか当てはまらないものは、上の入り口または出口の節に書く。

| # | ルール |
| --- | --- |
| 1 | 入力はサーバー側で必ず検査する。Service の `checkXxx` で `BindingResult.rejectValue` にエラーを積む方式とし、Bean Validation の注釈は使わない（`tech.md` の `## 主要ライブラリ`。回答 Q-STR-110 の「Bean Validation と ValidationUtils」は誤りとして、Phase 2 ゲート 2 回目 指摘15 の修正指示で訂正） |
| 2 | 出力は Thymeleaf の `th:text` でエスケープし、`th:utext` は使わない（回答 Q-STR-110） |
| 3 | SQL は MyBatis の `#{}` でバインドし、`${}` による文字列の埋め込みは使わない（回答 Q-STR-110） |

| --- | --- | --- |

> 慎重に扱う必要があるデータを種別ごとに分け、その扱いを確定させる節。\

| マイナンバーを受け取った日 | 取込ファイルの列にあるだけで、テーブルには保存しない。ログへの出し方は contract-info-import の design で定める（Phase 4 横断検査 1 回目の差戻しにあわせた開き直しの指示、回答者 Junichi Noumi） |

## 認証・認可

> **誰であるかを確かめること（認証）** と、**その人が何をしてよいかを決めること（認可）** の方針を確定させる節。\
> _分担_: トークンの保管と転送、なりすまし要求（CSRF）や読み込み元の制限（CSP）などの共通の備えは、このファイル前半の `## セッション / トークンの保管・転送` と `## ヘッダ / トランスポート`。リソースごとの権限の一覧やフィーチャー固有のルールは `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: 誰かを確かめてから権限を判定するまでの流れと、その方針だけを書く。実装の詳細は書かない。

### 認証・認可の設計思想

> 認証と認可で何を優先するかの原則を確定させる節。方式やモデルを選ぶときの判断軸になる。

> _書き方_: 1 項目 1 行で列挙する。利便性と安全性のどちらを優先するかなど、後で判断に迷う場面を想定して書く。

- 権限制御は既存 WTB（計画・工程管理）と同様のベンダー／施工会社の権限制御方式に合わせ、本プロジェクトで別の方式を作らない（REQ-043）
- 認証は既存 wing のログインに一本化し、新しい画面は wing のインターセプタによる確認を受ける（回答 1）

### 認証

> 誰であるかを確かめる側の取り決めをまとめる見出し。方式・流れ・通行証の寿命・設計時に必ず検討する方針をここに並べる。

#### 認証方式

> このプロジェクトで採用する認証のしかたと、その理由を確定させる節。

> _書き方_: 方式は 1 つだけ書く。代替案には、検討したが採用しなかった方式と、その理由を書く。後から見た人が同じ判断に至れるように書く。

- **方式**: ログインID とパスワードによるフォームログイン（`wing/src/main/java/jp/co/kccs/wt/common/controller/LoginController.java`・`LoginService.java`）。社内用ポート以外からのアクセスは、クライアント証明書のメールアドレスも照合する（`wing` プロファイルの `CertificateWingService.java`）
- **採用理由**: 既存 WiNG のログインであり、利用者ごとのログインID を使う（非機能要求。回答 6、REQ-045）
- **代替案と不採用理由**: <AUTH_METHOD_ALTERNATIVE>（不要：既存のログイン機能と権限制御をそのまま使う — 回答 Q-STR-110）

#### 認証フロー

> 誰であるかを確かめ、通行証を渡し、以後の要求ごとに確かめ直すまでの流れを確定させる節。\
> _分担_: 署名アルゴリズムなどの実装の詳細は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: 識別、検証、発行、添付、要求ごとの検証という順序を土台に、このプロジェクト固有のステップ（外部サービスからの折り返しなど）を当てはめて書く。

| 順 | ステップ |
| --- | --- |
| 1 | 識別：利用者がログイン画面でログインID とパスワードを送る（`POST /login`） |
| 2 | 検証：ユーザーマスタを引き、ロックの有無を確かめ、パスワードの SHA-256 を照合する。必要な場合はクライアント証明書を照合する（`LoginService.checkLogin`） |
| 3 | 発行：セッションを作り直し、ランダムなセッションキーを発行して、利用者情報を `ZSESSION` に保存する（`SessionService`） |
| 4 | 添付：以後の要求はセッション（または WTX からの遷移ではパラメータ `wing_session_key`）でキーを渡す |
| 5 | 要求ごとの検証：`SessionCheckInterceptor` が `ZSESSION` の最終アクセス時刻から期限を確かめ、切れていればセッションエラー画面へ送る。続いて権限を確かめる（`#### チェックの適用箇所`） |

#### トークン / セッションのライフサイクル

> 通行証をいつ発行し、いつ効力を失わせるかを確定させる節。\
> _分担_: 保管場所の具体的な守り方は `## セッション / トークンの保管・転送`。ここには場所の指定だけを書く。

> _書き方_: 寿命は期間で書く。失効トリガには、パスワード変更やログアウトなど、効力を失わせる出来事を書く。

| 項目 | 既定 |
| --- | --- |
| アクセストークン寿命 | 最終アクセスから 30 分（`ZSESSION` の判定。`wing/src/main/resources/wing-web.properties` の `SESSION_TIMEOUT`） |
| リフレッシュトークン寿命 | <REFRESH_TOKEN_TTL>（不要：トークンは使わず、Java のセッションで認証するため — 回答 Q-STR-110b） |
| 失効トリガ | ログアウト（`LogoutController`）と、最終アクセスからの期限切れ |
| ローテーション | ログインのたびにセッションを作り直し、新しいセッションキーを発行する |
| 保管場所（クライアント） | Java のセッション（HttpSession）の Cookie（回答 6） |

#### セキュリティパターン（認証レイヤ）

> 認証の流れを設計するときに必ず検討する方針を確定させる節。\
> _分担_: Cookie の属性、CSP、ヘッダの値など実装の詳細は、このファイル前半の `## セッション / トークンの保管・転送` と `## ヘッダ / トランスポート`。ここには、いつ発行し失効させるかと対で決める方針（端末との紐付け、通行証に載せる情報、追加認証を求めるかどうか）だけを書く。

> _書き方_: パターン名と、それを採用するかどうか、採用する場合の方針を対で書く。検討した結果採用しない場合も、その旨を書く。

| パターン | 方針 | 備考 |
| --- | --- | --- |

| パスワードの定期変更 | 一定期間後にパスワードの変更を求める（非機能要求。回答 6）。有効期限の 7 日前から変更画面へ誘導する | `wing/src/main/java/jp/co/kccs/wt/common/interceptor/PasswordCheckInterceptor.java` |

### 認証 → 認可の契約（AuthContext）

> 認証に成功した後、それより後ろの層へ渡す情報の形を確定させる節。後ろの層はこの情報だけを見て判断し、生の通行証やセッションの中身を業務ロジックへ渡さない。\
> _分担_: フィーチャー固有の権限の一覧は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: 必須フィールドには、どの機能でも必ず必要になるものだけを書く。載せる情報は必要最小限にとどめ、`#### セキュリティパターン（認証レイヤ）` で決めた方針と食い違わないようにする。

| 項目 | ルール |
| --- | --- |
| 生成タイミング | ログイン成功時に作り、`ZSESSION` に保存する |
| 必須フィールド | 会社コード、利用者ID、利用者名、権限区分（`Kengen_Kbn`）、所属グループ（グループID・既定区分・事業所コード）、BS ベンダー区分（`CoVendKbn`）、施工会社区分（`CoSekoKbn`）（`WTX_Common/ds/jp/co/kccs/ds/util/DSUserUtils.java` のキー定義） |
| 任意フィールド | メールアドレス、パスワードの有効期限 |
| 型の置き場 | `WTSessionImpl`（GreenEARTH の `GSession`。`wing/lib/` の geframe-core）と `GUser` |
| 消費側 | wing のインターセプタ（`SessionCheckInterceptor`・`AccessControlInterceptor`）と Service、WTX の各画面、バッチのタスク（会社コード・利用者ID・グループID を引数で受け取る） |

### 認可

> 確かめた相手が何をしてよいかを決める側の取り決めをまとめる見出し。しくみ・確認する場所・持ち主かどうかの判定をここに並べる。

#### 権限モデル

> 何をしてよいかを決めるしくみと、その理由を確定させる節。

> _書き方_: モデルは 1 つだけ書く。定義の置き場には、権限やロールの一覧をどこで管理するかを書く。禁止には、権限名やロール名をコードに直接書き込まないなど、避ける実装を書く。

- **モデル**: 2 段で使い分ける。画面を使えるかどうかは、権限区分（`Kengen_Kbn`）によるメニュー・プログラム単位のアクセス制御を既存の `AccessControlInterceptor` で判定する。承認フローで申請者・確認者・承認者の誰の番かは、審査権限マスタ `TWTGM170`（会社コードとユーザーID）とコードマスタ `P82` で判定する。これに社外ユーザー（ベンダー／施工会社）のデータ範囲の絞り込みを組み合わせる（Phase 4 property-basic-info ゲート 1 回目 指摘15〜18 の差戻し指示、回答者 Junichi Noumi）。起案者の権限は全員が持ち、`TWTGM170` では管理しない（Phase 4 issue-request 作成中の差戻し指示、回答者 Junichi Noumi）
- **定義の置き場**: メニュー権限 `ZMENUAUTH`（会社コード × メニューID × プログラムID）、利用者の権限区分 `TWTZM010.Kengen_Kbn`、項目の出し分け `TWTZM120`（項目フィルタマスタ）、承認フローの申請者・確認者・承認者の権限 `TWTGM170`（審査権限マスタ）とその権限コード `P82`（コードマスタ）（Phase 4 issue-request 作成中の差戻し指示、回答者 Junichi Noumi）
- **採用理由**: 既存 WTB と同様の権限制御方式に合わせる（REQ-043）
- **代替案と不採用理由**: <AUTHZ_MODEL_ALTERNATIVE>（不要：既存のログイン機能と権限制御をそのまま使う — 回答 Q-STR-110）
- **禁止**: 画面を使えるかどうかの判定を機能ごとに作らない（既存の `AccessControlInterceptor` と権限の設定を使う）。承認フローの申請者・確認者・承認者の番の判定は `TWTGM170` と `P82` 以外の仕組みで作らない（Phase 4 issue-request 作成中の差戻し指示、回答者 Junichi Noumi）。画面の表示だけで制御せず、サーバー側でも権限を判定する（回答 Q-STR-110b）

#### チェックの適用箇所

> 権限の確認を、どの層で行うかを確定させる節。\
> _分担_: 権限名の一覧やリソースごとの対応表は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。ここに書く例はあくまで書き方の見本であり、一覧ではない。

> _書き方_: 層には、要求を受け取る場所、業務ロジック、データ取得など、確認を行う位置を書く。同じ確認を複数の層で重ねる場合は、それぞれの層が何を担うかを書き分ける。

| 層 | 役割 | 例 |
| --- | --- | --- |
| 要求を受け取る場所（インターセプタ） | Controller の `@FuncID` とセッションのメニューID で `ZMENUAUTH` を引き、該当が無ければ `InvalidAccessErrorException` を投げる | `wing/src/main/java/jp/co/kccs/wt/common/interceptor/AccessControlInterceptor.java` |
| 画面の表示（Service・テンプレート） | 権限区分に応じて項目・ボタンを出し分け、入力不可にする（REQ-009・REQ-020）。社外ユーザーには一部の項目を表示せず、入力もさせない。どの項目かは各 feature で定める（Phase 2 ゲート 2 回目 指摘18 の修正指示）。ボタンには、ログインユーザーの組織で出し分けるものがある。閲覧と印刷のボタンは組織がプロセス管理4G（`P71` の G6）のときだけ、再製本ボタンは所属組織が KDDI か K-ENG のときだけ表示する。組織の判定のしかたは property-basic-info の design で定める（Phase 4 issue-request 作成中の差戻し指示、回答者 Junichi Noumi） | WTB の `WTFilterUtils.filteringData`（`TWTZM120`）とボタン制御 |
| データ取得（Mapper の SQL） | 社外ユーザーのとき、自社が関係するデータだけを検索条件で絞り込む | `#### 所有権・エンティティ境界` |

#### 所有権・エンティティ境界

> 「そのデータが本当にその人のものか」を確かめる方法を確定させる節。役割による権限だけでは、他人のデータへのアクセスを防げないため、別に定める。\
> _分担_: 利用組織ごとのデータの分け方そのものは `database.md` の `## 整合性`。ここには確認のしかただけを書く。

> _書き方_: 検証タイミングには、確認をいつ行うかを書く（データを取り出す前か、取り出した後か）。権限名の形式には、名前の組み立て方を実例で示す。

| 項目 | 既定 |
| --- | --- |
| パターン | WTG の社内と社外の判定は、コードマスタ（`TWTZM040`）の識別 WTG・PARAM・P71 で行う。キー3 がログインユーザーのグループで、文字項目1 が "1" なら社外ユーザーとする。社外ユーザーが見て操作できるのは、契約稟議起案会社が自社（P71 の文字項目2）のデータと、その社外ユーザー本人が登録したデータだけとする（Phase 4 property-basic-info ゲート 1 回目 指摘15〜18 の差戻し指示、回答者 Junichi Noumi）。WTB の計画マスタ（`TWTBM080`）による方式は、WTG の新しいデータには使わない（Phase 2 ゲート 2 回目 指摘18 の修正指示）。使わないのは本案件で新しく作るテーブルのことで、既存の WTG の契約情報（契約基本情報などの `TWTGM010`〜`TWTGM070`）の絞り込みは、既存の WTB と同じ計画マスタの方式を使う。条件は、ログインユーザーのベンダー区分か施工会社区分に値があるときだけ当てはめ、両方とも空の利用者には絞り込みをしない（contract-info-download で使う）（Phase 4 横断検査 1 回目の差戻しにあわせた開き直しの指示、回答者 Junichi Noumi） |
| 検証タイミング | データを取り出す前（検索 SQL の条件に加える） |
| 権限名の形式 | メニューID とプログラムID の組（例 プログラムID `PWTGO004`）。権限の名前は持たず、`ZMENUAUTH` の行の有無で判定する |
