# セキュリティ標準

> **責務宣言: このファイルは「横断防御」と「認証・認可」を扱う。**
> 横断防御では **どの機能にも適用される共通の防御パターン**（入力検証、出力エスケープ、シークレット管理、
> トークン/セッションの保管・転送、ヘッダ、攻撃対策、ログ、脆弱性対応）を、
> 認証・認可では **認証フロー本体（誰か → 検証 → 発行 → 失効）と認可方針（モデル → チェック層 → 所有権）** を扱う（本ファイル末尾の `## 認証・認可`）。
> 個別フィーチャー固有のセキュリティ判断は `specs/<feature-name>/design.md` の Security Considerations に書く。
> セキュリティインシデント対応の**骨格**は `non-functional.md` の **障害対応フロー**、**具体手順**は同ファイルの **運用手順書の正本** から運用手順書を参照する（セキュリティインシデント時は本ファイルの **修正 SLA** も併用）。
> エラー応答の機密排除は `api-standards.md` の `## エラーハンドリング（API 契約）` を参照する。
>
> **テンプレート**: 山括弧で囲んだ大文字の項目は、プロジェクト確定時に実値へ置換する。

> **本ファイルの記入根拠**: 本改修は既存 WiNG への機能追加であり、既存のアーキテクチャ・フレームワーク・コーディング規約に従う（REQ-053）。既存機能との整合性（権限制御を含む）を維持する（REQ-009）。したがって認証・認可と横断防御の方式は、既存実装（`jp.co.kccs.wt.common.interceptor` / `service` / `utils`）を根拠として記入している。

## 基本方針

> プロジェクトのセキュリティ原則を列挙する。採用しない行は削除する。

- 既存 WiNG の防御機構（セッション確認・権限制御・CSRF トークン・入力検証）に新規機能も必ず載せる。機能側で独自の防御を作らない（REQ-009 / REQ-053）
- 権限制御は既存の方式に合わせる。新規機能のベンダー／施工会社に対する権限制御は、既存 WTB（計画・工程管理）と同様の方式とする（REQ-046）
- 画面での制御（活性・非活性・非表示）は利用者への案内であり、認可の判定はサーバ側で行う（二重防御）
- 既存 WTG 機能にデグレードを発生させない。既存の防御機構の設定・共通クラスを新規機能の都合で変更しない（REQ-052）
- <SEC_PRINCIPLE_N>（不要 / 人間 2026-09-11: 既存 WiNG の運用・実装に従う）

> **本ファイルの未記入プレースホルダーの扱い（人間判断 / 2026-09-11）**: 既存 WiNG の運用・実装に従い、本プロジェクトで新たに定めない項目には `（不要 / 人間 2026-09-11: 既存 WiNG の運用・実装に従う）` と付記し、プレースホルダーを削除せず残している。

## 入力検証 / 出力エスケープ

> **入り口**（検証）と **出口**（エスケープ）は別作業。
> 信頼できない入力を止める最終防衛線は **API 境界**。DB 制約は **データ整合性** の最後（`database.md`）。
> _分担_: フィーチャー固有のファイル受付ルールは `specs/<feature-name>/design.md` に書く。

## 認証・認可

> **このセクションは「認証 = 誰か」と「認可 = 何をしてよいか」の方針を扱う。**
> トークン・セッションの **保管・転送の安全** や、横断的な防御（CSRF / CSP 等）は本ファイル上部の横断防御セクション（`## セッション / トークンの保管・転送`・`## ヘッダ / トランスポート` 等）に書く。重複を避け、認証フロー本体（識別 → 検証 → 発行 → 失効）と認可方針（モデル → チェック層 → 所有権）をここに集約する。
> 個別リソースの権限マトリクスやフィーチャー固有のルールは `design.md` の Security Considerations に書く。

### 認証・認可の設計思想

> このプロジェクトの認証・認可で優先する価値観を列挙する。後続（認証方式・認可モデル・セキュリティパターン）の判断基準になる。

- 既存 WiNG の認証・認可の仕組みをそのまま使い、新規機能のために認証方式を追加しない（REQ-009 / REQ-053）
- 認可は「メニューID × 機能ID」の対応で判定する。機能側にロール名をハードコードしない
- 権限は画面の表示制御（REQ-016 / REQ-027）とサーバ側の判定の二重で効かせ、判定の正はサーバ側に置く
- ベンダー・施工会社に対する制御は既存 WTB と同様の方式に合わせ、独自方式を作らない（REQ-046）

### 認証

#### 認証方式

> このプロジェクトで採用する方式と理由を 1 セットだけ書く。

- **方式**: サーバサイドセッションによるフォーム認証（`LoginController` / `LoginService`、`HttpSession` + `JSESSIONID`）。パスワードは SHA-256 のハッシュで照合する
- **採用理由**: 既存 WiNG が本方式で稼働しており、既存機能との整合性を維持したまま WTG に機能を追加するため（REQ-009 / REQ-053）
- **代替案と不採用理由**: <AUTH_METHOD_ALTERNATIVE> — **不要（記入者: 人間 / 2026-09-11）**: 既存構成を変えないため代替案の検討を行わない（REQ-053）

#### 認証フロー

> 識別 → 検証 → 発行 → 添付 → 毎リクエスト検証 という不変の骨格に、プロジェクト固有のステップ（OAuth コールバック等）を当てはめて記述する。署名アルゴリズム等の実装詳細は `specs/<feature-name>/design.md`。

| 順 | ステップ |
| --- | --- |
| 1 | 識別: ログイン画面でユーザーID・パスワードを受け取る（`LoginForm`） |
| 2 | 検証: パスワードのハッシュ照合、ロックフラグ・有効期限の確認（`LoginService`。有効期限の 1 週間前から警告） |
| 3 | 発行: セッションにログインユーザー情報（会社コード・ユーザーID・グループ等）を格納する（`SessionService` / `SESSION_LOGIN_USER_INFO`） |
| 4 | 添付: 以降のリクエストは `JSESSIONID` によりセッションへ紐づく |
| 5 | 毎リクエスト検証: `SessionCheckInterceptor`（セッションの有無）→ `PasswordCheckInterceptor`（パスワード有効期限）→ `AccessControlInterceptor`（メニューID×機能IDの権限）の順に確認する |
| 6 | 失効: ログアウト（`LogoutController`）またはセッションタイムアウトで無効化する |

| アカウントロック | ロックフラグ（`Lock_Flg`）が立っているユーザーの認証を拒否する | 解除の運用は既存 WiNG に従う |
| <AUTH_SECURITY_PATTERN_N> | <AUTH_SECURITY_POLICY_N> | <AUTH_SECURITY_NOTE_N>（不要 / 人間 2026-09-11: 既存 WiNG の運用・実装に従う） |

> **責務境界**: **横断防御の実装**（httpOnly、CSRF、CSP 等）は本ファイル上部の横断防御セクション。本セクションは **いつ発行・失効するか**（ライフサイクル）と、それとセットで決める **認証上のセキュリティ方針**（紐付け・クレーム・ステップアップの要否）のみ記述する。

### 認証 → 認可の契約（AuthContext）

認証成功後、以降のレイヤは **AuthContext のみ** を参照する（生の JWT / セッション payload をドメインに渡さない）。

| 項目 | ルール |
| --- | --- |
| 生成タイミング | ログイン成功時にセッションへ格納し、リクエストごとに `LoginUserUtils.getLoginUserInfo()` で取り出す |
| 必須フィールド | ユーザーID、会社コード（`CompanyCD`）、所属グループ、メニューID（`SESSION_MENU_ID`） |
| 任意フィールド | パスワード有効期限、ロックフラグ、権限に関する付帯情報（`LoginUserInfo` が保持する範囲） |
| 型の置き場 | `jp.co.kccs.wt.common.bean.LoginUserInfo`（取得は `jp.co.kccs.wt.common.utils.LoginUserUtils`） |
| 消費側 | Interceptor・Service・帳票／CSV 出力処理。Controller から直接 `HttpSession` を読み出さない |

- AuthContext に載せる情報は、上表の必須・任意フィールドに限って最小限にする（保管のしかたは本ファイルの `## セッション / トークンの保管・転送` のルール 1）
- フィーチャー固有の権限マトリクスは `design.md` の Security Considerations

### 認可

#### 権限モデル

> このプロジェクトで採用するモデルと理由を 1 セットだけ書く。

- **モデル**: メニューID × 機能ID（PGID）による権限判定。加えてベンダー／施工会社に対しては既存 WTB と同様のデータ範囲の制御を行う（REQ-046）
- **定義の置き場**: DB 上の権限情報（`MenuAuthMapper` が参照する `ZMenuAuth`）。コード側の宣言は Controller の `@FuncID`
- **採用理由**: 既存 WiNG の権限制御の仕組みであり、既存機能との整合性（権限制御）を維持する必要があるため（REQ-009 / REQ-053）
- **代替案と不採用理由**: <AUTHZ_MODEL_ALTERNATIVE> — **不要（記入者: 人間 / 2026-09-11）**: 既存構成を変えないため代替案の検討を行わない（REQ-053）
- **禁止**: コードベース全体での権限名・ロールのハードコーディング

#### チェックの適用箇所

| 層 | 役割 | 例 |
| --- | --- | --- |
| Interceptor | 画面・機能への到達可否を毎リクエスト判定する | `AccessControlInterceptor` が `@FuncID` の機能IDとセッションのメニューIDで `ZMenuAuth` を引く |
| 画面（Thymeleaf） | 権限に応じた表示制御（活性・非活性・非表示） | 物件基本情報登録・変更画面、発行依頼書登録・変更画面の画面制御（REQ-016 / REQ-027） |
| Service | データ範囲の制御（自社・自組織の範囲に限定する等） | ベンダー／施工会社に対する制御は既存 WTB と同様の方式に合わせる（REQ-046） |
| <AUTHZ_CHECK_LAYER_N> | <AUTHZ_CHECK_ROLE_N> | <AUTHZ_CHECK_EXAMPLE_N>（不要 / 人間 2026-09-11: 既存 WiNG の運用・実装に従う） |

> **責務境界**: 上記の「例」は **パターン例**。権限名の一覧・リソースごとのマトリクスは `design.md` に書く。二重防御の方針は本ファイル上部の横断防御セクションを参照。

#### 所有権・エンティティ境界

| 項目 | 既定 |
| --- | --- |
| パターン | 会社コード（`CompanyCD`）を全テーブル共通のキーに含め、ログインユーザーの会社コードで絞り込む |
| 検証タイミング | 検索・更新の SQL 実行時（`WHERE` 条件に会社コードを含める）。画面からの受け取り値に依存しない |
| 権限名の形式 | 機能ID（PGID。`PWTGOxxx` / `PWTGBxxx`）を権限の単位とする（REQ-051） |
