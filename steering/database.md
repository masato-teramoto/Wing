# データベース標準

> **目的**: スキーマ設計・命名・型・マイグレーション・クエリ・トランザクション・整合性・バックアップ/リカバリ の方針を統一する。
> 個別フィーチャーのテーブル定義は `specs/<feature-name>/design.md` の Data Models に書き、
> ここには **全フィーチャーに適用される共通ルール** だけを書く。
> ページネーションの **HTTP 契約** は `api-standards.md`、
> サービス全体の **DR 運用手順** は `non-functional.md` を参照する。
> システム全体の ER 図・スキーマは `docs/architecture/data-model.md`、業務コード・区分値・採番ルールは `docs/code-design.md` を参照する。
>
> **テンプレート**: 山括弧で囲んだ大文字の項目は、プロジェクト確定時に実値へ置換する。

> **本ファイルの記入根拠**: 既存マスタ構造との整合性を維持する（REQ-009）。既存のアーキテクチャ・フレームワーク・コーディング規約に従う（REQ-053）。したがって命名・型・共通カラム・排他の方式は、既存実装（`jp.co.kccs.wt.common.domain` の各テーブルクラスと Mapper XML）を根拠として記入している。**個々のテーブル・カラム・ER は本ファイルに書かない**（設計ルールのみを固定し、実体は各機能の設計で確定する）。

## 設計思想

> プロジェクトの DB 設計原則を列挙する。採用しない行は削除する。

- 既存 WiNG と同一の Oracle スキーマに、既存の命名・共通カラムの規約に沿って新規テーブルを追加する（REQ-009 / REQ-053）
- 既存テーブルの定義（カラムの削除・型変更・意味の変更）を行わない。既存 WTG 機能にデグレードを発生させないため、必要な項目は新規テーブルまたはカラム追加で表現する（REQ-052）
- マスタ（現在値）と変更履歴を分けて持つ。申請・承認時に項目の変更があれば履歴テーブルに登録する（REQ-019 / REQ-034）
- 物理削除を既定としない。画面に表示して編集だけを制御する必要があるデータは論理削除で扱う（REQ-038）
- 会社コードによる所有権境界のルールは `security.md` の `#### 所有権・エンティティ境界` を正とする。本ファイルはその実現手段（共通カラム `CompanyCD` と `WHERE` の書き方）のみを定義する

## 命名規則

> 主キーの型は `## 型の指針` の「主キー・ID」の行で確定する。

| 対象 | 規約 | 例 |
| --- | --- | --- |
| テーブル名 | `T` + サブシステムコード（3 文字） + 種別 1 文字 + 3 桁の連番。既存の採番と重複しない番号を採る | `TWTGM010`（契約基本情報マスタ） |
| テーブル名の種別 1 文字 | `M` = マスタ（現在値）／`A` = 変更履歴／`D` = データ（実績・トランザクション） | `TWTGM050` / `TWTGA040` / `TWTGD010` |
| カラム名 | 意味のある英字（または日本語のローマ字）を語ごとに先頭大文字にし、必要に応じて `_` で区切る。既存テーブルと同じ意味のカラムは既存と同じ名前にそろえる | `CompanyCD` / `Grp_Id` / `Keikaku_Kichikyoku_No` |
| Java 側のフィールド名 | カラム名の lowerCamelCase。MyBatis の `mapUnderscoreToCamelCase`（有効）と SQL の `AS` 別名で対応させる。**本行を正本とする**（`tech.md` の `## 命名規則` から参照される） | `CompanyCD` → `companyCd` |
| domain クラス名 | テーブル名をそのまま大文字で使う。**本行を正本とする**（`tech.md` の `## 命名規則` から参照される） | `TWTGA010` |
| 共通カラム | 全テーブルに `CompanyCD` / `RegisteredPerson` / `RegisteredDT` / `UpdatedPerson` / `UpdatedDT` / `ExclusiveFG` を持たせる | — |
| 採番の識別 | 採番マスタ（`TWTZM050`）のグループID（`Grp_Id`）と識別コード（`Shikibetsu_Cd`）で採番対象を識別する | — |

## 型の指針

> DB エンジン名は `tech.md` で確定する。ID の型は下表の「主キー・ID」の行に **統一** する（feature ごとに変えない）。

| 用途 | 推奨型 | 備考 |
| --- | --- | --- |
| コード・区分値 | `VARCHAR2`（固定長のコード体系） | Java 側は `String`。`jdbcType=VARCHAR` を明示する |
| 会社コード | `VARCHAR2` | 全テーブル共通のキー。既存の桁数にそろえる |
| 主キー・ID | 会社コードと業務キーの複合主キー。業務キーは `VARCHAR2`（Java 側は `String`。例: `CompanyCD` 5 桁 + `Application_No` 11 桁）、同じキーの中の連番（SEQ・通番）は `NUMBER`（Java 側は数値） | 既存テーブル（`TWTGA010` ほか）の主キーの形に合わせる。UUID / ULID / 代理キーの連番 ID 列は用いない（人間が確定 / 2026-09-25） |
| 連番・通番 | `NUMBER`（採番マスタの `Current_Seq` / `Min_Seq` / `Max_Seq`）、画面・帳票に出す番号は `VARCHAR2` の採番結果 | `jdbcType=NUMERIC` を明示する |
| 日時（登録・更新） | DB レイアウト上の型は **`3:DateTime`**（Oracle の `DATE`。`SYSDATE` で設定） | **`wing` の Java 側の domain は既存どおり `String` で受ける**（`jp.co.kccs.wt.common.domain` の既存クラスに合わせる）。Java-Kit（`WTX_Batch` / `WTX_Common`）側は `DateTime` 型の語彙で扱う。**feature ごとに変えない**（人間判断 / 2026-09-24: 2026-09-24 の記述を、DB レイアウトの型と `wing` の Java 側の型を書き分ける形に改めた） |
| 日付（業務上の日付） | `VARCHAR2(8)` | Java 側は `String` の 8 桁（`YYYYMMDD`）。**feature ごとに変えない**（人間判断 / 2026-09-24: 既存に合わせる）。既存テーブルに同種のカラムがある項目は、そのカラムの型に合わせる（REQ-009） |
| フラグ | `VARCHAR2(1)`（`1` = ON / `0` = OFF。`Constants.FLG_ON` / `FLG_OFF`） | 排他フラグ `ExclusiveFG` も同じ形式 |
| 金額 | `NUMBER` | Java 側は Java-Kit 共通の `Currency` 型で扱い、**端数は切り捨て**とする。金額の自動計算（REQ-031）もこの丸めに従う。桁は各機能の設計で確定する（人間判断 / 2026-09-24: 既存に合わせる） |
| 添付ファイル | ファイル本体は DB に格納せず、出力管理マスター・出力制御マスターとファイルアップロードの仕組みで管理する（REQ-020） | `security.md` の機密データの扱いと整合 |

## マイグレーション

| ルール | 内容 |
| --- | --- |
| 変更の原則 | 既存テーブルの破壊的変更（カラム削除・型変更・NOT NULL 化）を行わない。新規テーブルの追加、またはデフォルト値を持つカラム追加で対応する（REQ-052） |
| 適用の単位 | 検証機リリース・本番機リリースのタイミングで適用する（`non-functional.md` の `## デプロイ / リリース` と整合） |
| データ移行 | データ移行のテストは発注者にて実施する（REQ-054） |
| <DB_MIGRATION_RULE_N> | <DB_MIGRATION_POLICY_N>（不要 / 人間 2026-09-11: 既存 WiNG の運用に従う） |

| # | 操作 | 手順 |

| 2 | カラム追加 | NULL 許容またはデフォルト値付きで追加 → 書き込み側をリリース → 読み出し側をリリース |
| N | <DB_ROLLOUT_OPERATION_N> | <DB_ROLLOUT_STEPS_N>（不要 / 人間 2026-09-11: 既存 WiNG の運用に従う） |

## クエリパターン

> _分担_: ページネーションの HTTP 契約（カーソル / オフセットの API 形式）は `api-standards.md`。
> ここは **DB 層の実装方針** のみを定義する。
> 検索対象カラム・スコアリング・同期方式は `specs/<feature-name>/design.md` に書く。

| パターン | 方針 |
| --- | --- |
| SQL の置き場 | Mapper XML に書く。Java 側で SQL 文字列を組み立てない。**本行を正本とする**（`tech.md` の `## コード規約`・`security.md` の SQL インジェクション対策から参照される） |
| パラメータ | `#{...}` を使い `jdbcType` を明示する。`${...}` による文字列連結を使わない。**本行を正本とする**（`tech.md` の `## コード規約`・`security.md` の SQL インジェクション対策から参照される） |
| 検索条件の可変長 | MyBatis の動的 SQL（`<if>` / `<where>` 等）で組み立てる。検索項目が多い画面（20 項目程度 — REQ-013）でも条件の有無で分岐させる |
| 会社コードの絞り込み | 検索・更新の `WHERE` に必ず会社コードを含める（ルールの正本は `security.md` の `#### 所有権・エンティティ境界`。ここは SQL での実現方法のみ） |
| 一覧取得 | 表示件数の上限と並び順を SQL 側で確定させる。全件をメモリに読み込んでからの絞り込みを行わない |
| CSV 出力 | 一覧と同じ SQL の結果を用いる（REQ-014 / REQ-021 / REQ-047）。出力のためだけに別条件の SQL を作らない |
| 排他制御 | 更新時は排他フラグ（`ExclusiveFG`）を `WHERE` 条件に含めて更新件数を確認する楽観排他。更新件数が 0 件なら `ExclusiveException` を投げる。採番のように直列化が必要な処理のみ `SELECT ... FOR UPDATE`（`NumberingMapper.selectNumberingForLock`） |

- **インデックス方針**: インデックスは検索条件（REQ-013 の 20 項目程度の検索条件、および一覧の並び順）に基づいて設計する。既存テーブルへのインデックス追加は既存機能の実行計画に影響するため、影響範囲を確認してから行う（REQ-052）。個々のインデックス定義は `specs/<feature-name>/design.md` の Data Models に書く。

## 接続 / トランザクション

> コネクションプール・アイソレーション・長時間トランザクション禁止を固定し、DB の過負荷やデッドロックを予防する。

| 項目 | 既定 |
| --- | --- |
| 接続の取得 | JNDI データソース `java:comp/env/jdbc/wingDB`（コンテナ管理）。アプリケーション側で接続情報を持たない |
| コネクションプール | Tomcat のリソース定義に従う（アプリケーション側で設定を持たない） |
| トランザクション境界 | Service クラス。`@Transactional`（参照のみのクラスは `@Transactional(readOnly = true)`、更新メソッドに `@Transactional`）。`DataSourceTransactionManager` + `tx:annotation-driven` |
| アイソレーション | Oracle の既定（READ COMMITTED）。機能側で変更しない |
| ステートメントタイムアウト | 1800 秒（`mybatis-config.xml` の `defaultStatementTimeout`） |
| 長時間トランザクション | 画面操作をまたぐトランザクションを張らない。画面をまたぐ競合は排他フラグによる楽観排他で検出する |
| バッチの単位 | 大量件数の取込・洗替（REQ-042 / REQ-043）はコミット単位を決めて分割する。単位は各機能の設計で確定する |

## 整合性

> _分担_: 所有権チェック・マルチテナントの認可ロジックは `security.md` の `## 認証・認可`。
> ここは **制約の置き場所とマルチサービス整合** の方針のみを定義する。

- 主キー・一意制約・NOT NULL は DB 側の制約として持つ。アプリケーション側のチェックだけに依存しない
- 業務ルール（承認フローの遷移可否、金額の整合など）はアプリケーション側（Service）で判定する。DB のトリガに業務ルールを埋め込まない
- マスタと変更履歴の整合は同一トランザクション内で行う（マスタ更新と履歴登録を分けない — REQ-019 / REQ-034）
- オンラインとバッチが同じテーブルを更新する場合の競合は、排他フラグと更新件数の確認で検出する（`## クエリパターン` の排他制御）
- 取込（インポート）による洗替更新は、対象範囲を明示してから置き換える（REQ-043）
- <DB_INTEGRITY_RULE_N>（不要 / 人間 2026-09-11: 既存 WiNG の運用に従う）
