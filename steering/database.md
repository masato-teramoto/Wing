# データベース標準

> このファイルは、**全フィーチャーに共通して適用される DB のルール**（スキーマ設計・命名・型・マイグレーション・クエリ・トランザクション・整合性・バックアップ）を確定させる文書である。\
> _分担_: 個別フィーチャーのテーブル定義は `specs/<feature>/design.md` の `## データモデル（Data Models）`。ページネーションの HTTP としての約束は `api-standards.md` の `## 一覧取得（ページネーション / フィルタ / ソート）`、何を機密として扱うかは `security.md` の `## 機密データ`、サービス全体の災害復旧の進め方は `non-functional.md` の `## バックアップ / DR（サービス全体）`。システム全体の ER 図は `docs/architecture/data-model.md`、業務コード・区分値・採番ルールは `docs/code-design.md`。

> _書き方_: 全フィーチャーに共通するルールだけを書く。特定のテーブルにしか当てはまらない内容は書かない。

> _出典の表記_: 「回答 N」「回答 Q-STR-xxx」とパスの意味は `tech.md` の冒頭と同じ。DB 製品は `tech.md` の `## コアテクノロジ`（Oracle Database）。

## 設計思想

> このプロジェクトの DB 設計で何を優先するかの原則を確定させる節。後続の各節の判断軸になる。

> _書き方_: 1 項目 1 行で列挙する。判断が分かれたときに立ち返れる粒度で書く（正規化をどこまで進めるか、削除を実際に消すか印を付けるだけにするか、など）。

- 区分値はコードマスタ `TWTZM040` で管理し、採番は採番マスタ `TWTZM050` を使う（既存 WiNG の方式。計画了承時の人間確定事項）。画面は `wing/src/main/resources/jp/co/kccs/wt/common/mapper/NumberingMapper.xml`、バッチは `DSNumberingUtils`・`DSDaoTWTZM040`（`WTX_Common/ds/`）で扱う。個別のコード値と採番対象は `docs/code-design.md` が持つ
- 既存のテーブルとマスタ構造を維持し、新しいテーブルは既存の命名と共通カラムに合わせる（REQ-004）
- 申請・承認の対象データの履歴は、`product.md` の `## ビジネスルール / ポリシー`（申請・承認の履歴）に従う。項目の変更履歴を残す表は種別 `A` の履歴テーブルとし（既存例 `TWTGA010`〜`TWTGA070`）、本案件では発行依頼書の `TWTGA130` と契約局情報の `TWTGA150` の 2 つが該当する（Phase 4 property-basic-info ゲート 1 回目 指摘15〜18 の差戻し指示、回答者 Junichi Noumi。Phase 4 issue-request 作成中の差戻し指示、回答者 Junichi Noumi）

## 命名規則

> テーブル・カラム・制約などの名前の付け方を確定させる節。\
> _分担_: フィーチャー固有のテーブル名とカラム定義は `specs/<feature>/design.md` の `## データモデル（Data Models）`。主キーの型は `## 型の指針`。コード上の識別子の命名は `tech.md` の `## 命名規則`。

> _書き方_: 対象には、テーブル、カラム、主キー、外部キー、インデックス、制約など、名前の付け方が変わる単位を書く。例には、そのまま真似できる実例を書く。

| 対象 | 規約 | 例 |
| --- | --- | --- |
| テーブル（業務） | `TWT` ＋ サブシステム 1 文字 ＋ 種別 1 文字 ＋ 3 桁の番号。種別は `M`＝マスタ、`A`＝変更履歴、`D`＝データ、`F`＝トラン（既存のテーブル名とコメント。`wing/src/main/java/jp/co/kccs/wt/common/domain/`） | `TWTGM010`（契約基本情報）・`TWTGA060`（契約支払情報変更履歴）・`TWTGD010`（支払実績） |
| テーブル（共通基盤） | フレームワーク・共通の表は `Z` / `S` で始まる既存の名前をそのまま使う | `ZSESSION`・`ZMENUAUTH`・`STASKLIST` |
| カラム | 単語の先頭を大文字にし `_` でつなぐ（ローマ字・英語の混在あり）。フラグは `_FG` / `_Flg`、区分は `_Kbn`、コードは `_Cd` / `CD` | `Keikaku_Kichikyoku_No`・`Payment_Decision_FG`・`Kengen_Kbn`・`Shikibetsu_Cd` |
| 共通カラム | 全テーブルに会社コード・登録者・登録日時・更新者・更新日時・排他用の値を持つ | `CompanyCD`・`RegisteredPerson`・`RegisteredDT`・`UpdatedPerson`・`UpdatedDT`・`ExclusiveFG` |

## 型の指針

> 用途ごとに使う型を確定させる節。\
> _分担_: DB エンジンの製品名とバージョンは `tech.md` の `## コアテクノロジ`。ここには型の選び方だけを書く。

> _書き方_: 用途には、ID、金額、日時、真偽値、文字列、区分値など、型を迷いやすいものを書く。**ID の型は 1 種類に統一する。** 備考には、その型を選ぶ理由や、使ってはいけない型を書く。

| 用途 | 推奨型 | 備考 |
| --- | --- | --- |
| 金額 | 数値（Java は `BigDecimal`） | 浮動小数点で扱わない（`PWTGB030Job` の `convertBigDecimal`） |
| 登録・更新日時 | 日時（Java は `java.util.Date`。値は DB の `SYSDATE`） | 共通カラム `RegisteredDT`・`UpdatedDT` |
| 業務上の日付・年月 | 文字列（`yyyyMMdd` / `yyyyMM`） | 既存の業務項目の形式に合わせる |
| 区分値・フラグ | 文字列のコード（例 `'0'` / `'1'`、`'01'`） | 区分値の意味は `TWTZM040` に持つ |
| ID・番号 | 0 詰めの文字列 | 例 `Pay_CD`＝`001`。採番は `TWTZM050` |
| 排他用の値 | 文字列（ランダムな値） | 共通カラム `ExclusiveFG`。更新時に照合する |

> _書き方_: ルールには、ファイルの作り方、番号の付け方、適用済みのものを書き換えてよいか、戻す手段を用意するかなどを書く。

| ルール | 内容 |

## クエリパターン

> よく使う問い合わせの書き方と、索引（インデックス）の考え方を確定させる節。\
> _分担_: ページネーションを HTTP でどう表すかは `api-standards.md` の `## 一覧取得（ページネーション / フィルタ / ソート）`。検索対象のカラム、順位付け、同期のしかたは `specs/<feature>/design.md` の `### 物理データモデル（Physical Data Model）`。ここには DB 側の実装方針だけを書く。

> _書き方_: パターンには、一覧の取得、件数の取得、全文検索、まとめての更新など、書き方を揃えたいものを書く。インデックス方針には、どういう場合に索引を張り、どういう場合は張らないかを書く。

| パターン | 方針 |
| --- | --- |
| 検索（画面） | MyBatis の Mapper XML に書き、値は `#{}` でバインドする（`wing/src/main/resources/jp/co/kccs/wt/function/wtg/wtg002/Pwtgo005Mapper.xml`） |
| 検索・更新（バッチ） | VE の検索パラメータで位置を指定してバインドし、`findList` / `findRecord`、`insert` / `update` / `delete` を使う（`WTX_Batch/src/jp/co/kccs/wt/wtg/wtg030/PWTGB030Job.java`） |
| 件数の取得（バッチ） | VE の `getListCount` を使う |
| まとめての更新（バッチ） | `DSBatchInsertStatement` / `DSBatchUpdateStatement` / `DSBatchDeleteStatement` を使う（`WTX_Common/ds/jp/co/kccs/ds/core/db/`） |
| 洗替 | 対象行を履歴テーブルへ退避してから削除し、入れ直す（`PWTGB030Job` の `deleteTWTGM040`・`insertTWTGM040`）。このやり方は既存のバッチ（`PWTGB030Job`）の例で、すべての洗替の決まりではない。契約情報取込では、洗替の前の内容をトランに写し、洗替の後と比べて、変わった行だけを変更履歴に登録する（Phase 4 横断検査 1 回目の差戻しにあわせた開き直しの指示、回答者 Junichi Noumi） |

- **インデックス方針**: 主キーと検索条件に使う列に付ける。個々のインデックスは DB レイアウト設計書で定義する（回答 Q-STR-114b）

## 接続 / トランザクション

> DB への接続の持ち方と、複数の更新をひとまとまりとして扱う範囲を確定させる節。DB に負荷が集中することや、処理どうしが互いの終了を待ち続けることを防ぐための決まりを置く。

> _書き方_: 項目には、同時に持てる接続の数、待ち時間の上限、分離のしかた（同時に動く処理から互いの途中経過をどこまで見せるか）、1 つのまとまりに含めてよい処理の範囲などを書く。外部への通信を含んだまま長時間まとめない、といった禁止事項もここに書く。

| 項目 | 既定 |
| --- | --- |
| 接続の取得（画面） | Tomcat の JNDI データソース `jdbc/wingDB`（最大接続数 150。`wing/src/main/webapp/META-INF/context.xml`） |
| トランザクション（画面） | Service 単位。クラスは `@Transactional(readOnly = true)`、更新メソッドは `@Transactional`（`tech.md` の `## コード規約`） |
| トランザクション（バッチ） | ジョブ全体で 1 つ。`beginTransaction` → 全件処理 → `commitTransaction`、エラー時は全件ロールバック（`PWTGB030Job`）。例外として、契約情報取込で物件申請情報の状態を取込中にする更新と、元の状態に戻す更新は、取込の本体とは別に確定させる。取込がエラーで全件取り消しになったときも、元の状態に戻す（Phase 4 横断検査 1 回目の差戻しにあわせた開き直しの指示、回答者 Junichi Noumi） |
| 採番のトランザクション | 業務のトランザクションとは別の接続で、採番だけを確定させる（`DSNumberingUtils`） |
| 行ロック | 更新前に `SELECT … FOR UPDATE` で行をロックする。取得できないとき（ORA-54）は設定した回数だけ待って再試行する（`DSDBUtils.findRecordForUpdate`） |
| SQL のタイムアウト | 画面の MyBatis は 1800 秒（`wing/src/main/resources/mybatis-config.xml`）、バッチの geframe は 20 秒（`WTX_Batch/config/ge-framework.properties`） |

## 整合性

> データが矛盾しない状態を、どの層でどう守るかを確定させる節。\
> _分担_: 誰がそのデータを見てよいかの判定は `security.md` の `## 認証・認可`。入り口での入力検証は同ファイルの `## 入力検証 / 出力エスケープ`。ここには制約をどこに置くかと、複数のサービスにまたがる場合の揃え方だけを書く。

> _書き方_: DB の制約で守るもの、アプリケーション側で守るものを書き分ける。複数のサービスにまたがる場合は、どこまで即時に揃え、どこから遅れて揃うことを許すかを書く。

- 同時更新は共通カラム `ExclusiveFG` の照合で防ぎ、一致しなければ排他エラーにする（アプリ側。`tech.md` の `## コード規約`）
- 会社コード `CompanyCD` を検索条件に含め、会社ごとのデータを混ぜない（既存の Mapper・VE の条件）
