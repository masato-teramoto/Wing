## Introduction（概要）

> このフィーチャーが何のために、誰のためにあるかを 2〜3 段落で書く。`背景` はなぜ今このフィーチャーが必要か、`対象ユーザー` は想定する利用者像、`期待する変化` はこのフィーチャーがあると何が変わるか。

作成組織検索（ZOOM）は、物件基本情報登録変更画面と発行依頼書登録変更画面から呼び出され、担当者が作成組織を選んで入力欄に設定するための検索画面である（REQ-048 / REQ-050）。検索項目は 3 項目とし、いずれもプルダウンで表示する（REQ-049）。

本フィーチャー単体では利用者の用事は終わらず、呼び出し元画面の入力を助けるために働く Platform Feature である（`.aidd/feature-list.md`）。呼び出し元の 2 画面より先に用意する必要があるため、優先度 1 に置かれている。

- **背景**: 契約書発行依頼業務のシステム化にあたり、入力項目が多いことが担当者の負担になっている（REQ-002）。作成組織をコードの直接入力ではなく検索・選択で指定できるようにすることで、入力の負担と誤入力を減らす
- **対象ユーザー**: 物件基本情報および発行依頼書を登録・変更する担当者（`steering/product.md` の対象ユーザー）
- **期待する変化**: 作成組織のコードを記憶・転記することなく、プルダウンで絞り込んで選択できるようになり、誤った作成組織を指定することがなくなる

> プロダクトレベルの目的・価値は steering の `product.md` を参照。ここではこのフィーチャー固有の文脈を書く。

## Boundary Context（境界文脈）

> スコープの誤読が起こりやすい場合や、隣接するシステム / スペックに影響する場合は必ず記述する。
> `_N` の行を項目の数だけ増やす。`Out of Scope` は扱わない振る舞いに加えて理由または委譲先を書く。`Adjacent` は前提として動いている他フィーチャー / API / バッチ、およびこのフィーチャーが依頼している外部側の責務を書く。

- **In Scope（このフィーチャーで扱う）**:
  - 作成組織検索（ZOOM）画面を新規に作成する（REQ-048）
  - 3 項目（会社名・部署名・所属名）の検索条件をプルダウンで表示し、条件に一致する作成組織を検索して一覧に表示する（REQ-049）
  - プルダウンの選択肢を、作成組織を管理するマスタから取得する（REQ-049 の詳細化として人間が確定 / 2026-09-11）
  - 一覧から選択された作成組織の値を呼び出し元画面へ返して入力欄に設定する（REQ-050）
  - ログインユーザーの会社コードによる検索対象の絞り込み（`steering/security.md` の所有権・エンティティ境界）
- **Out of Scope（扱わない）**:
  - 作成組織そのものの登録・変更・削除。作成組織はマスタとして既に存在するものを参照するのみであり、マスタの保守は本プロジェクトの改修対象外（REQ-007 / REQ-008）
  - 呼び出し元画面の入力チェック・保存処理。呼び出し元である `property-basic-info` / `issue-request` が持つ
  - 作成組織以外の ZOOM 画面。既存の ZOOM 画面は改修対象外（REQ-008）
- **Adjacent（隣接システム / 隣接スペックへの期待）**:
  - `property-basic-info`: 物件基本情報登録変更画面から本画面を起動し、返された作成組織を自画面の入力欄に反映する（REQ-050）
  - `issue-request`: 発行依頼書登録変更画面から本画面を起動し、返された作成組織を自画面の入力欄に反映する（REQ-050）
  - 既存 WiNG の共通基盤: 権限制御（`AccessControlInterceptor` + `@FuncID`）・セッション・ZOOM 画面の表示サイズ定義（`wing-web.properties` の `ZOOM_DEFINE`）を提供する（`steering/architecture.md` / `steering/tech.md`）

## Requirements（要件）

> 要件 ID は **数値**（`1`, `1.1`, `2`, `2.1` ...）のみ。`A`, `B` などのアルファベット ID は使わない。
> 各要件は **User Story** + **Acceptance Criteria（EARS 形式）** で構成する。
> **`### Requirement` のブロックを要件の数だけ複製する。** 要件領域名は、その要件がどの範囲を扱うかが分かる名前にする。

### Requirement 1: 作成組織検索画面の表示

> 由来する要求ID: REQ-048

**User Story**: 物件基本情報または発行依頼書を登録・変更する担当者として、呼び出し元画面から作成組織検索画面を開きたい。なぜなら作成組織のコードを覚えていなくても入力欄を埋められるようにしたいから。

#### Acceptance Criteria（EARS 形式）

> 1 項目 = 1 基準。`_N` の行を基準の数だけ増やす。下の早見表のいずれかのパターンに当てはめて書く。

1. When 呼び出し元画面で作成組織検索の起動操作が行われたとき、the system shall 作成組織検索画面を別ウインドウで表示する。
2. The system shall 作成組織検索画面の表示サイズを、既存 ZOOM 画面と同じく `wing-web.properties` の `ZOOM_DEFINE.<PGID小文字>` の定義に従って決定する（`steering/tech.md` の命名規則）。
3. If ログインしていないセッションから本画面のリクエストが行われた場合、then the system shall 画面を表示せずログイン画面へ遷移させる（`steering/security.md` の認証フロー）。
4. If ログインユーザーが本画面の機能ID（PGID）に対する権限を持たない場合、then the system shall 画面を表示せずエラー画面にメッセージIDに対応する文言を表示する（`steering/security.md` の認可）。
5. The system shall 新規に採番する画面ID・PGID を、既存の採番体系に従って付与する（REQ-051 / `steering/tech.md` の命名規則）。どの体系に属させるかは基本設計で確定する（`## Dependencies / Assumptions` の未確定事項 ①）。

### Requirement 2: 作成組織の検索

> 由来する要求ID: REQ-049

**User Story**: 担当者として、作成組織を 3 つの条件で絞り込んで探したい。なぜなら候補が多い中から目的の作成組織を確実に選びたいから。

#### Acceptance Criteria（EARS 形式）

1. The system shall 作成組織検索画面に検索条件を 3 項目表示し、その内容を「会社名」「部署名」「所属名」とする。
2. The system shall 3 つの検索条件をいずれもプルダウン（選択式）で表示し、自由入力の欄を設けない。
3. The system shall 各プルダウンの選択肢を、作成組織を管理するマスタから取得して表示する。取得元のマスタは基本設計で確定する（未確定事項 ②）。
4. When 検索が実行されたとき、the system shall 指定された検索条件に一致する作成組織の一覧を表示する。
5. If 検索条件に一致する作成組織が 1 件も存在しない場合、then the system shall 一覧を空で表示し、該当が無いことを示すメッセージIDに対応する文言を表示する。
6. The system shall 検索の対象を、ログインユーザーの会社コードで絞り込む（`steering/security.md` の所有権・エンティティ境界）。絞り込みの範囲と検索条件「会社名」の関係は基本設計で確定する（未確定事項 ③）。
7. The system shall 検索結果の並び順を、実行のたびに同じ条件では同じ順序になるよう SQL 側で確定させる（`steering/database.md` のクエリパターン）。

### Requirement 3: 呼び出し元画面への選択結果の返却

> 由来する要求ID: REQ-050

**User Story**: 担当者として、選んだ作成組織が呼び出し元画面の入力欄に入ってほしい。なぜなら選択した内容を手で転記し直したくないから。

#### Acceptance Criteria（EARS 形式）

1. The system shall 本画面の呼び出し元を、物件基本情報登録変更画面と発行依頼書登録変更画面の 2 画面とする。
2. When 一覧から作成組織が選択されたとき、the system shall 選択された作成組織の値を呼び出し元画面の作成組織の入力欄に設定し、本画面を閉じる。設定する値がコードか名称か（または両方か）は基本設計で確定する（未確定事項 ④）。
3. When 作成組織を選択せずに本画面が閉じられたとき、the system shall 呼び出し元画面の入力値を変更しない。
4. The system shall 呼び出し元画面ごとに異なる返却仕様を持たず、2 つの呼び出し元に対して同一の形式で選択結果を返す。

## Out of Scope（明示的に対象外）

> Boundary Context だけで誤読を防ぎきれないとき、追加でここに書く。
> 1 項目 = 1 件。`_N` の行を件数だけ増やす。対象外にするものと、なぜ対象外か、どこで扱う予定かを書く。

- 作成組織マスタのデータ整備・移行。データ移行のテストは発注者にて実施する前提であり（REQ-054）、本フィーチャーはマスタを参照するのみ
- 既存の ZOOM 画面（`zwtz001` 以下）の改修。WTG 以外および既存機能は改修対象外（REQ-007 / REQ-008 / REQ-052）
- ベンダー／施工会社に対するデータ範囲の制御方式そのものの定義。方式の正は `steering/security.md` であり、本フィーチャーはそれに従う（REQ-046 は `制約` 分類）

## Dependencies / Assumptions（前提と依存）

> `前提` はこのフィーチャーが成立するために真でなければならない事項、`依存` は他フィーチャー / 既存システム / 外部 API / データ、`未確定事項` は調査・確認待ちのトピック（design に進む前に解消する）。

- **前提**: 作成組織のマスタが既存 WiNG に存在し、参照できること。既存 WiNG の認証・セッション・権限制御の仕組み（`LoginService` / `SessionCheckInterceptor` / `AccessControlInterceptor`）がそのまま利用できること（REQ-009 / REQ-053）
- **依存**: `.aidd/feature-list.md` の `依存` 列は「なし」。本フィーチャーは他 feature の完成を前提としない。既存 WiNG の共通基盤（権限制御・セッション・ZOOM 表示サイズ定義）には依存する
- **未確定事項**: 次の 5 件は **いずれも基本設計で確定する**（REQ-010。人間判断 / 2026-09-11）。
  - ① **画面ID・PGID の採番体系と具体値**。REQ-051 は新規機能を `GWTGxxx` / `PWTGOxxx` で採番するとし、`steering/tech.md` の命名規則は既存 ZOOM 画面を `z` 始まりのパッケージ（例 `zwtz002`）としている。本画面をどちらに属させるか
  - ② **作成組織のデータ源**。プルダウンの選択肢と検索対象を、コードマスタ（`steering/database.md` の区分値）から取るか、作成組織を管理する専用のマスタから取るか
  - ③ **検索条件「会社名」と会社コードによる絞り込みの関係**。`steering/security.md` はログインユーザーの会社コードで絞り込むと定めており、作成組織が複数会社にまたがるかどうかで「会社名」プルダウンの選択肢が変わる
  - ④ **呼び出し元へ返す値**。作成組織のコードか名称か、または両方か
  - ⑤ **検索結果の表示件数の上限**と、一覧に表示する項目・並び順
  - なお 3 つの検索項目を「会社名」「部署名」「所属名」とすることは 2026-09-11 に人間が確定した（REQ-049 の詳細化であり、要求一覧の変更を伴わない）
