---------- 印刷・閲覧用帳票（print-report） ----------

Q-RQ-PR-001：
今の手順は、ほかの feature と同じでよい。
帳票は、物件基本情報登録変更画面の閲覧ボタンと印刷ボタンで出す。
出すのは、発番の後の申請者・確認者・承認者（再製本は起案者も）で、組織がプロセス管理4G の利用者である。
主に、決裁に回す前の確認と、製本のための印刷に使う。

Q-RQ-PR-002：
原本の Excel のテンプレートがある。原本をコピーして値を入れ、PDF に変換して出す。原本が無いときはエラーにする。
ページは A4 縦で、次のように組む。
・閲覧で単独局：表紙と発行依頼書の2ページ
・閲覧で複数局：表紙、発行依頼書、契約局情報の3ページ
・印刷で単独局：表紙の1ページ
・印刷で複数局：表紙と契約局情報の2ページ
契約局情報には、全部の契約局を連番の順に、No・基地局番号・基地局名で並べる。1ページに入らないときはページを分け、ページ番号を付ける。
表紙には、代表局番号、提出日、申請者・確認者・決裁者の印、決裁日、基地局番号と基地局名、所在地、起案の部署と氏名、案件グループ、締結者、支払の内容、契約期間、受電方法、賃料、製本と押印の種別、部数、添付資料、QR コードなどを出す。
発行依頼書には、関係者①〜⑤、契約の内容、支払の内容、製本の情報、添付資料などを出す。
各ページの項目の全部と配置は、design の帳票設計で定める。

Q-RQ-PR-003：
QR コードには、代表局（契約局情報の1行目）の稟議バーコードNo を入れる。
稟議バーコードNo が空のときは、QR コードを出さない。

Q-RQ-PR-004：
閲覧は、別ウインドウで PDF を表示する。
印刷は、PDF をダウンロードさせる。
ファイル名は、どちらも「稟議バーコードNo.pdf」とする。
出せる人と申請の状態は、property-basic-info の閲覧ボタン・印刷ボタンの条件に従う。契約局情報と発行依頼書が登録済みで、発番の後であること。
作った Excel と PDF は、出したあとにサーバーから消す。

Q-RQ-PR-005：
PDF への変換に失敗したときは、エラーをログに残す。利用者はボタンを押し直してやり直す。
一時ファイルを置く場所が無いときは、エラーメッセージを表示して止める。
帳票を出したことは記録しない。

Q-RQ-PR-006：
前提は、申請に発行依頼書と、契約局情報の1行目があることである。
design の前に決めておく事項は無い。
非機能は、ほかの feature と同じ扱いでよい。
帳票には個人情報が載る。関係者①〜⑤の氏名・住所・電話番号・メールアドレス・FAX、起案者の氏名、申請者・確認者・決裁者の氏名である。

---------- 物件契約情報申請状況検索一覧（application-status-search） ----------

Q-RQ-AS-001：
今の手順は、ほかの feature と同じでよい。
承認フローの担当者と起案者が、自分の関わる申請を探して、物件基本情報登録変更画面を開くために使う。
メニューから最初に開く画面である。

Q-RQ-AS-002：
検索条件は約38項目で、どれも必須ではない。初期値は空とする。
ただし、時刻の範囲の初期値は 00:00〜23:59 とする。
一致のしかたは次のとおり。
・前方一致：申請No、稟議バーコードNo、基地局番号、発送書類名
・部分一致：基地局名、更新者名、起案の所属①②、起案担当者、案件小グループ
・完全一致：エリア、審査フェーズ、状態、依頼内容、施策、起案会社、押印種別、転貸借の契約種別
・範囲：起案日時、稟議承認日、初回支払日、申請日時、発送希望日、確認日時、進捗の日数（営業日で数える）
社外ユーザーには、起案会社と所属を変えさせず、進捗の検索は出さない。
項目の全部は、design の画面設計で定める。

Q-RQ-AS-003：
一覧の項目は14とする。
・申請No（リンク）、依頼内容、審査フェーズ（再申請のときは「(再申請)」を付ける）、状態
・稟議バーコードNo（代表局のもの）、基地局番号、基地局名（複数局は「〜他n局」）
・案件小グループ、起案会社名、エリア、起案担当者、起案日、発送希望日、施策
並び順は、申請No の降順とする。
1ページの件数と、検索結果の上限件数は、コードマスタの設定値に従う。上限を超えたときはエラーメッセージを表示する。
0件のときは、該当なしのメッセージを表示する。
申請No のリンクを押すと、物件基本情報登録変更画面へ移る。
状態が取込中の申請は、リンクにしない。
新規登録のボタンは置かない。新規の登録は、メニューから物件基本情報登録変更画面を開いて行う。
物件基本情報登録変更画面から戻ったときは、前の検索条件を残して、もう一度検索する。

Q-RQ-AS-004：
CSV の列は、一覧と同じ14列を同じ順に出す。
文字コードは Shift_JIS（MS932）、区切りはカンマ、見出し行を付ける。
ファイル名は「WTG060_年月日時分秒.csv」とする。
上限件数は、画面の検索と同じとする。0件や上限を超えたときは、見出し行だけを出す。
出せるのは、この画面を使える全員である。出す範囲は、画面の検索と同じ絞り込みに従う。

Q-RQ-AS-005：
物件基本情報登録変更の 6.5 と同じでよい。
契約稟議起案会社が自社（P71 の文字項目2 の会社コード）の申請と、本人が登録した申請だけを出す。

Q-RQ-AS-006：
固有の前提は無い。design の前に決めておく事項も無い。
非機能は、ほかの feature と同じ扱いでよい。
扱う個人情報は、起案担当者と更新者の氏名である。

---------- 契約情報取込（contract-info-import） ----------

Q-RQ-CI-001：
今の手順は、ほかの feature と同じでよい。
起案者・申請者・確認者が、自分の番のときに、契約局情報と発行依頼書をまとめて CSV で登録・更新するために使う。
物件基本情報登録変更画面の契約局取込ボタンから開く。

Q-RQ-CI-002：
画面の項目は、「ファイルの種類」と「登録するファイル」の2つで、どちらも必須とする。
ファイルの種類は「リバースデータ」と「発行依頼書データ」から選ぶ。初期値はリバースデータとする。
ボタンは、参照、実行、クリア、処理状況、戻るの5つとする。
物件基本情報登録変更画面から渡された値は、画面には出さず、取込の処理に渡す。
・申請No は、洗替の単位に使う。
・受付No と契約区分は、稟議バーコードNo を付けるのに使う。
・申請者と受付No などは、発行依頼書に入れる。
取込はバッチで行い、結果はバッチ処理状況一覧（/zzz010/）で確かめる形でよい。処理状況ボタンでその画面へ移る。
実行したあとは、物件契約情報申請状況検索一覧の画面へ移る。

Q-RQ-CI-003：
ファイルは CSV で、文字コードは Windows-31J、1行目は見出し行とする。
2行目からの1行が、契約局1件に当たる。
列の数は、ファイルの種類で違う。
・発行依頼書データ：228列
・リバースデータ：381列
物件基本情報登録変更の 9.1 の出力 CSV は、発行依頼書データと同じ 228列の形式とする。
契約情報ダウンロードの CSV は、リバースデータと同じ 381列の形式とする。
列の全部と順番は、design の帳票設計で定める。

Q-RQ-CI-004：
行ごとに新規・変更・削除を見分けることはしない。
申請No ごとに、今ある行を全部消してから、ファイルの内容を入れ直す（洗替）。
更新するテーブルは次のとおり。
・契約局情報（TWTGM140）：更新する。ファイルの1行を1件とし、連番はファイルの中の順とする。
・発行依頼書（TWTGM100）：ファイルの最初のデータ行の内容で登録する。
・物件申請情報（TWTGM080）：取込のあいだは状態を取込中にし、終わったら元の状態に戻す。単独局か複数局かは、データ行が1行なら単独局、2行以上なら複数局とする。
・契約文書情報（TWTGM110）：契約局情報に無くなった稟議バーコードNo の行を消す。
既存の契約情報のテーブルは更新しない。
本 feature も TWTGM140 を洗替で更新することは、本 feature の requirements の Boundary Context に書く。feature 一覧の注記は直さない（Phase 3 の5回目の判断による）。

Q-RQ-CI-005：
洗替の単位は申請No で、対象は契約局情報と発行依頼書である。
洗替の前の内容をトランに写し、洗替の後で比べて、変わった行について取込前の内容を変更履歴に残す。
・契約局情報の変更履歴は TWTGA150 に残す。
・発行依頼書の変更履歴は TWTGA130 に残す。
steering の product.md は、issue-request が変更履歴を残すきっかけを書いている。本 feature の取込も変更履歴を残すきっかけになる。これは product.md の「履歴に残す項目ときっかけは各 feature で決める」による。

Q-RQ-CI-006：
チェックは区分ごとに行い、ある区分でエラーが出たら、次の区分には進まない。
・画面：ファイルが選ばれているか、0バイトでないか、拡張子が .csv か
・区分1：ファイルがあるか
・区分2：列の数がファイルの種類と合っているか
・区分3：必須・桁・形式、コードの存在、ファイルの中の重複、項目どうしの整合
重複は、発行依頼書データでは基地局番号で、リバースデータでは計画基地局番号で見る。
整合は、KDDI転貸借契約書と契約種別の組合せ、日付の開始と終了の前後、組で入れる項目などを見る。
1件でもエラーがあれば、全件を取り消し、取込の件数を0にする。
郵便番号と住所が合わないときは、警告として取込を続ける。
エラーと警告は、バッチ処理状況の詳細に、行番号を付けて出す。
最後に、取り込んだ件数と、正常・異常の件数を出す。
取込を実行できる人と申請の状態は、property-basic-info の契約局取込ボタンの条件に従う。

Q-RQ-CI-007：
取り込んだファイルは、サーバーに保存する。画面からダウンロードはできない。
同じ申請No の取込が同時に走らないようにする。方法は design で定める。
design の前に決めておく事項は無い。
非機能は、ほかの feature と同じ扱いでよい。
扱う個人情報は、契約者の氏名・住所・電話番号・メールアドレスと、マイナンバーを受け取った日である。

Q-RQ-CD-002：

・代表契約局番号、代表契約枝番、転貸借、建物ビル、基地局番号、基地局名

steering の「TWTBM080 を WTG の新しいデータに使わない」は、本案件で新しく作るテーブルのことと読む。

design の前に決めておく事項は無い。
