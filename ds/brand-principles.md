## 禁止リスト（never — 全画面共通）

- 絵文字を UI 文言に使わない
- 記号文字（✓ ✕ × ▼ + 等）をアイコン代わりに使わない（アイコンは `icons/ICON-MAP.md` の語彙のみ。
  フォント・OS で字形が変わり、寸法・色・読み上げを管理できないため — 2026-08-25 ICN-05）
- マーケ調の煽り見出し・ヒーローセクションを業務画面に入れない
- グラデーション・独自の装飾色を使わない（色はセマンティックトークンの範囲のみ）

## 文言トーン

- 基本: 敬体（です・ます）。命令形にしない。専門用語は要件の用語集に従う
- 空状態: 「まだ〜はありません」+ 次にできる行動を 1 つ提示
- 操作完了の通知: 結果を短く言い切る。例:「保存しました」「申請を受け付けました」
  （NotificationBanner type=success のタイトル。装飾語・感嘆符・詫びを付けない）
- エラー（全般）: 復帰手段を先に、詫びは短く。例:「読み込めませんでした。再試行してください」
- フォーム入力エラー: 冒頭に全角アスタリスク「＊」+ 具体的な内容と訂正方法
  （デジ庁インプットテキストの作法 — InputText spec 参照）

## レイアウト原則（PC 業務画面 — 2026-08-25 REQ-01 / 02 で新設）

> 位置づけ: 各パターンの `density` / `layout` / `responsive` が参照する上位方針。
> デジ庁 DADS は対市民向け Web を主対象にしており、密度・段組み・幅の使い方に関する規定を持たない
> （レイアウト基本は 12 カラムグリッドとガター幅の原則のみ）ため、本節はすべて**自社定義**。
> 「PC」= `breakpoint.md`（1024px）以上を指す。breakpoint.md 未満（タブレット）は各パターンの `responsive` に従う。

### 1 画面収容の原則

- PC では、1 業務画面の入力・閲覧対象を**スクロール無しで 1 画面に収めることを目標**にする
- 基準ビューポート: **1366×768（ブラウザ UI を除いた実効高 約 650px）を第一目標**、1280×720 を最低ライン
- これは「収める努力」であり never_do ではない。収まらない場合の扱いは後述

### 収容のために取ってよい手段（優先順）

1. 余白の縮小 — 各パターンの `density` に書かれた段を既定とし、必要なら `space.ms`（12px）/ `space.xxs`（2px）の中間段を使う。段は詰めても飛ばさない（md の下は sm、その下は xs）
2. 段組み — form-page の**最大 4 列グリッド**（form-page pattern 参照）、detail-page の dl 2 列
3. 幅の活用 — 本体は画面幅いっぱいに使い、中央寄せの余白を作らない（app-shell pattern 参照）。ただし**単独の短い入力欄を行いっぱいに伸ばさない**（入力欄の幅は内容相応 — デジ庁 InputText 準拠。幅は段組みで埋める）
4. サポートテキストの簡略化 — 項目ラベルに統合できる補足はラベル側へ寄せる（入力例など必要な補足は残す）
5. セクションの Tabs 分割 — detail-page の関連情報のみ。**form-page では Tabs で入力項目を隠さない**

### 収容のために取ってはいけない手段

- 文字サイズの縮小（`font.size.body` 16px を下回らない。caption 13px は補足専用）
- 入力欄・ボタンの高さ縮小によるターゲット領域 44 CSS px 未満化（デジ庁 Button a11y 準拠）
- 必須項目の折りたたみ（Disclosure / Accordion で必須項目を隠さない — list-page の詳細検索パネルの規定と同じ）
- Textarea の 1 行化（複数行になりうる入力は Textarea のまま）
- Table の省略表示による情報欠落（ellipsis は全文を title 等で確認できる場合のみ — Table spec `text_overflow_guidance`）

### 収まらない場合の扱い

- 長大な申請書（明細 + 報告文を含む旅費精算など）は**セクション単位でスクロールを許容**する
- その場合、form-page のアクション行（保存 / 確認へ進む / キャンセル）は**画面下部に sticky で常時表示してよい**
  （自社翻案 — デジ庁に規定無し。sticky にする場合は本体の最下部に同じ高さの余白を確保し、最終項目がアクション行に隠れないようにする。
  app-shell の sticky ヘッダーと合わせて上下が固定されるため、実効高がさらに減ることを density で織り込む）

### 揃えの原則（ラベル = 左揃え / 数値 = 右揃え）

- **見出し・ラベルは常に左揃え**: Table の見出しセル（th）、dl の名前（dt）、RepeatingFieldGroup の見出し行、フォームの項目ラベル。
  対応する値が右揃えの列でも見出しは左揃えにする（デジ庁テーブルガイドラインは見出しセルの揃えを規定しておらず、
  従来の「データセルと同じ揃え」は自社判断だったため撤回 — 2026-08-25 REQ-01）
- **右揃えは「値が縦に並ぶ列」がある場合に限る**（2026-08-25 REQ-12）:
  - **Table のデータ列 / RepeatingFieldGroup の入力列** — 複数レコードが縦に並び桁を比較できるので、
    **数値・日付・金額は右揃え**（テキスト値は左揃え。デジ庁の右揃え規定はこのテーブルの列についてのもの）
  - **dl（説明リスト）・確認画面の名前-値ペア** — 1 レコードのみで比較対象が縦に無いので、
    **dt・dd とも常に左揃え**（数値・日付・金額も右揃えにしない）。右揃えにすると値が dd の幅ぶん
    dt から離れ、名前と値の対応が読み取れなくなる。数値の読み取りやすさは
    **3 桁区切りのカンマ + 単位**で担保する（InputText `numeric_input_guidance` の表示側規定）
- 見出しと右揃えの値が離れて見える場合は、列幅を内容相応に絞って緩和する（見出しを右揃えにして合わせない）
- **2 種類のラベルは置く位置が違う**（2026-08-25 REQ-11）: **項目ラベルは入力欄の前（上）**、
  **単位ラベル（年 / 月 / 日・円・個・％ 等）は値の直後（接尾）**に置く。
  「ラベルは項目の前」の一般原則を単位ラベルにまで当てて `年[2026] 月[08] 日[22]` のような接頭にしない
  （日本語の読み順は「2026 年 08 月 22 日」— DatePicker `variants.layout`。
  InputText `numeric_input_guidance`「単位は入力欄の右外に添える」と同じ規律）

### 表記の原則（数値・日付）— 2026-08-25 REQ-20 で新設

> 位置づけ: **表示側**（閲覧・確認・帳票）の表記を 1 か所に集約する。入力側の作法は各部品 spec
> （InputText `numeric_input_guidance` / DatePicker `variants.layout`）に従い、表示はここに従う。
> デジ庁 DADS に日付・時刻の表記規定は無い（スタイルガイドのページはデザインシステムとスタイルガイドの
> 定義・作成手順の解説で、数字・年月日の書き方を扱っていない — 2026-08-25 確認）ため、本節は**自社定義**。

- **日付の既定は `yyyy年MM月dd日`**（年は西暦 4 桁、月日はゼロ埋め 2 桁）。
  入力側の読み順（DatePicker の「2026 年 08 月 22 日」）と一致させる。
  適用先: detail-page の dl / confirm-flow の確認 dl / report / EmptyState・NotificationBanner の文言
- **Table では `yyyy/MM/dd` を許容**（日付列が複数あると単位込みでは列幅を食い、表の最小幅を押し上げて
  横スクロールが出やすくなるため）。ただし**同一画面内はどちらか一方に統一**する（列によって形式を変えない）
- **時刻を伴う場合は `yyyy年MM月dd日 HH:mm`**（秒は原則表示しない。監査ログ等で秒が必要なら起票）
- **年月のみ / 月日のみは `yyyy年MM月` / `MM月dd日`**（DatePicker の省略形 variant と対応させる）
- **数値・金額は 3 桁区切りのカンマ + 単位**（詳細は InputText `numeric_input_guidance` の表示側規定。
  桁を揃えて比較する場面の揃えは前節「揃えの原則」）
- **和暦は入力・保存とも西暦のまま**で、必要な場合に表示側で併記する
  （「2026年（令和8年）」— DatePicker `implementation_notes`）

### 形（角丸）でも操作可能性を区別する（2026-08-25 REQ-19 で新設）

- 押せる要素（Button / Link appearance="button" / 入力欄）は **`radius.sm`**、
  押せない表示要素（Badge = 状態チップ）は **`radius.full`（全周丸）**
- 色・padding・文字サイズは近づくことがあるため、**形を最後の識別子として残す**。
  新しい部品を追加するときは「押せるか / 押せないか」で角丸の段を選ぶ
- 角丸トークンの演算による代用（`calc(radius.md * 2)` 等）はしない。必要な段が無ければ起票する
  （`radius.full` は旧モックがこの演算で代用していたのを正式なトークンにしたもの）
