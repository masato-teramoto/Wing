# このデザインシステムの中身ガイド（デザイナー向け）

この文書は本リポジトリ（`aidd-ds-poc-digital-go-jp-based`）の中身を、デザイナーが自分の言葉で
他の人に説明できることを目指して解説するものです。技術用語はその場で噛み砕いて説明します。
運用ルールそのものは [AGENTS.md](AGENTS.md)、設計の背景は [DECISIONS.md](DECISIONS.md) が正です。

---

## 1. まず全体像 — このデザインシステムは「AI も読者」

ふつうのデザインシステムの読者は人間（デザイナーと開発者）です。
このデザインシステムはそれに加えて **AI エージェント（Claude などの自動プログラム）が
UI を組み立てるときに読む** ことを前提に作られています。これが「AI-Ready」の意味です。

そのため、次の 3 つの方針で貫かれています。

1. **正（マスター）はコード** — 色や部品の「本当の定義」はこのフォルダ内のファイル。
   Figma やドキュメントはそこから作られる「写し」という位置づけです。
2. **ルールは機械が読める形式で書く** — 「なんとなく察してね」ではなく、
   JSON という形式（後述）で「使ってよい場面」「禁止の場面」を明文化します。
   AI は空気を読めないので、曖昧なルールは守られないからです。
3. **ルール違反は機械が検出する** — 人間の目視レビューに頼らず、
   検査スクリプト（後述の scripts/）が違反を自動で見つけます。

この運用では、デザイナーの役割は「毎画面を自分で作ること」ではなく、
**デザインシステム自体を育てること**と**出来上がった画面の見た目を評価すること**に変わります。

> 💡 **JSON とは**: 「名前: 値」の組み合わせでデータを書くテキスト形式です。
> `{ "name": "Button", "status": "stable" }` のように書きます。人間も読めますが、
> 何よりプログラムや AI が確実に読み取れるのが利点です。Excel の表を
> テキストにしたようなもの、と考えると近いです。

## 3. tokens/ — デザイントークン（値の辞書）

**デザイントークンとは**、色・余白・角丸・文字サイズといったデザインの最小単位の値に
名前を付けて一元管理する仕組みです。「この青は `primary`」と名前で呼ぶことで、
値を 1 箇所直せば全画面に反映され、勝手な色が混ざることも防げます。

### 3-1. primitive.json / semantic.json — 唯一の正（いま登録されている値の全部）

値は 2 ファイルに分けて書きます。**`primitive.json`**（色のスウォッチ・余白・角丸・文字サイズなど
全プロジェクト共通の生値）と、**`semantic.json`**（用途名でプリミティブを参照する、ベースDSの
既定セマンティック値。ブランド色は付けず、どのプロジェクトでも上書き前提のプレースホルダにする）。
案件ごとに色が違う場合は `semantic.<project>.json` にキー差分だけを書き足します（詳細は §3-3）。
書式はどのファイルも **W3C DTCG 形式**という業界標準
（Web の標準化団体が策定中のデザイントークン共通フォーマット）に従っています。
1 つのトークンは次のように「型・値・説明」のセットで書かれます。

```json
"primary": {
  "$type": "color",
  "$value": "{color.primitive.blue.600}",
  "$description": "主要アクション。1画面に原則1つ"
}
```

`$value` が `{...}` になっているのは「別のトークンを参照する」という意味です。
これが後述の 2 層構造を作っています。

現在ファイルに書かれている中身は、この 4 カテゴリ・計 24 個です。

**① 色（color）— 2 層構造**

| 層 | トークン名 | 値 / 参照先 | 説明（$description に書かれた使い方ルール） |
|---|---|---|---|
| プリミティブ | `blue-600` | `#1d4ed8` | — |
| プリミティブ | `blue-700` | `#1e40af` | — |
| プリミティブ | `gray-50` | `#f9fafb` | — |
| プリミティブ | `gray-200` | `#e5e7eb` | — |
| プリミティブ | `gray-700` | `#374151` | — |
| プリミティブ | `gray-900` | `#111827` | — |
| プリミティブ | `red-600` | `#dc2626` | — |
| セマンティック | `primary` | → blue-600 | 主要アクション。**1 画面に原則 1 つ** |
| セマンティック | `primary-hover` | → blue-700 | （primary のホバー色） |
| セマンティック | `text` | → gray-900 | 本文の文字色 |
| セマンティック | `text-subtle` | → gray-700 | 控えめな文字色（補足など） |
| セマンティック | `border` | → gray-200 | 罫線・枠線 |
| セマンティック | `surface` | → gray-50 | 面（背景）の色 |
| セマンティック | `danger` | → red-600 | **破壊的操作・エラーのみ。強調目的で使わない** |

**② 余白（space）・③ 角丸（radius）・④ 文字サイズ（font.size）— 1 層のスケール**

| space | 値 | | radius | 値 | | font.size | 値 |
|---|---|---|---|---|---|---|---|
| `xs` | 4px | | `sm` | 4px | | `caption` | 13px |
| `sm` | 8px | | `md` | 8px | | `body` | 16px |
| `md` | 16px | | | | | `heading` | 24px |
| `lg` | 24px | | | | | | |
| `xl` | 40px | | | | | | |

色だけが 2 層なのは、色は「同じ青でも用途が違う」ことが起きるからです。
余白や文字サイズは大きさの段階（スケール）自体が意味を持つので 1 層で足ります。

### 3-2. 2 層構造のしくみ（ここがいちばん大事）

画面や部品が色を使うときの参照は、必ずこの流れになります。

```
 画面・部品が書く指定                セマンティック層              プリミティブ層      実際の値
 var(--color-semantic-primary) ──▶  primary                ──▶  blue-600      ──▶  #1d4ed8
                                    「主要アクションの色」        「青の 600 番」
```

画面・部品が使ってよいのは**セマンティック層（用途名）だけ**です。
このおかげで、ブランドカラーの変更は参照先の 1 行差し替えで済みます。

```
 変更前:  primary ──▶ blue-600（#1d4ed8）
 変更後:  primary ──▶ green-600（#16a34a）
          ↑ プリミティブ層に green-600 を足して、この参照を差し替えるだけで
            全画面の「主要アクション色」が一括で変わる。画面側の修正はゼロ
```

また `danger` の説明に「破壊的操作・エラーのみ。強調目的で使わない」とある通り、
**名前と説明自体が使い方のルール**になっていて、AI もこれを読んで判断します。

### 3-3. config.mjs と dist/ — 変換機とその出力

`primitive.json` / `semantic.json` はあくまで辞書なので、そのままでは画面に反映されません。
**Style Dictionary** という変換ツール（トークン界の定番）が、`config.mjs` に
書かれた設定に従って 3 種類のファイルに自動変換します。

```
 primitive.json（共有プリミティブ）+ semantic.json（ベースDSの既定値）
     │
     │  npm run build:tokens を実行すると Style Dictionary が変換
     │
     ├──▶ dist/tokens.css                … Web 画面用。var(--color-semantic-primary) の
     │                                      ような「CSS 変数」（値を名前で呼ぶ仕組み）になる
     ├──▶ dist/theme.ts                 … プログラム側から値を参照したいとき用
     └──▶ dist/theme-claude-design.css  … Claude Design（AI デザインツール）に読ませる用
                                           （中身は tokens.css と同じ）
```

変換結果が入る **dist/ は生成物なので直接編集禁止**です。
印刷物に手書き修正しても原稿が直らないのと同じで、直すのは常に `primitive.json` / `semantic.json` です。
生成物なので Git にも入れていません（`.gitignore` 済み。手元で `npm run build:tokens` を
実行すると作られます）。

**案件ごとにブランド色を変える場合**（設計判断14・2026-08-26 運用開始）は、`semantic.json` 自体を
書き換えず、差分だけを持つ `tokens/semantic.<project>.json` を追加し、専用の
`tokens/config.<project>.mjs`（source に primitive.json → semantic.json →
semantic.<project>.json の順で積む）を使って `dist/<project>/` に別出力します。
プリミティブ層と部品仕様は案件をまたいで共有のままです — **DS パッケージ自体は分割しません**。

書き方の実例が [examples/travel-expense-demo/](examples/travel-expense-demo/) に 1 件だけ
置いてあります（`npm run build:tokens:example:travel-expense-demo` で動かせます）。
**これは参考実装例であって、ひな形でも既定値でもありません** — 実案件のファイルは
上記のとおり `tokens/` 直下に置きます。対応表はそのフォルダの README を参照。

**工程によって色の入り方を変える**（2026-08-26 追加）ためにも同じ仕組みを使います。要件定義の段階で
作るワイヤーフレームは、まだブランド色が決まっていません。そこで**操作要素とブランドの色だけを
灰色に落とした差分** `tokens/semantic.wireframe.json` を重ねます（`npm run build:tokens:wireframe`）。
エラー・成功・注意などの**意味を持つ色は残します**（灰色にすると「色 + テキストで伝える」という
アクセシビリティのルールごと作り直しになるため）。

| プロファイル | 使う工程 | 色の状態 |
|---|---|---|
| base（既定） | 部品・パターンの検証 | 仮の紫（indigo）系プレースホルダ |
| **wireframe** | **要件定義**（ワイヤーフレーム） | 操作要素・ブランドは灰色 / 意味色は残る |
| **project** | **設計以降**（顧客確認用モック・実装） | 案件のブランド色 |

色が無いこと自体が「まだ決まっていません」というシグナルになり、顧客の関心が色ではなく
画面の型・構成・文言に向くことを狙っています。**キー名はどのプロファイルでも同じ**なので、
モックや部品仕様の側を書き分ける必要はありません（重ねるファイルを差し替えるだけ）。
なお wireframe と project は**同時に重ねません**（工程ごとにどちらか一方）。

### 3-4. HARVESTING.md — 値の採取手順書

ゼロから色を決め直すのではなく、**いま動いているサービスで実際に使われている値を
採取して整理する**ための手順書です。全体で 4〜5 日を目安に、次の 6 ステップが
書かれています。

```
 ① 画面インベントリ（0.5日）  主要画面 5〜10 枚のスクリーンショットを集める
         ↓
 ② 採取（1日）               DevTools やソース検索で色・余白・角丸・フォントを列挙。
         ↓                    検査スクリプト audit-tokens.mjs を既存ソースに向けると
         ↓                    「生値の検出一覧」がそのまま採取リストになる（検出器の逆利用）
 ③ 正規化（1日）              近い色を統合（例: #333 / #374151 / #3a3a3a の 3 種の濃灰を 1 つに）。
         ↓                    余白は 4px / 8px 単位に丸めて 5 段階に。文字サイズは 3〜4 段に絞る。
         ↓                    ★ 迷う統合はデザイナーが決める（AI に勝手に決めさせない）
 ④ 2 層化して記入（0.5日）    プリミティブ層＋セマンティック層に整理して primitive.json /
         ↓                    semantic.json に書く
         ↓
 ⑤ ビルドと検証（0.5日）      npm run build:tokens で dist/ を生成。
         ↓                    完了条件: 対象画面 1 枚をトークンだけで再現でき、検査が通ること
 ⑥ 部品 5 個の spec 化（1〜2日） 登場頻度が高く誤用されやすい部品（Button / Link / Card 等）から
                              5 個を選び、実装＋使い方ルール（component-spec.json）を書く
```

入力は「現行 UI のあるサービス（画面と CSS）」でも「新規サービスのモック
（Claude Design の生成物・カンプ・画像）」でもよく、モックすら無ければ
雛形の既定値のまま始めてデザイン検討の中で置き換えてよい、とされています。

## 4. components/ — UI 部品（1 部品 = 1 フォルダ）

各部品のフォルダには、**いまのところ 1 種類のファイル**が入っています。

```
 components/Button/
 │
 └── Button.component-spec.json … 判断ルール「いつ使う・いつ使わない・何と紛らわしいか」
                                   デザイナーが書き、AI が画面を組む前に必ず読む
```

現在 **21 部品**の spec が登録されています（一覧は `index.json`）。
以下、Button を例に中身を見ます。

> ⚠️ **v0.0.x に実装ファイル（`.tsx`）はありません。**
> README のバージョン規約どおり、v0.0.x は**仕様データのみ**の段階です。
> かつて Button / Link に置いていた `.tsx` は、動くために必要な CSS が
> 揃っておらず「コピーしても動かないのに動きそうに見える」状態だったため、
> v0.0.x の間は取り下げました（v0.1 で実装層とセットで入れ直します）。
> 経緯は [DECISIONS.md](DECISIONS.md) の 2026-08-26 の記録を参照。

### 4-1. 実装（`.tsx`）は v0.1 以降 — いま決まっていること

実装はまだありませんが、**実装をどう書くかの方針は先に決まっています**。
v0.1 で部品を実装するときは、次の 2 点を守ります。

**① Props（部品の「注文票」）は選択肢を限定する**

自由記述の文字列にせず、選べる値を列挙します（技術的には union 型と呼びます）。
プルダウンから選ぶ方式にしておけば、AI が「なんとなくオリジナルの見た目」を
発明できなくなるからです。Button なら次のような形になります。

```tsx
variant: "primary" | "secondary" | "danger";
```

この 3 つは spec の `color_map` に定義された variant と一致します
— **spec が先にあり、実装がそれに従う**という順序です。

**② 挙動のルールをコードに埋め込む**

たとえば `loading` を付けたら、①自動的に押せなくなり、②ラベルが「処理中…」に変わり、
③支援技術向けの「処理中です」印（`aria-busy`）が付く、というところまでを部品側で持ちます。
「ローディング中に二度押しできてしまう」ようなミスを、作る人の注意力ではなく
部品の仕様として防ぐためです。spec の `states_to_cover` と `a11y` が、この実装の
受け入れ条件になります。

> 💡 「React で書く = フロントエンド技術が固まらないと DS の作業ができない」
> ではありません。React に依存するのは将来の実装ファイルだけで、
> DS の大半は技術に依存しないデータです。依存の範囲と「いつ作るのか」は
> 14 章にまとめてあります。

### 4-2. `Button.component-spec.json` — 使い方ルール（いつ・なぜ使うか）

実装コードを読んでも「いつ使うべきか」は分かりません。それを補うのがこのファイルです。
実際に書かれている内容（**主な項目の抜粋** — spec は起票のたびに増えるため、最新は spec 本体を見てください）は
次の通りです。

| 項目 | 実際に書かれている内容 |
|---|---|
| `purpose`（何のための部品か） | ユーザーの操作（送信・保存・削除など、その場でアクションを実行する）に使う |
| `use_when`（使う場面） | フォーム送信、モーダルの確定/キャンセル、その場で完結する操作 |
| `never_use_when`（禁止の場面） | ① ページ遷移・外部リンク（→ Link を使う。見た目がボタンでも遷移なら Link）② danger variant を単なる強調目的で使う（破壊的操作の確認時のみ） |
| `confusable_with`（紛らわしい部品） | Link —「URL が変わるなら Link。onClick でその場の処理が走るなら Button」 |
| `states_to_cover`（確認必須の状態） | default / hover / disabled / loading |
| `a11y`（アクセシビリティの約束） | loading 中は aria-busy が付与される。**アイコンのみのボタンは作らない**（可視ラベル必須 — GAP-14）。ターゲット領域は 44×44 CSS px 以上。ラベルのコントラストは 4.5:1 以上。disabled は原則回避（使う場合は無効の理由を近傍のテキストで示す）。フォーカスリングの outline を消さない |
| `anti_pattern_example`（典型的な誤用例） | 「詳細を見る」ボタンに onClick で画面遷移を書く → Link を使う |

上の表に載せていない項目もあります（いずれも起票を経て後から増えたもの）:
`shape_guidance`（角丸 radius.sm — Badge の全周丸と形で区別する）/ `icon_guidance`（アイコンを添える
場合の語彙・配置・寸法・色）/ `color_map`（variant × state の色をトークン名で全パターン列挙）/
`source`（デジ庁の出典 URL と、どこが翻案かの記録）。`never_use_when` も現在 6 件、`confusable_with` は
Link / Badge / IconButton の 3 件あります。

デザイナーが普段レビューで口頭指摘している判断基準を、AI が読める形に
書き起こしたもの、と言えます。**ここを充実させるのはデザイナーの仕事**です。

### 4-3. Button と Link の使い分け — spec に書かれた判断を図にすると

Button と Link の spec は互いに「相手を使うべき場面」を明記し合っています。
2 つの spec を合わせると、判断はこの 1 本の木になります。

```
 その操作で URL（ページ）は変わる？
 │
 ├─ 変わる ─────────────────────▶ Link を使う
 │    │
 │    ├─ ボタンの見た目にしたい ──▶ <Link appearance="button">
 │    │                              （見た目がボタンでも、遷移なら Link）
 │    └─ 外部サイトへ飛ぶ ────────▶ external を付ける
 │                                   （別タブで開く設定と安全対策が自動で付く）
 │
 └─ 変わらない（その場の処理）───▶ Button を使う
      │
      ├─ 通常のアクション ────────▶ variant="primary" / "secondary"
      └─ 破壊的操作の確認 ────────▶ variant="danger"
                                     （強調目的での danger は禁止）
```

Link 側の spec には他に「`href="#"` にして onClick で処理する擬似ボタンは禁止」
「リンクテキストに『こちら』は禁止。遷移先が分かる文言にする」という
文言レベルのルールも書かれています。

### 4-4. 表示サンプル（Storybook）も v0.1 以降

**Storybook** は「部品カタログを画面で見られるツール」です。実装（`.tsx`）と対になる
ショーケース用のファイル（`*.stories.tsx`）を置くと、部品の各状態を並べて目視確認できます。

ルールでも実装でもなく、あくまでショーケースです。何を並べるかは spec が決めており、
`states_to_cover` に挙がった状態（Button なら default / hover / disabled / loading）が
そのまま並べるべき一覧になります。

実装と同じく **v0.0.x には含まれません**。v0.1 で実装を入れるときにセットで作ります。

## 5. patterns/ — 画面の型のレシピ

部品の使い方が正しくても、並べ方が自由だと画面ごとにバラバラになります。
そこで「一覧画面」「フォーム画面」のような**画面の型**ごとにレシピを JSON で定義します。
現在あるのは `list-page`（一覧画面）1 つで、状態は `draft`（下書き）です。

### 5-1. `list-page/pattern.json` に実際に書かれている内容

| 項目 | 実際の値 |
|---|---|
| `name` / `status` | list-page / draft（下書き） |
| `use_when`（この型を使う場面） | 複数レコードの検索・閲覧・選択 |
| `layout`（並べ方） | ページヘッダ（タイトル + 主アクション 1 つまで）→ フィルタ行 → テーブル → ページング |
| `components`（使う部品） | Table, Button, TextField, EmptyState |
| `states`（空・読込中・エラーの見せ方） | 下の表を参照 |
| `density`（密度） | 行高 md / セクション間 space-lg |
| `never_do`（禁止事項） | 一覧のカード羅列 / ヒーローセクション / 主アクションの複数配置 |

### 5-2. layout と density を図にすると

```
 +----------------------------------------------------------+
 | ページヘッダ：タイトル＋[主アクション]（1画面に1つまで） |
 +----------------------------------------------------------+
 | フィルタ行：[検索 TextField] [絞り込み Button など]      |
 +----------------------------------------------------------+
 | テーブル（Table）                                        |
 |   レコード行（行の高さ md）                              |
 |   レコード行                                             |
 +----------------------------------------------------------+
 | ページング                                               |
 +----------------------------------------------------------+
    ↑ セクションの間の余白は space-lg（= 24px、トークン参照）
```

### 5-3. states — 「うまくいっていないとき」の見せ方まで決めてある

一覧画面が崩れるのはたいてい「データが無い・読み込み中・エラー」のときです。
このレシピはその 3 状態の見せ方まで指示しています。

| 状態 | レシピの指示 | 意図 |
|---|---|---|
| 空（0 件） | EmptyState 部品を使う。文言トーンは brand-principles.md 参照 | 「まだ〜はありません + 次の行動」の統一トーンにする |
| 読み込み中 | スケルトン（内容の形をしたグレーの仮表示）。**スピナー単体は禁止** | 画面のガタつきを防ぎ、どこに何が出るか予告する |
| エラー | その場に再試行ボタンを出す（インライン再試行）。**モーダルにしない** | エラーのたびに作業を中断させない |

### 5-4. never_do — AI がやりがちな失敗の先回り

`never_do` の 3 項目は、AI に一覧画面を作らせると実際に起きがちな逸脱です。

- **一覧のカード羅列にしない** — AI はつい「おしゃれなカードグリッド」にしがち。業務の一覧はテーブルで
- **ヒーローセクションを入れない** — マーケサイト風の大きな見出しバナーは業務画面に不要
- **主アクションを複数置かない** — 「新規作成」も「インポート」も「エクスポート」も
  primary にすると、どれが主かわからなくなる

AI はこのレシピに従って画面を組むので、**「型」を設計するのがデザイナーの中心的な仕事**に
なります。ルール上、登録済みパターンにない画面構成を AI が勝手に発明することは禁止です。

> 💡 このレシピの `components` には Table / TextField / EmptyState という
> **まだ存在しない部品**が意図的に含まれています（ファイル冒頭のコメントに明記）。
> 「レシピが要求する部品が目録に無い → 検査で発覚 → 人間に起票」という
> 不足検出の流れを雛形として見せるためです。

## 6. index.json — 目録（「存在しないもの」も書いてある）

部品とパターンの**カタログ**です。AI が画面を作るとき、最初にここを見ます。
現在の登録内容は次の通りです。

- **components（2 件）**: Button（stable）、Link（stable）— 名前・状態・用途・spec ファイルの場所
- **patterns（1 件）**: list-page（draft）
- **does_not_exist_yet（まだ無いものリスト）**:
  部品 = ButtonGroup, IconButton, Table, Toast ／ パターン = form-page, detail-page
- **note_for_agents**: 「does_not_exist_yet の部品・パターンが必要になったら、
  実装せず人間に起票すること」

2 つの重要な特徴があります。

1. **自動生成** — scripts/generate-index.mjs が各フォルダの spec ファイルを集めて
   作り直します。手で編集してはいけません（編集してもチェックで差し戻されます）。
2. **`does_not_exist_yet`** — 「Table や Toast は、有りそうだがまだ存在しない」と
   明記してあるのは AI の**捏造防止**です。AI は「ありそうな部品」を勝手に作って
   しまう性質があるため、「無いものは無い。必要なら作らずに人間へ起票せよ」と
   目録自体に書いてあります。

## 7. AGENTS.md / CLAUDE.md — AI への「常時ルール」

`AGENTS.md` は、AI エージェントが作業するとき**毎回自動で読み込まれるハード制約**です。
中身は 3 部構成で、いずれも短く絞られています。

- **参照順序** — ① index.json（無いものは存在しない）→ ② pattern.json →
  ③ component-spec.json → ④ icons/ICON-MAP.md の順に見る
  （v0.0.x に実装 `.tsx` は無いため、③ の spec が最終）
- **ハード制約（違反は CI で自動検出）** — 色・余白等はトークン経由のみ（hex/px 直書き禁止）／
  UI 部品は本パッケージのみ（自作禁止）／画面は登録済みパターンに従う（無ければ起票）／
  tokens/dist/ 直接編集禁止／spec の never_use_when・pattern の never_do に従う／
  文言トーンは brand-principles.md に従う
- **責務境界** — このパッケージが担うのは「見た目・状態表現・アクセシビリティ属性」まで。
  状態管理・API 接続・ルーティング・エラーハンドリングはアプリ側の仕事

`CLAUDE.md` は Claude 用の入口ファイルで、中身は「AGENTS.md を読め」の 1 行だけです。
AI ツールごとに読むファイル名が違うため、実体を 1 つにして重複を防いでいます。

人間の職場に例えると「就業規則の掲示」です。手順書（マニュアル）は別の場所にあり、
ここには破ってはいけないルールだけが貼ってあります。

## 8. brand-principles.md — デザイナーが書く「らしさ」の 1 枚

トークン（値）にも部品仕様にもパターンにも収まらない「ブランドらしさ」を、
**禁止リストと文言トーン**の形で 1 枚に書くファイルです。現在は 3 セクション構成の
雛形で、記入例だけが置かれた「（記入）」状態です。

- **禁止リスト（全画面共通）** — 例: 絵文字を UI 文言に使わない／マーケ調の煽り見出し・
  ヒーローセクションを業務画面に入れない／ブランドカラー以外のグラデーションを使わない
- **文言トーン** — 基本（例: 敬体で書く、命令形にしない）／空状態（例: 「まだ〜はありません」+
  次にできる行動を 1 つ提示）／エラー（例: 復帰手段を先に、詫びは短く。
  「読み込めませんでした。再試行してください」）
- **ブランド資産** — ロゴ・コーポレートカラーの使用箇所

**「（記入）」をブランドの実際の内容で上書きするのがデザイナーの仕事**です。
AI が文言を起草するときと、人間が見た目をレビューするときの両方で参照されます。

## 9. DECISIONS.md — 「なぜこう決めたか」のメモ

運用ルールではなく、**設計判断の理由**を残す短いファイルです。次の 4 原則が
書かれています。

1. **正はコード** — `tokens/` 配下（primitive.json / semantic.json / semantic.wireframe.json /
   semantic.<project>.json）と
   components/ が唯一の正。Figma・Claude Design・ドキュメントは派生物
2. **セマンティック命名** — 役割で命名する。`blue-600` のような見た目名は
   プリミティブ層に閉じ、参照はセマンティック層経由
3. **判別可能な選択肢** — Props は自由文字列より選択肢型（union）。AI が迷わない API を優先
4. **機械で守れるルールだけをルールにする** — 人間の目視が必要なルールは、
   スクリプトで検証できる形に再設計するまで暫定扱い

新しく参加した人に思想を説明するときの拠り所です。

## 10. scripts/ — ルールを守らせる検査プログラム

ルールは書くだけでは守られません。この 3 つのスクリプト（小さな検査プログラム）が
**CI**（Continuous Integration の略。コードが変更されるたびに自動で検査を走らせる
仕組み。工場の全数検品のようなもの）で実行され、違反があれば変更を差し戻します。

| スクリプト | 具体的に何をするか | 例えるなら |
|---|---|---|
| `audit-tokens.mjs` | ソース内の `#1d4ed8` のような色コードと `16px` のような px 直書きを文字パターンで検索し、見つけたら「ファイル名:行番号 → トークンを使え」と指摘して失敗にする。tokens/ 自身と stories・テストは対象外。行に `audit-ignore` と書けば個別に除外できるのは **DS リポジトリ自身の監査（引数なし実行）だけ**。検査対象ディレクトリを指定する外部監査（モック / ワイヤーフレーム）では `audit-ignore` と書くこと自体が違反になる（除外で合格を作らせないため） | 「指定インク以外の持ち込み検査」 |
| `audit-components.mjs` | ① MUI / antd など**外部 UI ライブラリの import** を検出、② `ds-xxx` というクラス名のうち **index.json に無い名前**を「捏造部品の疑い」として検出。アプリ側のコードに向けて実行する想定 | 「持ち込み部品の検査」 |
| `generate-index.mjs` | 各部品・パターンの spec を集めて index.json を再生成。spec の無い部品フォルダはその場でエラー。`--check` 付きで実行すると「目録が古いまま」を検出して差し戻す | 「棚卸しと目録の突合」 |

「機械で守れるルールだけをルールにする」（DECISIONS.md）という原則の実行部隊です。
逆に言うと、デザイナーが新しいルールを作りたいときは
「それは機械で検出できる形か？」を考えるのがこの運用の作法です。

なお audit-tokens.mjs は違反を見つけたとき「対応するトークンが無い場合も
勝手にトークンを追加しない」と表示します。トークンを増やす判断は人間の仕事です。

## 12. package.json — このリポジトリで使えるコマンド

このリポジトリを 1 つの「パッケージ」（プログラムのまとまり）として定義するファイルです。
パッケージ名は `@kccs-ai-spec-platform/aidd-ds-poc-digital-go-jp-based`
（検証用名称。v0.0.x = 仕様データのみ、v0.1〜 = 実装入り）で、
開発者や AI が使うコマンドが登録されています。
`private: true` を付けてあり、外部（npm 公開レジストリ）へは配布されません。

| コマンド | やること |
|---|---|
| `npm run build:tokens` | primitive.json / semantic.json を CSS などに変換して dist/ を作る（ベースDS）|
| `npm run build:tokens:wireframe` | 上記 + 無彩色差分を重ねて dist/wireframe/ を作る（要件定義工程のワイヤーフレーム用）|
| `npm run build:tokens:example:travel-expense-demo` | 上記 + 参考実装例のブランド差分を重ねて dist/travel-expense-demo/ を作る |
| `npm run generate:index` | 目録 index.json を作り直す |
| `npm run audit` | 検査 2 種（生値・捏造部品）を実行 |
| `npm run ci` | 目録の鮮度チェック + 検査 2 種をまとめて実行（自動検査で使う一括コマンド） |

`npm run ci` は `.github/workflows/ci.yml` から push / PR のたびに自動実行されます。
検査スクリプトは Node.js の標準機能だけで動くため、実行前に何かをインストールする
必要はありません（`style-dictionary` は `build:tokens` のときだけ使います）。

## 13. 全部がどうつながるか — AI が画面を 1 枚作るときの流れ

1. **AGENTS.md** が自動で読み込まれ、AI はハード制約を把握する
2. **index.json** で「存在する部品・パターン」を確認する（無いものは作らず起票）
3. 作る画面に合う **pattern.json** を開き、並べ方・状態・禁止事項に従う
4. 使う部品ごとに **component-spec.json** で用途・禁止事項を確認する
5. アイコンを使うなら **icons/ICON-MAP.md** の語彙から選ぶ（v0.1 以降は続けて
   実装 `.tsx` で Props を最終確認する）。**語彙に無ければアイコンを付けずにラベルのみで組んで
   続行し、起票する** — アイコン不足で画面を作るのをやめない（2 の部品・パターン不足とは扱いが違う）
6. 色・余白はすべて**トークン**経由で指定する
7. 出来上がった変更は **scripts/ の検査**を通過して初めて取り込まれる
8. 最後に**人間（デザイナー）が見た目を評価**する

## 14. DS はいつ作るのか — React に依存するのは一部だけ

部品の実装が React（4 章）と聞くと「フロントエンドの技術要素が固まらないと
DS の作業が始められないのでは」と思えますが、そうではありません。ポイントは 2 つです。

### 14-1. React に依存するのは「実装層」だけ

設計判断として「スタイリングフレームワークに依存しない（shadcn/ui・Tailwind は
採用しない）。トークン層・spec/index/監査は完全非依存、**部品実装のみ React に依存**
（依存は React 本体のみの薄い状態を保つ）」と決定済みです
（[HANDOFF.md](../../HANDOFF.md) 設計判断 16）。層で分けるとこうなります。

| 層 | ファイル | 技術依存 |
|---|---|---|
| トークン | primitive.json / semantic.json（JSON）/ dist/tokens.css（CSS 変数） | なし（CSS 変数はどの Web 技術からも使える） |
| 使い方ルール | component-spec.json / pattern.json / index.json / brand-principles.md | なし（JSON と Markdown のデータ） |
| 検査 | scripts/ の 3 本 | なし（文字列を検査するだけ） |
| **実装**（v0.1 以降） | **components/\*.tsx / \*.stories.tsx / dist/theme.ts** | **React（+ Storybook）** |

つまり「技術が固まらないと DS が作れない」のではなく、「DS のうち実装層だけが
技術決定待ちで、それ以外はいつでも書ける」が正確です。仮に対象アプリが React 以外に
なっても、作り直しは実装層だけで、トークン・仕様・パターン・検査はそのまま使えます。

### 14-2. L1 テンプレ検証フローでの作りどころ

第一弾検証（DS 拡張フォーマットが埋められるかの検証。計画は
[MINIMAL-START.md](../../docs/MINIMAL-START.md)）では、**DS は仕様データのみで作り、
React 実装は 1 行も書きません**。実装が必要になるのは第二段
（[STAGE2-PLAN.md](../../docs/STAGE2-PLAN.md)）からです。

```
 ◆ フェーズ0（G1: requirements 承認の前）……… DS v0.0.x を構築【React 不要】
 │   土台選定 → 画面インベントリ → 部品仕様化 5〜7 個（component-spec.json のみ・実装なし）
 │   → パターン化 2〜4 個（pattern.json）→ index.json / brand-principles.md
 │   → GitHub リポジトリ化 + データのみタグ v0.0.x を配布
 │   ※ トークン実値の移植と「画面 1 枚の再現 + 監査」は第二段へ先送り
 │
 ◆ 第一弾（G1 → D1 → D2 → D3 → CHK → G2 → T1）… DS は「読まれるデータ」
 │   エージェントが index.json → pattern.json → component-spec.json を読んで
 │   design.md / refs/ui / tasks.md §5 を埋められるかを検証する。
 │   不足が出たら: CHK で停止 → 起票 → デザイナーが DS に追加 → v0.0.x+1 を再配布 → 再生成
 │   （= 検証中も DS は起票駆動で育ち続ける。この回転速度自体が計測指標）
 │
 ◆ 第二段（E1: エージェント実装 以降）…………… ここで初めて React が要る
     トークン実値の移植 / 部品の React 実装 + Storybook / 検査 CI /
     実装入りタグ v0.1〜 への更新
```

> 💡 G1 / G2 / G3 は L1 テンプレの承認ゲート（requirements / design / tasks の承認）、
> D1〜CHK・T1 は spec 作成の工程名です（詳細は MINIMAL-START.md §5-a の流れ図）。

この方針どおり、**v0.0.x のリポジトリに `.tsx` は 1 つもありません**。
以前は Button / Link の実装が「第二段でこういう形になる」という見本として置かれて
いましたが、動くために必要な CSS が無く「コピーすれば動きそうに見えて動かない」状態
だったため、2026-08-26 に取り下げました（DECISIONS.md の同日の記録）。
DS 自体も「パイロットの前提ではなく成果物」という位置づけです（HANDOFF.md 設計判断 13）。

## 15. デザイナーが「書く側」に回るファイル早見表
