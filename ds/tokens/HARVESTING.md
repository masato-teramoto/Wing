# トークン・部品の採取手順（DS v0.1 立ち上げ = パイロットのフェーズ 0）

自社に既存 DS が無い状態から、対象サービスの実態を正として tokens.json v0.1 を作る手順。
ゼロからデザインし直さない。**今そのサービスで事実上使われている値**を採取して正規化する。
DS はパイロットの前提ではなく成果物（HANDOFF 設計判断 13）。

## 入力（どちらか）

- **現行 UI があるサービス**: 稼働中の画面 + ソースの CSS / スタイル定義
- **新規サービス**: モック（Claude Design の生成物・デザインカンプ・画像なんでも）。
  モックも無い場合は雛形の既定値のまま開始し、デザイン検討の中で置き換えてよい

## 手順（目安 4〜5 日）

### 1. 画面インベントリ（0.5 日）
主要画面 5〜10 枚のスクリーンショットを集める（パイロット対象機能の画面は必須）。

### 2. 採取（1 日）
- 現行 UI: DevTools の computed style と、ソースへの生値検索で色・余白・角丸・フォントを列挙。
  `node scripts/audit-tokens.mjs` を対象サービスのソースに向けると、生値の検出一覧が
  そのまま採取リストになる（検出器の逆利用。exit 1 は想定どおり）
- モック: スクリーンショットからスポイト・目視で列挙
  （エージェントに画像を読ませて候補一覧を出させると速い。最終判断は人間）

### 3. 正規化（1 日）
- 近似色を統合する（例: 3 種類の濃灰 #333 / #374151 / #3a3a3a → 1 つに寄せる）
- 余白は 4px または 8px グリッドに丸めてスケール化（xs/sm/md/lg/xl の 5 段が目安）
- フォントサイズは 3〜4 段（caption / body / heading）に絞る
- **判断に迷う統合はデザイナーが決める**。エージェントに勝手に決めさせない（設計判断 8 と同思想）

### 4. 2 層化して tokens.json に記入（0.5 日）
- **プリミティブ層**: 正規化した生値に機械的な名前を付ける（blue-600, gray-900, ...）
- **セマンティック層**: 用途名でプリミティブを参照する（primary, text, border, ...）。
  **部品・アプリが参照してよいのはセマンティック層のみ**
- 雛形 tokens.json の color セクションが 2 層構造の見本。space / radius / font は
  スケール自体が意味を持つため 1 層でよい（用途別名が必要になったら追加する）

### 5. ビルドと検証（0.5 日）
- `npm run build:tokens` で dist/ を生成
- **完了条件（観測可能）**: 対象画面 1 枚をトークンだけで再現し、`npm run audit` が exit 0

### 6. 部品 5 個の component-spec.json 化（1〜2 日）
- インベントリで登場頻度が高い・誤用されやすい部品から 5 個選ぶ（Button / Link / Card 等）
- 実装 + component-spec.json（用途・never_use_when・類似部品との違い）→ `npm run generate:index`
- index.json の does_not_exist_yet に「有りそうで無い部品・パターン」を明記する（捏造防止）

## 現在の primitive.json の出所（2026-08-26 記録）

第一弾の `primitive.json` は上記手順の「採取」を経ておらず、**一般的な UI パレット
（Tailwind CSS の既定パレットと同一の値）を土台に選定**し、そこへ自社ブランド色
（`brand` / `teal` 系）を足したもの。**デジ庁のトークン実値は入っていない**
（デジ庁から借りているのは 2 層構造と Style Dictionary 配信という設計手法のみ）。

- ライセンス上の含意: トークン実値の再配布は発生していないため、
  design-tokens（MIT）の表示義務は生じていない
- 第二段でデジ庁の実値と突合する際は、**どのキーが借り物でどれが自前かを
  この記録で切り分ける**。突合後は本節を実際の採取結果へ書き換える

## サービスごとに分ける（設計判断 14・2026-08-26 に運用開始）

- `tokens/tokens.json` は `tokens/primitive.json`（共有プリミティブ）+ `tokens/semantic.json`
  （ベースDSの既定値・無ブランド）へ分割済み
- サービス固有のブランド色は `tokens/semantic.<service>.json` にキー差分のみを書き、
  `tokens/config.<service>.mjs` の `source` に primitive.json → semantic.json →
  semantic.<service>.json の順で積んで `dist/<service>/` に配信する
  （書き方の実例: `examples/travel-expense-demo/` — **参考実装例のため examples/ 配下に
  置いてあるが、実案件のファイルは上記のとおり `tokens/` 直下に置く**。
  対応表は `examples/travel-expense-demo/README.md`）
- プリミティブ層と部品実装は共有のまま。**DS パッケージは分割しない**。
  新しい色が要る場合は primitive.json に primitive を追加してよい（primitive は
  スウォッチの集合であり特定サービスに紐づく意味は持たない — 意味付けは semantic 層側）

## プロファイル — 工程ごとに色の入り方を変える（2026-08-26 追加）

オーバーレイの仕組みは案件ブランド色だけでなく、**工程によって色の入り方を変える**用途にも使う。
案件テーマ（`semantic.<project>.json`）とは置き場所で区別する — プロファイルは案件をまたいで
使うベースDS 側の資産なので `tokens/` 直下、案件テーマは実案件のリポジトリ規約どおりの場所。

| プロファイル | ファイル | 使う工程 | 色 |
|---|---|---|---|
| base（既定） | `semantic.json` のみ | 部品・パターンの検証 | indigo 系プレースホルダ |
| **wireframe** | `semantic.wireframe.json` | **要件定義**（ワイヤーフレーム / ローファイプロトタイプ） | 操作要素・ブランドは無彩色 / 意味色は残す |
| **project** | `semantic.<project>.json` | **設計以降**（顧客確認用モック・実装） | 案件のブランド色 |

- wireframe が無彩色なのは「色が無いこと自体を〈ブランド未確定〉のシグナルにし、顧客の関心を
  型・構成・文言へ向ける」ため（検証計画は別リポジトリの `docs/MOCK-A1-AB-TRIAL.md`）。
  **意味色（danger / success / warning / info / required）は無彩色化しない** — 状態・エラーの伝達が
  「色 + テキスト併用」のアクセシビリティ規約に依存しており、崩すと規約自体の見直しが要る
- **プロファイルは重ねない**（wireframe と project を同時に積まない。工程ごとにどちらか一方）
- キー名は全プロファイル共通。参照する側（HTML / component-spec / pattern）は
  プロファイルを意識せず `color.semantic.*` を使う
