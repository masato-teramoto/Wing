## B. 要承認（2 件）

### REQ-20 日付の「表示」形式の規定が無い — 入力と表示で表記が食い違う — ✅ 2026-08-25 承認・対応完了

> **実施**: 推奨案どおり承認（(a) 既定 `yyyy年MM月dd日` (b) Table では `yyyy/MM/dd` 許容・同一画面内は統一
> (c) 書き先は brand-principles.md の新設節）。
> brand-principles.md に **「表記の原則（数値・日付）」節を新設**（日付の既定 / Table の例外 / 時刻付き `HH:mm`・秒は非表示 /
> 年月のみ・月日のみ / 数値は 3 桁区切り + 単位 / 和暦は西暦のまま表示側で併記）。
> InputText `numeric_input_guidance`・detail-page・confirm-flow・report・Table の各所を同節への参照に統一。
> デジ庁は日付・時刻の表記規定を持たないことをスタイルガイドのページで確認済み（自社定義）。

- **経緯**: 前票 REQ-11 / 14 で**入力側**の日付は「yyyy 年 MM 月 dd 日」の読み順・単位ラベル可視で確定した。
  一方 **表示側（閲覧・確認・帳票）の日付形式は DS のどこにも規定が無い**
- **現状（モック実測）**: 表示側はすべてハイフン区切り。
  - detail-normal / detail-longtext の基本情報 dl: 「起票日 **2026-08-18**」「出発 **2026-08-20**」
  - list-page の Table の日付列・apply-confirm の確認 dl・apply-complete の受付情報も同じ `yyyy-MM-dd`
  - 同じ画面（apply-input → apply-confirm）で**入力は「2026 年 08 月 20 日」・確認は「2026-08-20」**と表記が変わる
    （`screenshots/a827ffc/apply-input-normal.png` / `apply-confirm.png`）
- **現行 DS 仕様**: 数値・金額には表示側の規定がある（InputText `numeric_input_guidance`「表示は 3 桁区切りのカンマ + 単位」）。
  **日付には対応する規定が無い**。DatePicker spec は入力の読み順のみ、Table `alignment_guidance` は揃えのみ、
  report パターンも「日付は右揃え」までで形式に触れていない
- **デジ庁（2026-08-25 新規確認）**: **日付・時刻の表記形式の規定は無い**。
  スタイルガイドのページ（`/dads/guidance/style-guides/`）はデザインシステムとスタイルガイドの定義・作成手順の解説で、
  数字・年月日の書き方は扱っていない。日付ピッカーのガイドラインも入力（3 分割・単位ラベル）についてのみ
  → **自社定義**
- **推奨案**:
  1. **既定の表示形式は `yyyy年MM月dd日`**（入力側の読み順と一致させる。年は西暦・4 桁、月日はゼロ埋め 2 桁）。
     適用先: detail-page の dl / confirm-flow の確認 dl / EmptyState 等の本文・NotificationBanner の文言
  2. **列幅が足りない Table では `yyyy/MM/dd` を許容**（一覧で日付列が複数あると単位ラベル込みでは幅を食うため。
     同一画面内では**どちらか一方に統一**する — 列によって形式を変えない）
  3. **時刻を伴う場合は `yyyy年MM月dd日 HH:mm`**（秒は原則表示しない。監査ログ等で秒が必要な場合は起票）
  4. **年月のみ / 月日のみ**は `yyyy年MM月` / `MM月dd日`（DatePicker の省略形 variant と対応させる）
  5. **書き先**: 日付は複数の部品・パターンに跨るため、`brand-principles.md` の
     「揃えの原則」と同じ節構成で **「表記の原則（数値・日付）」を 1 節新設**し、
     InputText `numeric_input_guidance` の数値表示規定もそこから参照する（1 か所に集約して取り違えを防ぐ
     — REQ-11 で「項目ラベルと単位ラベルが 1 か所に無いために取り違えた」のと同じ構図を避ける）
  6. 和暦は現行どおり併記のみ（DatePicker `implementation_notes`「2026年（令和8年）」の既存記述を維持）
- **トレードオフ（判断材料）**: `yyyy年MM月dd日` は `yyyy-MM-dd` より **2〜3 文字ぶん幅を食う**
  （caption 13px で約 20px、body 16px で約 26px）。日付列が 3 つある一覧では 1 行あたり約 60〜80px の増加になり、
  前票 REQ-16a の「表の最小幅」を押し上げて横スクロールが出やすくなる。
  これを避けるために 2.（Table では `yyyy/MM/dd`）を併記している
- **判断してほしい点**: (a) 既定を `yyyy年MM月dd日` にすること (b) Table での `yyyy/MM/dd` 許容（同一画面内は統一）
  (c) 書き先を brand-principles.md の新設「表記の原則」にすること（数値の表示規定もそこへ集約）

### REQ-21 テーブル状の行に選択肢群（RadioButton / Checkbox）を置く場合の規定が無い — 明細行が 3 行分の高さになる — ✅ 2026-08-25 承認・対応完了

> **実施**: 推奨案どおり承認（(a) ラジオを横並びで維持し列幅で収める・縦積み禁止 (b) 選択肢 4 つ以上に限り
> Select への置き換えを許容しデジ庁逸脱として記録 (c) 明細行の最小幅が 1366px を超えて横スクロールが出ることを了承）。
> RepeatingFieldGroup `layout_guidance` に「選択肢が 1 行に横並びで収まる列幅を確保（3 択で約 260〜300px）。
> 収まらない場合は列を減らすかその項目を明細行の外へ出す。選択肢は 3 つ以下・ラベルは 2〜4 文字。
> 4 つ以上は明細行に置かない（必要ならこの文脈に限り Select を許容 — デジ庁「5 つ以下はラジオ推奨」からの意図的な逸脱）」を追記し、
> `never_use_when` に縦積み禁止を追加。form-page `column_allocation` に **`scope`** を追加して
> 「本対応表は単項目のフォーム行の規定。テーブル状の行は RepeatingFieldGroup spec に従う」と適用範囲を明示。

- **発生箇所（モック実測）**: form-new の「旅費明細」（RepeatingFieldGroup）の「入力区分」列。
  3 択（例: 実費 / 定額 / 対象外）の RadioButton が**縦に積まれ、行高が約 3 行分**になっている
  （`screenshots/a827ffc/form-new.png`）。列幅が `auto-fit minmax(7rem, 1fr)` で 1 列 159px しかなく、
  選択肢が横に並ばないため縦積みになったもの（前票 REQ-15 と同じ原因の別症状）
- **現行 DS 仕様**: form-page `column_allocation`「RadioButton / Checkbox は選択肢 3 つ以下なら 1 列、
  4 つ以上は 2〜4 列」→ これは**単項目のフォーム行**を前提にした列数の規定であり、
  RepeatingFieldGroup のテーブル状の行（列幅を列ごとに決める）には**当てる先が無い**。
  RepeatingFieldGroup `layout_guidance` も「行内の項目が**同種の短い項目で揃う用途**」を前提に書かれており、
  選択肢群を含む場合の作法が無い
- **デジ庁（2026-08-25 新規確認）**: **「リストが 5 つ以下の場合はラジオボタンの使用を推奨」と明文がある**
  （ラジオボタン / セレクトボックスの概要ページ。セレクトボックスは「あまりに長いリストは使い勝手を下げる」ため
  選択肢を減らす検討を促す立場）。テーブル内・表形式での使用に関する規定は無い
  → **「選択肢が少ないなら Select ではなくラジオ」がデジ庁の方針**。したがって前票の「副次的な穴」欄に書いた
  方針案（テーブル状の行では Select にする）は**デジ庁逸脱**であり、本票では主案から外す
- **推奨案**（前票の案から差し替え）:
  1. **主案 — 列幅で収める**: RepeatingFieldGroup `layout_guidance` に
     「**行内に選択肢群（RadioButton / Checkbox）を置く場合は、選択肢が 1 行に横並びで収まる列幅を確保する**
     （選択肢を縦積みにして行高を増やさない）。収まらない場合は**列を減らす**か、その項目を明細行の外
     （行ごとの詳細ではなく明細群全体の設定）へ出す」を追記。
     前票 REQ-15（列幅は内容相応の固定幅）・REQ-16b（超過分は横スクロール）と同じ考え方の適用
  2. **選択肢 4 つ以上を明細行に置かない**（1 行に横並びで収める幅が現実的でなくなるため。
     4 つ以上が必要なら Select に替えることを**この場合に限り**許容する — デジ庁の「5 つ以下はラジオ推奨」は
     推奨であって禁止ではなく、表形式では行高の増加という別の不利益があるため。**この逸脱を明記する**）
  3. **選択肢のラベルは短く**（明細行では「実費 / 定額 / 対象外」のように 2〜4 文字。長い語が必要なら
     見出し行で補い、選択肢自体は短くする）
  4. form-page `column_allocation` の該当行に「この列数は**単項目のフォーム行**の規定。
     テーブル状の行（RepeatingFieldGroup）は同 spec の `layout_guidance` に従う」と適用範囲を明記
- **トレードオフ（判断材料）**: 3 択を横並びで収めるには実測で **約 260〜300px** の列幅が必要
  （ラジオ 1 つ = マーク 20px + 間隔 space.xs + ラベル 2〜4 文字。3 つで約 260px）。
  前票 REQ-14 で日付列に約 285px を確保したのと合わせると、明細 8 項目の行の最小幅は
  **おおよそ 1,400〜1,500px** になり、1366px のビューポートでも横スクロールが出る。
  これを避ける手段は 1. の「列を減らす」（＝明細行の項目数を業務側で見直す）であり、
  DS 側で縮小・折り返し・縦積みを許すことはしない（REQ-15 / 16b の決定と整合）
- **判断してほしい点**: (a) 主案（ラジオを横並びで維持し列幅で収める。縦積み禁止）でよいか
  (b) 選択肢 4 つ以上に限り Select への置き換えを許容し、デジ庁「5 つ以下はラジオ推奨」からの逸脱として記録すること
  (c) 明細行の最小幅が 1366px を超えて横スクロールが出ることの了承（代替は明細の項目数削減）
