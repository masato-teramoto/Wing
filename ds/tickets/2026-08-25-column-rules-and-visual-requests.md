## A. 採取・着手可（1 件・部分）

### REQ-16a Table は狭い画面で「縮小・省略」ではなく「領域内の横スクロール」で対応する（デジ庁準拠の具体化） — ✅ 2026-08-25 承認・対応完了

> **実施**: Table `text_overflow_guidance` に「内容相応の列幅の合計（最小幅）を持たせ、領域幅がそれを下回る場合は
> 列を縮めずスクロールさせる（`width: 100%` だけではスクロールしない旨の実装注記つき）」を追記し、ellipsis を
> 「最小幅を確保しても収まらない長文列」に限定。`a11y` の「モバイルでは」を「領域幅が表の最小幅を下回る場合」に
> 一般化し、あわせて REQ-16b でスクロール領域の a11y 作法（`role="region"` + `aria-label` + `tabindex="0"`）を追記。

- **デジ庁**: テーブル使い方・a11y に「モバイルではテーブル領域内の横スクロールで対応する（表の構造を崩さない。
  スクロール可否はシャドー表示で示す）」と明文がある。現行 Table spec の `a11y` にも同じ文が既に入っている
- **現状（モック）**: `.mk-table-scroll { overflow-x: auto }` の**スクロール用ラッパは在るが、`.ds-table` が
  `width: 100%` + `table-layout: fixed` のため表がラッパ幅を超えず、スクロールが一度も発生しない**。
  結果、狭い画面では列が均等に潰れ `text-overflow: ellipsis` で内容が省略される
  （＝ブランド原則「収容のために取ってはいけない手段: Table の省略表示による情報欠落」に実質抵触）
- **対応（承認不要・spec の具体化）**: Table `text_overflow_guidance` または `a11y` に
  「**表には内容相応の列幅の合計（最小幅）を持たせ、領域幅がそれを下回る場合は列を縮めずスクロールさせる**
  （実装例: 表に `min-width` を与えたうえでラッパを `overflow-x: auto`。`width: 100%` だけではスクロールしない）」を追記。
  ellipsis は「最小幅を確保しても収まらない長文列」に限る
- ※ 同じ要望を入力側の RepeatingFieldGroup にも広げる部分は自社定義部品なので **REQ-16b（B 区分）**として分けた

## B. 要承認（7 件）

### REQ-10 段組みのルール（部品 → 列数の対応）を一意に決めたい — 出発日・帰着日の 2 段組で余白が空く — ✅ 2026-08-25 承認・対応完了

> **実施**: 推奨案どおり承認（(a) 最小列数・左詰め (b) 対応表・DatePicker = 1 列 (c) 表に無い部品は起票）。
> form-page pattern に **`column_allocation`** を新設（`principle` / `grid` / `table` 8 行 / `label_wrap` / `unlisted`）し、
> `layout` の「DatePicker は 1〜2 列」等の範囲指定を対応表への参照に置き換え。never_do に
> 「余白を埋めるために列を余分に割り当てる」を追加。

- **原文**: 「段組みのルールを明確にしたい。例えば、新規登録の際の出発日、帰着日は 2 段組だが、余白が空いてしまうので
  それなら左に詰めた方がいいと思う」
- **発生箇所（モック実測）**: form-new / form-edit / apply-input の「出張スケジュール」。
  4 列グリッドの 1 列幅は **330px**（1366px 幅 − ページ padding 16px×2 − ガター 4px×3 の 4 等分）に対し、
  **PC の DatePicker（Consolidated）の実効幅は 214px**。にもかかわらず出発日・帰着日はいずれも
  `span 2`（665px）で置かれているため、**1 項目あたり約 450px の余白が空き、出発日と帰着日の間に大きな隙間が生じる**
  （`screenshots/a827ffc/form-new.png` / `apply-input-normal.png`。帰着日は 3 列目 x=685px から始まる）
- **現行 DS 仕様**: form-page `layout`「短い入力欄をグリッドの列に割り付ける。1 行あたり最大 4 項目。
  **金額・コード・件数など短いものは 1 列、DatePicker は 1〜2 列**、氏名・名称など長めの InputText は 2 列。
  単独の短い入力欄を行いっぱいに伸ばさない」／ brand-principles.md レイアウト原則「幅は段組みで埋める」
  → **「1〜2 列」の範囲指定と「伸ばさない」の定性表現だけで、どちらを選ぶべきかが決まらない**。
  実装は広い側（2 列）を選び、結果として「伸ばしてはいないが余白が空く」状態になった
- **デジ庁**: 段組み・列割当の規定なし（レイアウト基本は 12 カラムグリッドとガター幅の原則のみ）。
  InputText 使い方の「入力欄の幅は内容（想定桁数）相応」のみが手がかり
- **推奨案**（form-page `layout` を「範囲」から「対応表」に書き換える）:
  1. **原則を 1 文で置く**: 「各項目に割り当てる列数は、**その部品の実効幅が収まる最小の列数**とする。
     余白を埋めるために列を余分に割り当てない（余った列は行の右側にまとめて空ける＝**左詰め**）」
  2. **部品 → 列数の対応表を spec に持つ**（PC・4 列グリッド前提。数値は 1 列 = 330px 相当での実測に基づく）

     | 項目・部品 | 列数 | 根拠 |
     |---|---|---|
     | 金額・数量・件数・コード・時刻（短い InputText） | **1** | 想定桁数相応（InputText `numeric_input_guidance`） |
     | DatePicker（PC = Consolidated） | **1** | 実効幅 214px < 1 列 330px（単位ラベル可視化後も収まる — REQ-14 参照） |
     | Select（選択肢の語が短いもの） | **1** | 現行モックの実測（在籍事業所・組織・勘定科目はいずれも 1 列で収まっている） |
     | RadioButton / Checkbox（選択肢 3 つ以下） | **1** | 前票 REQ-08 の規定を踏襲 |
     | RadioButton / Checkbox（選択肢 4 つ以上） | **2〜4** | 同上（選択肢の折り返しで行が伸びるのを防ぐ） |
     | 氏名・名称・訪問先など中程度の InputText | **2** | 全角 20 文字程度の想定 |
     | Combobox（候補一覧を伴う） | **2** | 候補リストの可読幅 |
     | Textarea / FileUpload / RepeatingFieldGroup | **4（全幅）** | 現行規定どおり（REQ-18 参照） |

  3. **対をなす項目は隣接**（現行の推奨を維持）。上記を当てると出張スケジュールの 1 行目は
     **出発日(1) + 帰着日(1) + 出発時刻(1) + 帰着時刻(1) = 4 項目**が左から詰まり、要望どおり余白が消える
  4. **表に無い部品・想定外に長い値**が出た場合は実装裁量で広げず起票（AGENTS.md ハード制約と同じ運用）
- **トレードオフ（判断材料）**: 列数を固定すると、ラベルが長い項目（「プロジェクトコード」等）でラベルが折り返す場合がある。
  ラベルの折り返しは許容し、**入力欄の幅はラベル長に合わせて広げない**（内容相応の原則を優先）ことを併記したい
- **判断してほしい点**: (a)「最小列数・左詰め」原則の承認 (b) 対応表の粒度と値（DatePicker を 1 列に確定してよいか）
  (c) 表に無い部品が出たら起票、という運用

### REQ-12 詳細画面の dl（説明リスト）で日付だけ揃えが違い読みにくい — 「ラベルが横に着くとき」の揃えの規定 — ✅ 2026-08-25 承認・対応完了

> **実施**: 推奨案（dl は左揃えに統一）で承認。代替案 (i)（右揃え + 幅制限）は採らない。
> brand-principles.md 揃えの原則に「右揃えは『値が縦に並ぶ列』がある場合に限る」（Table / RepeatingFieldGroup は右揃え、

  → テキスト値まで右揃えになり、日本語の読み出し位置が項目ごとに変わって読みにくくなるため推奨しない

### REQ-13 同じ行の項目でサポートテキストの有無により入力欄の縦位置がずれる — ✅ 2026-08-25 承認・対応完了

> **実施**: 「① subgrid に揃える」方針で承認（4 段 = ラベル / サポート / 入力欄 / エラー）。
> form-page pattern に **`row_alignment`** を新設（`rule` / `implementation`〔subgrid 既定・不可の場合は等価実装〕/
> `not_default`〔②「行単位でサポートテキストを統一」は採らない〕/ `tradeoff`〔行高 +最大 23px〕）。
> `layout` のエラー時限定の記述を要因非限定に一般化し、never_do にも 1 行追加。

- **原文**: 「新規登録の出発帰着時刻と訪問先の段済みがずれる。訪問先に例がないから。」
- **発生箇所（モック実測）**: form-new「出張スケジュール」2 行目。出発時刻・帰着時刻にはサポートテキスト
  「例: 09:00」「例: 18:30」が付き、訪問先には無い。サポートテキストは caption 13px × 行間 1.6 + 下 margin
  `space.xxs` 2px = **約 23px** ぶん高さを持つため、**訪問先の入力欄の上端だけが 23px 高い位置**に来る
  （`screenshots/a827ffc/form-new.png`: 時刻の入力欄 y=583 に対し訪問先 y=560）。
  同じ画面の他セクションでも「例）…」を持つ項目と持たない項目が同じ行に並ぶと必ず発生する
- **現行 DS 仕様**: form-page `layout`「各項目 = ラベル + 要否表示 + サポートテキスト + 入力欄」
  「**エラー表示で項目の高さが伸びても、同じ行の他項目の位置はずらさない**（行内で吸収）」
  → **エラー時の規定はあるが、サポートテキストの有無による差の規定が無い**（同じ問題の別要因が抜けている）
- **デジ庁**: 該当規定なし（サポートテキストは「ラベルの下・入力欄の上」に置く作法のみ）
- **推奨案**: form-page `layout` の当該文を**要因を限定しない形に一般化**する:
  1. 「**同じグリッド行に置く項目は、ラベル / サポートテキスト / 入力欄 / エラーテキストの各段の上端を行内で揃える**。
     サポートテキストの有無・行数の違い、エラーテキストの有無で入力欄の縦位置をずらさない」
  2. **実装手法を `implementation_notes` 相当として併記**（どちらでもよい）:
     ① 行内の項目を 3 段（ラベル / サポート / 入力欄）の subgrid に載せる
     （CSS `grid-template-rows: auto auto auto` + `display: grid` を各項目に、`grid-row` を揃える）／
     ② サポートテキストの有無を**行単位で統一**する（入力例が必要な項目が 1 つでもあれば、
     同じ行の他項目にも短い補足を置くか、逆に入力例をラベルへ寄せる）
  3. ① を既定として推奨（②は「必要のない補足を書く」動機になりやすい）
- **トレードオフ**: ① は行内で最も高い項目に合わせて行高が決まるため、密度は ② より僅かに下がる
  （1 行あたり最大 23px。1 画面収容の原則との衝突は軽微と判断）
- **判断してほしい点**: (a) 揃える対象を「ラベル / サポート / 入力欄 / エラー」の 4 段でよいか
  (b) 既定の実装手法を ①（subgrid）とすること
