# DS起票 — 業務システム対応のギャップ棚卸し（2026-08-24）

> 「業務システムを対応するにあたって足りない内容」の棚卸しに基づく一括起票。
> AGENTS.md のハード制約により、記載の部品・パターンは**自作しない**。
> 要否・優先順位・具体案の確定は人間（DS側の設計判断者）が行う。
> 現状把握の根拠: index.json（does_not_exist_yet 含む）/ 各 pattern.json / DECISIONS.md。
>
> 前提: 基本的な CRUD 業務（一覧→詳細→登録/編集→確認）は現行の
> 部品 13 + パターン 5（app-shell 含む）で成立する。以下は本格展開時に詰まる穴。
>
> **検討方針（全 GAP 共通・2026-08-24 決定）**:
> 各 GAP の対応は**基本デジタル庁デザインシステム（DADS）に則る**。まずデジ庁に
> 対応する部品・パターン・ガイドラインが無いか確認し、あればそれを採取する。
> デジ庁に該当が無い・ガイドライン準備中の場合は、**独断で自社翻案を確定せず、
> 適切な方針案を人間に提案し承認を得て決める**（決定の経緯は DECISIONS.md に記録する）。

---

## 高優先（ほぼすべての業務システムで早期に必要）

### GAP-01: 保存成功フィードバック手段の新設（Toast / NotificationBanner）

**種別**: 部品新設（両方とも does_not_exist_yet 登録済み）+ パターン改定（form-page）

**現状**: form-page の `states` は input-error / submitting / loading / leave-confirm まで
規定済みだが、**「保存しました」を伝える手段が未定義**。confirm-flow は完了画面を持つが、
編集 variant の上書き保存後の挙動が決まっていない。

**検討してほしい内容**:
1. Toast（自動消滅・軽量）と NotificationBanner（ページ内静的表示）のどちらを先に部品化するか、
   両方か
2. form-page の `states` に `save-success` を追加し、使う部品と表示位置を規定するか
3. a11y（aria-live の扱い、自動消滅とスクリーンリーダーの両立）の方針

**影響範囲**: form-page を使う全画面（実質全アプリ）

### GAP-02: Combobox（検索付き選択）の新設

**種別**: 部品新設（does_not_exist_yet 登録済み）

**現状**: Select は「既定選択肢 6 個以上」用で、選択肢が数十〜数百件になる
**マスタ参照入力（取引先・社員・勘定科目等）**をカバーする部品が無い。
業務システムの定番入力であり、Select で代替すると操作性・パフォーマンスとも破綻する。

**検討してほしい内容**:
1. デジ庁ガイドラインに対応部品があるか確認のうえ採取するか、自社翻案とするか
2. Select との使い分け境界（件数目安）を両 spec の `confusable_with` に明記
3. 非同期検索（API 連携）はアプリ側責務 — 部品が規定するのは UI 挙動のみ、の責務境界の明文化

**影響範囲**: マスタ参照を持つ全フォーム

### GAP-03: FileUpload の新設

**種別**: 部品新設（does_not_exist_yet 登録済み）

**現状**: 添付ファイル入力の部品が無い。travel-expense（旅費精算）では領収書添付で
確実に必要になる見込み。

**検討してほしい内容**:
1. 対応形式・サイズ上限の表示作法（制約はアプリ側定義、表示作法のみ DS 側）
2. アップロード進行・失敗の状態表現（states_to_cover）
3. 複数ファイル対応の要否

**影響範囲**: 添付を伴う申請・登録系フォーム全般

### GAP-04: error-page パターンの新設（403/404/500・セッション切れ）

**種別**: パターン新設（does_not_exist_yet 登録済み）

**現状**: エラーページの型が無い。全システム共通で必要。app-shell が確定した今、
「app-shell の内側に何を置くか」として規定しやすくなった。

**検討してほしい内容**:
1. 対象エラー種別の範囲（403/404/500/メンテナンス/セッションタイムアウト）
2. EmptyState 部品の転用可否（spec の purpose は「一覧・検索結果 0 件」限定 —
   転用するなら purpose 拡張、しないなら専用レイアウトを pattern 側で規定）
3. 文言トーンは brand-principles.md 準拠であることの明記

**影響範囲**: 全アプリ共通

### GAP-05: Table の行選択＋一括操作の作法の規定

**種別**: 既存仕様のギャップ（Table spec + list-page パターン改定。未登録の穴）

**現状**: Table の `states_to_cover` に `row-selected` はあるが、選択行に対する
**一括操作（一括削除・一括ステータス変更等）の UI 作法が未規定**。list-page は
「主アクション 1 つまで」のため、現行ルール上、一括操作ボタンを置ける場所が存在しない。

**検討してほしい内容**:
1. 選択列（Checkbox 列）の作法を Table spec に追記するか
2. 一括操作の配置（選択時に出現するアクションバー等）を list-page の layout に規定するか、
   「主アクション 1 つまで」との整合をどう取るか
3. 全選択（ヘッダ Checkbox）と「全ページ選択」の扱い

**影響範囲**: 一括操作を持つ一覧画面全般

## 中優先（対象業務によって必要）

### GAP-06: Pagination 専用部品への昇格

**種別**: 部品新設（does_not_exist_yet 登録済み。デジ庁名: ページナビゲーション）

**現状**: list-page 内の簡易構成（件数表示 + 前へ/次へ Button）のみ。
大量データでページ番号ジャンプ・末尾移動が必要になった時点でカバー外。

**検討してほしい内容**: デジ庁ガイドライン（準備中だった — 公開状況を再確認）の採取可否、
簡易構成との使い分け基準（総件数の目安）。

**影響範囲**: 大量データの一覧画面

### GAP-07: advanced-search パターンの新設

**種別**: パターン新設（does_not_exist_yet 登録済み）

**現状**: list-page のフィルタ行は「検索 InputText + 絞り込み」の 1 行想定。
検索条件が多い業務検索画面（期間・区分・ステータス複合等）はカバー外。

**検討してほしい内容**: list-page の拡張（フィルタ領域の展開/折りたたみ）か独立パターンか。
折りたたみに Accordion 相当（GAP-08）が必要になる場合は依存関係に注意。

**影響範囲**: 複合条件検索を持つ一覧画面

### GAP-08: Tabs / Accordion の新設

**種別**: 部品新設（両方とも does_not_exist_yet 登録済み）

**現状**: 項目数の多い詳細画面・設定画面で情報を分割する手段が無い
（現行は detail-page の 1 ページ縦積みのみ）。

**検討してほしい内容**: デジ庁ガイドラインからの採取可否、detail-page への組み込み方
（`components` への追加はパターン改定として扱う）。

**影響範囲**: 情報量の多い詳細・設定画面

### GAP-09: login パターンの新設

**種別**: パターン新設（does_not_exist_yet 登録済み）

**現状**: 認証処理自体はアプリ側責務（AGENTS.md 責務境界）だが、ログイン画面の
レイアウトの型が無い。app-shell の外側に置く初の「シェル無し」パターンになる点も要整理。

**検討してほしい内容**: SSO リダイレクト型（画面ほぼ不要）か ID/パスワード型かで
要否が変わるため、対象システムの認証方式を先に確認。

**影響範囲**: 全アプリの入口 1 画面

### GAP-10: print-preview / report パターンの新設

**種別**: パターン新設（両方とも does_not_exist_yet 登録済み）

**現状**: 帳票出力・印刷プレビューの型が無い。印刷用トークン（余白・白黒時の
コントラスト）も未整備。

**検討してほしい内容**: 対象システムに帳票要件があるかを先に確認し、無ければ
後続フェーズ送りで可。

**影響範囲**: 帳票要件のあるシステムのみ

### GAP-16: approval パターンの新設（承認フロー）

**種別**: パターン新設（does_not_exist_yet 登録済み）

**現状**: 申請→承認/差戻しの画面型が無い。MK2 レビュー（2026-08-18）では
「承認機能は当面実装しない（起票者のみ閲覧）」と確定していたが、**この判断は
当時のお題（travel-expense モック）を前提としたもの**。別お題で承認フローを
持つシステムを対応する可能性が出てきたため、2026-08-24 に正式起票へ切り替えた
（初版の本ファイルでは「起票対象外・記録のみ」としていた）。

**検討してほしい内容**:
1. 独立パターンとするか、detail-page の variant（閲覧 + 承認/差戻しアクション +
   コメント入力）として拡張するか
2. 承認待ち一覧（inbox パターンとの関係 — does_not_exist_yet 登録済み）まで
   スコープに含めるか、まずは単票の承認画面のみか
3. 差戻し理由の入力手段（ModalDialog + Textarea で足りるか）と、
   承認/差戻し後のフィードバック（GAP-01 の Toast / NotificationBanner に依存）
4. 承認ステータスの表現（Badge の variant で足りるか）と承認履歴の表示
   （audit-log パターンとの境界）
5. 一括承認を想定するなら GAP-05（Table 行選択＋一括操作）が前提になる点

**影響範囲**: 承認フローを持つシステム（別お題で発生見込み）。権限モデル
（誰が承認できるか）はアプリ側責務 — DS 側が規定するのは画面の型のみ

## カタログ未登録の穴（does_not_exist_yet にも無い）

### GAP-11: Skeleton の仕様が存在しない（ルールだけあって実現手段が無い）

**種別**: 部品新設または横断ガイダンス新設（**未登録** — does_not_exist_yet への追記も必要）

**現状**: list-page / form-page とも states で「スケルトン（スピナー単体は禁止）」と
規定しているが、スケルトン自体の部品仕様・色トークン（プレースホルダ面の色）・
アニメーション方針がどこにもない。実装側が自作すると「新規 UI 部品の自作禁止」に抵触しうる
矛盾状態。

**検討してほしい内容**:
1. Skeleton を部品として新設するか、各パターンの states に実装ガイダンスとして書くか
2. 使用トークン（`color.semantic.surface` 転用か専用トークンか）
3. アニメーション（パルス等）の要否と `prefers-reduced-motion` への配慮

**影響範囲**: loading 状態を持つ全画面（現行ルールが既に参照しているため優先度高め）

### GAP-12: 金額・数値入力の作法が未規定

**種別**: 既存 spec の拡張（InputText）または部品新設（**未登録**）

**現状**: 業務システム頻出の金額・数量入力について、右寄せ・カンマ区切り表示・
単位（円等）の添え方・`inputmode` の指定が未規定。InputText spec は氏名・電話番号・
メール等の例のみ。

**検討してほしい内容**:
1. InputText の variant / ガイダンス追記で足りるか、専用部品（InputNumber 等）が必要か
2. カンマ整形のタイミング（入力中 or blur 時）は挙動仕様として DS 側で規定するか
   アプリ側責務とするか
3. デジ庁の「maxlength・入力文字種制限の禁止」（form-page never_do）との整合

**影響範囲**: 金額・数量を扱う全フォーム（旅費精算は直撃）

### GAP-13: 年/月/日分割入力の部品・パターン化

**種別**: 部品またはガイダンス新設（**未登録**。DECISIONS.md 2026-08-18 ログで
「必要になれば別途起票」とされていた既知の保留 — 本票で正式化）

**現状**: デジ庁方針により、生年月日等の既知日付はカレンダー UI（DatePicker）・
`<select>`・`<input type="date">` のいずれも不可で、年/月/日を分けた
`input type="text"` + autocomplete 属性を使うとされている。DatePicker / InputText /
Select の `never_use_when` はこの方針を参照済みだが、**正しい実現手段そのものが未定義**。

**検討してほしい内容**: 複合部品（DateFieldSet 等）として新設するか、InputText 3 連の
組み方を form-page のガイダンスとして規定するか。autocomplete 属性・和暦対応の要否も判断。

**影響範囲**: 生年月日・有効期限等の既知日付入力を持つフォーム

### GAP-14: Table 内の行操作列（編集/削除等）の作法 + IconButton

**種別**: 既存仕様のギャップ（Table spec / list-page）+ 部品新設
（IconButton は does_not_exist_yet 登録済み、行操作列の作法は**未登録**）

**現状**: 一覧の各行に「編集」「削除」等のアクションを置く作法が未規定。
テキスト Button を並べるのか、IconButton（未提供）が必要か、行クリック =
detail-page 遷移（Link）との使い分けも決まっていない。

**検討してほしい内容**:
1. 第一弾は「行クリックで detail-page へ、操作は詳細画面側で行う」に統一して
   行操作列自体を不要にする案（部品追加なしで済む）
2. 行操作列を認める場合の作法（列位置・ボタン数上限・破壊的操作の扱い）と
   IconButton 部品化の要否

**影響範囲**: 一覧から直接操作させたい画面全般

### GAP-15: 「※必須 / ※任意」表記作法の未記載部品への展開

**種別**: 既存 spec の追記 5 件（Select / DatePicker / RadioButton / Checkbox /
RepeatingFieldGroup。DECISIONS.md 2026-08-18 ログで「別途起票候補」とされていた既知の
ギャップ — 本票で正式化）

**現状**: 要否表示（「※必須」テキスト + `color.semantic.required`）の作法が
InputText / Textarea の spec にのみ記載されており、他のフォーム部品 5 件には
表記作法自体が未記載。form-page の layout は全項目に要否表示を求めているため不整合。

**検討してほしい内容**: InputText と同一の記述を 5 spec の a11y 欄へ横展開するだけで
足りるか（RadioButton / Checkbox はグループラベル側に付す等、部品特有の差分がないか確認）。

**影響範囲**: フォーム部品全般（記述の一貫性）

## 運用メモ（チケット外）

- **第二段（React 実装 + トークン実値移植 + tokens/dist 生成）が未着手**であることは
  既定のフェーズ計画（GUIDE-for-designers.md）どおりであり本票の対象外。ただし
  「業務システムを実際に作る」段階では上記ギャップより先に必要になるため、
  着手判断の際は本票の高優先チケット（GAP-01〜05）を第二段のスコープに含めるか
  併せて判断されたい。
- **静的 HTML 検証の再現範囲（2026-08-24 ユーザー決定）**: 第二段完了までの
  静的 HTML モックで再現するのは色・余白・レイアウトの見た目のみ。状態表現の挙動・
  最終確定色・複数アプリ間の一貫再現は第二段の対象であり、モックでは保証しない
  （DECISIONS.md 同日ログ参照）。本票の各チケットをモックで先行検証する場合も
  この前提で行う。
- 新規部品・パターンを採用した場合は、従来どおり index.json 再生成（`npm run ci`）と
  速やかなタグ配布（v0.0.3 以降の都度配布運用）を維持する。
