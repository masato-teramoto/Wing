# データベース標準

> このファイルは、**全フィーチャーに共通して適用される DB のルール**（スキーマ設計・命名・型・マイグレーション・クエリ・トランザクション・整合性・バックアップ）を確定させる文書である。\
> _分担_: 個別フィーチャーのテーブル定義は `specs/<feature>/design.md` の `## データモデル（Data Models）`。ページネーションの HTTP としての約束は `api-standards.md` の `## 一覧取得（ページネーション / フィルタ / ソート）`、何を機密として扱うかは `security.md` の `## 機密データ`、サービス全体の災害復旧の進め方は `non-functional.md` の `## バックアップ / DR（サービス全体）`。システム全体の ER 図は `docs/architecture/data-model.md`、業務コード・区分値・採番ルールは `docs/code-design.md`。

> _書き方_: 全フィーチャーに共通するルールだけを書く。特定のテーブルにしか当てはまらない内容は書かない。

## 設計思想

> このプロジェクトの DB 設計で何を優先するかの原則を確定させる節。後続の各節の判断軸になる。

> _書き方_: 1 項目 1 行で列挙する。判断が分かれたときに立ち返れる粒度で書く（正規化をどこまで進めるか、削除を実際に消すか印を付けるだけにするか、など）。

- <DB_PRINCIPLE_N>

## 命名規則

> テーブル・カラム・制約などの名前の付け方を確定させる節。\
> _分担_: フィーチャー固有のテーブル名とカラム定義は `specs/<feature>/design.md` の `## データモデル（Data Models）`。主キーの型は `## 型の指針`。コード上の識別子の命名は `tech.md` の `## 命名規則`。

> _書き方_: 対象には、テーブル、カラム、主キー、外部キー、インデックス、制約など、名前の付け方が変わる単位を書く。例には、そのまま真似できる実例を書く。

| 対象 | 規約 | 例 |
| --- | --- | --- |
| <DB_NAMING_OBJECT_N> | <DB_NAMING_RULE_N> | <DB_NAMING_EXAMPLE_N> |

## 型の指針

> 用途ごとに使う型を確定させる節。\
> _分担_: DB エンジンの製品名とバージョンは `tech.md` の `## コアテクノロジ`。ここには型の選び方だけを書く。

> _書き方_: 用途には、ID、金額、日時、真偽値、文字列、区分値など、型を迷いやすいものを書く。**ID の型は 1 種類に統一する。** 備考には、その型を選ぶ理由や、使ってはいけない型を書く。

| 用途 | 推奨型 | 備考 |
| --- | --- | --- |
| <DB_TYPE_USE_N> | <DB_TYPE_RECOMMENDED_N> | <DB_TYPE_NOTE_N> |

## マイグレーション

> スキーマの変更をどう管理し、どう本番へ反映するかを確定させる節。\
> _分担_: マイグレーションツールの選定は `tech.md` の `## 主要ライブラリ`。リリースの承認と切り戻しは `non-functional.md` の `## デプロイ / リリース`。ここには変更管理のルールだけを書く。

> _書き方_: ルールには、ファイルの作り方、番号の付け方、適用済みのものを書き換えてよいか、戻す手段を用意するかなどを書く。

### 後方互換のあるロールアウト

> _書き方_: 操作には、カラムの追加、削除、名前の変更、必須化など、順序を誤ると止まるものを書く。手順には、何回のリリースに分けて、それぞれで何をするかを書く。

## クエリパターン

> _分担_: ページネーションを HTTP でどう表すかは `api-standards.md` の `## 一覧取得（ページネーション / フィルタ / ソート）`。検索対象のカラム、順位付け、同期のしかたは `specs/<feature>/design.md` の `### 物理データモデル（Physical Data Model）`。ここには DB 側の実装方針だけを書く。

> _書き方_: パターンには、一覧の取得、件数の取得、全文検索、まとめての更新など、書き方を揃えたいものを書く。インデックス方針には、どういう場合に索引を張り、どういう場合は張らないかを書く。

## 接続 / トランザクション

> DB への接続の持ち方と、複数の更新をひとまとまりとして扱う範囲を確定させる節。DB に負荷が集中することや、処理どうしが互いの終了を待ち続けることを防ぐための決まりを置く。

> _書き方_: 項目には、同時に持てる接続の数、待ち時間の上限、分離のしかた（同時に動く処理から互いの途中経過をどこまで見せるか）、1 つのまとまりに含めてよい処理の範囲などを書く。外部への通信を含んだまま長時間まとめない、といった禁止事項もここに書く。

| 項目 | 既定 |
| --- | --- |
| <DB_CONNECTION_ITEM_N> | <DB_CONNECTION_DEFAULT_N> |

## 整合性

> データが矛盾しない状態を、どの層でどう守るかを確定させる節。\
> _分担_: 誰がそのデータを見てよいかの判定は `security.md` の `## 認証・認可`。入り口での入力検証は同ファイルの `## 入力検証 / 出力エスケープ`。ここには制約をどこに置くかと、複数のサービスにまたがる場合の揃え方だけを書く。

> _書き方_: DB の制約で守るもの、アプリケーション側で守るものを書き分ける。複数のサービスにまたがる場合は、どこまで即時に揃え、どこから遅れて揃うことを許すかを書く。

- <DB_INTEGRITY_RULE_N>

## バックアップ / リカバリ

> バックアップの取り方と、そこから戻せることをどう確かめるかを確定させる節。\
> _分担_: 通信の保護は `security.md` の `## ヘッダ / トランスポート`。何を機密として扱うかは同ファイルの `## 機密データ`。保存時の暗号化はこの節で決める。サービス全体としての災害復旧の進め方は `non-functional.md` の `## バックアップ / DR（サービス全体）`。**取得頻度・保持期間・目標復旧時点（RPO）・目標復旧時間（RTO）・復元テストの数値はこの節を正とし、他のファイルに同じ数値を書かない。**

> _書き方_: 項目には、取得の頻度、保持する期間、RPO、RTO、実際に戻せるか試す周期、取得に失敗したときの気づき方を書く。
