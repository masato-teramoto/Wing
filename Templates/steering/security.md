# セキュリティ標準

> このファイルは、**どの機能にも共通して適用される防御のしかた**（入力検証、出力エスケープ、攻撃対策、シークレット管理、トークンの保管と転送、機密データ、ヘッダ、ログ、脆弱性対応）と、**認証・認可の方針**（誰かを確かめてから、何をしてよいかを決めるまで）を確定させる文書である。\
> _分担_: フィーチャー固有のセキュリティ判断と権限の一覧は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。エラー応答から機密を除く扱いは `api-standards.md` の `## エラーハンドリング（API 契約）`。セキュリティ事故が起きたときの流れは `non-functional.md` の `### 障害対応フロー（プロセス骨格）`、具体的な手順は同ファイルの `### 運用手順書の正本`。

> _書き方_: 全機能に共通する方針だけを書く。特定の機能にしか当てはまらない判断は書かない。

## 基本方針

> このプロジェクトのセキュリティで何を優先するかの原則を確定させる節。後続の各節の判断軸になる。\
> _分担_: ネットワークの公開範囲・アクセス経路・接続元の制限もこの節に書く（`non-functional.md` の `## 環境` には書かない）。

> _書き方_: 1 項目 1 行で列挙する。判断が分かれたときに立ち返れる粒度で書き、個別の設定値は書かない。

- <SEC_PRINCIPLE_N>

## 入力検証 / 出力エスケープ

> 受け取った値を確かめる作業（入り口）と、外へ出す値を無害な形に直す作業（出口）を分けて確定させる節。この 2 つは別の作業であり、片方だけでは守れない。\
> _分担_: 値が正しいかどうかを止めるのは API の境界で、ここが入り口側の要となる。DB の制約はそこを通り抜けたものに対する最後の受け皿であり、`database.md` の `## 整合性` を正とする。フィーチャー固有のファイル受付ルールは `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: どの機能にも共通して適用する内容だけを書く。

### 入り口 — 入力検証

> 受け取った値をどの層で、どこまで確かめるかを確定させる節。

> _書き方_: 層には画面、API の境界、業務ロジック、DB など、値が通過する順に書く。同じ検証を複数の層で重ねる場合は、それぞれの層が何を担うかを書き分ける。詳細の列には、より詳しい規定がある場合の参照先を書く。

| 層 | この層の役割 | 実装の要点 | 詳細 |
| --- | --- | --- | --- |
| <INPUT_VALIDATION_LAYER_N> | <INPUT_VALIDATION_ROLE_N> | <INPUT_VALIDATION_IMPLEMENTATION_N> | <INPUT_VALIDATION_REFERENCE_N> |

### 出口 — 出力エスケープ

> 外へ出す値を、出力先ごとに無害な形へ直す方法を確定させる節。

> _書き方_: 出力先には画面（HTML）、SQL、シェル、ログ、外部 API など、値の行き先を書く。やってはいけない例には、実際に起きやすい誤った書き方を書く。

| 出力先 | 防ぐこと | やること | やってはいけない例 |
| --- | --- | --- | --- |
| <OUTPUT_SINK_N> | <OUTPUT_THREAT_N> | <OUTPUT_MITIGATION_N> | <OUTPUT_ANTIPATTERN_N> |

### 共通ルール

> 入り口と出口の両方に当てはまるルールを確定させる節。

> _書き方_: どちらか一方にしか当てはまらないものは、上の入り口または出口の節に書く。

| # | ルール |
| --- | --- |
| N | <INPUT_OUTPUT_COMMON_RULE_N> |

## 攻撃対策（主要パターン）

> 想定する攻撃と、それぞれへの備えを確定させる節。設計・実装・レビューのときの確認リストとして使う。\
> _分担_: 具体的な設定値は `## ヘッダ / トランスポート`、認証まわりの備えは `## 認証・認可`。ここには攻撃と対策の対応だけを書く。

> _書き方_: 攻撃には広く知られた名前を書く。参照の列には、対策の詳細が書かれている節やファイルを書く。

| 攻撃 | 対策 | 参照 |
| --- | --- | --- |
| <ATTACK_PATTERN_N> | <ATTACK_MITIGATION_N> | <ATTACK_REFERENCE_N> |

## シークレット管理

> 認証情報や鍵など、外部に漏れてはいけない値の扱いを確定させる節。\
> _分担_: 環境ごとの値そのものはこのファイルに書かず、保管場所だけを書く。

> _書き方_: 保管場所、参照のしかた、入れ替えの周期、漏れた場合の対応などを項目として挙げ、それぞれの方針を対で書く。実際の値は書かない。

| 項目 | 内容 |
| --- | --- |
| <SECRET_MGMT_ITEM_N> | <SECRET_MGMT_POLICY_N> |

## セッション / トークンの保管・転送

> 発行済みのトークンやセッションを、どう保管し、どう運ぶかを確定させる節。\
> _分担_: いつ発行し、いつ失効させるかは `## 認証・認可` の `#### トークン / セッションのライフサイクル`。ここには守り方だけを書く。

> _書き方_: 保存先、付ける属性、通信経路、有効期限の扱いなどをルールとして書く。

| # | ルール |
| --- | --- |
| N | <TOKEN_STORAGE_RULE_N> |

## 機密データ

> 慎重に扱う必要があるデータを種別ごとに分け、その扱いを確定させる節。\
> _分担_: ログへの出力可否は `non-functional.md` の `#### 出力しない`、保存時の暗号化は `database.md` の `## バックアップ / リカバリ` を正とする。ここには種別と扱いの対応だけを書く。

> _書き方_: 種別には個人情報、認証情報、決済情報など、扱いが変わる単位で書く。扱いには、保存の可否、加工のしかた、閲覧できる範囲、保持する期間を書く。

| 種別 | 扱い |
| --- | --- |
| <SENSITIVE_DATA_TYPE_N> | <SENSITIVE_DATA_POLICY_N> |

## ヘッダ / トランスポート

> 通信とレスポンスヘッダに関する推奨値を確定させる節。\
> _分担_: CDN やロードバランサへの設定は `tech.md` の `## コアテクノロジ`、実際の作業手順は `non-functional.md` の `### 運用手順書の正本`。ここには推奨する値だけを書く。

> _書き方_: ヘッダ名と、設定する値をそのまま書く。値の意味の説明は書かない。

| ヘッダ / 設定 | 推奨 |
| --- | --- |
| <SECURITY_HEADER_N> | <SECURITY_HEADER_VALUE_N> |

## セキュリティログ

> セキュリティ上の出来事を、何を記録し、その記録をどう守るかを確定させる節。\
> _分担_: ログの形式と共通フィールドは `non-functional.md` の `### ログ方針` を正とする。ここには記録する対象と、記録自体の守り方だけを書く。

> _書き方_: 記録する出来事（ログイン成功と失敗、権限の変更、機密データへのアクセスなど）と、改ざんを防ぐ方法、保持する期間をルールとして書く。

| # | ルール |
| --- | --- |
| N | <SEC_LOG_RULE_N> |

## 脆弱性対応

> 見つかった弱点を、どう見つけ、どれだけの期間で直すかを確定させる節。\
> _分担_: 事故が起きたときの流れは `non-functional.md` の `### 障害対応フロー（プロセス骨格）`、具体的な手順は同ファイルの `### 運用手順書の正本`。セキュリティ事故のときは、この節の修正期限（修正 SLA）も併せて使う。

> _書き方_: 検査の方法と周期、深刻度ごとの修正期限、報告を受け付ける窓口を項目として挙げ、それぞれの方針を対で書く。

| 項目 | 内容 |
| --- | --- |
| <VULN_MGMT_ITEM_N> | <VULN_MGMT_POLICY_N> |

## 認証・認可

> **誰であるかを確かめること（認証）** と、**その人が何をしてよいかを決めること（認可）** の方針を確定させる節。\
> _分担_: トークンの保管と転送、なりすまし要求（CSRF）や読み込み元の制限（CSP）などの共通の備えは、このファイル前半の `## セッション / トークンの保管・転送` と `## ヘッダ / トランスポート`。リソースごとの権限の一覧やフィーチャー固有のルールは `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: 誰かを確かめてから権限を判定するまでの流れと、その方針だけを書く。実装の詳細は書かない。

### 認証・認可の設計思想

> 認証と認可で何を優先するかの原則を確定させる節。方式やモデルを選ぶときの判断軸になる。

> _書き方_: 1 項目 1 行で列挙する。利便性と安全性のどちらを優先するかなど、後で判断に迷う場面を想定して書く。

- <AUTH_DESIGN_PRINCIPLE_N>

### 認証

> 誰であるかを確かめる側の取り決めをまとめる見出し。方式・流れ・通行証の寿命・設計時に必ず検討する方針をここに並べる。

#### 認証方式

> このプロジェクトで採用する認証のしかたと、その理由を確定させる節。

> _書き方_: 方式は 1 つだけ書く。代替案には、検討したが採用しなかった方式と、その理由を書く。後から見た人が同じ判断に至れるように書く。

- **方式**: <AUTH_METHOD>
- **採用理由**: <AUTH_METHOD_RATIONALE>
- **代替案と不採用理由**: <AUTH_METHOD_ALTERNATIVE>

#### 認証フロー

> 誰であるかを確かめ、通行証を渡し、以後の要求ごとに確かめ直すまでの流れを確定させる節。\
> _分担_: 署名アルゴリズムなどの実装の詳細は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: 識別、検証、発行、添付、要求ごとの検証という順序を土台に、このプロジェクト固有のステップ（外部サービスからの折り返しなど）を当てはめて書く。

| 順 | ステップ |
| --- | --- |
| N | <AUTH_FLOW_STEP_N> |

#### トークン / セッションのライフサイクル

> 通行証をいつ発行し、いつ効力を失わせるかを確定させる節。\
> _分担_: 保管場所の具体的な守り方は `## セッション / トークンの保管・転送`。ここには場所の指定だけを書く。

> _書き方_: 寿命は期間で書く。失効トリガには、パスワード変更やログアウトなど、効力を失わせる出来事を書く。

| 項目 | 既定 |
| --- | --- |
| アクセストークン寿命 | <ACCESS_TOKEN_TTL> |
| リフレッシュトークン寿命 | <REFRESH_TOKEN_TTL> |
| 失効トリガ | <TOKEN_REVOCATION_TRIGGER> |
| ローテーション | <TOKEN_ROTATION_POLICY> |
| 保管場所（クライアント） | <TOKEN_CLIENT_STORAGE> |

#### セキュリティパターン（認証レイヤ）

> 認証の流れを設計するときに必ず検討する方針を確定させる節。\
> _分担_: Cookie の属性、CSP、ヘッダの値など実装の詳細は、このファイル前半の `## セッション / トークンの保管・転送` と `## ヘッダ / トランスポート`。ここには、いつ発行し失効させるかと対で決める方針（端末との紐付け、通行証に載せる情報、追加認証を求めるかどうか）だけを書く。

> _書き方_: パターン名と、それを採用するかどうか、採用する場合の方針を対で書く。検討した結果採用しない場合も、その旨を書く。

| パターン | 方針 | 備考 |
| --- | --- | --- |
| <AUTH_SECURITY_PATTERN_N> | <AUTH_SECURITY_POLICY_N> | <AUTH_SECURITY_NOTE_N> |

### 認証 → 認可の契約（AuthContext）

> 認証に成功した後、それより後ろの層へ渡す情報の形を確定させる節。後ろの層はこの情報だけを見て判断し、生の通行証やセッションの中身を業務ロジックへ渡さない。\
> _分担_: フィーチャー固有の権限の一覧は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。

> _書き方_: 必須フィールドには、どの機能でも必ず必要になるものだけを書く。載せる情報は必要最小限にとどめ、`#### セキュリティパターン（認証レイヤ）` で決めた方針と食い違わないようにする。

| 項目 | ルール |
| --- | --- |
| 生成タイミング | <AUTHCONTEXT_CREATION_TIMING> |
| 必須フィールド | <AUTHCONTEXT_REQUIRED_FIELD_N> |
| 任意フィールド | <AUTHCONTEXT_OPTIONAL_FIELD_N> |
| 型の置き場 | <AUTHCONTEXT_TYPE_LOCATION> |
| 消費側 | <AUTHCONTEXT_CONSUMER> |

### 認可

> 確かめた相手が何をしてよいかを決める側の取り決めをまとめる見出し。しくみ・確認する場所・持ち主かどうかの判定をここに並べる。

#### 権限モデル

> 何をしてよいかを決めるしくみと、その理由を確定させる節。

> _書き方_: モデルは 1 つだけ書く。定義の置き場には、権限やロールの一覧をどこで管理するかを書く。禁止には、権限名やロール名をコードに直接書き込まないなど、避ける実装を書く。

- **モデル**: <AUTHZ_MODEL>
- **定義の置き場**: <AUTHZ_DEFINITION_LOCATION>
- **採用理由**: <AUTHZ_MODEL_RATIONALE>
- **代替案と不採用理由**: <AUTHZ_MODEL_ALTERNATIVE>
- **禁止**: <AUTHZ_PROHIBITED>

#### チェックの適用箇所

> 権限の確認を、どの層で行うかを確定させる節。\
> _分担_: 権限名の一覧やリソースごとの対応表は `specs/<feature>/design.md` の `### セキュリティ上の考慮（Security Considerations）`。ここに書く例はあくまで書き方の見本であり、一覧ではない。

> _書き方_: 層には、要求を受け取る場所、業務ロジック、データ取得など、確認を行う位置を書く。同じ確認を複数の層で重ねる場合は、それぞれの層が何を担うかを書き分ける。

| 層 | 役割 | 例 |
| --- | --- | --- |
| <AUTHZ_CHECK_LAYER_N> | <AUTHZ_CHECK_ROLE_N> | <AUTHZ_CHECK_EXAMPLE_N> |

#### 所有権・エンティティ境界

> 「そのデータが本当にその人のものか」を確かめる方法を確定させる節。役割による権限だけでは、他人のデータへのアクセスを防げないため、別に定める。\
> _分担_: 利用組織ごとのデータの分け方そのものは `database.md` の `## 整合性`。ここには確認のしかただけを書く。

> _書き方_: 検証タイミングには、確認をいつ行うかを書く（データを取り出す前か、取り出した後か）。権限名の形式には、名前の組み立て方を実例で示す。

| 項目 | 既定 |
| --- | --- |
| パターン | <OWNERSHIP_PATTERN> |
| 検証タイミング | <OWNERSHIP_CHECK_TIMING> |
| 権限名の形式 | <PERMISSION_NAME_FORMAT> |

### パスワード / MFA

> パスワードと多要素認証（MFA）の扱いを確定させる節。\
> _分担_: 外部サービスに認証を任せる場合、この節のうち任せる項目には委任先を書く。

> _書き方_: パスワード強度には、満たすべき条件を書く。ハッシュには、使うアルゴリズムと設定値を書く。アカウントロックには、何回失敗したら止めるか、どうすれば解除されるかを書く。

| 項目 | 内容 |
| --- | --- |
| パスワード強度 | <PASSWORD_STRENGTH_POLICY> |
| ハッシュ | <PASSWORD_HASH_POLICY> |
| パスワードリセット | <PASSWORD_RESET_POLICY> |
| MFA | <MFA_POLICY> |
| アカウントロック | <ACCOUNT_LOCK_POLICY> |

### API 間認証

> 利用者を介さず、システム同士が呼び出し合うときの認証を確定させる節。\
> _分担_: 使う鍵や証明書の保管は `## シークレット管理`。ここには認証のしかただけを書く。

> _書き方_: スコープには、呼び出し元ごとに許す範囲をどう絞るかを書く。監査には、呼び出しの記録をどこに残すかを書く。

| 項目 | 内容 |
| --- | --- |
| 方式 | <SERVICE_AUTH_METHOD> |
| スコープ | <SERVICE_AUTH_SCOPE> |
| ローテーション | <SERVICE_AUTH_ROTATION> |
| 監査 | <SERVICE_AUTH_AUDIT> |
