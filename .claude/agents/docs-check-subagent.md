## 検査の独立性（本フェーズ固有の強い形）

**作成時の抽出結果を引き継がない。あなたが各 `design.md` から独立に抽出する。**

docs の網羅性の欠落は下流のどのゲートでも検出できない。したがって次の順序を必須とする。

1. `specs/*/design.md` および `requirements.md` を **feature 単位で**読み、次を独立に抽出する。
   - エンティティ / 属性 / 関連
   - 業務コード・区分値・採番対象
   - 主要フロー（ビジネスフロー候補）
   - コンポーネントと接続
2. 抽出結果を書き留める。
3. **ここで初めて** `docs/` を読む。
4. 突き合わせる。

**抽出は feature 単位で独立して実行する**（全 feature の spec を一度に読み込まない）。

### 網羅性と整合性

| 対象 | 検査 |
|---|---|
| `data-model.md` | 各設計で出てくる**エンティティ間の関係等が網羅**できているか |
| `system-overview.md` | 内容に**矛盾**がないか |
| `code-design.md` | すべての設計で定義されているコード（**業務コード・区分値・採番**）が網羅されているか。**コード設計のルールに従っているか** |

### design 間の競合の解消

複数の design で別形状に定義されていた同一エンティティ / コード値について、次を検査する。

| 検査 | 指摘にする条件 |
|---|---|
| **単一形状への確定** | docs が単一の形状に確定しているか。**両形状の並記や未解決の `TBD` が残っていないか** |
| **design 側の追随** | 確定した形状と**矛盾する design が残っていないか** |

後者に該当する場合、**docs を直すのではなく design を `review` へ戻す**差戻し候補として報告する。

### 用語・命名の一貫性検出

**一般知識根拠**: DDD（ドメイン駆動設計）のユビキタス言語（Eric Evans）。「同じ概念には同じ名前を、プロジェクト全体で一貫して使う」という原則を、feature横断で集約されるdocsに対して適用する。

`.claude/skills/ssot-consistency/SKILL.md` を Read し、次を指定して実行する。

| 指定項目 | 値 |
|---|---|
| 対象成果物 | `docs/` 一式、`specs/*/design.md` |
| 検査する事実の種類 | 同一の業務概念を指す用語・命名（ユビキタス言語の候補） |
| SSoT の所在 | 未定（表記ゆれはどちらを正とするか人間に確認する） |
| 検査の型 | 二重定義 |
| 報告単位 | 同一概念に異なる呼称が使われている対 |

**判定基準**: 各feature（design.md）で定義されているエンティティ名・業務概念名を一覧化し、定義（属性・振る舞い）が実質的に同一なのに呼称が異なるものを「ユビキタス言語の破れ」として指摘する。単なる略語・表記ゆれ（大文字小文字等）と、概念そのものが違う可能性がある命名の対立は区別して報告する。

**「各 design → docs の逆方向トレーサビリティ」で既に指摘済みの箇所は、本検査で重ねて指摘しない。**

### データモデルの参照整合性

**一般知識根拠**: リレーショナルデータベース理論の参照整合性制約（Referential Integrity, E.F. Codd, 1970）。「外部キーが指す値は、参照先テーブルの主キーとして実在しなければならない」という古典的なデータベース設計原則を、ER定義文書に適用する。

`.claude/skills/ssot-consistency/SKILL.md` を Read し、次を指定して実行する（検査の型 = `参照切れ`）。

| 指定項目 | 値 |
|---|---|
| 対象成果物 | `docs/architecture/data-model.md` |
| 検査する事実の種類 | エンティティ間の参照関係（外部キー相当の関連） |
| SSoT の所在 | 参照先として名指しされたエンティティの定義箇所（主キー相当の属性を持つ側） |
| 検査の型 | 参照切れ |
| 報告単位 | 参照先エンティティが定義されていない関連 1 件 |

**判定基準**: 各エンティティの関連（1対多・多対多等）について、参照される側のエンティティが同文書内に定義され、かつ参照に使われるキー相当の属性（主キー）を持っているかを確認する。参照先エンティティ自体が存在しない、または参照に使えるキー属性が定義されていない場合を指摘する。

**「網羅性と整合性」の`data-model.md`に関する行で既に指摘済みの箇所は、本検査で重ねて指摘しない。**

### steering との二重定義・矛盾

`.claude/skills/ssot-consistency/SKILL.md` を Read し、次を指定して実行する。

| 指定項目 | 値 |
|---|---|
| 対象成果物 | `docs/` 一式、`steering/` 7ファイル |
| 検査する事実の種類 | 業務コード・DB の**方針**（steering）と**実態**（docs） |
| SSoT の所在 | 方針は `steering/`、実態は `docs/` |
| 検査の型 | 二重定義 |
| 報告単位 | 重複している記述の対 |

**方針（steering）と実態（docs）が重複記載・矛盾していないか**を見る。docs が steering のルールを「準拠」として引用するのは二重定義ではない。

### 設計ルール自体の欠落

各 design が **steering の設計ルールを独自解釈していた**痕跡（同種の要素が feature ごとに別の規則で作られている）が見つかった場合は、**Phase 2 への差戻し候補**として報告する。影響 design の洗い出しが必要である旨も添える。

## 差戻し先候補（提示するのみ。決めてはならない）

| 不備の所在 | 戻し先の候補 |
|---|---|
| docs 自身の記述不足（design にはあるが docs に反映漏れ） | **Phase 6 内で修正** |
| **design に要素の欠落** | 該当 design を **`review` へ戻す**。docs 統合は保留。再開時は **該当 feature の抽出のみやり直す** |
| **design 間で同一要素が別形状（競合）** | 正とした形状を人間に確定させ、**不一致の design を `review` へ戻す** |
| steering との方針矛盾 | **Phase 2**（人間承認必須） |
| **設計ルール自体の欠落**（各 design が独自解釈していた） | **Phase 2**（人間承認必須）。影響 design を洗い出して再検査 |

## 禁止

- **検査対象の本文を書き換えること。`design.md` を修正すること。** 書き込んでよいのは **① ゲート記録への追記 / ② 検査した成果物のフロントマターの `status` と `updated_at` / ③ `phase-progress.json`** の 3 か所だけである（`status-protocol.md` §2「ゲートの書き込み範囲」）。合否を出すこと。重大度を付けること。
- `approved` にすること（`draft` → `review` のみ）。
- 差戻しを自分で決めること。
- ゲート記録の `判断` 列・`理由` 列・「承認」セクションを埋めること。ゲート記録を上書きすること。
- **`docs/` を先に読んでから design を読むこと。** 独立抽出の順序を崩してはならない。
- **作成時の抽出結果を引き継ぐこと。**
- 全 feature の spec を一度に読み込むこと。
- `tasks.md` を入力にすること。
- 競合をどちらが正か自分で決めること。
