## 概要

上流成果物（要求一覧・feature-list・requirements・design・non-functional 等）と下流成果物の
あいだで、ID や要素が過不足なく対応しているかを突合する。方向（上流→下流の網羅性チェックか、
下流→上流の出典チェックか、双方向の突合か）と対象を呼び出し元が指定することで、全フェーズの
トレーサビリティ検証に使い回せる（取り漏らし検出・要求ID双方向突合・非機能反映突合・可観測性
反映突合・design網羅性検証・AC突合・コンポーネント突合・誤配置検出など）。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 上流 | 突合の起点（独立抽出する場合はその旨も明記） | `RFP`（独立抽出） / `.aidd/requirement-list.md` |
| 下流 | 突合の終点 | `.aidd/feature-list.md` |
| 突合方向 | `上流→下流`（網羅性・取り漏らし） / `下流→上流`（対応の抜け・誤配置） / `双方向` | `双方向` |
| 対応の単位 | 何を1対1で対応させるか。IDを持たない上流では「何を同一とみなすか」 | `要求ID` / `要件ID` / `コンポーネント名` / `要求の意味単位` |
| 分母の絞り込み | 分母から除く行の条件。無ければ「なし」と明記する | `分類=機能の行のみ` / `なし` |
| 報告単位 | 何を1件の指摘にするか | `未割当の要求ID` / `docs未反映のdesign要素` |

`分母の絞り込み` は誤検出を防ぐための必須指定である。指定が無いまま分母を自分で決めず、入力不足として呼び出し元へ返す。
対応関係を持ちえない行は分母に含めない（例: 出典種別=壁打ちの要求を RFP 突合の分母に、非機能/制約の要求を feature 割当の分母に入れない）。

## 手順

1. `上流` から対応単位（ID・要素）を独立に抽出する。**下流を先に読んで「それらしきもの」を
   逆算しない**（下流の記述に引きずられると取り漏らしを見逃す）。
2. `下流` から同じ単位で対応関係（参照・言及）を抽出する。
3. `突合方向` に従って比較する。
   - `上流→下流`: 上流にあるが下流に反映されていない単位を「取り漏らし」として指摘する
   - `下流→上流`: 下流にある ID・参照が上流に無い（ID の不一致・参照先が無い）単位を「対応の抜け」または「誤配置」として
     指摘する。内容が上流に根拠を持たないこと（上流に根拠のない追記）は evidence-guard が持ち主なので出さない
     （finding-rules の持ち主の表）
   - `双方向`: 両方向を行い、欠落側をそれぞれ指摘する
4. 対応単位が別カテゴリに誤って反映されている場合（例: 非機能要求が機能要件として書かれている）は
   「誤配置」として指摘する。
5. キーの一致だけで足りない場合は、意味の落とし込みも見る（層②）。IDが書かれていても上流の内容が
   下流で満たされていなければ指摘し、意味判定を行ったこと（「ID対応あり・内容未充足」等）と判定の内容を `evidence` に書く。
6. 指摘を `報告単位` でまとめる。

### 上流が自由形式の場合（RFP）

- 章・見出しのような構造単位を突合キーにしない（網羅表を作らない）。単位の切り出し自体が推論になり、
  抽出しなかった箇所を並べても検出力を持たない。`要求の意味単位` で独立に抽出する。
- 上流の該当箇所は `evidence` に引用する（位置ではなく内容で特定できるようにする）。

## この工程で指摘しない事項

- `.claude/skills/finding-rules/SKILL.md` の工程の境界の表・`confirmed_answers`・`learned` に当たる事項
- `TBD（<工程> で確定）` と書いてある値
- 下流→上流の「上流に根拠のない追記」（evidence-guard が出す。ここは ID・参照の対応の抜けだけを出す）
- その工程で決めない対応（例: requirements では桁数・形式・項目の対応まで求めない。境界の表 B-02）

当たるものは指摘にせず、除外として返す（除外の出典を付ける。書き方は finding-rules）。

## 出力の形

指摘ごとに次を返す。書き方は `.claude/skills/finding-rules/SKILL.md`（検査の最初に読む）に従う。重大度は出さない（L3 が `kind` から決める）。

```
{ location, subject, kind, summary, evidence, suggestion, recommendation, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `location` | 検査対象（下流）の箇所。取り漏らしは、上流の単位を受けるべき下流の節（見出しが無ければ対象ファイル）を書き、上流の単位は `subject` と `evidence` に書く（location を上流にすると、節の変更による自動の解消・引き継ぎが効かないため）。相手側の箇所は `evidence`。`<案件相対パス> § <節見出し> / <ID>` の形。複数箇所なら代表 1 か所＋「ほか n か所」（全件は `evidence`） |
| `subject` | 対象の語（例: `REQ-014`） |
| `kind` | `.claude/skills/finding-rules/SKILL.md` の種類から 1 つ選ぶ。迷ったら上の行。ID・参照の対応の抜けは `文書間の参照`。上流の内容が下流に無い・満たされていない（取り漏らし、ID対応あり・内容未充足）は `業務の欠落・矛盾`。別カテゴリへの誤配置は `工程・文書の分担` |
| `summary` | 60 字以内。結論を先に、何が・どこで（例: 「`REQ-014` が requirements.md のどこにも反映されていない」） |
| `evidence` | 上流の該当箇所（自由形式の上流は引用）と下流の対応箇所。意味判定を行ったときはその旨と判定の内容 |
| `suggestion` | 修正案（差分・書き換え文）。業務の新しい事実が要るときは、修正案ではなく「何を決めればよいか」と選べる案 |
| `recommendation` | `修正：理由` / `差戻し：理由` / `対応せず進める：理由` / `質問：理由` のどれか。業務の新しい事実が要るときは `質問：…` |
| `is_rollback_candidate` | 上流側の欠落・誤りが原因の場合は `true` |

## 禁止

- 対象成果物を書き換えない（欠落を自動で埋めない）
- 合否を出さない
- 下流の記述を根拠に上流の抽出結果を後から書き換えない（§手順1の独立抽出を維持する）
- 作成側が抽出した結果を再利用しない（ゲート側が上流を読み直して導出する）
- `分母の絞り込み` の指定が無いまま分母を自分で決めない
- 自由形式の上流を章・見出し単位に区切って網羅表を作らない
