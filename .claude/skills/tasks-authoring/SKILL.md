# tasks-authoring（Phase 7: tasks 作成）

承認済み `requirements.md` / `design.md` から **実装の実行計画**を作成する。**本フェーズは Spec 生成フローの最終フェーズである。**

- 成果物: `specs/<feature-name>/tasks.md`
- テンプレート: `Templates/specs/_template/tasks.md`

---

## 入力

| 項目 | 内容 |
|---|---|
| 対象 feature の requirements / design | `specs/<feature-name>/requirements.md` / `design.md`（**ともに `approved`**） |
| steering | `steering/` 一式（全文） |
| feature-list | `.aidd/feature-list.md`（**`approved`**。生成順の参照元） |

- **`docs/` を入力にしない。** docs は各 design を集約した派生物であり、feature 単位の設計の正は `design.md` である。docs を根拠にタスクを起こすと、正でないものを参照することになる。

---

## 実装フェーズ接続の前提

`tasks.md` は将来の **実装エージェントの実行入力**である。「人間が読む計画書」ではないため、次を必須とする。

| 必須 | 内容 |
|---|---|
| **観測可能な完了条件** | 各タスクに 1 行以上。テスト・ログ・出力など **外から確認できる形**で書く |
| **要件ID の紐づけ** | 各タスクに `_Requirements:` を付ける。要件ID を持たないタスクは `—` を置く（テンプレートの表記に従う） |
| **検証前提との整合** | `steering/tech.md` の検証前提（コマンド・テスト方針）と矛盾しない |

> 実装フェーズ本体は本フローのスコープ外である。ただし将来接続するため、**接続に必要な最低制約は本フェーズで満たしておく。**

### 完了条件の書き方

| 良い（観測可能） | 悪い（観測不能） |
|---|---|
| `pnpm typecheck` が緑 | 正しく実装されている |
| `/health` が 200 を返す | 動作確認できる |
| `OrderService.test.ts` が全件パス | テストを書く |
| マイグレーションが up/down ともテスト DB で成功 | DB を整備する |

**「完了条件」の欄に主観的な達成判定を書かない。** 誰が見ても同じ結論になる観測手段を書く。

---

## 手順

### 1. 優先度順に対象 feature を選ぶ

`tasks.md` は実装の実行入力であり、実装は `feature-list.md` の優先度順に着手する。生成順を優先度順に合わせることで、**先に着手する feature の tasks が先に揃う。**

### 2. テンプレートを埋める形で作成する

- 注記表記（`_Requirements:` / `_Design:` / `_Boundary:` / `_Depends:` / `(P)`）はテンプレートの早見表を正とする。
- `_Design:` は **`design.md` の該当セクション**を指す。実装者が `design.md` 全文を読まずに作業できるようにするためである。

### 3. 壁打ちで未記入箇所を埋める

**tasks フェーズを例外にしない。** 他フェーズと同じ手順を適用する（下記 §未記入箇所の質問化）。

### 4. タスク網羅の自己診断を行う

1. `requirements.md` の **全要件ID と全受入基準（AC）** を列挙する。
2. `design.md` の **設計要素**（コンポーネント・契約・データモデル・フロー）を列挙する。
3. 次を確認して人間へフィードバックする。
   - 要件を満たすタスクが網羅されているか
   - `design.md` を満たすタスクが網羅されているか
   - **すべての AC が、少なくとも 1 つのタスクの完了条件で検証されるか**

> 自己診断は作成側の工程であり、**品質ゲートの代わりにならない。**

### 5. 繰り返す

1〜4 を feature の数だけループさせる。

### 6. 品質ゲートを通す

`tasks-check-subagent` を **別コンテキストで**起動する（起動時の制約は `.claude/skills/aidd-flow/SKILL.md` §5 Step 3）。**指摘の要約は呼び出し元へ返す。③ の提示と人間の判断の反映は呼び出し元が行うため、本 Skill が人間へ承認を求めない。**

---

## tasks は設計を決める場ではない（最重要）

**`design.md` に根拠のない設計判断をタスクに書いてはならない。** tasks は実装計画であり、**API 形状・エンティティ・技術選定などを新たに決める場ではない。**

| 状況 | 行うこと |
|---|---|
| タスクを起こすのに必要な設計が `design.md` に無い | **タスクの中で決めない。** 該当 design を `review` へ戻す差戻し候補として人間に提示する |
| `design.md` の記述が曖昧でタスクに落とせない | 同上。壁打ちで自分が決めて埋めてはならない |

- design を差戻した場合、**`docs/` も `review` へ引き下げる**（docs は design の派生物）。引き下げの判断は ③ 人間レビューが行う。
- **要件の受入基準が検証不能**（観測可能な完了条件に落とせない）と判明した場合は、該当 `requirements.md` を `review` へ戻す差戻し候補として提示する。

## 未記入箇所の質問化

1. テンプレートから **`<UPPER_SNAKE>` 系統**のプレースホルダー（記法と扱いは `.claude/skills/aidd-flow/references/status-protocol.md` §7 を正とする）を抽出し、**タスク単位 / セクション単位**で人間に提示する。`{{...}}` 系統は機械的に埋めるため質問化しない。
2. 提示は「この項目の根拠が requirements / design / steering に無い」という形にする。**推測した候補を選択肢として並べない。**
3. **設計不足に起因して埋められない箇所は、質問ではなく差戻し候補として提示する**（§tasks は設計を決める場ではない）。
4. **埋める必要がないプレースホルダーは、人間が明記した不要理由を記載して保持する。削除しない。**
5. 未回答が残る場合は `phase-progress.json` の `waiting_for` を `human_answer`、`open_placeholders` を **不要理由が明記されていない未記入数**に更新して停止する。

## 禁止

- 完了条件の無いタスクを作ること。
- 要件ID の紐づけが無いタスクを作ること（要件ID 不要な場合は `—` を置く）。
- **`design.md` に根拠のない設計判断をタスクに書くこと。**
- 観測不能な完了条件を書くこと。
- `docs/` を入力にすること。
- `steering/tech.md` の検証前提と矛盾する検証手段を書くこと。
- プレースホルダーを削除すること。
- `approved` でない requirements / design を入力にすること。
- 自ら `status: approved` にすること。
