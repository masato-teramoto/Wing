## 概要

`.aidd/requirement-list.md` のうち出典種別が「壁打ち」の行（RFPに出典を持たない、対話の中で
判明した新規要求）が、`references/status-protocol.md` §3 の定めどおり正しい手続き（Phase 1の
壁打ちとして確定し、出典種別を明記して追記されている）を経ているかを検証する。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象 | 壁打ち由来の要求一覧の行 | `.aidd/requirement-list.md` のうち出典種別=壁打ちの行 |

## 手順

1. `対象` の各行について、出典種別が明示的に「壁打ち」と記載されているかを確認する
   （無記載や他フェーズ発の記述を壁打ちとして紛れ込ませていないか）。
2. その要求が Phase 1 の成果物（`.aidd/requirement-list.md`）に追記される形で確定しており、
   他フェーズの成果物が要求一覧を経由せず直接要求を書き換えていないかを確認する
   （`references/status-protocol.md` §3「検出フェーズが要求一覧を書き換えてはならない」）。
3. 出典種別が「壁打ち」でありながら、実際には RFP に対応する記述がある（つまり本来は
   RFP由来として扱うべき）ものを指摘する。
4. 既存要求の詳細化にすぎないものが新規の要求IDとして追加されていないかを確認する。該当すれば、
   寄せるべき既存の要求IDを示して指摘する（詳細化は requirements.md の要件として既存IDに紐づける）。

## 出力の形

```
{ id, location, finding, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `id` | この Skill 内で一意な通し番号 |
| `location` | 該当する要求一覧の行 |
| `finding` | 手続き違反の事実（例: 「`REQ-030` は壁打ち由来とされているが出典種別の記載が無い」） |
| `is_rollback_candidate` | 通常 `false`（同一フェーズ内での記載修正で解消できるため） |

## 禁止

- 対象成果物を書き換えない
- 合否を出さない
- 壁打ち由来の要求そのものの是非（要求すべきかどうか）は判断しない（手続きの妥当性のみ）

入力文書から確認できる出典・所在だけを検査する。実際の人間の回答が公開された根拠に無い場合、手続きが正しかったとも違反だったとも推測しない。確認不能であることを明示して返す。作成時の非公開推論・会話履歴は読まない。
