# requirement-clarification — 明確化セッションの進め方

## 使い方

要求に曖昧さが残る状態で、質問を通じて意図を確定させるための進め方。**確定するまで下流工程へ進まない**
のが本パックの中心であり、質問そのものを目的にしない。

## 入力（必須）と解決規則

回答は成果物へ書き戻す（ルールC）ため、**何を明確化し・どこへ書き戻すか**が決まるまでセッションを
始めない。skill が自動で読み込まれても、これらの入力が一緒に渡るわけではない。

| 入力 | 内容 |
|---|---|
| `clarification_target` | 明確化の対象（対象の要求・機能・決定事項。通常は依頼文そのものが与える） |
| `writeback_ref` | 受理した回答の書き戻し先（成果物のパスと**該当節**。既存成果物が無い場合は新規記録先） |

**解決の順序**

1. **明示があればそれを使う（ただし解決できて書けることを確かめてから）**: 与えられた値を使う（探索しない）。
   ただし `writeback_ref` が**不存在／読取不能／書込不能**、あるいは**複数の節を指して1つに定まらない**なら、
   推定で選ばず**確認して止まる**。
2. **明示がなければ候補を挙げてよい**: ただし検索は**候補の発見**であって書き戻し先の確定ではない。
   ファイル名・置き場所・候補が1件しかないことは根拠にならない。
3. **既存成果物が無いときは、記録先を確認してから作る**: 新規ファイルの作成・場所・名前を**推定で決めない**。
   確認を得ずに任意のファイルへ書かない。
4. **確定するまで開始も完了もしない**: 入力が決まらないうちはセッションを**始めず**、また
   **完了・確定として扱わず**、`requirement-authoring-core` への引き継ぎもしない。
   確認は **A-02 に従い1回のやり取りにつき1問**で行う（不足が複数あるなら回を分ける）。

**A-03 の「省略」との関係**: A-03 が許すのは**明確化そのものの省略**であって、**回答を受理したのに
書き戻さないこと**の許可ではない。回答を受理した以上、`writeback_ref` は必要になる。

## 実行フロー

### 1. 詳細質問の前に分解要否を判定する

要求が複数の独立したサブシステム・利用目的・成果物を含み、それぞれを別々に実装・検証できるなら、
詳細を聞き始める前にスコープ超過を知らせる。独立な部分、部分間の関係、取り組む順序を簡潔に示し、
どの単位を今回の `clarification_target` にするかを一問で確認する。対象単位が決まるまで、その内側の
詳細質問へ進まない。

### 2. 曖昧性の被覆マップを作る

`clarification_target` と参照できる既存成果物を、次の観点で走査する。各観点を内部作業上
`Clear`／`Partial`／`Missing` に分類し、`Partial` と `Missing` だけを質問候補にする。

| 観点 | 確認する内容 |
|---|---|
| 機能範囲と振る舞い | 利用者・目的・含むもの／含まないもの・主要分岐・状態変化 |
| ドメインとデータ | 対象となる実体・属性・識別・ライフサイクル・データ源 |
| 操作と利用体験 | 起点・操作の流れ・権限・利用者への応答・アクセシビリティ |
| 非機能品質 | 性能・可用性・セキュリティ・プライバシー・監査・運用 |
| 外部連携と依存 | 接続先・契約・認証・責任境界・依存先障害時の扱い |
| 異常系と境界 | 不正入力・空／上限・競合・タイムアウト・再試行・復旧 |
| 制約とトレードオフ | 技術・互換性・期限・費用・禁止事項・優先する品質 |
| 用語と整合性 | 曖昧語・同義語・単位・時刻／タイムゾーン・記述間の矛盾 |
| 完了条件 | 利用者が観測できる成功・受入可能な結果・測定方法 |
| 未完了の印 | TBD／TODO／placeholder・未回答参照・仮定のままの記述 |

- `Clear`: 実装や検証の選択が一意になるだけの情報がある。適用外であることが文脈から明確な場合も含む。
- `Partial`: 記述はあるが、高影響な解釈が複数残る。
- `Missing`: 対象範囲の判断に必要だが、記述がない。

### 3. 高影響な不足だけを一問ずつ解消する

質問候補を「答えによる変更の大きさ」と「現時点の不確かさ」で並べ、最上位の1件だけをルールBに従って
質問する。回答を書き戻したら、影響を受けた観点を再走査して次の候補を選ぶ。網羅表を埋めるためだけの
低影響な質問や、文脈で既に解決している質問は行わない。

### 4. 残余を再走査し、終了理由を明示する

終了報告の直前に、書き戻し後の `clarification_target` と `writeback_ref` を次の4点でもう一度走査する。

- TBD／TODO／placeholder や曖昧語が残っていないか
- 同じ成果物の中に互いに矛盾する記述がないか
- 今回の対象が、1つの実装・検証単位として扱える範囲に収まっているか
- 重要な箇所に複数の解釈が残り、採る解釈が明示されていない状態がないか

ここで新たに見つかった論点を黙って補完・修正しない。高影響なら質問候補へ戻し、すぐに解決しないなら
下記の `Deferred`／`Outstanding` へ送る。本パックが行うのは残余曖昧性の検出と引き継ぎまでであり、
要求文書の正式なセルフレビューや finalize は `requirement-authoring-core` の領分である。

質問を終えるときは、少なくとも次を報告する。この報告は正式な合否判定ではなく、下流へ渡す判断材料である。

- **明確化結果**: `質問不要`（高影響な曖昧さなし）／`確認終了`（必要な回答を反映済み）／`省略`（依頼者の指示）のいずれか。
- **解決済み**: 今回の回答で確定し、`writeback_ref` へ反映した論点。
- **残余**: 無ければ `なし`。残すなら、意図して後工程へ送るものを `Deferred`、現時点で下流を止めるものを
  `Outstanding` とし、観点・未解決事項・残す理由・影響を添える。

質問を打ち切っただけなのに「問題なし」「曖昧さなし」と報告しない。`質問不要` の報告も、A-01 が求める
依頼者の明示的な承認を代替しない。

## ルールA: 進行

- **A-01 意図が確定するまで下流へ進まない**: 明確化と設計案の提示を経て**依頼者の明示的な承認**を得るまで、
  実装・雛形生成・次工程への移行を行わない。
- **A-02 一度に一問**: 1回のやり取りにつき質問は厳密に1つ。深掘りが要るなら回を分ける。用意した質問を
  まとめて先出ししない。
- **A-03 省略されたらリスクを告げてから進む**: 依頼者が明確化の省略を明示した場合は進んでよい。ただし
  **下流の手戻りリスクが増えることを必ず伝える**。「簡単そうだから明確化は不要」を既定にしない。
  省略できるのは明確化の実施であり、**受理した回答の書き戻し**（ルールC）は省略の対象ではない。

## ルールB: 質問の選び方と出し方

- **B-01 高影響の質問だけを選ぶ**: 答えによって設計・データの持ち方・分割・検証の仕方が**実質的に変わる**
  ものに絞る。文脈から読み取れることを確認のためだけに聞かない。
- **B-02 選択肢にして推奨を先に置く**: 可能な限り選択肢の形で提示し、**自分の推奨案とその理由を先頭**に
  置く。受け身の自由回答質問を並べない。
- **B-03 答えの粒度を指定する**: 短答で足りるものは短答を求め、長い説明を要求しない。

## ルールC: 記録

- **C-01 回答は即時に書き戻す**: 受理した回答はその場で `writeback_ref` が指す成果物の該当節へ**最小限**
  反映する。会話の中に置き去りにしない。**書き戻し先が未確定のまま回答を受理し続けない**（前節の解決規則）。**本パックが行うのは受理した回答の最小反映と、矛盾する旧記述の
  置換までである**——受入基準・NFR・スコープとしての正式な構造化と finalize は
  `requirement-authoring-core` の領分（下記の引き継ぎ）。
- **C-02 旧記述は置換する**: 回答によって無効になった記述は、複製して残さず**置き換える**（新旧が並存すると
  下流が矛盾を読む）。

## 関連パックへの引き継ぎ

- **確定した内容を要求文書として構造化し finalize する**作業は `requirement-authoring-core` の領分
  （任意の handoff）。本パックは意図の確定と受理回答の最小反映までを扱い、受入基準・NFR・スコープの
  記述規約は持たない。**受入判定は要求成果物になってからの経路に委ねる**（本パックからは直接引き渡さない）。

## 適用範囲外

- 要求文書の記述規約（受入基準・NFR・スコープの書き方）
- 質問件数の上限・選択肢数・短答の語数といった具体値 — プロジェクトの決定事項
- 明確化手法のカタログ・ログの見出し様式 — 同上
