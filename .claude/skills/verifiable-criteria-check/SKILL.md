## 概要

受入基準（AC）やタスクの完了条件が、第三者が実行結果だけを見て合否を判定できる、観測可能な
表現になっているかを検証する。「使いやすい」「高速に」のような主観語・曖昧語は、検証できない
記述として指摘する。呼び出し元が対象を指定することで、Phase 4（受入基準）・Phase 7（完了条件）
に使い回せる。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象 | 観測可能性を検証する記述 | `specs/<feature>/requirements.md` の各要件AC |
| 曖昧語リスト | 検出対象とする主観語・曖昧語（任意。既定の一般的な語彙を使う） | `使いやすい` / `高速に` / `適切に` / `など` |

## 手順

1. `対象` から受入基準・完了条件の記述を1件ずつ抽出する。
2. 各記述が「入力→期待される出力/状態」の形で、数値・具体的な状態・具体的な手順として
   検証可能かを確認する。
3. `曖昧語リスト`（または一般的な曖昧語・主観語）に該当する表現が含まれていないかを確認する。
4. 「〜すること」で終わるだけで判定基準（何を満たせば完了か）が書かれていない記述も、
   観測不能として指摘する。

## この工程で指摘しない事項

- `.claude/skills/finding-rules/SKILL.md` の工程の境界の表・`confirmed_answers`・`learned` に当たる事項
- `TBD（<工程> で確定）` と書いてある値
- 値が design で決まる AC のうち、`TBD（design で確定）` の記載があるもの

当たるものは指摘にせず、除外として返す（除外の出典を付ける。書き方は finding-rules）。

## 出力の形

指摘ごとに次を返す。書き方は `.claude/skills/finding-rules/SKILL.md`（検査の最初に読む）に従う。重大度は出さない（L3 が `kind` から決める）。

```
{ location, subject, kind, summary, evidence, suggestion, recommendation, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `location` | 観測不能な記述の箇所。`<案件相対パス> § <節見出し> / <ID>` の形。複数箇所なら代表 1 か所＋「ほか n か所」（全件は `evidence`） |
| `subject` | 対象の語（例: `AC-3`） |
| `kind` | `.claude/skills/finding-rules/SKILL.md` の種類から 1 つ選ぶ。迷ったら上の行。通常 `業務のあいまい・不足` |
| `summary` | 60 字以内。結論を先に、何が・どこで（例: 「AC-3 の『高速』に数値基準がなく検証できない」） |
| `evidence` | 該当の記述の引用と、観測できない理由（曖昧語・判定基準の欠落） |
| `suggestion` | 観測可能な書き換え文（入力→期待される出力/状態）。数値が業務の新しい事実なら「何を決めればよいか」と選べる案 |
| `recommendation` | `修正：理由` / `差戻し：理由` / `対応せず進める：理由` / `質問：理由` のどれか。業務の新しい事実が要るときは `質問：…` |
| `is_rollback_candidate` | 通常 `false`（同一フェーズ内の書き直しで解消できるため） |

## 禁止

- 対象成果物を書き換えない（曖昧な記述を自動で具体化しない）
- 合否を出さない
- 業務の新しい事実が要る値を自分で決めない。`suggestion` に「何を決めればよいか」と選べる案を書き、`recommendation` を `質問：…` にする
