# requirement-authoring-core — 要求文書 authoring の契約済み記述規約

## 使い方

要求・要件定義文書の**受入基準・非機能要求・スコープ境界を書く**際、以下の各節の規範を満たす形で書き下ろす。
未確定と思われる箇所は推測で埋めず、明示マーカーで表面化するか質問として残す。
**未解決マーカーは draft 中のみ許可する。未解決のまま finalize・レビュー依頼・下流 handoff せず、
non-final を明示して停止する。** 依頼対象の節（受入基準だけの追記等）には、その節に対応する規範だけを
適用する。3領域（受入基準・NFR・スコープ）すべてを適用するのは、完成形 requirements の finalize 時のみ。
本 skill は文書を**書く**側であり、
既存文書の判定・レビューは行わない（判定は `requirement-sparring-generic` と各 Contract の領分）。

## 確定済み基線を改訂するとき

- 意味・範囲・受入条件・公開契約を変えない誤字や表記の訂正は、案件の既存の変更管理と依頼の承認範囲で本Skillが扱う。既に許可された編集に新しい提案・承認を一律に要求しない。
- それらを変える修正は案件の既存の変更管理に従う。重大な変更と判定されたときだけ `spec-change-proposal` へ渡し、承認後に本Skillで反映する。重大でない意味変更も誤字修正と同じ扱いにはせず、既存の手続きに従う。
- 意味が変わるか、重大度や適用する手続きが不明なら、その判断を確認してから進める。例えば受入条件の「30秒」を「20秒」へ変える修正は意味変更であり、文字数の小ささでは分類しない。意図不明の言い換えも勝手に適用しない。

成果・測定方法の具体化や、要件から計画・被覆表へのつながりを確認したい場合は、任意の補助 `requirements-authoring-guide` を利用できる。未導入なら本Skillの通常の執筆を止める理由にはしない。補助の例を案件の確定済み要求としてコピーしない。

## 受入基準を書く

- 各受入基準は、自動テスト可能または明示的に検証可能な具体性で書く。検証不能な願望記述にしない。
- 観測可能な振る舞い（入力・出力・エラー条件）で書き、実装内部詳細（tech stack・内部クラス/関数名・
  ライブラリ選定・内部処理手順）を混入させない。公開 API シグネチャは What 側＝書いてよい。
- 各機能要求／ユーザーストーリーに、最低1件の受入基準を紐付ける。宙に浮いた要求を残さない。
- 「条件／トリガ → 期待される応答」の構造（GWT / EARS 相当）で書く。素の散文にしない（特定方言は強制しない）。
- 測定可能な境界で書く。境界なしの曖昧形容詞（"fast" / "user-friendly"・「高速」「使いやすい」等）を使わない。
- 未確定事項は明示マーカー（NEEDS CLARIFICATION / Open Questions / [ASSUMPTION] 等）で表面化し、
  回収可能な形にする。マーカー語彙は固定しないが、存在と回収可能性を保つ。
- 要求強度は助動詞（shall / must / should、RFC 2119 相当）で明示する（Requirement レベルの被覆で可）。
- happy path だけでなく、境界・エラー条件・異常系（edge cases）を受入基準に含める。
- 自分の仮定を確認済み要求のように書かない。複数解釈の余地は質問で解消し、残す仮定は Assumptions 節へ隔離する。

## 非機能要求を書く

- 主要4カテゴリ（Performance / Security & Privacy / Reliability & Availability / Compliance）の**それぞれ**に
  「対象」または「対象外」を明示宣言する。無宣言の欠落（silent omission）を作らない。他カテゴリ文中の
  傍論的言及は宣言と数えない。
- この4カテゴリは**必須最低線であり走査上限ではない**。Observability・Operational・Scalability・Safety・
  Cost 等、案件に関連する追加カテゴリの走査と採否宣言を妨げない。4カテゴリを網羅 taxonomy と誤認しない。
- 対象カテゴリは、数値閾値または具体的なユーザ/オペレータ観測可能な期待に変換して書く。
  閾値なきボイラープレート（「スケーラブル/セキュア/高信頼であること」のコピペ＝NFR theater）を書かない。
- 数値はドメイン固有の単位ファミリ（req/s・p95 レイテンシ・SLA/RTO/RPO 等）で書く。
- 「NFR が指定されているか」自体を、文書のチェック項目・レビュー対象として書き込む。

## スコープ境界を書く

- 対象外（out of scope / Non-Goals 相当）を明示宣言し、配下に実質的な項目を1件以上置く。
  宣言欠落・全項目無内容（「特になし」「TBD」のみ）にしない。
- スコープは in/out 対の**専用構造スロット**（独立の節・欄・リスト）に置く。散文に埋没させない。
- スコープが誤読されうる場合・隣接システム/外部仕様に触れる場合は、「隣接に何を期待し、何を所有しないか」
  まで宣言する。
- 省略が「意図的除外」か「単なる書き漏れ」か、読み手が判別できる形で書く。将来対応を含意する対象外項目には
  行き先（deferral 先）または理由を添える。
- 対象外項目には、下流の判断材料になる実質（機能・ユーザー群・ユースケース単位の特定可能性）を持たせる。

## 書かないこと（他 skill の領分）

- 既存文書を**変更しない立場**でのギャップ検出・壁打ち → `requirement-sparring-generic`
- **確定済み基線への重大な意味変更の提案** → `spec-change-proposal`。その他の改訂は上記「確定済み基線を改訂するとき」で分類する
- 用語集の作成・更新・語彙整合 → `canonical-terminology-authoring`
- エッジケースの**網羅列挙**（読み取り専用の検出作業） → `edge-case-enumeration`
- 誘導先の skill が未導入の場合は、処理を代行せず「当該 skill の導入が必要」と報告して停止する

## validation（紐づく Contract の INV/DEV チェックリスト）

成果物の自己チェックに使う。詳細な採点規則（0/5/10・Critical Fail・PASS≥70%）は supplier 側の Contract
本体が持つ（本パックには同梱しない）。正式な採点が必要で、判定ハーネス（verifier＋Contract）が未導入の
場合は、採点を代行せず導入要求を出して停止する。

**CT-REF-002（受入基準）**: INV-01 テスト可能性／INV-02 実装詳細の不混入（公開APIシグネチャは可）／
INV-03 要求↔受入基準の紐付け／INV-04 条件→応答の構造化／INV-05 曖昧形容詞禁止／INV-06 未確定の明示マーカー／
INV-07 強度助動詞／INV-08 edge case 被覆。**DEV**: 実装詳細混入・境界なし曖昧形容詞・推測断定＝Critical Fail。

**CT-REF-008（NFR宣言）**: INV-01 4カテゴリの採否明示宣言（傍論的言及は不可）／INV-02 曖昧形容詞→数値閾値・
観測可能期待／INV-03 未確定マーカーの回収可能性（soft hedge「想定」「程度」は正規マーカーでない）／
INV-04 in/out 境界と隣接期待の宣言／INV-05 意図的除外の判別可能性。**DEV**: カテゴリの silent omission・
全面 NFR theater・推測充填＝Critical Fail。

**CT-REF-009（スコープ境界）**: INV-01 対象外の明示宣言＋実質項目≥1／INV-02 in/out 対の独立構造スロット／
INV-03 隣接への期待と非所有の宣言（隣接言及がある場合のみ適用）／INV-04 対象外項目の実質性／
INV-05 将来含意項目の行き先・理由。**DEV**: 宣言の完全欠落/全項目無内容・隣接依存があるのに境界宣言が実質を
欠く・黙ったデスコープ＝Critical Fail。
