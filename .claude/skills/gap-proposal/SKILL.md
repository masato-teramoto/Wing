## 概要

他の観点 Skill が「欠陥パターンの検出」であるのに対し、この Skill は**判定ではなく提案**という
別種の出力を行う（命名規則の例外）。RFP 全体を俯瞰し、要求一覧にまだ記載が無い領域（RFPで
言及されているが要求として具体化されていないテーマ、または一般的に必要とされるが RFP・要求
一覧のどちらにも現れていない観点）を提案する。**提案であり指摘ではないため、③ 人間レビューでの要否判断を
必要とする**（確定した不備ではない）。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象 | 俯瞰する範囲 | `.aidd/rfp/**` 全体 |
| 突合先 | 記載の有無を確認する先 | `.aidd/requirement-list.md` |

## 手順

1. `対象`（RFP）全体を通読し、扱われているテーマ・業務領域・非機能観点を俯瞰的に洗い出す。
2. `突合先`（要求一覧）に、それぞれのテーマが要求として具体化されているかを確認する。
3. RFP で言及されているのに要求化されていない領域、または RFP・要求一覧のどちらにも現れて
   いないが一般的に必要となりうる領域（例: エラー時の挙動、権限管理の詳細、監査ログ）を
   提案としてまとめる。
4. 確信度の低い提案も、根拠（なぜその領域に触れる必要があると考えたか）を `evidence` に書いて出す。
   採否は人間が判断する。

## この工程で指摘しない事項

- `.claude/skills/finding-rules/SKILL.md` の工程の境界の表・`confirmed_answers`・`learned` に当たる事項
- `TBD（<工程> で確定）` と書いてある値
- 要求一覧に既に具体化されているテーマ

当たるものは指摘にせず、除外として返す（除外の出典を付ける。書き方は finding-rules）。

## 出力の形

指摘ごとに次を返す。書き方は `.claude/skills/finding-rules/SKILL.md`（検査の最初に読む）に従う。重大度は出さない（L3 が `kind` から決める）。

```
{ location, subject, kind, summary, evidence, suggestion, recommendation, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `location` | 提案の根拠となる RFP の箇所（無ければ「RFP・要求一覧のいずれにも記載なし」）。`<案件相対パス> § <節見出し> / <ID>` の形。複数箇所なら代表 1 か所＋「ほか n か所」（全件は `evidence`） |
| `subject` | 対象の語（例: `返金フロー`） |
| `kind` | `.claude/skills/finding-rules/SKILL.md` の種類から 1 つ選ぶ。迷ったら上の行。通常 `業務のあいまい・不足` |
| `summary` | 60 字以内。結論を先に、何が・どこで（例: 「返金フローの要求が要求一覧に無い（提案）」） |
| `evidence` | 提案の根拠（RFP の該当箇所の引用、なぜその領域に触れる必要があると考えたか） |
| `suggestion` | 確認する要求の案（「何を決めればよいか」と選べる案） |
| `recommendation` | `修正：理由` / `差戻し：理由` / `対応せず進める：理由` / `質問：理由` のどれか。業務の新しい事実が要るときは `質問：…` |
| `is_rollback_candidate` | 常に `false`（提案であり、差戻しの対象となる不備ではない） |

## 禁止

- 対象成果物を書き換えない（提案を要求一覧へ自動で追記しない）
- 合否・要否を自分で決めない（採否は人間が判断する。`recommendation` は通常 `質問：…`）
- 提案を断定的な不備として書かない（「〜すべきである」ではなく「〜が提案できる」と書く）
