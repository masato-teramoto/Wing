# api-contract-design — API・サービスI/Fの契約を記述する

## 入力と記述対象を確認する

要求、設計上の制約、対象のAPI・サービス一覧、既存の契約文書を読む。既存契約を変更する場合は変更前の
入出力・エラー・認証・バージョン方針も確認する。案件で明示された制約を引き継いで設計する。

作成対象の操作を一覧にし、各操作について入力、成功時の結果、想定エラー、利用者や呼出元を整理する。
型、エラー形式、認証方式などが未確定なら、決定済みの内容と分けて未決事項へ置く。空欄を推測で埋めて
合意済みの契約として扱わず、分かっている範囲から文書を作る。

## 操作ごとの入出力と条件を書く

実装前に、各操作の契約を表または型で記述する。HTTP API ではメソッドとエンドポイントを識別できるようにし、
入力・成功応答・エラーを同じ操作へ結び付ける。サービスI/Fでは操作名と入力型・出力型・エラー型を記し、
次の条件を添える。

- **事前条件**: 呼出前に成立している前提。
- **事後条件**: 正常終了後に成立する状態や返される結果。
- **不変条件**: 操作の前後を通じて維持する制約。

書き出しには次の欄を使える。案件の文書形式に合わせて表と型定義を組み合わせ、実装コードを読まなければ
入出力が分からない記述を残さない。

| 操作またはメソッド・エンドポイント | 入力 | 成功応答 | エラー |
|---|---|---|---|
| 対象操作 | 入力の型・内容 | 出力の型・内容 | 起こり得るエラーと応答 |

## エラーの共通形式を決める

API全体で使うエラー応答の正規形を1つ定義し、操作ごとのエラーをその形式に対応づける。形式には、
呼出側が安定して識別するコード、人が読める説明、追跡に使う情報を含める。エラーコードは許容する値の
列挙集合（enum）を契約に定義する。フィールド名や具体的なコード値は案件で決め、既存契約がある場合は
その定義と整合させる。

各操作のエラー記述を並べて、同じ意味のエラーが異なる構造で返されていないか確認する。認証情報や
スタックの内部詳細を応答内容に含めず、呼出側の機械処理と人による確認の両方に使える形へ揃える。

## HTTPエラーを分類して応答へ対応づける

HTTP APIのエラー応答を設計する場合は、エラーが何に起因するかを分け、応答ステータスと共通エラー形式へ
対応づける。次の表を記入補助にできる。具体的なコード値やフィールド名は案件の契約で決める。

| エラーの起因 | 応答の考え方 |
|---|---|
| 入力・検証・利用者の操作 | クライアント側の問題を示す4xxへ対応づける |
| システム障害・予期しない例外 | サーバ側の問題を示す5xxへ対応づける |
| 業務ルール・状態の違反 | 業務上の理由を識別できるコードと4xxへ対応づける |
| 外部サービス・ネットワーク | 失敗の文脈を確認して4xxまたは5xxを選び、外部の応答を無条件に転送しない |

各操作で起こるエラーについて、分類、公開するコード、ステータス、共通形式の応答を対応づける。
HTTPを使わないサービスI/FへHTTPコードを強制しない。エラー分類だけで再試行可能とは判断しない。

## 層をまたぐエラーの変換責任を記す

エラーがAPI、業務サービス、データ・外部接続の境界をまたぐ設計では、実在する境界ごとに何を受け取り、
何へ変換して渡すかを書く。このためだけに新しい層を設けず、対象設計の責任分担へ対応づける。

- **API境界**: ドメインのエラーを共通形式の応答へ変換する位置を記す。HTTP APIではHTTPステータスへの
  対応も記す。非HTTPのサービスI/FへHTTPステータスを強制しない。
- **業務サービス**: 業務エラーを型や識別可能な構造で表し、説明文字列の一致だけで処理を分岐させない。
- **データ・外部接続**: プロバイダ固有のエラーを、安全で次の対応が分かるコードへ包み直して渡す。
- **未知のエラー**: 共通のハンドラへ集約し、内部情報を含めない一般的な説明へ変換する。
  HTTP APIではサーバ側の失敗を示す応答とし、内部例外をそのまま公開しない。

型名やハンドラの実装方法は案件で決める。既知の業務エラーが途中で自由文へ潰されていないか、外部エラーや
未知のエラーが変換を迂回して公開されないかを、操作から応答まで辿って確認する。

## 再試行と冪等性を対にして記述する

ネットワーク越しの呼出しで再試行を検討する操作では、採用可否も含め、失敗の条件、再送の安全性、API側の
指示、待機と打切りを契約に記す。4xx／5xxの分類だけで一律に許可・禁止しない。HTTPでは次を照合する。

| 失敗・応答の条件 | 記述する判断 |
|---|---|
| ネットワーク障害・応答待ちのタイムアウト・一時的な5xx | 再送で改善する可能性と、下記の再送の安全性を確認する。応答がないだけでは、元の処理が未適用だったとは判断しない |
| 408で、送信済みの要求がまだ未完了 | サーバが要求全体を受け取るまでの時間切れであることを確認し、再送条件を記す。接続が使えなければ新しい接続を使う。一般的な応答待ちタイムアウトと混同しない |
| 429 | レート制限の条件、APIの契約、再送の安全性を照合し、待機後に再送できるかを記す。Retry-Afterの存在だけでは安全とは判断しない |
| 同じ入力・業務状態のまま再送しても解消しない失敗 | 入力や状態を修正する対応へ渡し、同じ要求の自動反復で解決しようとしない |
| 安全性・失敗条件・APIの指示が不明 | 不足する情報を残し、自動再試行できる前提にしない |

再送の安全性は、同じ要求を繰り返しても意図した効果が変わらないかで確認する。冪等性は毎回同じ応答が返る
こととは異なる。HTTPクライアントで非冪等なメソッドを自動再試行する判断は、実際の操作の意味が冪等だと
分かっているか、元の要求が適用されていないと確認できる場合に限定する。HTTPプロキシによる非冪等な要求の
自動再試行は採用しない。その他の4xxも個別の原因とAPI契約を確認する。案件で一律禁止する場合は、その
意図と影響を明記する。これらのHTTP固有条件を、非HTTPのサービスI/Fへ強制しない。

冪等性キーを採用するAPIでは、同じ操作の再試行に同じキーを渡す方法と、受け手が重複適用を防ぐ契約を
記す。キーがあるだけでは安全と判断せず、操作自体が冪等ならキーを一律の必須欄にしない。
キーの名前・型・有効範囲などの具体化は案件の契約で決める。

Retry-Afterがある場合は、HTTP-dateまたは非負整数の秒数として解釈し、その待機指示を方針へ反映する。
欠落・解釈不能の場合は案件の待機方針に従うか未決事項へ残し、即時の反復を既定にしない。
指数バックオフと揺らぎを待機の設計候補とし、試行回数・時間の上限と打切りを記す。待機指示が案件の
許容時間を超えるなら、早めて再送せず打ち切る。具体値は案件で決める。自動再試行自体が失敗した場合は、
さらに自動再試行しない方針を基本とし、追加を選ぶなら理由と有限の上限を記す。

記述には「対象操作／失敗条件／再送の安全性と根拠／APIの指示／待機と打切り／採用時の重複防止契約」の
対応表を使える。これは記入補助であり、既存契約と別の固定schemaではない。再試行コードや外部呼出しは
実行しない。

## 認証と認可を別々に記述する

認証では「誰かをどの方式で確認するか」と選択理由を記す。認可では「その主体が何を許されるか」と
強制する位置を記す。必要な権限を絞り、判定できない場合は許可しない方針を契約へ反映する。

未認証の呼出しをビジネスロジック到達前に拒否する位置を明記する。認可の配置は、入口の
route／middlewareで行う粗い制限と、domain／serviceで行う細かな制限を区別する。
UIの表示制御だけを認可の根拠にしない。方式や強制位置が未確定なら、具体的な決定が必要な点として残す。

## バージョンと互換性を決める

バージョンをURL、ヘッダ、メディア型などのどの手段で伝えるかを選び、文書に記す。変更がある場合は
旧契約と新契約を照合し、既存の呼出側にとって互換性を壊す変更かを確認する。

- **互換性を壊す変更**: 新バージョンとして扱い、旧版の廃止までの周知期間と周知方針を書く。
- **互換性を保つ変更**: 同じバージョンで扱うことを確認する。

廃止期間の具体値を本パックの既定値で埋めない。案件の利用者・既存契約に照らして決め、未確定なら
未決事項へ記す。破壊的変更を無宣言で既存バージョンに混ぜない。

## 一覧・検索応答を有界にする

一覧・検索を返す操作では、ページ方式またはカーソル方式を記述し、取得上限か明文化したデフォルトを
宣言する。応答にはページネーションの情報を含め、呼出側が続きを取得する方法を読み取れるようにする。
フィルタとソートを提供する場合は、それぞれのパラメータを契約に記す。

対象操作を一覧から辿り、上限・デフォルト・ページ情報の記述が抜けていないか確認する。
具体的なパラメータ名と上限値は案件で決め、無制限の一覧応答を暗黙の既定にしない。

## 自己確認して引き渡す

契約文書を読み返し、次を確認する。未確定の箇所は該当する操作や共通方針と結び付けて列挙する。

- 各操作の入力・成功応答・エラーを、実装コードに頼らず確認できるか。
- サービスI/Fの事前条件・事後条件・不変条件が記述されているか。
- エラー形式が揃い、安定したコードの許容列挙集合・説明・追跡情報が定義され、各操作のコードがその集合に
  属しているか。秘密や内部詳細を含めていないか。
- HTTP APIではエラーの起因と応答ステータスが対応し、外部エラーも文脈を踏まえて変換されるか。
- 層をまたぐエラーでは変換責任が決まり、型付き業務エラー・安全な外部エラー・未知エラーの扱いを追えるか。
- 再試行を検討する操作で、408・429を含む該当条件、再送の安全性と根拠、APIの指示、待機と打切りを
  記したか。4xxを全面解禁せず、キー採用時は重複防止契約まで確認し、キーを全操作へ強制していないか。
- 認証方式と理由、認可対象と強制位置が分かれ、入口での未認証拒否が記述されているか。
- バージョンの伝達手段と変更の互換性判断が整合し、破壊的変更に新版と周知期間が伴うか。
- 一覧・検索操作の上限またはデフォルト、ページ情報、提供するフィルタ・ソートが明記されているか。

成果物は契約文書と、未決事項・不足する入力・次に決める内容の一覧として渡す。タイムアウトやSLOの
設計が必要な案件では、要求や案件固有の基準を確認する作業へ引き継ぎ、値や方式を推測で補わない。
実装タスクへの分割は `implementation-planning`、要求との被覆関係の作成・監査は `traceability-audit`、
成果物の受入レビューは `acceptance-review` の作業へ渡す。別パックが未導入なら、契約文書と未決事項を
依頼元へ引き渡す。

## 適用範囲外

- 認証・認可のコード実装、CLI固有の表面設計、システム全体のアーキテクチャ設計。
- イベント・バッチ・状態管理固有の契約欄、token/sessionのライフサイクル設計。
- 契約の正式採点・合否判定、実装や外部サービスの変更。
