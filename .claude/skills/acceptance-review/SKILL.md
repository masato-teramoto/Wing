# acceptance-review — 受入レビューの実施規律と成果物品質

## 使い方

レビューを**実施する側**はルールA〜Dに従って走査し、**指摘リストを出す前**に validation で自己チェックする。
出来上がったレビュー報告を**評価する側**は validation の INV/DEV だけを使えばよい。

## ルールA: レビュー実施規律

- **A-01 文脈隔離**: レビューは実装時の会話文脈から隔離して行い、実装者の自己報告を真実の情報源として扱わない。
- **A-02 一次ソース自読**: spec・diff・周辺コードを自分で読む。要約・報告経由で判定しない。
- **A-03 diff 単体で判定しない**: diff ハンクだけから指摘・severity を確定しない。呼び出し元・ガード・diff 外の検証コードまで
  読んで到達可能性を判断する。文脈不足ならその旨を明示して周辺ファイルを要求する。
- **A-04 敵対的前提**: 問題は存在すると仮定して懐疑的にレビューする。解釈上の楽観で通さず、具体的な失敗根拠で棄却する。
- **A-05 多次元観点**: 単一観点でなく複数の独立した観点（例: セキュリティ／性能／テスト／アーキテクチャ、機械検査／判断検査、正確性／受入基準）で走査する。
- **A-06 spec/AC 照合**: 実装を承認済み要求・受入基準・設計と突き合わせ、AC 違反・spec 意図からの逸脱・仕様済み挙動の実装漏れを検査する。
- **A-07 エッジケース探索**: 空入力・null/undefined・境界値・依存の例外・競合状態など、エッジケースの取り扱いを能動的に探す。
- **A-08 テストの実質検証**: テストの存在でなく実質を見る。アサーションを読み、実装を壊したら落ちるか・モックだけを検査していないかを確認する。
- **A-09 スコープ監査**: 変更が承認済みスコープ・責務境界の内側に留まるか監査する。境界外への漏出・隠れた結合・スコープクリープは有用でも逸脱として扱う。
- **A-10 欠落の探索**: 書かれているものの誤りだけでなく、書かれていないもの（実装漏れ・欠けた機能・happy path 以外の未実装）を探す。
- **A-11 レビュアーはコードを修正しない**: 成果物は指摘と verdict であり、コード本体の変更ではない。

## ルールB: severity・トリアージ

- **B-01 段階的 severity**: 全指摘に段階的 severity を付与する（語彙は下記「プロジェクトで決める項目」）。
- **B-02 実結果基準・インフレ禁止**: severity は実際の呼び出し文脈での実結果で決める。最悪の理論的解釈で決めない。nit を最上位に格上げしない。
- **B-03 ゼロ指摘の懐疑**: 指摘ゼロは疑わしい状態として扱う。検査せずに「問題なし」と言わない。
  ゼロ指摘で合格を出すなら、何をどの観点で検査したか（検査済み観点・機械検査結果）を列挙する。

## ルールC: 指摘の出力品質

- **C-01 file:line 引用**: 各指摘にファイルパスと行番号（または行範囲）を付ける（位置を持ちうる指摘に限る）。
- **C-02 具体性**: 曖昧語だけの指摘（「危なそう」「エラーハンドリングを改善」）は指摘として認めない。何がどこでどう問題かを特定する。
- **C-03 why 説明**: 各指摘に「なぜ問題か」（帰結・影響）を付ける。
- **C-04 修正提案**: 自明でない指摘には具体的な修正方法を付ける。REJECTED 級の verdict では remediation が必須。
- **C-05 単一 verdict**: レビューは定義済み enum の単一 verdict で終える。verdict の回避・複数併記は違反。
- **C-06 構造化出力**: 指摘は定義済みの構造（テンプレ／スキーマ）で出力する。自由散文にしない。
- **C-07 不確実性明示**: 確信が持てない指摘・検証できない事項は、その旨と必要な追加文脈を明示する。断定に偽装しない。
- **C-08 範囲外への指摘禁止**: レビュー範囲外のコード・存在しない位置を**指摘の位置**として出力しない
  （範囲内の指摘を裏付ける**根拠**として範囲外・実配備文脈に言及することは可。位置と根拠を区別する）。

## ルールD: 完成度衛生（完了主張を受け入れる前の検査）

- **D-01 未完了マーカーの残置禁止**: 変更差分の**追加行**に、正当化なき新規の未完了マーカーを残置しない。
  正当化（説明コメント・将来タスクとしての文書化）があるマーカーは違反ではない。判定前に該当行の**上下10行のコメント**を読む
  — 設計判断コメントの存在は「意識的な選択」のシグナルである。
- **D-02 Reality Check**: 実装が実本番コードであること。placeholder・stub・fake path・deferred-work shell・mock 実装の据え置きは完了と認めない。
- **D-03 プレースホルダテスト禁止**: 本体が `pass` のみ・自明アサーション（isinstance / hasattr 確認のみ）のテストは
  実テストに置換するか削除する。プロジェクトコードを検証しないテストは「無いより悪い」（数を水増しし偽の信頼を生む）。
- **D-04 未完了の明示記録**: 残す未完了（正当化付きマーカー・省略テスト・FAILED タスク）は明示経路に記録する
  — 説明コメント／将来タスク化／untestable の明記／Outstanding Issues・Status 報告。隠さない。
- **D-05 scaffolding 値の誤検知抑制**: `change-me` / `placeholder` / `example` / `default` 等の名前を持つ値は欠陥ではなく
  自己文書化マーカーである。既定で無効の機能がプレースホルダ値を使うのは「未完成機能」であり「脆弱性」ではない。
  **scaffolding 値のみを根拠とした欠陥・脆弱性報告を出さない**（追加根拠—到達可能性・実配備文脈—があるときのみ報告する）。
- **D-06 秘密情報の grep はマーカー grep と並列に実行する**: 完了ゲートの機械検査として同時に走らせ、結果を同じ形式で報告する。
  秘密パターンの本体規約（何を秘密とみなすか・取り扱い）は本パックの対象外（別資産・現在未供給）。

## 決定的検査（judge を呼ぶ前に機械で落とす）

- 指摘リスト側: 各指摘の `path:line` 存在・severity ラベル存在・verdict 行の存在と単一性・テンプレ必須欄の存在 — いずれも regex 判定可能
- 完成度側: `git diff` の追加行（`^+`）に対する語境界つき `\b(TBD|TODO|FIXME|HACK|XXX)\b`。
  報告形式は `CLEAN | <count> matches` の二値（例: `TBD/TODO grep: CLEAN`）。テスト実行の setup error（fixture 未定義・
  import 失敗）は failure と別勘定でカウントし 0 件を確認する。完成宣言される文書には全文へのマーカー語彙＋
  `placeholder` の grep を掛ける（検出＝疑いであり、正当化の有無は別判定）
- 意味判断（機械にしない）: severity の妥当性・why の実質・正当化の妥当性・Reality Check・「scaffolding 値のみが根拠か」

## 適用範囲の限定（このテンプレート環境での誤検知防止）

- マーカー検査の対象は**案件が新規に書いた・変更した差分のみ**。既存コードの棚卸しではない。
- テンプレート由来の記入欄はマーカーではない: `<UPPER_SNAKE_CASE>`（steering の確定待ち値）・`[説明的日本語]`（記入ガイド）・
  `{{...}}`（フロントマター変数）。これらの残存はテンプレートの設計であり欠陥報告の根拠にしない。
- テンプレートが **TBD を明示的に許容する欄**（例: 運用手順書の索引・テスト体制の詳細仕様書）は、
  その許容宣言自体が D-01 の「正当化」にあたる。違反にしない。
- **WIP と明示された中間成果物**には完成度衛生（ルールD）を適用しない。対象は完了主張を伴う成果物のみ。

## プロジェクトで決める項目（本パックは既定値を持たない）

- **severity 段階語彙** — 上流に現れる系: `Critical/Important/Suggestion/FYI`・`Critical/Important/Minor`・
  `blocker/important/nit`・`low/medium/high`。プロジェクトで**1系に固定**して記録する。
- **verdict enum** — 上流に現れる系: `APPROVED|REJECTED`・`Yes|No|With fixes`・`Safe to merge|needs changes|reject`。同上。

## validation（CT-REF-006・CT-REF-007 の INV/DEV チェックリスト）

成果物の自己チェックに使う。**本判定は消費先のドキュメント状態に影響しない。判定ハーネスと Contract 本体は同梱されない。**

**レビュー成果物（指摘リスト・verdict）— CT-REF-006**:

- [ ] **INV-01** 位置を持ちうる全指摘に file:line（または範囲）引用
- [ ] **INV-02** 全指摘に段階 severity・実結果と整合（インフレなし）
- [ ] **INV-03** 全指摘が何がどこでどう問題かを特定（曖昧語のみの指摘なし）
- [ ] **INV-04** 各指摘に why・自明でないものに修正提案・REJECTED 級なら remediation
- [ ] **INV-05** 定義済み enum の単一 verdict で終端
- [ ] **INV-06** ゼロ指摘で合格を出すなら検査済み観点・機械検査結果を列挙
- [ ] **INV-07** 不確実事項にその旨と必要な追加情報を明示
- [ ] **INV-08** 範囲外・存在しない位置が指摘位置として出力されていない
- [ ] **INV-09** scaffolding 値のみを根拠とした欠陥報告が存在しない

**DEV（該当すれば Critical Fail）**: 曖昧語のみの指摘（DEV-01）／単一 verdict の欠落・回避（DEV-02）／
位置引用の全面欠落（DEV-03）／severity 欠落の指摘（DEV-04）／根拠なしの「問題なし」（DEV-05）／
scaffolding 値のみを根拠とした欠陥報告（DEV-06）

**完成宣言された成果物 — CT-REF-007**:

- [ ] **INV-01** 差分追加行に正当化なき新規マーカーなし
- [ ] **INV-02** 完了報告に機械検査結果が `CLEAN | <count> matches` 形式で含まれる（完了報告を伴う場合）
- [ ] **INV-03** プレースホルダテストなし（全テストが実プロジェクトコードを実行）
- [ ] **INV-04** テスト実行の setup error 0件（error は failure と別勘定）
- [ ] **INV-05** 完成宣言される文書にプレースホルダ・TBD の残存なし（将来タスクとして文書化済みの残存は減点扱い・満点ではない）
- [ ] **INV-06** 残す未完了はすべて正当化記録付きで明示経路に報告・placeholder 実装の完了主張なし（Reality Check）

**DEV（該当すれば Critical Fail）**: 主要経路への正当化なき TODO 残置・placeholder 実装（DEV-01）／
検証証拠のテスト群がプレースホルダで占められ無効化（DEV-02）

採点は各 INV を 0 / 5 / 10（適用外の INV は N/A として分母から除外）。DEV 該当は Critical Fail。
Critical Fail が無く適用 INV の平均 7.0 以上で PASS。詳細な採点規則と N/A 規則は Contract 本体（同梱されない）を参照。

## 引き継ぎ元との境界（handoff の受け口）

本パックは、上流の各パックが出した所見・成果物を受けて**受入判定を出す側**である。受け取る側として、
次の境界を守る。

- **受け取るもの**: 上流パック（要件の壁打ち／被覆監査／変更提案／実装計画／エッジケース列挙／禁止事項の
  authoring・review・用語監査など）が出した指摘リスト・所見・成果物と、その重大度・位置引用。
- **本パックが出すもの**: ルールA〜D に基づくレビュー所見と、定義済み enum の**単一 verdict**。上流の
  成果物そのものの作り直し・代筆は行わない。
- **各領域の規範の所有者は上流側にある**: 受入基準・NFR・スコープの記述規範は要求の authoring パック、
  要求→下流の被覆規範は被覆監査パック（`traceability-audit`）、要件文書の観点レビューは
  `requirement-sparring-generic` が持つ。本パックはそれらの規範を再定義せず、**引き渡された所見を
  受入判定に変換する**役割に限る。上流の規範に踏み込んだ指摘が必要になった場合は、当該パックへ差し戻す。
- **被覆状態と受入 verdict を混同しない**: 被覆監査パックが出す被覆状態（COMPLETE／INCOMPLETE／
  UNDETERMINED）は工程遷移の材料であり、本パックの verdict とは別の軸である。被覆に gap があることを
  もって自動的に REJECTED とはせず、当該案件の受入条件に照らして判定する。
- **上流パックが未導入の場合**: 引き渡されるはずの所見が無いことを「問題なし」と読み替えない。何を検査
  できなかったかを明示し（B-03 のゼロ指摘懐疑と同じ扱い）、必要なら当該領域の検査を依頼元へ要求する。

## 適用範囲外

- レビュー指摘の**受領側**の規律（検証してから実装・性能的同意の禁止等）— 別テーマの資産
- レビュー対象コードの修正そのもの（A-11 のとおりレビュアーの成果物ではない）
- 秘密パターンの本体規約（検出パターン・取り扱い）— 別資産・現在未供給
- 完了検証の手続き機構（fresh evidence・Gate Function・claim type 別の要求証拠）— 別テーマの資産
- デバッグ出力の残置（print/console.log 等）— 源泉に規範記述がなくスコープ外
- severity 語彙・verdict enum の選定の妥当性 — プロジェクトの決定事項
