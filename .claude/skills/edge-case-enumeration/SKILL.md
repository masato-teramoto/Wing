# edge-case-enumeration — エッジケースの網羅列挙

## 起動時に確定する項目（dispatch）

- **mode** — `authoring`（これから列挙する）／`review`（提出済みの一覧を判定する）。依頼者の明示を優先し、
  明示がなければ対象と操作から一意に判定できる場合のみ自動で決める。**一意に決まらないときは質問して停止する**。

本パックは project profile を読まない。

対象の要求が曖昧で、期待する挙動・境界・削除後の契約を一意に置けない場合は、推測で列挙を始めない。
曖昧な位置、残る解釈、列挙への影響を finding として示し、`requirement-clarification` へ redirect して止まる。

## ルールA: 列挙の方法

- **A-01 方法駆動で列挙する（直感で狩らない）**: 対象の**全分岐パス**（条件分岐・ループ・エラーハンドラ・
  早期 return）と**全ドメイン境界**（値・状態・条件が遷移する箇所）を**体系的に walk して**列挙する。
  「経験上ありそうなもの」から始めない。さらに、**エッジクラスは対象自体から導出する**——
  **固定チェックリストの写経で終えない**（A-02 は最小セットであって、それを埋めれば完了ではない）。
- **A-02 標準エッジクラスを最小網羅する**: 少なくとも (a) null・空入力 (b) 境界値（最小・最大・境界の
  前後1） (c) エラー／異常系（未処理例外・沈黙失敗・default 節の欠落） (d) 並行性（競合・同時アクセス）
  — の**4類型**を列挙対象に含める。これを欠く一覧は網羅列挙とみなさない。該当なしのクラスは「該当なし」と
  明示する（黙って飛ばさない）。**この4類型は最小セットであり、対象から導出したクラス（A-01）を加える。**
- **A-03 列挙型の残余も分岐として扱う**: enum、status、sentinel、type tag、feature flag、有限の値域で
  変更が一部の値だけに触れている場合、**触れられていない残りの値**を暗黙の分岐として列挙する。変更値だけを
  見て列挙を終えない。
- **A-04 diff があるときは範囲を制御する**: diff レビューでは変更 hunk と、そこから直接到達できる
  未防護の境界を対象にする。依頼者が明示していない限り、列挙を無制限なリポジトリ全体監査へ広げない。
- **A-05 削除・置換には専用の二次パスを行う**: 削除・置換された挙動や契約が、別の場所で再確立されたか、
  意図して廃止されたかを確認する。孤立参照、到達不能になった経路、古い分岐の残存を別枠で走査する。
- **A-06 二次パスで確定する**: 一次列挙をそのまま最終版にしない。**全クラスを機械的に再訪する二次パス**を
  行い、漏れを拾ってから確定する。

## ルールB: 指摘の書き方（接地4要素）

各指摘は次の4つを持つ。1つでも欠けたら vague 指摘として扱う。

1. **位置** — file:line（または対象の節・項目）
2. **引き金条件** — 何が起きるとその経路を踏むか
3. **帰結** — 実際に何が壊れるか（利用者・データ・運用のどれにどう出るか）
4. **是正の手がかり** — どの方向で直せるか（実装そのものは書かない）

## ルールC: 役割の限定

- **C-01 列挙者は検出専任**: 未処理箇所を挙げるのが役割であり、コードの良し悪しの論評・文体の指摘・
  修正の実施はしない。

## review 時の出し方

提出された一覧について、**方法駆動の痕跡があるか**（全分岐パスと全ドメイン境界を walk した跡・対象から
導出したクラスの有無。固定チェックリストの写経で終わっていないか）、A-02 の4類型、列挙型の残余、
削除・置換の専用パスが**点検されたか**（該当なしの明示を含む）、diff がある場合に範囲を広げすぎていないか、
各指摘が接地4要素を満たすか、二次パスの痕跡があるかを判定する。一覧を書き足して埋めない（判定と作成の分離）。
**指摘は【SHOULD】として提示する。**

## 関連パックへの引き継ぎ

- **受入基準にエッジケースを書き込む**作業は `requirement-authoring-core` の領分。列挙結果を要求へ反映する
  必要があれば、そちらへ redirect し **handoff** する（本パックで要求本文を書かない）。
- **列挙結果の受入判定**は `acceptance-review` へ handoff する。
- **要求が曖昧で列挙の基準を確定できない場合**は `requirement-clarification` へ redirect する。

## 適用範囲外

- 修正の実施・テストコードの作成
- 発見した欠陥の重大度づけと優先順位の決定 — 受入判定側の領分
- 出力スキーマの具体（フィールド名・語数上限・severity や confidence の語彙）— プロジェクトの決定事項
