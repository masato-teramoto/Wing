# MU: mockup 生成（画面の具体形・feature ごと・再生成する）

> フロー内の位置・実行順・人間停止点の概要は **入口 skill `aidd-system-design`（配布ワークスペースの `.claude/skills/aidd-system-design/SKILL.md`）が正**。単独で呼ぶときは「単独起動時の前提」を満たすこと。
> **本 SKILL.md が工程内の生成規約と手順の正**（実行規約は本書で自己完結する）。
> 書式の正は雛形 **本 skill の `templates/mockup-manifest.json`**（読み取り専用）。

## 位置づけ（生成規約の前提）

- mockup は **画面設計書・画面マップ・STYLEGUIDE.md の三者から生成する「画面の具体形」**であり、
  **独立の正を持たない**。提示・実装の突合先であって、仕様ではない
- **再生成する成果物**である（画面マップ・画面設計書は確定文書で再生成しない）。
  **手で磨かない** — 修正は入力を直して再生成する
- **実装に変換しない。** 実装は STYLEGUIDE.md / styleguide.css と画面設計書を読んで組む。
  mockup は見比べる相手であり、流用するソースではない
- 優先順位は ① 挙動・要件（requirements / design.md）② 切り出し・所有・遷移・入口とナビ（画面マップ）
  ③ 構成・項目・状態・文言（画面設計書）④ 見た目（STYLEGUIDE.md）。**mockup はこれらの描画であり、優先順位に入らない**

## ハード制約

- 【MUST】**入力は三者だけ**（画面設計書 `status: confirmed` + 画面マップ + STYLEGUIDE.md / styleguide.css）。
  **requirements から画面を洗い出さない**（画面と状態は画面設計書で、繋ぎは画面マップで確定済み）
- 【MUST】**1 画面 × 1 状態 = 1 ページ**の独立した静的 HTML
- 【MUST】**共通シェル（ヘッダ・グローバルナビ・パンくず）を全ページに載せる。シェルは生成入力の一部であり、
  生成後に後付けしない**（再生成で消えない・結合のやり直しが無い）
- 【MUST】**画面マップ §4-2 のナビ項目はすべて載せる**（mockup 未生成 feature の項目も）
- 【MUST】**見た目は `styleguide.css` の変数・部品クラスのみ。** 参照する実体は
  **`pages/tokens/styleguide.css`**（案件直下の正の複製）。**ページ側に色（hex / rgb / hsl）・px の生値を書かない**
- 【MUST】**`pages/tokens/styleguide.css` は案件直下の `styleguide.css` の複製で、内容が同一**であること
  （1 バイトでも違うと機械検査で落ちる。手で編集しない）
- 【MUST NOT】**JS を書く**（遷移・バリデーション・部品挙動の再現を含む）
- 【MUST NOT】**STYLEGUIDE.md §4 に無い部品を作る・近い部品で代用する**（`missing[]` に記録して該当箇所を作らない）
- 【MUST NOT】**画面設計書の遷移表と画面マップ §3 に無いリンクを張る**
- 【MUST NOT】**共有画面を参照する側の `pages/` に複製する**（描画が 2 つになり突合先がぶれる。所有 feature の mockup だけが描く）
- 【MUST NOT】**実在の人名・社名を転記する**（データは固定値ダミー。識別子は汎用的な数値）
- 【MUST NOT】**位置づけの注記をページの HTML に書く**（置き場は `pages/README.md` と manifest の `notice` の 2 か所）
- 【MUST NOT】**生成した mockup を手で磨く・部分修正する**（修正は入力を直して再生成する。
  **手で磨かないことが、報告が失われても差分と機械検査で全部検算できること = 並行実行の検算可能性を担保する**）
- 【MUST NOT】**画面設計書 / 画面マップ / STYLEGUIDE.md / styleguide.css を書き換える**
- 【MUST NOT】**目視・提示・凍結を代行する**（人の担当 — 「完了後」）
- 【MUST】**機械検査 2 本の exit 0 を完了条件とする**（fail のまま報告して終わらない）
- 【MUST】Markdown・表示文言は ja で記述する

## 開始時の宣言（MUST）

- 対象 feature と、**画面設計書の `status`（`confirmed` であること）**。draft なら生成せず停止する
- 入力の版（画面マップの `revision` と本 feature 行の `confirmed.at` / STYLEGUIDE.md の `version` /
  画面設計書 frontmatter の `inputs`）
- **生成する画面 × 状態の一覧**（画面設計書 §3 の小節から。**参照行は数に入れない**）と、その総ページ数
- **シェルのナビ項目**（画面マップ §4-2 の全行）と、**本 feature に対応する現在地**
- 出力先 `.aidd/screen-design/<feature>/pages/` と、機械検査 2 本の所在
- **再生成かどうかと、その契機**（既存の `pages/` が在る場合）:

  | 契機 | 対象 | 目視の範囲 |
  |---|---|---|
  | 画面設計書が改訂された | その feature | 変わった画面 × 状態 |
  | **STYLEGUIDE.md の版が上がった** | **全 feature** | 見た目の変化 |
  | **画面マップ §4（入口とシェル）が変わった**（ナビ項目・ヘッダのリンク・現在地のいずれか） | **全 feature** | シェルだけ |
  | **無効表示のナビ項目のリンク先が生成された**（参照先 feature の mockup が出来た） | **その項目を無効表示で持つ全 feature** | シェルだけ |
  | 機械検査 fail の修正 | その feature | 落ちた箇所 |

  > **4 行目は画面マップ §4 の値が変わらないため 3 行目に該当しない。** 見落とすと、
  > **無効表示のまま残ったナビ項目が実態と食い違う**（リンク先は在るのにリンクが張られない）。
  > **相手 feature の生成で pending が解消しただけなら、HTML は再生成せず** manifest の `checks` と
  > `cross_feature_links[].status` だけを更新する（本文もシェルも変わらないため）。

## 機械検査（生成のたびに回す。exit 0 が完了条件）

**パレット検査**（`check-palette.mjs` — feature の `pages/` 単位）:

| 段 | 検査 | 扱い |
|---|---|---|
| **A-1** | `pages/*.html` に色（hex / rgb / hsl）と px の**生値**が無いこと | **fail（exit 1）** |
| **A-2** | `pages/tokens/styleguide.css` が**案件直下の正と同一**（= feature 間でも同一） | **fail（exit 1）** |
| **B-1** | `styleguide.css` が定義していない部品クラスを使っていないか | **件数報告のみ**（fail にしない） |

**動線検査**（`check-links.mjs` — `.aidd/screen-design/` 全体。feature の mockup を生成・再生成するたびに回す）:

| 段 | 検査 | 扱い |
|---|---|---|
| **A-3** | 内部の参照が実ファイルに解決すること。**遷移と資源を分けて扱う** — 遷移（`<a href>`）は **pending**（遷移先 feature の `pages/` がまだ無い = 許容）と **broken**（ディレクトリは在るがファイルが無い）を区別する / **資源（`<img src>` / `<link href>`）は pending にせず、解決しなければ必ず broken**（「相手 feature が未生成」という事情が資源に無いため）。`data:` と外部 URL は対象外 | **broken のみ fail（exit 1）**。pending は **exit 0 のまま件数を報告** |
| **B-2** | 入口から生成済みの全 feature に到達できるか | **件数報告のみ**。状態バリエーション（空・エラー等）は**どこからもリンクされないのが正常**で、ページ単位の到達率は判定に使わない |

- **fail の 2 分岐**（パレット検査）: `styleguide.css` に対応する変数・クラスが**あるのに生値を書いた**
  → 再生成して直す / **無い** → `missing[]` に記録し該当箇所は作らない（**変数・クラスを勝手に足さない**）
- **broken の直し方**: 画面設計書か画面マップを直して再生成する（HTML のリンクを手で書き換えない）
- **pending の扱い**: `notes[]` と `checks.links.pending` / `pending_targets` に記録する。
  相手 feature が生成された時点で消える。**遷移先 feature 名の誤記も pending として現れる**ため、
  報告された相手 feature 名を **manifest の `cross_feature_links`（出どころ = 画面マップ §3）と突き合わせる**

## シェルは 1 か所から出す

**シェルは全ページに載る**（feature 1 本でも数十ページ）。**ページごとに書くと一致を保証できず**、
シェルだけを直すのに**全ページを書き換えることになる**（【MUST NOT】手で磨く、に触れる）。

- 【MUST】**シェルの HTML を 1 か所で組み、全ページに同じものを差し込む。**
  ページごとに書き分けるのは**現在地の印だけ**
- 【MUST】**生成の手段を案件に残す**（既定の置き場は **`.aidd/screen-design/_tools/mockup/`**。
  `pages/` の外であれば置き場は案件裁量でよい）。
  残さないと、**シェルの 1 行を直すのに全 feature の MU を回し直すことになる**（実測）。
  残せない場合は、**その旨と再生成の手順を manifest の `notes[]` に書く**
- 【MUST】**入口画面自身には、入口へ戻るリンクを置かない**（自己参照になる。現在地の印だけを持つ）
- 【MUST】**パンくずは現在ページ以外の段をリンクにする。** 現在ページはリンクにしない
  （STYLEGUIDE.md §4-10）。**規定が無いと生成回ごとに揺れ、どの段もリンクでない回が出ると
  案件のどこからも入口に戻れなくなる**（実測）
- **シェルだけの変更でも、対象 feature の mockup は全ページ再生成する。**
  本文の入力は不変なので、**目視はシェルだけでよい**

## 見るときの観点を成果物側に渡す

**目視は人の担当**だが、**何を見るかが配布物側（本 SKILL.md）にしか無いと、目視する人に届かない**
（「どの観点で確認すればいいんでしたっけ」が実際に起きる）。
【MUST】**`pages/README.md` に「見るときの観点」節を置く。** 形は A + B の 2 段。

**A. 毎回同じ 3 観点**（逐語で置く）:

1. **読み込み切れ** — `tokens/styleguide.css` が当たっているか（素の HTML に見えるページが無いか）
2. **崩れ** — 部品の重なり・はみ出し・折り返し・間隔の詰まり
3. **シェルとナビの一致** — 全ページに同じシェルが載り、ナビ項目と現在地が画面マップ §4-1 / §4-2 と合っているか

**B. その回だけの観点**（**新規に書き起こさない。`missing[]` と `notes[]` から導く**）:

- `missing[]` の各件 → 「その部品が無いまま描いた箇所が、見て許容できるか」
- `notes[]` の各件（pending・無効表示のナビ項目・規定と実体の食い違い）→ 「その箇所の見え方」
- **観点は「見る場所を示すもの」であって「漏れを防ぐもの」ではない。** B は `missing[]` / `notes[]` から導くので、
  **生成側が気づいていない欠陥は構造上そこに載らない**（機械検査 2 本も描画を見ない）。観点の外は目視でしか出ない
- **観点は「中身が器に入るか」で書く**（「器が宣言どおりか」ではなく）。人は溢れているところを見る

【MUST】**各観点に、少なくとも 1 枚の代表ページを対応させる。**
観点だけ書いて代表ページを指名しないと、**その観点にしか現れないページが目視から漏れる**（実測）。
代表ページの選び方は「その観点が最も強く出るページ」で、**A の 3 観点には全ページ共通のものを 1 枚**、
**B の各観点にはその事象が現れるページを 1 枚以上**挙げる。

## 文言が無いときの起草

**画面設計書 §3-x-6 の「コード参照形」（`FORM_VALIDATION_FAILED` のような書き方）は、
画面設計書の中で条件文とメッセージを転記しないための書式であって、画面に出す文言ではない。**
そのまま描くと**利用者に見せる mockup にエラーコードが出る**（実測）。

- 【MUST】**コード参照形をそのまま画面に出さない。** STYLEGUIDE.md §7 の文言トーンで**起草する**
- 【MUST】**起草した文言は `mockup-manifest.json` の `drafted_wording[]` に記録する**
  （`notes[]` に混ぜない）。1 件 = `{ page, element, drafted, source_code, reason }`。
  **記録しないと再生成のたびに違う文言になり、目視の指摘が前回とつながらない**
- 【MUST】**報告に `drafted_wording[]` の一覧を出し、上流へ返す。**
  **文言の正は画面設計書 §3-x-6** なので、起草した文言は画面設計書に取り込まれるべきものである
  （design.md はエラーコードの正・画面マップ §5 は業務状態名等の書式・STYLEGUIDE.md §7 はトーンと表記）
- 【MUST NOT】**起草した文言を根拠に画面設計書を書き換える**（返すのは報告であって、書き込みではない）
- 【MUST NOT】**部品のラベル（様式側の文言）まで起草する。** 起草の対象は画面の表示文言だけで、
  部品のラベルが無いときは **`missing[]` に追記候補として記録する**（正は STYLEGUIDE.md §4 の側にある）

## 擬似 feature（`_app-shell` など）の入力

擬似 feature は `requirements.md` / `design.md` を持たず、画面設計書の根拠が **steering** にある。

- 【MUST】**画面設計書 §6 参照が指す steering の節を入力に含める**（節を指定して読む。全文ではない）。
  読まないと、**入口画面の文言・ロール・並びの根拠が確かめられないまま描くことになる**
- **本体の「読まないもの」（`requirements.md` / `design.md`）はそのまま効く**
  （擬似 feature にはそもそも存在しない）

## 注記の定型文（逐語で使う・言い換えない）

**`pages/README.md` に置く形**:

> **これは画面設計書とスタイルガイドから生成した画面の具体形です**
> 構成・項目・状態・文言と、案件の見た目を確認するためのものです。
> 挙動は再現していません（JS なし・画面遷移はリンクのみ・表示データはすべて固定値のダミーです）。
> 正は**画面設計書**（構成・項目・操作・状態・文言）と**スタイルガイド**（見た目）であり、
> この HTML を実装のソースには使いません。
> 直したいところは、この HTML ではなく**入力（画面設計書・画面マップ・スタイルガイド）を直して再生成**します。

**manifest の `notice` に置く形**（雛形が持つ圧縮形をそのまま — 言い換えない）:

> 画面設計書とスタイルガイドから生成した画面の具体形。構成・項目・状態・文言と案件の見た目の確認用で、挙動は再現していない（JS なし・データは固定値ダミー）。正は画面設計書とスタイルガイドであり、この HTML を実装のソースに使わない。修正は入力を直して再生成する。

置き場は **`pages/README.md`** と **manifest の `notice`** の**2 か所だけ**。
**ページの HTML には書かない**（注記が画面の一部と誤解され、見た目の確認そのものを妨げる）。
開発者向けの一時的な補足も HTML に書かず manifest の `notes[]` に記録する。

## 完了条件（自己確認してから報告する）

1. **画面設計書の画面 × 状態と manifest の `pages[]` が 1:1**（他 feature の画面の参照行は数に入れない）
2. **パレット検査・動線検査 exit 0**（manifest の `checks` に機械記録。動線検査の pending は件数と相手 feature を `notes[]` に）
3. **全ページに共通シェルが載り、ナビ項目が画面マップ §4-2 と一致する**（機械検査はクラス名の存在確認まで。項目の一致は目視）
4. **`pages/README.md` に「見るときの観点」（A 3 点 + B）と、各観点の代表ページが書かれている**
   （→「見るときの観点を成果物側に渡す」）。**目視そのものは人**（→「完了後」）
5. **`missing[]`（作れなかった部品・状態）を報告に明示し、`STYLEGUIDE-backlog.md` に転記済み。黙って落とさない**
6. **`drafted_wording[]` に起草した文言が記録され、報告に出ている**（→「文言が無いときの起草」）

## 出力

```
<案件ルート>/.aidd/screen-design/<feature>/pages/
├── *.html                  … 状態別ページ（再生成する。全ページにシェルを載せる）
├── mockup-manifest.json    … 承認対象（status の担体 — トップレベル）
├── README.md               … 位置づけの注記（定型文の逐語）+ 生成条件
└── tokens/styleguide.css   … 案件直下 styleguide.css の複製（内容同一）
```

入口を新設した案件では、入口ページを **`.aidd/screen-design/_app-shell/pages/`** に同じ規約で生成する。

報告に必ず含める:

- **画面 × 状態の数**と、manifest の `pages[]` との 1:1 の確認結果
- **機械検査 2 本の結果**（exit code / Tier A の違反 0 / **pending の件数と相手 feature** / Tier B の報告件数）
- **`missing[]`** の一覧（STYLEGUIDE.md §4 に無くて作れなかった部品・状態）— **STYLEGUIDE.md への追記候補**。
  **`STYLEGUIDE-backlog.md` に転記した行の番号**もあわせて出す
- **`drafted_wording[]`** の一覧（起草した表示文言と、その出どころのコード）— **画面設計書 §3-x-6 へ返す**
- **リンク先が無いナビ項目**（mockup 未生成の feature）と、**今回リンクが張れるようになった項目**
- 再生成の場合: **再生成した契機**（→「開始時の宣言」の表のどれか）と、**目視の範囲**

## ガードレール

- 【MUST NOT】**画面設計書に無い画面・状態・項目・操作を足す**（足りないと分かったら画面設計書を直して再生成する）
- 【MUST NOT】**シェルを後付けする**（生成入力に含める。後付けは再生成で消え、結合をやり直すことになる）
- 【MUST NOT】**ナビ項目を間引く**（mockup 未生成 feature の項目も載せる — システム内の位置が見えることが動線の理解を助ける）
- 【MUST NOT】**共有画面を自 feature の `pages/` に複製する**（所有側だけが描く）
- 【MUST NOT】**pending を消すために、他 feature の mockup を勝手に生成する**（その feature の SD-1 が confirmed になってから）
- 【MUST NOT】**検査を通すために HTML を手で直す**（入力を直して再生成する）
- 【MUST NOT】**`missing[]` を空にするために近い部品で代用する**
- 【MUST NOT】**エラーコードをそのまま画面の文言として描く**（→「文言が無いときの起草」）
- 【MUST NOT】**シェルをページごとに書き分ける**（現在地の印を除く。→「シェルは 1 か所から出す」）
- 【MUST NOT】**wireframe 工程の HTML・CSS・`tokens/`・クラス名・変数名を持ち込む**（見た目の正は `styleguide.css` 1 枚。
  DS の `var(--…)` は未定義のまま検査を通り、目視の「読み込み切れ」でしか出ない）
- 【MUST】**再生成は `pages/` に上書きする。** `presented/` には触れない（凍結した提示版）
- 【MUST】**再生成では `pages/README.md` の生成条件と観点も書き直す**（前回の版のまま残さない）

## 完了後

- **目視は人**（開発者）。**`pages/README.md` の「見るときの観点」に沿って**ブラウザで開き、
  manifest の `viewed` を記入する。**判断は人・記入は代筆可**で、`by` = 判断した人 /
  `recorded_by` = 記入した主体（代筆ならその skill 名）を分けて残す。
  返し方は 1 つではない — `findings[]`（指摘）/ `ok_findings[]`・`state_observations[]`（見て問題なかったもの）/
  **`questions[]`（質問と回答）/ `verification_requests[]`（検算の依頼と結果）**。質問を `findings[]` に混ぜない
- **人の OK とエージェントの実測は別のキーに持つ。** 人が「この見た目でよい」と判断したうえで
  エージェントに確かめさせた結果は **`agent_verification`（by / at / method / results[]）**に入れ、
  `pages[]` / `findings[]` に混ぜない。**目視そのものを代行しない**（人が見ていないものは見ていないと書く）
- **再生成の契機は「開始時の宣言」の表が正**。とくに次の 2 つは見落としやすい:
  **① 画面マップ §4 が変わった**（ナビ項目・ヘッダのリンク・現在地のいずれか。全 feature）
  **② 無効表示のナビ項目のリンク先が生成された**
  （その項目を無効表示で持つ全 feature。**§4 の値は変わらないので ① には該当しない**）。
  いずれも本文の入力は不変なので**目視はシェルだけでよい**
- **顧客提示は案件裁量**（feature 単位で提示してよいが、**入口とシェル込みで見せる**）。
  提示する版は **`presented/<yyyy-mm-dd>/` に `pages/` ごと複製して凍結**し、以後手を入れない
  （`tokens/styleguide.css` を含める — 含めないと版を上げた後に凍結版が新しい見た目で描かれる）。
  提示後は開発者が `presented_at` を記入する
- **顧客提示の指摘の行き先は 5 分類**: 挙動・要件 → requirements / design.md の**変更管理** /
  動線・ナビ・所有 → **画面マップ**（差分確認の後に影響 feature を再生成）/
  構成・項目・状態・文言 → **画面設計書** / 見た目 → **STYLEGUIDE.md**（版を上げて全 feature に効く）/
  **入力は正しく生成の側が誤っている → mockup そのもの**（**生成器を直して再生成する**）。
  **いずれも mockup を手で直さない**
- **指摘を台帳に起こす前に、原因を特定し、同じ器を使う全ページを機械で数え上げる**
  （字面どおり直すと誤った直し方になり、人が名指ししたページだけを直すと同じ器の残りに穴が残る）
