# steering-conformance（② steering 適合検査）

> 層 **②**。呼び出し元は各フェーズの `<Phase>-Check-Subagent`。

steering はプロジェクト全体で固定した前提である。**steering に違反する成果物を通してはならない。**

---

## 入力（呼び出し時に必ず指定する項目）

| 項目 | 内容 |
|---|---|
| `対象成果物` | 検査するファイル（複数可） |
| `steering パス` | `steering/` 一式のパス。**7ファイルすべて**を指定する |
| `検査観点` | このフェーズで特に見る観点 |
| `報告単位` | 何を 1 件として報告するか |

### `steering/` は一式（全文）を読む

該当章だけを選んで読むことはしない。feature 数に依存しない固定量であり、**どの章が該当するかの判定自体がブレを生む**ためである。

### 呼び出し例

| フェーズ | `検査観点` の指定例 |
|---|---|
| Phase 3 | feature 分割が steering の方針（対象範囲・アーキテクチャ境界）と整合しているか |
| Phase 4 | 当該 `requirements.md` が steering の内容に違反していないか |
| Phase 5 | 設計が steering の技術選定・アーキテクチャ・DB / 業務コードの設計ルールに従っているか |
| Phase 7 | `tech.md` の検証前提（コマンド・テスト方針）と矛盾していないか |

---

## 手順

1. `steering パス` の 7 ファイルを全文読み、**制約として機能する記述**を列挙する。「方針」「規約」「禁止」「必須」「準拠」を述べている箇所が対象である。
2. `対象成果物` を読む。
3. `検査観点` に沿って次の 3 種を判定する。

| 種別 | 内容 |
|---|---|
| **違反** | steering が禁止・限定していることを成果物が行っている |
| **矛盾** | steering の記述と成果物の記述が両立しない |
| **逸脱（無断の拡張）** | steering に無い前提を成果物が独自に導入している。steering 側の記述不足である可能性があるため、**成果物の不備と断定せず**「どちらを直すべきか」を問う形で出す |

4. 該当箇所ごとに、**steering 側の根拠（ファイル名とセクション）**を必ず添える。根拠を示せないものは指摘にしない。
5. 指摘を `報告単位` で整理し、層 **②** として `gate-report` に渡す。

---

## 設計ルールの粒度を見る場合（Phase 2 / 5 / 6）

steering は **業務コード・DB エンティティの「設計ルール」を持ち、「実体」を持たない**。この境界を検査する場合は次を見る。

| 検査 | 判定 |
|---|---|
| ルールの粒度 | **各 `design.md` がそのルールを参照するだけで設計できるか。** 粒度が足りないと feature ごとに独自解釈が発生し、Phase 6 の集約時に衝突する |
| 実体の混入 | steering に **個々のコード値・区分値・採番対象・テーブル定義**が書かれていないか |
| 判定基準 | 「**全 feature に等しく適用されるか**」。等しく適用されるならルール（steering）、feature ごとに異なるなら実体（`design.md`） |

---

## 禁止

- 対象成果物を修正しない。
- 合否を出さない。重大度を付けない。
- **steering 側の根拠を示せない指摘を出さない**（一般論としての良し悪しは本 Skill の対象外）。
- steering の該当章だけを読んで判定しない（一式全文が前提）。
- steering 自身の方針の妥当性を評価しない。それは ③ 人間レビューの観点である。
- steering の記述不足を成果物側の不備として断定しない（「逸脱」として区別する）。
