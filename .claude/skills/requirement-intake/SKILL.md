# requirement-intake（Phase 1: 要求受入）

> 出典: フロー設計 `01_要求受入フェーズ設計書.md`。

**このフェーズの本質は「検査」ではなく「正規化」である。** RFP は作成主体が案件ごとに異なり型を強制できないため、入力の形式に関わらず必ず正規化を通し、**テンプレート化された出力**を作る。

- 成果物: `.aidd/requirement-list.md`
- テンプレート: `Templates/Flow/requirement-list.md`
- **本ファイルを更新できるのは Phase 1 だけである。**

---

## 入力

| 項目 | 内容 |
|---|---|
| RFP | フロー外で作成済み。**自由形式**。既定の置き場は `.aidd/rfp/`。人間がパスを指定した場合はそれに従う |
| 要求一覧テンプレート | `Templates/Flow/requirement-list.md` |

---

## 停止条件（RFP の受入判定を最初に行う）

RFP が次の 3 点を満たさない場合、**Phase 2 に進まず人間へ差戻す**（フロー外へのエスカレーション）。要求一覧を作り始めてはならない。

- システムの目的・対象ユーザーが読み取れる
- 実現したい業務・機能の範囲が列挙されている
- やらないこと（対象外）が判別できる、または確認すべき論点として明示されている

---

## 手順

### 1. 抽出

RFP を読み、要求項目を抽出する。

### 2. 要求ID の採番と出典の付与

- 要求ID は `REQ-` + 3桁以上の数字。
- **出典種別**を付ける。

| 出典種別 | 使う条件 |
|---|---|
| `RFP` | **RFP に記載があるものに限る。** 記載が無いものを補って `RFP` 種別にしてはならない |
| `壁打ち` | **人間が壁打ちで確定した要求に限る。** ゲートの指摘に人間が「必要」と答えた要求もここに入る。**AI が推測で補完した要求を `壁打ち` 種別にしてはならない** |

- **出典アンカー**を付ける。`RFP` 種別は RFP の章・見出し・引用位置、`壁打ち` 種別は `壁打ち` と記載する。
- **出典アンカーの無い行を作らない。**

#### 要求IDの安定性ルール

- 採番は **追記のみ**。既存 ID の番号を振り直さない。
- **欠番は再利用しない。**
- 廃止された要求は削除せず、テンプレートの「廃止済み要求」表に**廃止マークを残す**。

#### 改版時

RFP が改版された場合、**採番の前に既存 ID との差分判定（維持 / 変更 / 新規 / 廃止）を行う**。

- **差分判定の対象は出典種別が `RFP` の行に限る。** `壁打ち` 種別の行は RFP の改版では増減しないため、廃止するかどうかは人間が個別に判断する。
- 判定後は `status` を `review` に戻し、**再承認を要する**。

### 3. 分類

各項目を `機能` / `非機能` / `制約` の 3 値に分類する。

- **RFP に明記された前提・仮定**（既存基盤の利用、稼働環境、他システムの存在など）は `制約` に含める。
- 分類は下流の振り分け先を決める。`機能` は Phase 3 の feature 割当、`非機能` / `制約` は Phase 2 の steering へ向かう。

### 4. 品質ゲートを通す

`intake-check-subagent` を **別コンテキストで**起動する（起動時の制約は `.claude/skills/aidd-flow/SKILL.md` §5 Step 3）。**指摘の要約は呼び出し元へ返す。③ の提示と人間の判断の反映は呼び出し元が行うため、本 Skill が人間へ承認を求めない。**

### 5. 壁打ちで指摘を解消して再ゲート

修正と判断されたものを壁打ちで解消する。**推測での補完は禁止。** この壁打ちで扱うのは次の 2 つである。

- ゲートの指摘への回答
- 下流フェーズから戻された新規要求の確定

---

## 本フェーズがやらないこと

**要求文の曖昧さを解消しない。** 担保するのは **網羅性**（RFP の要求が漏れなく載っていること）のみである。

- 値の未確定・対象の不特定は、**反映先のフェーズの壁打ち**で確定させる（`機能` は Phase 3 / 4、`非機能` / `制約` は Phase 2）。
- 要求一覧に **明確性を表す項目を持たせない**。`明確` / `要確認` のような判定を追加してはならない。
- 要求一覧に **「対応 feature」列を持たせない**。要求 ↔ feature の対応の正は `.aidd/feature-list.md` の「対応要求ID」のみである。

---

## 未確定箇所の質問化

埋まらない箇所を推測で補完せず、質問して人間の回答で埋める。

1. RFP から読み取れなかった項目を **要求ID 単位で列挙**して人間に提示する。
2. 提示は「この要求の○○が RFP から読み取れない」という形にする。**推測した候補を選択肢として並べない**（選ばせると補完になる）。
3. 回答を得た要求は、出典種別を `壁打ち`・出典アンカーを `壁打ち` として記入する。
4. 回答が得られない項目は **プレースホルダーを残したまま**（削除も空欄化もしない）、`phase-progress.json` の `waiting_for` を `human_answer`、`open_placeholders` を **不要理由が明記されていない未記入数**に更新して**停止する**。

---

## 下流フェーズから戻された要求の追記

下流フェーズの壁打ちで新規要求が判明した場合、その要求は **本フェーズで確定させる**。

1. **既存要求の詳細化か新規要求かを切り分ける。** 要求一覧のいずれかの要求に含まれると読めるなら詳細化であり、要求一覧は変えない（`requirements.md` の要件として既存の要求IDに紐づける）。
2. どの要求にも属さない場合のみ新規要求とし、Phase 1 の壁打ちとして人間に確定させる。
3. 出典種別 `壁打ち`・出典アンカー `壁打ち` で追記する。
4. `status` を `review` に戻し、**再承認を要する**。
5. 分類に応じて波及先を人間へ伝える（`機能` → Phase 3 の feature 割当と feature-list の再承認、`非機能` / `制約` → Phase 2 の steering）。

---

## 禁止

- RFP に記載が無い要求を `RFP` 種別で書くこと。
- AI が推測で補完した要求を `壁打ち` 種別で書くこと。
- 出典アンカーの無い行を作ること。
- 記載欠如を「欠落」と断定すること（欠落の指摘は品質ゲートの提案として出し、採否は人間が判断する）。
- 既存 ID の振り直し、欠番の再利用、廃止要求の削除。
- プレースホルダーを削除・空欄化すること。
- 自ら `status: approved` にすること。
