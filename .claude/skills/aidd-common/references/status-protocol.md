# status・進捗・承認の規約（L3）

所有は L3。実行仲介は L0、検査は L4。具体的なホスト操作は host-protocol.md。

## 1. status の値

not_started は未作成、draft は作成中、review は検査記録あり・人間確認待ち、approved は
人間承認済み。review には一部の層だけを検査した状態も含む。承認・完了には必要な検査の
実施と、status・現在の成果物ハッシュに一致する承認記録を併せて確認する。
phase-progress.json の progress は派生表示で、単独では完了の証拠にならない。
人への提示直前に L3 の progress で再生成し、古い保存値を最新表示として使わない。
progress_view は表示の可用性と更新日時、progress は文書 status 一覧の控えである。
未確定の feature 別一覧と表示できない一覧は null とし、0件完了と解釈しない。

## 2. 遷移権限

| 遷移 | 実行主体・条件 |
|---|---|
| 未作成 → draft | L3 生成 Skill |
| draft/review → review | L4 の inspection_path を L3 scope-check が検証・末尾追記した後。指摘件数には依存しない。cross とコードprofileは対象外 |
| review → approved | 実 review wait・scope-check 証明・必要な全検査の実施を照合後、人間の実回答を L3 approve が記録し代行する |
| review/approved → draft | L3 の明示的な修正・差戻し・入力変更の無効化処理 |

L4 は対象本文、上流文書、状態 JSON、人間判断を書き換えない。approved を下げない。
L3 はゲート前後の保護ハッシュと記録のバイト先頭ハッシュで書込範囲を検査する。
生成・修正 Skill は自成果物のみを編集し、進捗操作・承認・検査起動を行わない。

検査ゲートの `target_review`（gate.yaml）から外した出力は、上の review / approved への遷移を持たない（draft のまま）。
検査中（snapshot から scope-check まで）は本文も status も変更できず、scope-check が snapshot の値と照合する。
下流はその status の値を承認の証跡にせず、存在だけを確認する。ホストは context の `unreviewed_inputs` で明示する。
以前に承認され、後から `target_review` から外した出力は、フロントマターが approved のままでも未検査として扱う。
Phase 1–7 の修正アクション は生成アクション の後、修正要求があるあいだ入口 Skill が修正の 1 回ごとに呼ぶ。修正要求が無ければ
修正アクションは呼ばれない（万一呼ばれても何も編集せず completed（targets 0 件）を返す）。修正対象がある場合は L3 進行制御による draft 化を前提とし、
対象が draft でなければ編集せずホストへ返し、Skill 自身では status を変更しない。
回答後の同じ draft への再入は維持する。

## 3. 指摘と差戻し

人間が対象指摘と所有工程を決める。当該成果物の不足は同じ工程の修正アクション
（`<base>-revise`）へ戻す。**当該工程内の修正が既定**であり、上流を疑う前に、
当該工程の記述で解消できないかを先に確認する。
要求一覧は Phase 1、steering は Phase 2、feature 分割は Phase 3、requirements は
Phase 4、design は Phase 5、docs は Phase 6、tasks は Phase 7 が修正する。

| 検出 | 不備の所在 | 戻し先 |
|---|---|---|
| Phase 1 | RFP そのもの（目的不明・機能範囲欠落・矛盾） | フロー外（人間が RFP を改訂）。Phase 1 を保留し、質問への回答だけで解除しない |
| Phase 5 | 依存先 design の公開契約不足 | 該当する依存先 design。自 feature は draft 維持 |
| Phase 6 | design の欠落・design 間の競合 | 該当 design。docs 統合は保留 |
| Phase 7 | tasks にしか存在しない設計判断 | 該当 design。docs も再統合の対象 |
| Phase 7 | requirements の AC が検証不能 | 該当 requirements |
| 全工程 | 壁打ちで判明した新規要求（RFP に出典が無い） | Phase 1。Phase 1 の壁打ちとして確定し出典種別「壁打ち」で追記・再承認する。検出工程が要求一覧を書き換えない |

docs 間や tasks 上で設計を決め直さず、その設計を所有する design/steering へ戻す。
生成・修正 Skill は戻し先を return_candidates として返すだけで、差戻しを確定しない。

差戻しは上流の再承認だけで解除しない。中間工程の再構築、発見元の再検査、
旧指摘の明示的な解消確認と承認まで必要。blocker は resolved として履歴を残す。
自動修正ループや回数による機械的打切りは行わない。

## 4. フロントマター

status 遷移では status/updated_at のみを更新し本文を保持する。updated_at は
オフセット付き ISO 8601。承認者はゲート記録へ書く。横断検査は status を動かさない。
構造・必須欄は L1 Templates を実行時に読む。

## 5. 状態の所有と保存

L0 は events、trace、engine_schema、engine_reports、current の実行欄（pending の発行情報を含む）を所有する。L3 は workflow、
blockers、features、feature_manifest、progress/progress_view と人間の質問・回答を所有する。
保存時は最新 JSON へ担当欄をマージし、未知の欄や質問を消さない。処理は直列に実行する。
L0 の再実行は公開 redo を介し無効化履歴を追記する。L3 から成功印を捏造しない。

workflow.completions は L0 完走後に現在の入力・成果物・検査・承認を照合した証明。
修正アクション（`<base>-revise`）の完了で生成工程（`<base>-generate`）を満たせるが、元の実行履歴は保持する。
feature の原本は承認済み feature-list.md。JSON は毎回同期してハッシュを確認する。
原本変更時は計画・影響する完了証明・下流検査を無効化する。

上流の再承認だけで下流の完了証明の入力ハッシュを更新しない。status/updated_at と
正規の tasks 実績更新を除く入力内容が変わった場合、記録された入力を実際に使用する
成果物を修正・再検査へ戻す。無関係な成果物の承認は保持する。過去の証明は保持し、
当該成果物が新しい入力で完走したときだけ新しい完了証明を発行する。
Phase 8 はタスクごとの生成／修正アクションを使い、feature 全体の検査と人間承認を行う。
入力が変わった実装は証跡を保持して無効化し、実装契約の明示的な rebase で再検証する。

再生成できるのは表示等の派生情報であり、質問・回答・修正要求・了承・blocker・実行履歴を
消して復元できるという意味ではない。表示更新の失敗と、承認・完了の保存結果は分ける。
保存済みの主処理を再送せず、表示だけを再生成する。具体的な返却は host-protocol.md に従う。

scope-check 成功時、snapshot 隣に `.checked.json` を保存する。検査回・対象・原本・入力・
記録先頭のハッシュを含み、実 review wait の detail に同じ検査の識別情報を結び付ける。
L3 は workflow.review_operations に人間書込みの prepared/applied、
L0 の host は状態ストアの `host_operations`（L0 所有）に受領から report/次の call までの prepared/saved/reported/finished を保存する。
これらは再送と途中停止からの継続に必要な証跡で、進捗キャッシュと同様に削除・再生成してはいけない。
個々のファイル更新は一時ファイルから置換し、中断時は保存済みハッシュを照合して未実施分のみ進める。
複数成果物の承認は全ファイル同時のトランザクションではなく、中断時は未完了操作として停止する。
同じ操作ID・payloadの再送が完了するまで別の業務操作を受け付けない。

## 6. 末尾追記のゲート記録

1 Phase 1 ファイル。L1 gate-record.md と gate-record-format.md に従う。
各回の実行＋指摘＋任意の差戻し候補を末尾へ追記し、人間の判断・解消・承認・確認も
別ブロックとして追記する。既存行やフロントマターを更新しない。
最新日時は最終ブロックから導く。feature 別表示はパース結果から作る。

形式不備があれば意味検査を省略し実行した層を①とする。横断の意味検査のみなら②。
承認・横断確認・最終完了には、対象とハッシュが一致する各スコープの最新回で次を満たす。

| 検査の対象 | 必須の層 |
|---|---|
| 通常工程・feature 個別（生成／修正） | ①② |
| requirements / design の cross | ② |
| tasks 最終の phase | ②。併せて全 feature の最新回に①②が必要 |

過去回や別スコープの層を合算しない。指摘0件や「対応せず進める」は検査の省略許可ではない。
必要な検査が未実施なら承認不可とし、免除経路は設けない。部分検査の記録と人間の判断・
修正への移行は可能。tasks 個別 event の完走は中間処理であり、最終承認とは区別する。
prepared の承認操作を再送するときも必要な検査を照合する。旧版の部分検査による承認記録は
履歴として保持するが、それだけで現在の完了証明を満たしたとは扱わない。

指摘の判断は修正・差戻し・対応せず進める・未対応。後二者は理由必須。
修正・差戻しは同一スコープの再検査と人間の解消確認が必要。未判断と未解消は承認を止める。
過去回の未解消指摘は「最新回の指摘件数」と分けて持ち越す。古い書式を黙って無視しない。

## 7. プレースホルダーの 2 系統

テンプレートのプレースホルダーは **次の 2 系統のみ**である。**これ以外の表記をプレースホルダーとして扱わない。**

| 系統 | 例 | 誰が埋めるか | `open_placeholders` |
|---|---|---|---|
| **山括弧 + 大文字**（`<UPPER_SNAKE>`） | `<PRODUCT_NAME>` / `<REQUIREMENT_ID_N>` | **人間**。壁打ちで確定した回答をエージェントが記入する | **数える** |
| **二重波括弧**（`{{UPPER_SNAKE}}`） | `{{FEATURE_NAME}}` / `{{ISO_8601_TIMESTAMP}}` | **エージェント**。上流成果物と実行時の情報から機械的に埋める | 数えない |

- **判定は記法で行い、フロントマターか本文かでは行わない。** `{{...}}` はフロントマター以外（見出しなど）にも現れる。
- **`{{...}}` を人間への質問にしない。** 導出元が上流成果物に無い場合のみ質問する。
- **小文字を含む山括弧はプレースホルダーではない。** `specs/<feature>/requirements.md` のようなパスの可変セグメント、`<br/>`、`<https://…>` が該当する。埋めずにそのまま残す。
- **末尾が `_N` のスロットは可変個数**を表す。必要な数だけ行・ブロックを増やす。
- **どちらの系統も削除しない。** 埋める必要がないものは、**人間が明記した不要理由**を添えたままプレースホルダーを残す。
- `TBD` / `未定` / `_(未記入)_` のような語は**プレースホルダーではない**。テンプレート由来の注記・初期値としてそのまま残っていてよく、逆に**記入欄へ新たに書き込んではならない**（根拠のない値と同じ扱いになる）。

tasksの「実装メモ」の3節は着手時に空でよい。対応するTSK_DECISION_LOG_N / TSK_KNOWN_ISSUE_N /
TSK_HANDOVER_Nの実績用スロットだけはPhase 7の必須回答・open_placeholdersから除外する。
新規計画では空欄で作成できる。既存のスロット行は一括削除しない。この例外を計画本文・他工程へ広げない。
完了条件・4注記等の実装に必要な欄は、Phase 8開始時にも機械で検証する。

### 未記入数の返却と保存

生成／修正 Skill は、担当対象の未記入欄を記入位置ごとに数え、不要理由のあるものを
除いた数を `open_placeholders` として返す。質問の件数からは導出しない。
具体的な返却条件は `authoring/contract.md` に従う。
L3 の `submit`（内部の result 保存処理）が型と完了条件を検査し、`workflow.results[event[item]]` へ保存する。
待機時は submit が同じ payload を質問保存処理へ渡し、`workflow.waiting[event[item]]` にも保持する。
回答受領だけでは数を減らさず、文書への反映後に Skill が再集計して `result` へ返す。
現在の値は最新の results、waiting は質問・回答時点の記録として読む。
Skill に旧方式の `phase-progress.json` 直接更新を戻さず、L0 にも案件固有の集計を持たせない。

この数は Skill の意味判断を含む報告値である。L3 のスクリプトは型と状態整合を検査するが、
文書中の不要理由の妥当性まで自動判定した値ではない。0件でも他の未回答・差戻し候補が
あれば completed にできず、後続の L4 検査と人間承認は引き続き必要となる。
