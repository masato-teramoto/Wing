# 単一タスクの生成・修正

補助操作（implement-check / implement-note）には、contextの今回のexecution_idを必ず渡す。
itemはemit.itemを保持し、execution_idから作り直さない。

1. 渡された1件の完了条件、Requirements / Design / Boundary / Dependsを読む。
   承認済み要件・設計・steering・docsと依存契約を照合する。指定外タスクを始めない。
   contextの`unreviewed_inputs`に挙げた上流は検査・承認されないdraftだが、approvedでなくても読む。
2. 既存コード・テスト・案件の実行設定を読み、要求に必要な変更と検証を決める。
   不明な仕様や設計矛盾はquestions/return_candidatesとして返し、推測で承認済み計画を変えない。
   準備タスクでは必要ツールの版・機能を変更なしで確認し、不足時だけ承認済みの導入を実行する。
   タスク一覧の承認範囲内では別の導入確認を求めない。範囲が変わる場合は通常の計画見直しへ戻す。
   実行結果とログの場所をimplement-noteへ残す。導入はcheck_idsやレポートコマンドに登録せず、
   終了後に環境確認をVERIFYする。中断後はプロセスと部分導入状態を確認してから再開する。
   新規作成も担当する準備スクリプトは、空の専用配置先でその経路を確認する。
   手動復旧した環境のcheck成功と、スクリプトによる新規作成成功を混同せず記録する。
3. コードタスクは完了条件を表す失敗テストを追加する（修正なら不具合を再現する）。
   implement-checkのredを実行し、出力から意図したassertionの失敗を確認する。
   import失敗、依存未導入、起動不能、timeoutはREDの達成と扱わない。
4. テストが通る最小限の実装を行いgreenを実行する。成功後、必要なリファクタリングを行う。
5. 判断・理由はその場でimplement-noteの「決定ログ」に追記する。
   未解決の制約は「既知の制約 / 残課題」、宛先がある事項は宛先付き「後続への申し送り」へ記す。
   既知の制約が解消したら同じ欄に、元の記述・決定・確認結果を特定した解消の追記を行う。
   過去の判断待ちを削除せず、決定ログだけの更新で未解決に見える状態を残さない。
6. タスクの完了条件に必要な全checkをverifyで実行する。共有コード・他タスク・先行featureへの
   影響を調べ、計画に不足する検証があればホストへ返す。単体テストだけに一律限定しない。
7. コード以外のタスクは検証計画にtdd=falseと理由がある場合だけTDDを省ける。検証は省かない。
8. 実差分と結果を確認し、completed/waiting/failedを返す。検証失敗中にcompletedを返さない。
   tasksのチェック、人間指摘の解消、feature承認、次タスクの選択を自身で確定しない。

参照: cc-sdd spec-impl.md 固定版 b505e83994a6300bde65018fda6bb290ffa120c7のTDD・タスク選択、
L1 tasks.mdの整数ID・4注記・判断時の実装メモ。既存L3_workspaceの実装方式は前提にしない。
