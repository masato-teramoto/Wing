# Requirements の作成規則

- 指定された1featureの「何を作るか／完了基準」を記す。対象・順序はホストから受け取り、自分で次のfeatureを選ばない。
- 承認済み要求一覧・steering・feature-listを根拠にする。要件IDは数値のみ（1、1.1）。REQ-形式の要求IDとは別の名前空間にする。
- 各要件に由来する要求IDを紐付け、feature-listの当該featureの対応要求IDを分母として漏れを自己確認する。
- ACはテンプレートのEARS形式で、観測可能な条件にする。観測手段を確定できなければセクション単位の質問を返す。
- 人間回答が既存要求の詳細化ならその要求IDへ紐付ける。どの要求にも属さない新規要求は `owner: intake`、`target: .aidd/requirement-list.md` の差戻し候補にし、要求一覧を直接変更しない。詳細化で足りるものを新規要求へ昇格させない。
- 要求一覧に無い要求を要件として書かない。要件ID → 要求ID の突合を保つため、新規要求は Phase 1 で確定・追記・再承認されるまで要件に採用しない。
- Dependencies / Adjacentはfeature-listの依存と一致させ、受け手側のIn Scopeに対応する責務があるか確認する。依存を独自に追加しない。
- 新しい依存が必要なら、対象 feature と相手、必要な責務・根拠を示し、feature-list の更新を Phase 3 への差戻し候補として返す。
- AC の観測方法を確定できないまま完成としない。後続の design / tasks を作った後で検証不能と判明すると、それらも作り直すことになる。
- 自己診断結果を返すが、検査・承認・後続featureへの進行は行わない。
