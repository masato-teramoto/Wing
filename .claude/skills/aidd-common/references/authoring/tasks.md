# Tasks の作成規則

- 指定された1featureの承認済みrequirements / design、steering、feature-listを根拠に実装計画を作る。docsの承認はフローの前提確認であり、`docs/` は生成入力として読まず、タスク設計の根拠にも使わない（feature 単位の設計の正は design）。
- 各タスクに観測可能な完了条件を1行以上記す。テスト・ログ・出力など外から同じ結論を確認できる条件にする。「正しく実装」「動作確認できる」だけで済ませない。
- テンプレートのチェックリスト書式を使う。タスク番号は正の整数で一意。_Requirements: / _Design: / _Boundary: / _Depends: の意味・適用条件はテンプレートの早見表を正とする。要件IDが不要な場合は—を置き、_Design:は該当セクションを指す。
- `(P)` は現行 L1 テンプレートに意味・適用条件の定義がないため付与しない。旧 Skill の列挙から推測して並列実行の指示を追加しない。
- _Depends:は依存なしなら「なし」、依存ありなら先行するタスク番号を半角カンマ区切りにする。循環・未知番号・自己依存・後続タスクへの依存を作らない。
- 全要件ID、全AC、designのコンポーネント・契約・データモデル・フローを分母に網羅を自己確認する。各ACは最低1タスクの完了条件から検証できること。
- steering/tech.mdの検証前提に従う。API形状・エンティティ・技術選定など tasks にしか存在しない設計判断を tasks で新設しない。必要なら `owner: design`、`target` に該当 `specs/<feature>/design.md` の差戻し候補として返し（design の差戻しは docs の再統合も伴う旨を添える）、waiting とする。design不足や曖昧さも同様にPhase 5、ACが検証不能ならPhase 4への差戻し候補を返す。designやdocsを直接降格しない。
- 検証・レポート用ツールの準備が必要なら通常のタスク本文へ、導入対象・版の条件または固定manifest/lockfile、導入先、変更範囲、使用コマンドまたは案件スクリプト、ネットワーク取得の有無を記す。既存のタスク一覧の最終承認に導入範囲を含め、実行時の別承認を定型作業として追加しない。曖昧な「必要なツールを導入」だけで済ませない。
- 既存環境で必要な版・機能が揃う場合、先行featureの共有環境を利用する場合、既存の環境構築タスクが扱う場合は専用タスクを重複作成しない。利用可能性の確認は省かない。新設する場合も現在の整数ID・4注記・完了条件を使い、実在のBoundaryと後続のDependsへ対応付ける。直接のACがなければRequirementsは—とし、架空の業務要件や製品コンポーネントを追加しない。
- 準備の完了条件は、導入処理の実行ではなく必要な版・機能が実際に利用可能であることにする。導入と変更を伴わないVERIFYを分ける。ビルド・配布物が準備時点で存在しなければ、実行可能になる後続タスクで依存衝突・製品への混入を確認する。レポートの数やテストケースの粒度に合わせてタスクを再分割しない。
- 作成・修正結果はdraftで返す。feature別検査と最後の全体確認・人間承認はL0のイベント管理に委ねる。実装作業自体はこのSkillの範囲外。
- 実装メモ3節は着手時に空でよい。TSK_DECISION_LOG_N / TSK_KNOWN_ISSUE_N / TSK_HANDOVER_Nの実績スロットだけはPhase 7のopen_placeholders・必須質問へ数えない。計画本文のID・完了条件・4注記の未記入には適用しない。新規計画の実績欄は空にでき、既存のスロットはまとめて削除しない。

## 観測可能な完了条件の例

以下は観測手段と成功条件の具体化例。案件の承認済み design と tech の検証前提に
合わせて書き、例にあるコマンド・API・ファイルを新たな必須要件にしない。

| 良い例（外から確認できる） | 悪い例（判定方法がない） |
|---|---|
| `pnpm typecheck` が終了コード0で完了する | 正しく実装されている |
| `/health` が HTTP 200 を返す | 動作確認できる |
| `OrderService.test.ts` のテストが全件パスする | テストを書く |
| マイグレーションの up/down がともにテスト DB で成功する | DB を整備する |

tasks は実装エージェントの実行入力になる。各タスクには、実行者が結果を観測して
同じ完了判定をできる手段を書く。自己診断での網羅確認は、後続の品質検査を代替しない。
