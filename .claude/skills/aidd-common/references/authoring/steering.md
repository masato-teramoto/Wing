# Steering の作成規則

- 承認済み要求一覧、とくに非機能／制約を根拠に7ファイルを作る。docsは暫定版も作らない。
- 記入順は product → tech / architecture → security / non-functional / database / api-standards。上位の未確定事項を残して下位を推測しない。
- product は目的・ユーザー・対象外、tech は技術選定・言語・フレームワーク・コード規約・テスト方針・検証コマンド、architecture は論理構成・境界・ディレクトリ、security は認証認可・機密情報・脆弱性、non-functional はSLO・性能・可用性・ログ・監視・障害対応、database は命名・型・整合性・移行、api-standards はAPI形状・エラー・版・共通検証を所有する。
- 同じ事実を複数ファイルへ定義しない。上位規則を参照するなら参照先が実在し、内容が記入されていることを確認する。
- 業務コードの体系・桁数・型・採番方式、DBの命名・型・整合性・移行方針はここで定める。個別コード値・採番対象・テーブル・カラム・ERはdesignが所有する。
- 全featureに等しく適用するものをルールとし、designが参照して設計できる粒度で記す。根拠不足はファイル×セクション単位の質問として、上位から順に返す。
- 要求一覧にない新規要求（非機能・制約を含む）は要求一覧を編集せず、`owner: intake` の差戻し候補として返す。
- 修正では下流specへの影響候補を報告するが、下流statusの変更や差戻し確定は行わない。
