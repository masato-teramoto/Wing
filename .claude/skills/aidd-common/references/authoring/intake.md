# 要求受入の作成規則

- 自由形式の RFP を正規化し、`.aidd/requirement-list.md` だけを編集する。RFP 自体を作成・編集しない。
- 最初に RFP の受入判定を行う。次の 3 点をすべて満たすまで要求一覧を作り始めない。
  - システムの目的・対象ユーザーが読み取れる
  - 実現したい業務・機能の範囲が列挙されている
  - やらないこと（対象外）が判別できる、または確認すべき論点として明示されている
- 満たさない場合はフロー外（人間が RFP を改訂）へ戻す。`status: waiting`、`targets: []` とし、満たさない条件ごとに `owner: rfp`、`target` に RFP のパス（`.aidd/rfp/` 配下）、`location` に該当章または「記載なし」、`reason` に不足条件を記した return_candidates を返す。この不足を questions にしない。人間の回答だけで受入済みとせず、再入時は改訂後の RFP の実内容で 3 点を判定し直す。
- 要求ID は REQ- に3桁以上の数字。既存IDを振り直さず、欠番を再利用しない。新規IDは過去の最大番号より後。廃止は「廃止済み要求」表へ残す。
- 出典種別 RFP は原文に存在する要求だけに使い、章・見出し・引用位置を付ける。壁打ちは実際に人間が確定した要求だけに使い、出典アンカーも「壁打ち」とする。推測を人間回答やRFPの記載に見せない。
- RFP 改版時は既存IDとの維持／変更／新規／廃止を採番前に整理する。RFP 出典の行だけを改版の差分対象とし、壁打ちの要求を自動廃止しない。
- 分類は機能／非機能／制約の3値。RFPの前提・仮定は制約に含める。機能はfeature割当、非機能・制約はsteeringに反映される。
- 担保するのは網羅性と出典。要求文の曖昧さを本工程で解消せず、曖昧な値を推測して明確化しない。値の未確定・対象の不特定は反映先フェーズの壁打ちで確定させる（機能は Phase 3 / 4、非機能・制約は Phase 2）。要求一覧へ明確性の判定列や対応feature列を追加しない。
- RFP に記載がないことだけで、必要な要求の「欠落」と断定しない。追加の必要性は品質ゲートの提案として扱い、採否は人間が決める。推測で要求を足さない。
- 下流からの追加では、既存要求の詳細化と新規要求を分ける。詳細化なら要求IDを維持し、新規要求だけを人間の確定後に壁打ちとして追記する。機能ならfeature割当、非機能／制約ならsteeringへの影響を結果に添える。
