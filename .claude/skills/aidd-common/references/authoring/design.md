# Design の作成規則

- 対象featureの承認済みrequirements、steering、feature-listと、依存先の承認済みdesignから作成する。対象requirementsは全文、feature-listは対象行と順序、steeringは一式を読む。
- 依存先はfeature-listの依存を正とする。直接依存から必要に応じて間接依存を参照する。依存先のrequirementsを全件積み上げない。
- 依存designは全文を読めるが、設計の前提にできるのはAPI / Event / Data / Service / Batchの公開契約だけ。Design Decisions、内部構成、ファイル計画、内部メソッド、内部の速度、所有データへの直接アクセスに依存しない。
- 依存先の公開契約が不足していれば推測で埋めず、`owner: design`、`target` に依存先 `specs/<依存feature>/design.md`、不足する契約と根拠を記した差戻し候補を返して waiting とする。上流statusを変更せず、自分のdraftを保つ。人間の回答だけで契約を補わず、依存先の修正・再承認後に再入する。steeringの設計ルール不足も同様にPhase 2への候補を返す。
- 依存先が approved であることを確認する。未確定の契約を根拠にすると、その修正が契約を利用した後続 feature へ波及するためである。
- 新規の業務コード・区分値・採番対象・エンティティはsteeringのルールに従って当該designに定義する。他featureの既存定義は再定義せず参照する。docsは作成・更新しない。
- 検証・レポート用ツールは既存の言語・フレームワーク・ランナー・manifest/lockfileを調べ、steering/tech.mdの共通方針に合わせて選ぶ。新規案件は採用する技術構成を根拠にする。既存ランナーの出力機能とOSS reporterを優先し、言語名だけで決めたりランナーを乗り換えたりしない。
- 共通事項はsteering/tech.mdを参照し、feature固有の追加・例外は既存の「技術スタック」、対象・出力・実測できる品質指標は「テスト戦略」、比較が必要だった選択理由は「設計判断」に記す。同じ情報を重複記載する専用節は作らない。導入が必要なら版の条件・導入先・変更対象・担当コンポーネントを特定する。
- ツールは開発・検証用とし、案件の実行時依存や配布物へ混入させない。既存のdev/test依存・manifest・lockfileの共有は許容し、依存衝突と本来のビルド・配布物を確認する方法を定める。全ツールの別環境化は必須にしない。OSSで取得・可読化できない指標は限界として示し、独自計算で補わない。
- 要件トレーサビリティを自己診断する。対象requirementsの全要件IDを抽出し、設計上の対応位置を確認し、feature ごとに結果（抽出件数・未対応ID）を summary へ報告する。未対応IDがあれば feature × セクションの質問として返し、completed にしない。自己診断は別コンテキストでの検査を代替しない。
