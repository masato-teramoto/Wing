# Feature 分割の作成規則

- 承認済み要求一覧とsteeringから、`.aidd/feature-list.md` の固定7列に feature 名／種別／目的／依存／優先度／想定規模／対応要求IDを記入する。
- 対応要求IDの分母は「機能」の要求。非機能／制約はsteeringへ反映し、featureへ割り当てない。要求一覧へ対応featureを書き戻さない。
- 単体で利用者が目的を終えられるならUser、他のfeatureで使われて働く共通機構ならPlatform。運用者・管理者も利用者に含む。画面の有無や先に作る必要性を種別の根拠にしない。
- 例: 監査ログを記録する共通機構は Platform、監査担当が検索して確認を終えられる機能は User。同じ題材でも利用者が用事を終えられる境界で判定する。
- 想定規模が大、または独立した複数目的にまたがる場合は分割案を返し、人間が採否を決める。未回答を採用扱いにしない。
- 依存先を先行させる。依存だけでは順序が決まらない範囲は、product の提供価値・主要ユースケースと要求を根拠に並べる。根拠が無ければ該当 feature 同士を示して質問し、waiting で返す。人間の並べ替えを毎回必須にはしない。
- 依存の逆転を含む順序は禁止する。循環があれば関係する feature と依存辺を示し、依存の見直しを人間に提示するため waiting で返す。辺を推測で削除して優先度を確定しない。
- 名前・数値優先度・依存の区切りはテンプレートの機械入力契約に従う。表順を実行順にする。変更後は再検査・再承認・同期が必要であり、SkillからJSONや下流を更新しない。
- スコープ・完了条件はrequirements、横断方針はsteering、要求文・出典・分類は要求一覧が所有する。これらをfeature-listへ重複定義しない。
- 複雑な依存だけMermaid図を作る。不要な図のスロットは人間が示した不要理由を添えて保持する。新規要求は要求一覧を編集せず、`owner: intake`、`target: .aidd/requirement-list.md` の差戻し候補として返す。
