# SD-0: 画面マップの起草（案件に 1 つ・増分で改訂）

> フロー内の位置・実行順・人間停止点の概要は **入口 skill `aidd-system-design`（配布ワークスペースの `.claude/skills/aidd-system-design/SKILL.md`）が正**。単独で呼ぶときは「単独起動時の前提」を満たすこと。
> **本 SKILL.md が工程内の起草規約と手順の正**（実行規約は本書で自己完結する）。
> 書式の正は雛形 **本 skill の `templates/screen-map.md`**（読み取り専用）。

## 位置づけ（起草規約の前提）

- 画面マップは **案件に 1 つ**。**feature 横断で決めなければ壊れるものだけ**を持つ —
  画面の切り出しと所有 / feature 間遷移 / 入口とシェル / 語彙の出どころ
- **画面の中身（項目・操作・状態・文言）は書かない**（画面設計書 SD-1 の役割）。
  **視覚仕様は書かない**（STYLEGUIDE.md の役割。シェルの様式は STYLEGUIDE.md §4-10）
- **2 段に分ける理由**: feature 横断で決めなければ壊れるもの（同じ画面の別名再発明・所有の重複・
  終端画面から次工程への遷移・ナビの並び・状態名と識別子書式の揺れ）は**すべて切り出しの層**にあり、
  項目・操作・状態・文言は 1 画面の中で閉じる。全 feature の詳細を 1 つの文脈に入れると、
  読み落としが出るうえ、**隣接 feature の操作 UI を足す越境が増える**
- **すべて design 承認の後。** requirements だけで先に切り出す前倒しは置かない
- **確定文書であり、再生成しない。** 増分で行を足し・直す（作り直さない）

## ハード制約

- 【MUST】**画面 ID は `<feature>:S-xx` の修飾形で案件全体に一意。所有 feature は 1 つ**
- 【MUST】**同じ目的の画面は 1 行にまとめる。** 共通画面（操作ログ一覧・権限なし・エラー・お知らせ等）は
  1 行に統合し、所有を 1 つ決める。**feature ごとの別名を許さない**
- 【MUST】**feature 間遷移は 4 つの類型に分けて書く**（→「feature 間遷移の 4 類型」）。
  **「行き先は 1 つまで」の制限が掛かるのは第 3 類型（終端画面から次工程）だけ**である
- 【MUST】**UI を持つ全 feature がナビから到達できる**こと
- 【MUST NOT】**画面の中身（項目・操作・状態・文言）を書く**
- 【MUST NOT】**視覚仕様（色・余白・書体・部品の形）を書く**
- 【MUST NOT】**requirements の中身を根拠に、他 feature の画面を足したり直したりする**
  （足りないと分かった場合は §6-2 の確認事項に記録する）
- 【MUST NOT】**requirements にも steering にも無い業務状態名・識別子書式を本書で決める**
  （§6-2 に記録し、ダミー識別子は汎用の数値のみを既定とする）
- 【MUST NOT】**wireframe 工程の成果物のうち manifest 以外（HTML・CSS・`tokens/`）を読む**
  （見た目の正は STYLEGUIDE.md。DS のクラス・変数名を本工程に持ち込まない — →「wireframe-manifest の使い方」）
- 【MUST NOT】**wireframe-manifest を画面・遷移・ナビ項目の根拠にする**
  （根拠は AC / System Flows / steering。manifest は**種と突合先**であり、「wireframe に在るから」で画面を足さない）
- 【MUST NOT】**作り直す**（増分で行を足す・直す。既存行の `confirmed` を消さない）
- 【MUST NOT】**確定の判断を代行する**（`confirmed` / `status` は開発者の判断。記入は `recorded_by` を残して代筆できる）
- 【MUST NOT】**requirements.md / design.md / steering を書き換える**
- 【MUST】Markdown・表示文言は ja で記述する

## 開始時の宣言（MUST）

- **初回か増分か**（`.aidd/screen-design/_app-shell/screen-map.md` が**在るか**で決まる）
- **対象 feature**: design 承認済み（`design.md` が `status: approved`）で、**UI を持つと宣言済み**の feature。
  増分の場合は**今回足す feature だけ**を挙げ、既存行は据え置くことを宣言する。
  **通過済みの UI feature を全部は取らずに絞った場合は、その理由**
- 入力の所在（各 feature の `requirements.md` / `design.md` / `steering/` / あれば各 feature と `_app-shell` の
  `.aidd/wireframe/<feature>/pages/wireframe-manifest.json` — **その `confirmed_at`** も宣言する。HTML・CSS は読まない）
- 出力先 `.aidd/screen-design/_app-shell/screen-map.md` と雛形の所在（本 skill の `templates/screen-map.md`）
- **STYLEGUIDE.md の版**（§4-10 アプリシェルの様式を参照するだけ。値は写さない）

## 根拠は AC 単位で書く

**§2 の根拠列は「要件被覆の突合先」**である。要件単位（`要件 3`）で書くと、
**その要件の中の一部の受け入れ基準（AC）が落ちても気づけない**。

- 【MUST】**根拠列には AC の番号を書く**（`AC 1.1, 1.2` の形）。要件番号だけを書かない
- 【MUST】**画面側からではなく AC 側から数え上げる。** 対象 feature の**全 AC を列挙し、
  それぞれがどの画面に紐づくかを 1 件ずつ確かめる**（画面側から辿ると、
  **どの画面にも紐づかない AC が残っていることに気づけない**）
- **どの画面にも紐づかない AC が出たら 2 通り**: ① 画面が足りない → 画面を足す
  ② 画面を伴わない AC（バッチ・採番・他工程の呼び出し等）→ **§6-2 に「画面を伴わない AC」として記録する**。
  **黙って落とさない**
- 【MUST】**「画面を伴わない」の判定基準**:
  ① **特定の画面の挙動・状態・見え方を規定する AC は、実装がサーバ側でも根拠列に入れる**
  ② **画面を伴わない = どの画面の設計にも書きようがないもの**（①に当たらないもの）
  ③ **「否定形の AC」（…が表示されないこと）は SD-1 が状態の分母から外す類型**であって、
  **本 skill が画面から外す理由ではない** — 根拠列に入れる
- **1 つの AC が複数画面に跨ってよい**（一覧で選び、確認画面で確定する等）。逆に
  **1 画面が複数 AC を持つのも正常**。**過大に含めない** — 画面で行わない操作の AC を根拠に書かない

## feature 間遷移の 4 類型

**§3 の行は 4 つの類型を持つ。**「行き先は 1 つまで」は第 3 類型にだけ掛かる。
【MUST】**行ごとに「類型」列を書く。**

| 類型 | 形 | 行き先の数 |
|---|---|---|
| **① 入口からの分岐** | 入口（`_app-shell:S-01` か流用元の画面）→ 各 feature の最初の画面 | **1 → N**（UI を持つ feature の数。§4 のナビ項目と 1 対 1） |
| **② 参照のための往復** | 一覧・詳細から他 feature の画面を参照 → 元の画面へ復帰 | **往路 1 + 復路 1**（対で書く） |
| **③ 終端画面から次工程** | 終端画面（完了・通知等）→ 業務プロセス上の次の行き先 | **1 つまで**（複数並べない） |
| **④ 全画面からの遷移** | 全画面（または全業務画面）→ 1 画面。入口へ戻る / 1 つ前へ戻る / 共通のシステムエラー画面へ | **N → 1**（**1 案件で先ごとに 1 行**） |

- **④ が持つのは業務の動線ではなく、シェルの導線と共通画面の inbound である。** 遷移元は「全画面」と書き、
  **入口画面自身は自己参照しないので除く**（入口へ戻るリンクは入口画面では無効表示）。
  **共通画面の inbound は「全画面（§3 ④）」と書く**。
  **「1 つ前へ戻る」の行き先は状態で変わりうる** — 本書は先を 1 つ決めて条件を備考に書き、
  画面設計書 §2 の遷移表は**遷移元を `S-xx（状態）` で書ける**
- **「1 つまで」は ④ に掛からない**（④ は N → 1 が正常）。**④ の行き先が案件に無い場合は「なし（無効表示）」**と書く
- **§1 の出口列が指すのは ③ だけ。** ①②④ は出口ではないので、**出口が「なし」でも §3 に行があるのは正常**
- **① も §3 に書く。** 入口画面の本体の導線から各 feature への遷移は **feature をまたぐ**。
  **§4 は全ページに載るシェルのナビ**（並び・グルーピング・可視ロールの正）、**§3 は入口という 1 画面からの遷移**
  （動線の正・mockup がリンクを張る根拠）。**重複ではないのでどちらかを消さない。**
  ① の行の根拠列には **§4-2 のナビ項目番号**を書く
- **遷移先が「同一画面の別状態」の場合**（参照専用で開く・ReadOnly で開く等）は
  **遷移先列は画面 ID のまま**にし（状態を書くのは MUST NOT）、**状態は備考に書く**

## マスタ参照項目の表示形式

**同じマスタを参照する同じ項目が feature ごとに別の形になる。**
**画面設計書は feature 単位なので、feature をまたぐ項目の形は本書でしか揃えられない。**

【MUST】**§5 に「マスタ参照項目の表示形式」の行を持つ。**

| 参照項目 | 何を見せるか | 何を裏に持つか | 出どころ |
|---|---|---|---|
| {{利用者}} | {{社員番号 + 氏名}} | {{利用者 ID}} | {{design.md の該当契約 / steering の節}} |

- **「何を見せるか」は利用者が読む形、「何を裏に持つか」は画面が保持する識別子**
- **選び方の UI（直接入力か・選択ダイアログか）を本書で決めない**（画面設計書の役割）。
  本書が揃えるのは**見せる値と裏に持つ値**だけである
- **出どころが design.md に無い場合**（画面からマスタを引く契約が無い等）は
  **§6-2 に確認事項として記録し、本書で形を決めない**

## wireframe-manifest の使い方（wireframe 工程を実施した案件のみ）

wireframe 工程（要件定義工程のワイヤーフレーム）は **DS を正にして描かれ、顧客が型・構成・情報量を確認している**。
本工程は見た目の正を STYLEGUIDE.md に置くので、**wireframe の見た目を持ち込まない**。
持ち込むのは manifest の**語彙と記録**だけである。

- 【MUST】**読むのは `wireframe-manifest.json` だけ**（各 feature の `pages/` と `_app-shell/pages/`）。
  **HTML・CSS・`tokens/` を読まない**（DS のクラス・変数名が本工程に流れ込む）
- 【MUST】**使い方は 2 つ — 種と突合先。根拠にしない。** 画面・遷移・ナビ項目の根拠は AC / System Flows / steering のまま。
  **「wireframe に在るから」で画面を足さない。** 突合は**切り出しの後**に行う（先に読むと wireframe が根拠になる）
- **wireframe は design 承認前の産物である。** `notes` の判断は要件定義時点のもので、design.md と食い違えば **design.md が正**
- **翻訳は近似で当てない。** 対応が無いものは無いと書き、§6-2 か §6-5 に落とす
- **manifest には表示文言・画面名・項目の並びが無い**（`screen` は英字の slug）。これらは従来どおり steering / requirements / design.md から起こす

### フィールド別の使い方

| フィールド | 使い方 | 書く先 |
|---|---|---|
| `screens[].screen` | **突合先。** 切り出した §2 と突き合わせ、wireframe に在って §2 に無い画面を洗う。画面名・ID は流用しない | §6-5 |
| `screens[].pattern` | **種。** 下の翻訳表で画面の型に写す | §2 の型 |
| `screens[].requirements` | **突合先。** Requirement 単位なので AC 単位の根拠列には写せない。wireframe が画面に当てた Requirement が §2 に 1 行も無ければ欠落の疑い | §6-5 の備考 |
| `screens[].notes` | **種。** 隣接 feature のデータの読み取り専用参照（所有・共有の判断材料）/ 設けなかった要素と理由 / 被覆の分母から外した要件 | §6-1・§6-2 |
| `_app-shell` の `screens[].notes` | **種。** ナビの並び順・グルーピングと、根拠にした steering の節。**形（ヘッダのナビか・メニュー画面か・パンくずの有無）はもらわない**（STYLEGUIDE.md §4-10 が正） | §4 の根拠列 |
| `confirmed_at` / `ds_version` | **記録。** 顧客が構成を確認した時点の印 | frontmatter `inputs` / §6-4 |
| `states` / `components` / `missing[]` / `unrealized[]` / `acknowledged` | SD-1 が使う（本 skill は読み飛ばす） | — |
| `token_profile` / `audit` / `wireframe_notice` | 使わない | — |

### 翻訳表 — DS のパターン → 画面の型

| DS パターン（`screens[].pattern`） | 画面の型 | 注意 |
|---|---|---|
| `list-page` / `inbox` | 一覧 | inbox の行選択・一括操作は画面ではなく SD-1 の状態・操作 |
| `detail-page` / `approval` | 詳細 | approval の承認・差戻しは SD-1 の操作 |
| `form-page` | フォーム | 登録・編集の variant は同じ型 |
| `confirm-flow` | フォーム → 確認 → 完了（**3 画面**） | wireframe は通常 3 つの `screens[]` に分けて記録している。1 つに畳まれていれば 3 行に開く |
| `error-page` | システムエラー（500）/ 権限なし（403） | **404 とメンテナンスは型に無い** → §6-2 に記録（近い型で仮置きしない） |
| `app-shell` | 入口（ポータル） | `_app-shell` の manifest に現れる。入口の形（流用 / 新設）は手順 4 で決める |
| `login` | **型に無い** | 本工程の「入口」はメニュー画面を指し、ログイン画面ではない → §6-2 に記録 |
| `report` | **画面にしない** | 印刷ビューは親画面の状態（手順 1A-3） |
| 表に無いパターン | — | §6-2 に記録。近似で当てない |

### 突合の記録（§6-5）

wireframe の `screens[]` を 1 行ずつ、**`<feature>:S-xx に対応` / `状態にした（親 <feature>:S-xx）` / `画面にしない（理由）`**
のどれかに落とす。【MUST】**全行がどれかに落ちること**（黙って落とさない）。
対応する画面の根拠は §2 の根拠列にあり、§6-5 は根拠ではない。

## 記入規約

- **画面 ID は `<feature>:S-xx` の修飾形で案件全体に一意。所有 feature は 1 つ。**
  同じ目的の画面が複数 feature の requirements に現れたら 1 行にまとめ、所有を決める（優先順は手順 2）。
  判断は §6-1 に記録する
- **共通画面（操作ログ一覧・権限なし・エラー・お知らせ等）は 1 行に統合し、所有を 1 つ決める。**
  feature ごとの別名を許さない。使う feature は「使う feature」列に列挙する
- **feature 間遷移は 4 類型に分け、行ごとに類型を書く**（→「feature 間遷移の 4 類型」）。
  **「1 つまで」は ③ 終端画面から次工程にだけ掛かる。**
  根拠は steering の状態遷移・ユースケース。**requirements の中身を根拠に他 feature の画面を足したり直したりしない**
- **入口とナビ**: 並び順・グルーピングは steering `product.md` の**ロールと業務プロセスの前後関係**から導き、
  どの節から導いたかを書く。機能名を根拠なく並列に並べない。**UI を持つ全 feature がナビから到達できる**こと。
  **パンくずと現在地は「何を何段で並べるか」だけを書く**（例: `入口の表示文言 → ナビ項目 → 画面名` の 3 段）。
  **区切り記号・書体・色は書かない**（様式の正は STYLEGUIDE.md §4-10）。
  **パンくずを持たない案件では「持たない」と書き、現在地の示し方を同じ表に書く**
- **ナビ項目と入口の表示文言は「利用者が画面で読む名前」を書く。** 工程の語彙（「入口」等）を
  そのまま表示文言にしない。**画面名も同じ**（入口画面の画面名は §4 の表で持つ —
  入口の表示文言と同語でよいが、別の値にもできる）
- **語彙**: 業務状態名・ロール名・共有識別子の書式、および**マスタ参照項目の表示形式**は
  steering の節を出どころに書く（→「マスタ参照項目の表示形式」）。無ければ
  「steering への確認事項」に記録し、**requirements にも steering にも無い書式を画面マップで決めない**
  （ダミー識別子は汎用の数値のみ）。**`【人】の決着（日付・場）` は、mockup の目視後などに
  案件の中で人が決めたものの出どころとして書ける**（**エージェントが決めるのではない**）
- **視覚仕様を書かない。** シェルの様式は STYLEGUIDE.md §4-10
- **wireframe-manifest は種と突合先**（→「wireframe-manifest の使い方」）。**根拠列・出どころ列に wireframe を書かない**。
  突合の結果は §6-5 に書く
- **§1 の `mockup` 列**: `作る` / `省く（理由）` を feature ごとに書く（UI を持たない feature は `—`）。
  **エージェントが省略を判断しない** — 宣言が無ければ `作る` と書く

## タイミングと増分（すべて design 承認の後）

- **初回は、その時点で design 承認を通過している UI feature をまとめて切り出す。**
  行の確定は所有 feature 単位（frontmatter `features[]` の `confirmed`）。
  **SD-1 は自 feature の行が `confirmed` になってから始める**
- **後から design 承認を通過した feature は行を足し、差分だけ確認する**（作り直さない）。
  所有の移動・遷移の追加・ナビ項目の追加・「使う feature」列の更新も同じ（改訂の記録を §6-3 に残す）。
  改訂の影響を受ける feature の**画面設計書は該当箇所を直し、mockup は再生成する**。
  **ナビ項目が増えた場合は他 feature の mockup も再生成する**
- **改訂者は案件で 1 人**（STYLEGUIDE.md の改訂者と同じ。既定は開発リード）

## ガードレール

- 【MUST NOT】**画面の中身を書く**（項目・操作・状態・文言は画面設計書。ここは切り出しと繋ぎだけ）
- 【MUST NOT】**同じ目的の画面を feature ごとに別名で置く**（1 行に統合して所有を 1 つ決める）
- 【MUST NOT】**③ 終端画面から複数の行き先を並べる**（業務プロセス上の次を 1 つ）。
  **①②④ にこの制限を掛けない**（① は 1 → N、② は往復 2 本、④ は N → 1 が正常）
- 【MUST NOT】**④ の遷移元に入口画面自身を含める**（入口へ戻るリンクは入口画面では無効表示）
- 【MUST NOT】**requirements にも steering にも無い書式・採番規則を決める**（確認事項へ）
- 【MUST NOT】**どの画面にも紐づかない AC を黙って落とす**（画面を足すか §6-2 に記録する）
- 【MUST NOT】**既存の確定行を作り直す・`confirmed` を消す**（増分で足す・直す）
- 【MUST NOT】**シェルの様式を書く**（正は STYLEGUIDE.md §4-10。ここはナビ項目・並び・現在地の対象だけ）。
  **パンくずの区切り記号を書かない** — 書くと STYLEGUIDE.md と食い違ったまま両方が正になる（実測）
- 【MUST NOT】**工程の語彙をそのまま表示文言・画面名にする**（「入口」は工程の語彙）
- 【MUST NOT】**wireframe の HTML・CSS を読む / wireframe を根拠に画面・ナビ項目を足す**
  （manifest は種と突合先。→「wireframe-manifest の使い方」）
- 【MUST】**mockup 未生成 feature のナビ項目も §4 に載せる**（リンク先が無いことは mockup 側が記録する）

## 完了後

- **確認と確定は開発者**（差分の数え上げ — 上の 6 項目）。skill は代行しない。
  確定は**行単位**（frontmatter `features[]` の `confirmed`）で、`status` を `confirmed` にするのも開発者
- **`confirmed` は `by` / `at` / `recorded_by` の 3 つ**。`by` = 判断した人、
  `recorded_by` = 記入した主体（人が直接書けば `by` と同じ。エージェントが代筆したら skill 名）。
  **判断は代行しない。記入だけを代筆できる**（シェルだけの改訂は §6-3 の行の `confirmed` に同じ形で書く）
- **自 feature の行が `confirmed` になってから SD-1（`screen-spec-authoring`）を始める**
- 増分で**ナビ項目が増えた**場合は、**既存 feature の mockup も再生成する**
  （本文の入力は不変なので目視はシェルだけでよい）
