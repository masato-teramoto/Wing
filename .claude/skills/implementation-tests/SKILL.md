## 手順

profileが`implementation-task-review-v1`・`implementation-task-reverify-v1`の場合は、task-implement-checkの対象・返却契約を使う。
当該タスクの完了条件、実テストと適用されるRED/GREEN/VERIFYを照合する。非コードでtdd=falseなら専用VERIFYを評価し、RED/GREENや単体テストを一律に要求しない。feature最終のtool_results_path/report_summaryは要求しない。最終レポートの不存在をタスク欠陥にしない。
以下のfeature向け手順のうち全タスク・最終レポートを要求する部分は適用せず、実コードで判断する観点は共用する。


implement-checkの「今回の開発補助レポーティングの扱い」を適用する。
各タスクの観測可能な完了条件と実テストのassertion・入力・依存代替を読む。
形だけの成功、重要経路の未検証、REDが環境エラーであること、承認済みのcoverage等の基準不足を指摘する。
task実績とfeature最終のtool_results_pathを区別し、全体検査が現在のコードを対象にしているか確認する。
report_summaryから仕様・OSSのケース別結果・coverageを読み、実テスト・収集設定と照合する。
task-specificationで生成した単体テスト仕様書は、実テストの内容を人へ説明する確認資料として読む。
この生成仕様書の文章品質・表現の独立レビューは追加しない。実際の入力・assertion・依存代替は
引き続き実コードで検査し、資料があることだけをテスト品質の証明にしない。
MCPの実結果はrequest.mcpから確認する。ACEの結果だけで本観点の実ファイル確認を省略しない。
対象要求または技術的な検証理由、実際の対象範囲・除外・未カバー箇所を確認する。
表示名だけで入力型や期待値を判断せず、実テストを確認する。別スイートの成功を読み替えない。
境界値は名前だけで判断せず、実入力を計算して既存ケースとの同値性を確認する。
複数の境界を同時に満たす例も有効であり、分離した例の追加提案を必須ケース欠落と混同しない。
契約にある期待値・例外理由・エラーコードを実テストで検証しているか確認する。
coverage 100%だけでは期待値の検証済みとしない。
複数違反の優先順やメッセージの完全一致は、仕様にない限り検査要件として追加しない。
タスクとテストスイートを1対1に対応させず、既存のテスト生成物の用途や粒度を維持する。
同じ用途のケースを報告用に複製している場合、参照元との差異・欠落を確認する。
機械検査は実ケースの十分性や未ロードソースを含むcoverage範囲までは保証しない。
選択した内部品質指標はツール固有の定義・粒度・制約で読む。未対応を0で埋めない。
準備タスクでは、既存環境の利用確認と、新規環境を作れることの証跡を区別する。
新規作成も提供する契約なら専用の新規配置先での実績を確認し、手動復旧後のcheck成功だけで代用しない。
「既知の制約 / 残課題」の判断待ちと決定ログの解決が矛盾していないか、後続の解消記録を含めて読む。
コマンド成功を業務的正しさと同一視しない。gate=implementation-testsとして返す。指摘ごとに location（実ファイルと箇所）・subject・kind・summary（60 字以内）・evidence（根拠と実ファイル箇所）・suggestion・recommendation・is_rollback_candidate を返す。書き方と kind は `.claude/skills/finding-rules/SKILL.md` に従い、重大度は出さない。
不足する検証をその場で追加実行・コード修正せず、指摘としてホストへ返す。

## この工程で指摘しない事項

- `.claude/skills/finding-rules/SKILL.md` の工程の境界の表・`confirmed_answers`・`learned` に当たる事項
- `TBD（<工程> で確定）` と書いてある値
- 仕様にない複数違反の優先順・メッセージの完全一致

当たるものは指摘にせず、除外として返す（除外の出典を付ける。書き方は finding-rules）。
