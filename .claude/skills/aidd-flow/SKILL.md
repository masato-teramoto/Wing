# AIDD Spec 生成フロー オーケストレータ（リリース α2: Phase 1〜5）

RFP を入力に、`steering/` → `feature-list.md` → `requirements.md` → **画面モック（ワイヤーフレーム）** を順に確定させる。本 Skill は **どのフェーズを・どの単位で・どの順に実行するか**を決め、実作業は各フェーズ固有 Skill、検査は各ゲートのサブエージェントに委ねる。

> 出典: フロー設計 `00_全体フロー設計書.md`（横断ルール）および `01`〜`04`（各フェーズ）。本 Skill 群は設計の写しではなく実行手順である。設計との齟齬を見つけた場合は **設計側を正**として扱い、人間に報告する。

---

## 0. 本リリースのスコープは Phase 5 までである

**Phase 6（design 作成）以降は本リリースに含まれない。** 該当する作成 Skill もゲートのサブエージェントも配置されていない。

- **Phase 5 の完了がフローの終端である。** 全対象 feature の `wireframe-manifest.json` が `approved` になり、横断スコープのゲートの ③ が済んだ時点で、**次フェーズへ進もうとせず** §7 の終端処理を実行して停止する。
- **`design.md` / `tasks.md` / `docs/` を作らない。** 依頼された場合は、本リリースの対象外であることを伝えて停止する。**存在しない Skill やサブエージェントを代替で自作してはならない。**
- 上流成果物に「後続フェーズで扱う」と書かれた事項（業務コード・エンティティの**実体**設計など）は、**そのまま残す。** 本リリースは実体設計を行わない。

### フェーズ番号の繰り下げ（α2 で変更した点）

**Phase 5 に画面モック生成を挿入したため、design 以降のフェーズ番号が 1 つ繰り下がっている。**

| 旧番号（α1 まで） | 新番号（α2 以降） | フェーズ |
|---|---|---|
| — | **5** | **画面モック生成（ワイヤーフレーム）** ← 新設 |
| 5 | 6 | design 作成 |
| 6 | 7 | docs 作成 |
| 7 | 8 | tasks 作成 |

- **α1 の期間に作られた成果物・ゲート記録には旧番号が残っている。** それらは当時の判断の記録であり、**書き換えない**（ゲート記録は追記のみ／`approved` 成果物の本文は書き換えない）。旧番号の記述に出会った場合は本表で読み替える。
- `docs/` を「Phase 5 以降で作成」と書いている `approved` 成果物の記述は、繰り下げ後も真である（`docs/` は Phase 7）。**差戻しの対象にしない。**

## 1. 一気通貫の意味（最初に読む）

本フローは **全自動では完走しない。** 次の 3 点は仕様であり、回避してはならない。

1. **`review` → `approved` は人間のみ**が行う。エージェントが自ら承認してはならない。
2. **ゲートは合否を出さない。** ① / ② は指摘を列挙してゲート記録へ出力するだけで、進行の可否は ③ 人間レビューが決める。
3. **自動修正・自動ループを行わない。** 「指摘がゼロになるまで繰り返す」ことはしない。

したがって本 Skill の役割は「**人間が判断するたびに、次にやるべきことを迷いなく続行できる状態を保つ**」ことである。停止点は次の 2 つであり、これ以外に停止点を設けない。

| 停止点 | いつ | 提示するもの |
|---|---|---|
| **フェーズ開始**（Step 0） | Phase 2〜5 に新しく入る直前 | 当該フェーズの実行計画 |
| **③ 人間レビュー**（Step 4） | ① / ② が終わり `review` へ遷移した時点 | ゲートの指摘と差戻し先の候補 |

**Phase 5 の未画面化要件の承認（`wireframe-manifest.json` の `acknowledged` 記入）を独立した停止点にしない。** ③ 人間レビューの場で `status` の承認とあわせて行う。承認の主体と判断材料が同じであり、停止点を分けると同じ材料で 2 回止まることになる。

## 2. 実行前提

- `.claude/`（本 Skill 群とサブエージェント）と `Templates/` が **出力ルートに配置**されている。
- パスは必ず [references/paths.md](references/paths.md) から引く。**推測でパスを組み立てない。**
- status 遷移・差戻し・`phase-progress.json` の操作は必ず [references/status-protocol.md](references/status-protocol.md) に従う。
- テンプレート構造の正は **実行時に読む `Templates/`** である。

**Phase 5 のみ追加の実行環境要件を持つ**（Phase 1〜4 には不要）。満たされていない場合は Phase 5 を開始せず人間へ提示して停止する（§7 手順 0）。

| 要件 | 内容 |
|---|---|
| **Node.js** | 監査（`audit-tokens` / `audit-components`）・トークン一致検査・動線チェックの実行に必要 |
| **デザインシステム（DS）** | 版（タグ）を固定して `ds/` に取得済みであること。**版の指定は人間が行う**（§7 手順 0） |

## 3. 起動手順

1. [references/paths.md](references/paths.md) と [references/status-protocol.md](references/status-protocol.md) を読む。
2. `.aidd/phase-progress.json` を読む。
   - 存在しない場合は `Templates/Flow/phase-progress.json` を雛形に作成し、**Phase 1〜5 を** `not_started` で初期化する（Phase 6 以降のエントリは作らない）。
3. **再開点を判定する。** `phase-progress.json` は派生物なので、判定は実ファイルの `status` を読んで確定させる。齟齬があればドキュメント側を正として `phase-progress.json` を再生成する。
   - Phase 1〜4 の `status` の所在は各ドキュメントの**フロントマター**である。
   - **Phase 5 の `status` の所在は `.aidd/wireframe/<feature>/pages/wireframe-manifest.json` のトップレベル `status`** である（Markdown ではないためフロントマターを持たない。`references/status-protocol.md` §1）。
4. `blockers` に未解消のエントリがあれば、**新しいフェーズに進まず**その解消を先に人間へ提示する。
5. 再開点のフェーズを §5 の共通ループで実行する。

### 再開点の決め方

| `phase-progress.json` の状態 | 次の行動 |
|---|---|
| 上流フェーズが `approved` 未満 | **そのフェーズを実行する**（下流に進まない） |
| 当該フェーズが `not_started` かつ `waiting_for: human_go_ahead` | フェーズ開始の実行計画を再提示して停止（Step 0 待ち） |
| 当該フェーズが `not_started` | **Step 0 から実行する**（Phase 1 は Step 0 を持たないため Step 1 から） |
| 当該フェーズが `draft` かつ `waiting_for: human_answer` | 未回答の質問を人間へ再提示して停止 |
| 当該フェーズが `draft` かつ `waiting_for: agent_work` | 作成を継続（Step 0 は済んでいるため繰り返さない） |
| 当該フェーズが `review` | ゲート記録の指摘を人間へ提示して停止（③ 待ち） |
| 当該フェーズが `approved` | 次フェーズへ。**Phase 4 の横断スコープまで済んでいる場合は Phase 5 へ**（Step 0 から）。**Phase 5 の横断スコープまで済んでいる場合は §7 の終端処理へ**（Phase 6 へ進まない） |
| Phase 5 で **DS（`ds/`）が未取得**、または版（タグ）が宣言されていない | 生成に入らず、**DS の取得を人間へ提示して停止**（§7 手順 0）。版を推測で決めない |
| Phase 5 で **`unrealized[]` があり `acknowledged` が未記入** | 当該 manifest の `status` を見る。`review` なら ③ 待ち（承認と同じ停止点で記入する）。`approved` であれば記入漏れなので**その事実を人間へ提示して停止**する |

## 4. フェーズと担当の対応

| Phase | フェーズ | 生成単位 | 作成 Skill | ゲートのサブエージェント | ゲート記録 |
|---|---|---|---|---|---|
| 1 | 要求受入 | 一括 | `requirement-intake` | `intake-check-subagent` | `.aidd/gates/phase-1-intake.md` |
| 2 | Steering 作成 | 一括（依存順） | `steering-authoring` | `steering-check-subagent` | `.aidd/gates/phase-2-steering.md` |
| 3 | Feature 分割 | 一括 | `feature-decomposition` | `feature-check-subagent` | `.aidd/gates/phase-3-feature.md` |
| 4 | requirements 作成 | **1 feature ずつ**（優先度順） | `requirements-authoring` | `requirements-check-subagent` | `.aidd/gates/phase-4-requirements.md` |
| 5 | 画面モック生成（ワイヤーフレーム） | **1 feature ずつ**（優先度順・**UI を持つ feature のみ**）＋ 複数 feature なら結合 | `wireframe-authoring` / `wireframe-integration` | `wireframe-check-subagent` | `.aidd/gates/phase-5-wireframe.md` |

作成 Skill は `.claude/skills/<Skill 名>/SKILL.md` を **Read して手順に従う**（自動発火に依存しない）。

**この 5 行が本リリースの全てである。** 表に無いフェーズは実行しない（§0）。

**Phase 5 の 2 つの作成 Skill は外部パッケージ由来の配布物である。** 工程内部の生成規約（DS の参照順序・監査の運用・要件 ID の紐づけ・未画面化申告・位置づけ注記）の正は各 `SKILL.md` にあり、**本 Skill はフロー制御（位置・実行順・停止点・進行状態の判定）のみを持つ**。両者が食い違う場合は、生成規約は各 `SKILL.md`、フロー制御は本 Skill を正として扱い、食い違いを人間に報告する。

**両 `SKILL.md` は α2 より前のフェーズ番号で書かれている。** 本フローへの組み込み前に作られた配布物であり、**書き換えない**（§9）。読むときは §0 の対応表で読み替える。

| 両 `SKILL.md` の表記 | 本フローでの意味 |
|---|---|
| 「requirements 承認後（**Phase 4** ゲート通過後）」 | そのまま Phase 4（変わらない） |
| 「**design（Phase 5）**着手前」「後工程（**Phase 5** design-authoring）へ引き継がれる」「反映先は **Phase 5** design-authoring」 | **design = Phase 6**。ワイヤーフレーム自体が Phase 5 である |
| 「ワイヤーフレーム工程」「MK1」「結合段」 | **Phase 5**（本フローのフェーズ名は「画面モック生成」） |
| 「開発者の承認を得てから**次フェーズへ**進む」 | Phase 5 の **③ 人間レビュー**での承認を指す（§1・Step 5） |

## 5. フェーズ実行の共通ループ

どのフェーズも次の 7 ステップで実行する。**Step 0 はフェーズに新しく入るときに 1 回だけ**実行し、Phase 4 / 5 のような feature ごとのループでは繰り返さない。フェーズ固有の差異は §6 に示す。

### Step 0: フェーズ開始の実行計画を提示して停止する

Phase 2〜5 に **新しく入るとき**に実行する。**Phase 1 では行わない**（人間が起動した直後であり、計画が起動指示と重複する）。中断後の再開時は §3 の再開点の提示がこれを兼ねる。

次の文面で提示して停止する。**見出しと項目の順序を変えない。該当しない項目は省略せず「該当なし」と書く**（省略すると提示漏れと区別できない）。

```markdown
**Phase <N>（<フェーズ名>）に入ります。** 開始前に実行計画を確認してください。

**生成単位**: <§4 の「生成単位」列。あわせてゲートを feature ごとに通すか、全 feature 揃えてから一括で通すかを書く>

**対象 feature と順序**（`.aidd/feature-list.md` の優先度順）
1. `<feature 名>`（<種別> / 依存: <依存先 feature 名。無ければ「なし」>）
2. ...

**対象外とする feature とその理由**（Phase 5 のみ。他フェーズは項目自体を出さない）
- `<feature 名>`: <UI を持たないと判断した理由。判断の根拠にした requirements の箇所>

**使用するデザインシステム**（Phase 5 のみ。他フェーズは項目自体を出さない）
- 所在: `ds/` / 版（タグ）: <人間が指定したタグ。未指定なら「**未指定 — 指定してください**」> / 短縮 SHA: <取得済みの場合のみ>
- トークンのプロファイル: <wireframe / project / base>

**入力として読むもの**（すべて `approved`）
- <`references/paths.md` §6 の当該フェーズの行を列挙する>

**出力先**: <`references/paths.md` §2・§3 のパス。作成するファイル数も書く>

**想定される停止回数**: <Phase 4 / 5 は「feature 数 + 1 回」、それ以外は「1 回」>。作成中に根拠が足りない箇所があれば、その都度質問して停止する。

この計画で進めてよいか指示してください。
```

- **対象 feature と順序** を列挙するのは Phase 4 / 5 のみ。Phase 2 / 3 は「該当なし（feature 単位ではない）」と書く。
- Phase 4 / 5 では最後の 1 行に次を続ける。「**対象 feature や順序を変える場合は `.aidd/feature-list.md` の変更になるため、Phase 3 への差戻しとして扱います。**」
- **Phase 5 では「対象外とする feature」を必ず提示する。** UI を持たない feature を対象から外すこと自体は正しいが、**黙って除外してはならない**。除外が 0 件の場合も「なし」と書く。除外の判断は本 Skill が下書きし、**確定は人間が行う**。
- **Phase 5 で DS の版（タグ）が人間から指定されていない場合は、計画にタグを埋めずに提示して停止する。** 版を推測で決めてはならない（§7 手順 0）。
- **Skill 名・サブエージェント名を文面に出さない。** 人間が判断に使う情報ではない。

あわせて次を守る。

- `phase-progress.json` の `current.waiting_for` を `human_go_ahead` にする。**`status` は動かさない**（対象成果物がまだ存在しない）。
- **計画が了承されたら `current.waiting_for` を `agent_work` に戻してから Step 1 に入る。** `human_go_ahead` のまま作業を始めると、Step 1 や Step 2 で停止したときに §3 の再開判定が実行計画を再提示し、**本来提示すべき停止理由（上流が未承認・未回答の質問がある）が隠れる**。
- **「開始してよいですか」だけを問わない。** 上記を提示せずに可否だけを尋ねてはならない。この停止は許可を得るためではなく、成果物が量産される前に人間が範囲と順序を修正できるようにするためにある。
- **対象 feature と順序の変更指示が出た場合は `.aidd/feature-list.md` への変更を伴うため、Phase 3 への差戻しとして扱う**（`references/status-protocol.md` §3）。このフェーズで `feature-list.md` を書き換えてはならない。優先度は依存の必須先行を満たす順序であり、崩すと依存先が未確定のまま設計することになる。
- 作業を分割して進める指示（今回は上位 N 件だけ作る等）は計画に反映してよいが、**フェーズの完了条件は全 feature の完了である**ことを変えない。

### Step 1: 上流の前提を確認する

- そのフェーズの Input（`references/paths.md` §6）がすべて `status: approved` か確認する。
- **1 つでも `approved` でなければ、フェーズを開始せず**その旨を人間に報告して停止する。

### Step 2: 作成 Skill を実行する

- 該当フェーズの作成 Skill（§4）を Read し、**その手順に従って実行する**。何をどう作るかの判断は作成 Skill が持つ。オーケストレータの担当は **どのフェーズのどの Skill を、どの単位で呼ぶか**を決めることである。
- 作成 Skill は成果物の作成に続けて **自フェーズのゲートを起動し**（Step 3 の制約に従う）、指摘の要約を返すところまでを行う。
- テンプレートをコピーして埋める形で作成する。フロントマターはテンプレートが持つものをそのまま使い、`status` は `draft` のまま、`{{...}}` 系統のプレースホルダー（更新日時・feature 名・フェーズ名など）を上流成果物と実時刻から機械的に埋める（`references/status-protocol.md` §7）。
- **根拠のない値を書かない。** 要求一覧・上流成果物に根拠が無い、または判断に迷う箇所は **推測で補完せず質問して停止**する（`waiting_for: human_answer`）。この場合は Step 3 へ進まない。

### Step 3: ゲート起動の制約（起動するのは作成 Skill）

**ゲートの起動は作成 Skill の手順に含まれる。オーケストレータがここで別に起動してはならない**（同じスコープのゲートが二重に走り、ゲート記録・フロントマター・`phase-progress.json` を競合して書く）。オーケストレータは次の制約が守られたことを確認し、守られていなければ人間に報告して停止する。

- **別コンテキストで起動されているか。** Task ツールでサブエージェントとして起動する。**作成側と同一コンテキストで検査してはならない**（自己採点の回避）。
- **1 件ずつ起動されているか。並列に起動してはならない。** サブエージェントは対象成果物のフロントマターと `phase-progress.json` を書くため、同時に走らせると同じ箇所を競合して書く。複数 feature・複数スコープを検査する場合も順に起動し、前の 1 件が書き終えてから次を起動する。
- **渡した入力が次の 3 つに限られているか。作成時の中間結果・判断根拠を渡してはならない。**
  - 検査対象の成果物のパス
  - 上流の `approved` 成果物のパス
  - スコープ（成果物単位 / 横断）と、当該スコープで何回目のゲートか
- サブエージェントは指摘をゲート記録へ追記し、対象成果物を `draft` → `review` へ遷移させる。**遷移が起きていなければゲートは完了していない。** その場合は Step 4 へ進まない。

#### Phase 5 のみの例外: ゲートを起動するのはオーケストレータである

**Phase 5 の 2 つの作成 Skill は外部パッケージ由来の配布物であり、ゲート起動の手順を持たない**（§4）。したがって Phase 5 では **オーケストレータがゲートを起動する**。二重起動の恐れが無いのは、作成 Skill 側が一切起動しないためである。

- **配布物である 2 つの `SKILL.md` にゲート起動の手順を書き足してはならない。** パッケージが更新されたときに追記が失われ、更新のたびに差分を手当てすることになる。フロー制御は本 Skill 側に置く。
- 起動時に渡すのは、上記 3 つに加えて次のみとする。**いずれも実行条件であり、作成側の中間結果・判断根拠ではない。**
  - **DS の所在と版**（タグ + 短縮 SHA）と**トークンのプロファイル** — 監査・一致検査の再実行に必要
  - **対象外とした feature の一覧と理由** — **Step 0 で人間が確定した宣言**を渡す。作成 Skill の報告を渡してはならない（宣言なき除外の検出が自己申告になる）
- 起動の単位は Phase 4 と同じである。**1 feature の生成が終わるたびに feature スコープで 1 件、（複数 feature の案件では）結合段の完了後に横断スコープで 1 件**を、**順に**起動する。

### Step 4: ③ 人間レビューへ提示して停止する

- ゲート記録の当該実行分の指摘を人間へ提示する。
- あわせて **ゲートが挙げた差戻し先の候補**を提示する。ただし **差戻すかどうかを自分で決めてはならない。**
- ここで **必ず停止する。** 人間の指示を待つ。

### Step 5: 人間の判断を実行する

| 人間の判断 | 行うこと |
|---|---|
| **修正（同一フェーズ）** | 対象成果物を `review` → `draft` に戻し、Step 2 の作成 Skill を該当工程から再実行する（再ゲートも作成 Skill が行う）。**指摘を根拠に勝手に本文を書き換えない**（何をどう直すかは人間の指示に従う） |
| **差戻し（上流）** | `status-protocol.md` §3 の表に従って上流の status を引き下げ、`blockers` に追記し、上流フェーズへ移る |
| **対応せず進める** | ゲート記録の `判断` 欄に人間の記入内容（理由必須）を転記する |
| **承認** | 人間から承認者名を受け取り、対象成果物を `status: approved` にする。**承認者名・承認日はフロントマターではなくゲート記録の `## 承認` へ記入する。** そのうえで次フェーズへ（**Step 0 から**）。**Phase 5 の横断スコープまで済んでいる場合は §7 の終端処理へ** |

**Phase 5 の承認では、`status` の更新と同時に次を行う**（③ の停止点で完結させ、停止点を増やさない）。

- 当該 feature の `unrealized[]` が空配列でない場合、**人間から受け取った承認内容を `acknowledged` の `by` / `at` / `decision` へ転記する**。**内容を代筆・補完してはならない**（記入するのは人間の判断であり、転記だけを代行する）。`unrealized[]` が空配列 `[]` の feature では記入せず、未記入のまま次へ進む。
- `unrealized[]` があるのに承認内容を受け取っていない場合は、**`approved` にせず**その旨を人間へ返して停止する。
- **`confirmed_at` には触れない。** MK2（顧客確認）の実施後に人間が記入する欄である。

### Step 6: 進捗を更新する

- `.aidd/phase-progress.json` を `status-protocol.md` §5 の手順で更新する。
- 次に人間がすべきことを 1 行で伝える。

## 6. フェーズ固有のゲート単位と停止回数

**作成とゲート起動の手順は各作成 Skill が持つ**（Phase 5 のみ起動はオーケストレータ — Step 3 の例外）。ここには Step 0 の計画提示・停止管理・再開点判定に必要な情報だけを置く。

| Phase | ゲートのスコープと回数 | ③ の停止回数 | 進行上の注意 |
|---|---|---|---|
| 1 | 一括 1 回 | 1 | — |
| 2 | 一括 1 回（7ファイルを 1 スコープで検査） | 1 | — |
| 3 | 一括 1 回 | 1 | — |
| 4 | **feature ごとに 1 回** ＋ 全 feature が `approved` になった後に **横断 1 回** | **feature 数 + 1** | feature ごとに `approved` まで通してから次へ進む（伝播を止めるため）。横断は承認対象の文書を持たないため **status を遷移させない**。引き下げが必要かは ③ が判断し、引き下げられた requirements は修正後 **feature スコープのゲートから通し直す** |
| 5 | **対象 feature ごとに 1 回** ＋ 結合段の完了後に **横断 1 回** | **対象 feature 数 + 1** | feature ごとに `approved` まで通してから次へ進む。承認の担体は `wireframe-manifest.json` のトップレベル `status`。横断は承認対象の文書を持たないため **status を遷移させない**（`_app-shell` の `status` を `"n/a"` に落とすことのみゲートが行う）。**1 feature の案件では結合段を実行しないが、横断スコープのゲートは実行する**（対象 feature の網羅・宣言なき除外の検出は 1 feature でも必要） |

## 7. Phase 5（画面モック生成）の実行手順

**工程内部の生成規約の正は `wireframe-authoring` / `wireframe-integration` の各 `SKILL.md` である。** 本節はフロー制御（位置・実行順・停止点・進行状態の判定・読み取り範囲）のみを持つ。

### 位置と起動条件

- **Phase 4（requirements）の横断スコープの ③ が済んだ後・Phase 6（design）着手前に、全案件で 1 回実施する。** 改善サイクルの周回内には入れない（requirements 確定後に 1 回）。
- 対象 feature は `.aidd/feature-list.md` から宣言する。**UI を持たない feature は対象から外し、外したことを Step 0 の計画で宣言する**（黙って除外しない）。
- **全対象 feature の `requirements.md` が `status: approved` であることを確認する。** 1 つでも未承認なら停止する（承認を代行・省略しない）。`steering/` 一式が記入済みであること。

### 手順 0: DS の取得

- **使う DS の版（タグ）は人間が指定する。** エージェントが版を選んではならない。
- 規約は 2 条件のみである。**① 版（タグ）を固定して参照する ② 参照した版を `wireframe-manifest.json` の `ds_version` に記録する**（取得手段は問わない）。
- 未取得なら既定手順で取得し、`.gitignore` に `ds/` が無ければ追加する（DS 本体はコミットしない）。

```
git clone --depth 1 --branch <タグ> <DS リポジトリ URL> ds
git -C ds rev-parse --short HEAD   # 短縮 SHA を開始宣言に含める
```

- トークン CSS は**取得した DS のトークン JSON から `wireframe-authoring` が生成する**（DS が `tokens/dist/` をタグ同梱しないための運用。同梱される版に変わったら複製へ切り替わる）。**別途トークン CSS を配る必要はない。**
- 監査・一致検査・動線チェックの実行に **Node.js が必要**である（§2）。

### 実行手順

1. **対象 feature ごとに `wireframe-authoring` を実行する**（1 feature ずつ順に。並行しない）。各実行の完了条件は Skill 側が持つ（監査 exit 0・manifest 生成・未画面化申告）。
2. **feature スコープのゲートを起動する**（Step 3 の Phase 5 例外）。
3. **③ 人間レビューで停止する。** ここで `unrealized[]` の承認（`acknowledged`）と `status` の承認（`review` → `approved`）を**同じ停止点で**受け取る（Step 5）。主要画面が作れていない feature は進めず、扱いを人間が判断する（要件変更の検討・DS 側の課題化 — 工程内では解消しない）。
4. 1〜3 を対象 feature の数だけ繰り返す。
5. **複数 feature の案件のみ `wireframe-integration` を実行する**（1 feature の案件ではスキップする）。
6. **横断スコープのゲートを起動する**（1 feature の案件でも実行する）。
7. **③ 人間レビューで停止する。** MK2（顧客確認）を実施してよいかの判断を受け取る。
8. 本節の終端処理（下記「Phase 5 完了時の終端処理」）を実行して停止する。

### MK2（顧客確認）の扱い

- **MK2 は人間の工程であり、本フローは実施しない。** 前提は **監査 exit 0 + 全対象 feature の `approved`（`unrealized[]` の承認済み）** である。
- 実施後は**人間が** `confirmed_at` を記入する。顧客の指摘は記録に残し（manifest の `notes`、または案件側の記録 — 所在を `notes` から辿れるようにする）、**ワイヤーフレームは作り直さない**（使い捨て）。指摘の反映先は Phase 6（design）である。
- **`confirmed_at` が記入済みの一式には以後手を入れない。**

### 進行状態の判定（Phase 5 に限る）

`status` の担体は各 feature の `wireframe-manifest.json` のトップレベル `status` である。それだけでは決まらない状態を次で補う。

| 状態 | 次のアクション |
|---|---|
| `ds/` が無い・版が宣言されていない | 手順 0 の DS 取得を人間へ提示して停止 |
| manifest が無い | `wireframe-authoring` を実行 |
| manifest あり・`audit.result` ≠ `pass` | `wireframe-authoring` で再生成（**手直しで直さない**） |
| `status: draft`・監査 pass | feature スコープのゲートを起動 |
| `status: review` | ③ 待ち（指摘 + `unrealized[]` を提示） |
| `status: approved`・未処理の対象 feature が残っている | 次の feature の手順 1 へ |
| 全対象 feature が `approved`・複数 feature・共通シェル未適用 | `wireframe-integration` を実行 |
| 全対象 feature が `approved`・（複数なら）結合済み・横断ゲート未実行 | 横断スコープのゲートを起動 |
| 横断スコープの ③ が済んだ | 本節の終端処理へ（**Phase 6 へ進まない**） |
| `confirmed_at` 記入済み | MK2 実施済み。**以後ワイヤーフレーム一式に手を入れない** |

### 読み取り範囲

- **requirements 承認までのワークフロー内部資料（FAQ・質問ログ・品質ゲートレポート・checkpoint 等）と `docs/` 配下を、画面内容の根拠として作成 Skill に渡さない。** requirements に落ちていない情報は要件として確定していないため、根拠にすると正が二重になる。
- **ゲート記録（`.aidd/gates/`）と `phase-progress.json` も渡さない**（全フェーズ共通の禁止事項 §9）。
- Skill ごとに読んでよい範囲の詳細は各 `SKILL.md` の「入力」節が正である。

### Phase 5 完了時の終端処理（本リリース固有）

全対象 feature の `wireframe-manifest.json` が `approved` になり、横断スコープの ③ が済んだら **次フェーズへ進まない。** 次を人間へ報告して停止する。

1. `approved` になった `requirements.md` の一覧（feature 名・要件数・承認者。**承認者はゲート記録の `## 承認` から取る**）
2. `approved` になったワイヤーフレームの一覧（feature 名・画面数・承認者）と、**対象外とした feature とその理由**
3. **`unrealized[]`（未画面化要件）の一覧と `acknowledged` の記入内容**、および **`missing[]`（DS 不足）の一覧**（DS 側の課題として引き継ぐ材料）
4. Phase 4 / Phase 5 の横断スコープのゲート記録で ③ が **「対応せず進める」と判断した指摘**（記入された理由つき）
5. 未解消の `blockers` があればその一覧
6. `.aidd/phase-progress.json` の最終状態
7. **次に人間が行うこと**: MK2（顧客確認）の実施と、実施後の `confirmed_at` の記入
8. **Phase 6（design 作成）以降は本リリースの対象外**であること

**この時点で `design.md` の作成に着手してはならない。**

## 8. 停止条件（人間に判断を返して止まる場面）

次のいずれかに該当したら、作業を進めずに人間へ報告する。

- 上流成果物が `approved` でない。
- RFP が停止条件を満たさない（目的・対象ユーザーが読み取れない / 機能範囲が列挙されていない / 対象外が判別できない）。
- テンプレートを埋める根拠が上流成果物に無い。
- 設計書・テンプレート・実成果物のあいだで前提が矛盾している。
- 差戻し先の判断が必要である。
- 新規要求と思われる内容が下流フェーズの壁打ちで出た（**その場で要求一覧を書き換えず** Phase 1 へ戻す）。
- **Phase 6 以降（`design.md` / `tasks.md` / `docs/`）の作成を依頼された**（本リリースの対象外。§0）。
- **Phase 5 で DS の版（タグ）が指定されていない、`ds/` が取得されていない、または Node.js が使えない**（§7 手順 0）。
- **Phase 5 で `unrealized[]` があるのに承認内容を受け取っていない**（`approved` にせず停止する）。
- **Phase 5 で主要画面が生成できなかった feature がある**（進めるかどうかは人間が判断する）。

## 9. 全フェーズ共通の禁止事項

- エージェントが `approved` を付けること。
- ゲートに合否を出させること、指摘に重大度を付けること。
- ゲートの指摘を自動修正すること、指摘がゼロになるまでループさせること。
- ゲートを作成側と同一コンテキストで実行すること。
- **ゲートのサブエージェントを並列に起動すること**（Step 3）。Claude Code はエージェントチーム有効時にサブエージェントを teammate として起動しうるため、有効にしないか 1 件ずつ起動する。
- `approved` でない成果物を下流の入力にすること。
- **プレースホルダーを削除すること。** 埋める必要がないものは、**人間が明記した不要理由**をプレースホルダーに残したまま保持する。
- 検出フェーズが要求一覧（`.aidd/requirement-list.md`）を書き換えること。更新できるのは Phase 1 のみ。
- ゲート記録を上書きすること（追記のみ）。
- ゲート記録・`phase-progress.json` を生成入力にすること。
- **フェーズ開始の停止（Step 0）を省略して作成に入ること。**
- Step 0 で実行計画を示さず「開始してよいですか」だけを問うこと。判断材料の無い問いは反射的な承認を招き、③ の実効性を損なう。
- **Phase 6 以降の成果物（`design.md` / `tasks.md` / `docs/`）を作ること。** 配置されていない Skill・サブエージェントを代替で自作することを含む。

### Phase 5 に固有の禁止事項

- **DS の版（タグ）をエージェントが選ぶこと。** 指定は人間が行う（§7 手順 0）。
- **DS（`ds/`）配下のファイルを変更すること。** トークン JSON・監査スクリプトを含め、DS は読み取り専用である。
- **DS に無い部品・パターンを自作すること、近いもので代用すること。** 不足は `missing[]` に記録する（DS への起票・改修は本フローのスコープ外）。
- **生成済みワイヤーフレームを手で磨くこと・部分修正すること。** 修正は作成 Skill の再実行（再生成）で行う。
- **`acknowledged` / `confirmed_at` の内容をエージェントが起案・補完すること。** 人間から受け取った内容の転記のみを代行する。
- **承認済みの `requirements.md` を編集すること。** 要件側の手当てが要る気づきは「要件変更の提案」として報告し、変更の要否は人間と Phase 4 への差戻しに委ねる。
- **UI を持たない feature を宣言なく対象から外すこと**（Step 0 で必ず提示する）。
- **配布物である `wireframe-authoring` / `wireframe-integration` の `SKILL.md` を書き換えること**（Step 3 の Phase 5 例外）。
- **機械での見た目確認（ヘッドレスブラウザ等）を工程に持ち込むこと。** 実行環境・フォントに依存し案件ごとに結果が変わる。表示確認は人がブラウザで行う。
