## 概要

同じ事実・定義が複数箇所に重複して書かれていないか（二重定義）、参照している先が実在するか
（参照切れ）、同じ対象が複数に割り当てられていないか（多重割当）、書いた側に対応する受け手が
いるか（受け手不在）を検出する。呼び出し元が「検査する事実の種類」と「検査の型」を指定することで、
Phase 2（相互参照切れ・SSoT維持）・Phase 3（多重割当・責務重複）・Phase 4（意味的重複・
Dependencies整合・受け手不在）・Phase 5（契約衝突・エラー形状・業務コード重複）・Phase 6（用語・
参照整合性・steering二重定義）のいずれの検証にも使い回せる。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象成果物 | 検査対象（1件または複数） | `steering/*.md` / `specs/*/design.md` |
| 検査する事実の種類 | 何の重複・整合を見るか | `業務概念の呼称` / `API/Event/Data契約` / `エラー形状` |
| SSoTの所在 | この事実の正がどこにあるべきか（任意。未定なら「未定」） | `feature-list.md` / `api-standards.md` |
| 検査の型 | `二重定義` / `参照切れ` / `多重割当` / `受け手不在` のいずれか、またはその組み合わせ | `参照切れ` / `二重定義 + 参照切れ` |
| 報告単位 | 何単位で1件の指摘にするか | `対象ペアごと` |

## 手順

1. `対象成果物` を読み、`検査する事実の種類` に該当する記述（定義・参照・割当）をすべて抽出する。
2. `検査の型` に応じて次のいずれかを行う。
   - `二重定義`: 同じ事実が複数箇所に矛盾しうる形で重複して定義されていないかを突き合わせる。
     同じ事実かは単語の一致ではなく、述べている内容が同一かで判定する。上位方針を下位が「準拠」として
     引く記述（意図的な引用）は二重定義にしない
   - `参照切れ`: 参照先（ID・ファイル・セクション）が実在し、かつ空でない（該当記述がある）かを確認する
   - `多重割当`: 同じ対象（feature・責務等）が複数の主体に割り当てられていないかを確認する
   - `受け手不在`: ある成果物からの参照・依存に対応する受け手（宛先）が存在し、その責務が受け手の
     スコープ内にあるかを確認する。受け手のファイルが未作成なら欠落と断定せず「未作成のため判定不能」と区別する
3. `SSoTの所在` が指定されている場合は、そこにある値を正として突き合わせる。
4. 二重定義の指摘では、所在（両方）・`SSoTの所在` に照らしてどちらが所有すべきか・両者が同一内容か
   食い違っているか（食い違いは必ず書き分ける）を `evidence` に書く。`SSoTの所在` が未指定・未定なら両形状を
   `evidence` に並べ、どちらを正とするかを `suggestion` の選べる案にして `recommendation` を `質問：…` にする。
5. `報告単位` に従って指摘をまとめる（重複したペアを1件の指摘に集約する等）。

### スコープの仕分け

未作成を欠落と誤判定しうる項目（受け手不在など）は横断スコープでのみ実行し、片側だけで判定できる部分
（参照切れ等）は成果物単位スコープに前倒しする。同じ項目を両スコープで実行しない。
問題ごとに feature と横断のどちらで出すかは finding-rules の持ち主の表に従う（二重定義は横断で出す。
feature 内の重複要件は feature で出す）。表の別スコープが持つ問題は、呼ばれたスコープでは出さない。

## この工程で指摘しない事項

- `.claude/skills/finding-rules/SKILL.md` の工程の境界の表・`confirmed_answers`・`learned` に当たる事項
- `TBD（<工程> で確定）` と書いてある値
- 持ち主の表で別のスコープ（feature／横断）が出す問題
- 受け手のファイルが未作成のための欠落（「未作成のため判定不能」として区別する）

当たるものは指摘にせず、除外として返す（除外の出典を付ける。書き方は finding-rules）。

## 出力の形

指摘ごとに次を返す。書き方は `.claude/skills/finding-rules/SKILL.md`（検査の最初に読む）に従う。重大度は出さない（L3 が `kind` から決める）。

```
{ location, subject, kind, summary, evidence, suggestion, recommendation, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `location` | 重複・参照切れ・多重割当・受け手不在が見つかった箇所。`<案件相対パス> § <節見出し> / <ID>` の形。複数箇所なら代表 1 か所＋「ほか n か所」（全件は `evidence`） |
| `subject` | 対象の語（例: `決済処理`） |
| `kind` | `.claude/skills/finding-rules/SKILL.md` の種類から 1 つ選ぶ。迷ったら上の行。参照切れは `文書間の参照`。食い違う二重定義・多重割当・受け手不在は `業務の欠落・矛盾`。同一内容の二重定義（置き場所だけの問題）は `工程・文書の分担` |
| `summary` | 60 字以内。結論を先に、何が・どこで（例: 「`決済処理` の責務が `login` と `checkout` に重複して割り当てられている」） |
| `evidence` | 検出した事実と所在（全件）。二重定義は所在（両方）・どちらが所有すべきか・同一か食い違いか（未指定なら両形状） |
| `suggestion` | 修正案（差分・書き換え文）。業務の新しい事実が要るときは、修正案ではなく「何を決めればよいか」と選べる案 |
| `recommendation` | `修正：理由` / `差戻し：理由` / `対応せず進める：理由` / `質問：理由` のどれか。業務の新しい事実が要るときは `質問：…` |
| `is_rollback_candidate` | 上流フェーズの成果物が原因である場合は `true` |

## 禁止

- 対象成果物を書き換えない（どちらが正しいかを自分で決めて統合しない）
- 合否を出さない
- SSoTの所在が指定されていない場合に、推測で「どちらが正か」を断定しない（両形状を `suggestion` の選べる案にし、
  `recommendation` を `質問：…` にする）
- 未作成のファイルを欠落として報告しない（「判定不能」と区別する）
- 意図的な引用（「準拠」として上位方針を引く記述）を二重定義として報告しない
