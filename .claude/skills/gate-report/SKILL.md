## 入力

当該実行の snapshot、gate_record_path（読むだけ）、inspection_path（書き出し先）、実行した層、指摘一覧（gate / location / finding / is_rollback_candidate）、差戻し候補の宛先と理由。指摘の採否や人間回答は受け取らない。

## 手順

1. `Templates/Flow/gate-record-format.md` と既存のゲート記録を読む（読むだけで編集しない）。ファイルは snapshot ゲートが初期化済みである。無い、旧形式、対象が不一致の場合はfailedで戻る。
   コードprofileのハッシュはコード在庫と証跡を束ねたmanifestのSHA256で、成果物status更新は行わない。
2. inspection_path のファイルを**上書きで**作り、`## 実行` の表を1行書く（中断後にもう一度実行しても同じファイルを書き直すだけで、記録は二重にならない）。スコープ・回数・実行日時・対象成果物・原本SHA256はsnapshotから転記する。実行した層は実績、指摘件数は今回の一覧の件数を使う。
3. 同じファイルの直後に `### 指摘` の固定6列表を書く。番号は今回の中で1から連番。判断・理由は必ず空欄。0件でも見出しと区切りだけの表を追加する。
4. 差戻し候補があれば `### 差戻し先候補` を続けて書き、今回の指摘番号・候補の宛先・理由を記す。候補先を確定できなければ「人間による確認」と記す。機械指摘の本文に候補文字列を混ぜて改変しない。
5. scope / run / findings_count / layers を返す。ステージの指摘がすべて元の観点・対象箇所・本文のまま含まれることを確認する。

## 禁止

- フロントマターの更新、途中の表への挿入、既存の改行・文字コード・行順の変更。
- 判断・理由の記入、承認の空行やプレースホルダーの追加、解消・承認・確認ブロックの作成。
- 以前の未解消指摘を今回件数へ加えること、指摘を勝手に採否判定して削ること。
- inspection_path 以外への書込み（ゲート記録・成果物・進捗を含む）。ゲート記録への追記と成果物の draft → review 遷移は、次の scope-check で L3 が1回だけ行う。

表の各セルに `|` が含まれる場合は `&#124;`、改行は `&#10;` とし、固定列数を壊さない。実行表の対象一覧とハッシュ辞書はJSONとして記す。空の値で検査完了を作らない。
