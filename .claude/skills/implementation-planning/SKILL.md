# implementation-planning — 実装計画の作成とレビュー

必要なときは任意の補助 `requirements-authoring-guide` で、要件・タスクの受け渡し・被覆6表のつながりを確認できる。例の固有名・閾値・証拠を案件へ流用せず、本Skillの入力・出力・未確定時の規則を適用する。補助が未導入でも本Skillの通常の作業は開始できる。

## 起動時に確定する項目（dispatch）

- **mode** — `authoring`（これから作る）／`review`（提出済みを判定する）。依頼者の明示を優先し、明示が
  なければ対象と操作から一意に判定できる場合のみ自動で決める。**一意に決まらないときは質問して停止する**。

本パックは project profile を読まない。

## 必須の文脈: ファイルパス

**パス文脈（対象リポジトリの構造と、作成／変更先のパス）は両 mode で必須**である。区別:

- **既存ファイルの変更** — **実在を確認したパス**を書く。
- **新規作成** — リポジトリ構造に整合する**確定した予定パス**を書く（まだ存在しないことは欠落ではない）。
  親ディレクトリも新規なら、**その作成をタスクに含める**。

不足している場合:

- **authoring** — 「パス未解決」を**ブロッカーとして報告**し、推測のパスでタスクを書かない。
- **review** — 当該検査を **UNDETERMINED**（判定不能）として報告する。パスの当否を推測で断じない。

## ルールA: 被覆と依存

- **A-01 全要求の被覆自己検査**: 計画の最終工程で、上流の全要求を1件ずつ辿り、それを実装するタスク／
  ストーリーが最低1件あることを確認する。**各要求の ID を、対応するタスク／ストーリーの記述に明記する**
  （意味の上で対応していると読めるだけでは不足。ID が一度も現れない要求は未被覆として扱う）。
  未被覆が残るなら計画を確定しない。
- **A-02 依存は過去方向にのみ向く**: 各タスク／ストーリーは、**既に完了した先行項目の出力だけ**を前提に
  完了できること。未来の項目に依存する記述（後で作る予定のものを前提にする）を書かない。

## ルールB: 分割と粒度

- **B-01 分割単位はユーザー価値の独立スライス**: 「利用者が何を達成できるようになるか」で切る。
  技術レイヤ（DB 層・API 層・UI 層）での横割りにしない。
- **B-02 独立してテスト可能**: 各スライスは単独で検証できる形にする。
- **B-03 粒度の上限は実行者1単位**: 各タスク／ストーリーは、**単一の実行者が1つの文脈で完了できる**
  サイズに収める。上限を超える項目は分割する（具体的な分数・件数はプロジェクトで決める）。

## ルールC: タスク記述の自己完結性

- **C-01 正確なファイルパスを書く**: 作成・変更・テスト対象のパスを記す（既存の変更は実在確認済みのパス、
  新規作成は構造に整合する確定予定パス）。「適切な場所に」「該当ファイルを」等のパスなし記述は計画として不完全。
- **C-02 プレースホルダ・曖昧タスクを置かない**: 各項目は、実行者が**追加の文脈なしに**完了できる実内容
  （何を・どこに・どうする・完了をどう確かめる）を含む。
- **C-03 完了条件を書く**: 各項目に、何をもって完了とするかを1行で添える。

## タスク間の受け渡しを具体化する

タスク間で関数・型・データを受け渡す場合は、各タスクに次の情報を添える。自分のタスクだけを読む実行者が、
先行タスクから何を受け取り、後続タスクへ何を提供するか分かる形にする。

- **受け取るもの（Consumes）**: 先行タスクから利用する関数・型・データと、正確なシグネチャを記す。
- **提供するもの（Produces）**: 後続タスクが依存する関数名・引数・返り値型などを記す。

後続タスクが使う型・シグネチャ・プロパティ名を、先行タスクの定義と照合する。同じ機能を別名で参照している
場合や引数・返り値型が食い違う場合は、`authoring` では計画内の記述を揃え、`review` では両方の箇所と
食い違いを示して指摘する。`review` では計画本体を書き換えない。これらも案件の前提に照らして使う
【SHOULD】相当の観点として扱う。

## review 時の出し方

各ルールについて **適合／違反／判定不能** を示し、違反は対象箇所を引用して指摘する。計画本体を書き換えない
（判定と修正の分離）。**指摘は【SHOULD】として提示する。**

## 関連パックへの引き継ぎ

- **要求そのものの記述品質**（受入基準・NFR・スコープ）は `requirement-authoring-core` の領分。計画側から
  要求の欠落を見つけたら、そちらへ差し戻す（本パックで要求本文を書かない）。
- **要求→タスクの被覆マトリクス**の作成・判定は `traceability-audit` が所有する。A-01 は計画作成者の
  自己検査であり、監査成果物の生成はそちらへ redirect し、**再監査を handoff** する。
- **計画の受入判定**（承認／差し戻し）は `acceptance-review` へ handoff する。

## 適用範囲外

- 要求・仕様の記述そのもの
- 被覆マトリクス・被覆報告の生成と被覆状態の確定
- 見積り手法・スケジューリング・体制設計
- タスク ID の採番規則・チェックリスト書式・フェーズ構成の具体 enum — プロジェクトの決定事項
