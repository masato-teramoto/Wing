# SG: スタイルガイドの作成（案件の見た目の正・案件に 1 枚）

> フロー内の位置・実行順・人間停止点の概要は **入口 skill `aidd-system-design`（配布ワークスペースの
> `.claude/skills/aidd-system-design/SKILL.md`）が正**。単独で呼ぶときは「単独起動時の前提」を満たすこと。
> **本 SKILL.md が工程内の作成規約と手順の正**（実行規約は本書で自己完結する）。
> 書式の正は雛形 **本 skill の `templates/STYLEGUIDE.md`**（読み取り専用）。

## 位置づけ（作成規約の前提）

- **STYLEGUIDE.md は案件の見た目の正**（色・書体・部品の様式・余白・階層・禁止事項・エージェントへの指示）。
  設計文書（`design.md`・画面設計書）は色・余白・書体を書かず、本書を指す
- **STYLEGUIDE.md は画面の構成・項目・操作・状態・文言を決めない。** それは画面設計書（SD-1）の役割で、
  画面の切り出し・所有・入口とナビは画面マップ（SD-0）の役割である
- **案件に 1 枚。** リポジトリ直下（= 案件ルート直下）に置く。`steering/` には置かない
  （steering は上流の全工程が一式全文を読むため、見た目の正を混ぜると入力が重くなる）
- **案件初回に 1 回だけ作る。** feature ごとには作らない。**2 feature 目以降は本 skill を実行せず、版の確認だけを行う**
- `styleguide.css` は STYLEGUIDE.md の**機械可読形**（同じ版）。**雛形を持たない生成物**であり、形の正は本 SKILL.md の生成規約
- **ベース DS からの導出はルートに置かない。** DS との関係は逆向きで、STYLEGUIDE.md が肥大化したときに
  STYLEGUIDE.md の内容を DS に落とし込む（→「完了後」）。**先回りして DS を作らない**

## ハード制約

- 【MUST】**出力は 3 つだけ**: 案件ルート直下の `STYLEGUIDE.md` と `styleguide.css`、
  および追記候補の台帳 `STYLEGUIDE-backlog.md`（→「STYLEGUIDE-backlog.md」）。他の場所にファイルを作らない
- 【MUST】**frontmatter の `tokens` と本文（§2〜§6）の値を一致させる。** 食い違ったら frontmatter が正
- 【MUST】**部品クラスを生むのは §4「部品の様式」だけ。** §5 レイアウトの原則・§6 奥行き・§7 Do / Don't は
  原則と禁止事項であってクラスを生まない。**アプリシェル（ヘッダ・ナビ・パンくず・本文領域）の様式も §4 に置く**
  （§4-10）— シェルは全ページに載るため、§4 に無いクラスでシェルを描くと**全ページでパレット検査に掛かる**
- 【MUST】**変更は必ず版を上げる**（追記のみでも。frontmatter `version`）。
  ただし**人が確定する前の草案は、同一版のまま直してよい**。版が意味を持つのは人が確定した時点からで、
  未確定の草案に版を積むと**確定済みの版と草案の版が見分けられなくなる**。
  確定の後は必ず版を上げる（→「改訂モード」）
- 【MUST】**版を書くのは突合される欄だけ** — frontmatter `version` / §1-2 / `styleguide.css` の冒頭。
  **散文に版を書かない。確定文書に工程の通し番号を書かない**（工程名で書く）
- 【MUST】`styleguide.css` の冒頭コメントに **STYLEGUIDE.md と同じ版番号**と、何を流用したかを記録する
- 【MUST NOT】**`styleguide.css` を STYLEGUIDE.md と切り離して直す。**
  作り方（全文を生成し直す / 既存ファイルを編集する）は問わないが、**STYLEGUIDE.md から機械的に導ける結果と
  一致すること**が条件であり、一致しない手入れをしない。**改訂では既存ファイルの編集が現実的である**
  （変数とクラスを 1:1 に保つ必要があるため、作り直すと差分が読めなくなる）
- 【MUST NOT】**画面の構成・項目・操作・状態・文言を書く**（本書を根拠に画面へ情報や操作を足させない）
- 【MUST NOT】**§4 の必須項目を、既存 UI に対応物が無いまま skill の判断で作る / 黙って落とす**
  （**人が選ぶ** — →「決められない項目の扱い」）
- 【MUST NOT】**確定を代行する**（人がキャプチャと突合して確定する — 「完了後」節）
- 【MUST NOT】**requirements.md / design.md / steering を書き換える**
- 【MUST NOT】**雛形を案件ルートに複製して、その写しから起草する**
  （毎回**本 skill の `templates/`** から読む。写しは版が分かれて黙って drift する）
- 【MUST NOT】**既存 UI のコード・キャプチャの出所を偽る**（コードが無くキャプチャだけから起こした値は近似であり、
  frontmatter `sources.note` に近似である旨を明記する）
- 【MUST】Markdown・表示文言は ja で記述する

## 開始時の宣言（MUST）

- **初回か改訂か。** 案件ルート直下の `STYLEGUIDE.md` の有無と、**改訂の起点**の有無で 3 分岐する:

  | 状態 | 挙動 |
  |---|---|
  | `STYLEGUIDE.md` が**無い** | **初回**として続行する（本節の以下の項目を宣言する） |
  | `STYLEGUIDE.md` が**在り、改訂の起点が特定できる** | **改訂**として続行する（→「改訂モード」。宣言の項目が違う） |
  | `STYLEGUIDE.md` が**在るが、起点が示されない** | 実行せず、版（frontmatter `version`）を報告して**停止する** |

- **ルート**（A / B / C。選び方は →「入力」の表）と、その入力の所在
- 出力先（案件ルート直下の `STYLEGUIDE.md` / `styleguide.css`）と雛形の所在（本 skill の `templates/STYLEGUIDE.md`）
- **コードの有無**（ルート A で、コードが無くキャプチャだけの場合は値が近似になる旨）

## 前提

- 本工程は **design 承認の後**にある。UI を持つ feature が 1 つ以上、承認済みであること
- ルート A: 既存システムの**代表画面のキャプチャ**（5 画面程度 — 一覧 / フォーム / 詳細 / ダイアログ / エラーか空）が在ること。

## 決められない項目の扱い（ルート A / B 共通）

**skill が決めない項目は必ず出る。** ルートによって出方が違うだけで、扱いは同じである。

| ルート | 出方 |
|---|---|
| **A** | 既存 UI から読み取れない（既存 UI が古い / ナビの形が違う / 状態の表し方が違う） |
| **B** | **ヒアリングでは §4 部品の様式・§5 レイアウトが決まらない**（手順 2B）。雛形も値を持たない |

**決め方の原則は 1 つ**: 【MUST】**skill は決めず、選択肢と推奨を添えて人に返し、停止する。**
黙って作る・黙って落とす、のどちらもしない（ハード制約）。**返し方は次の 4 点を必ず持つ**:

1. **選択肢**（最低 2 案。既定は「最小で起こす」「持たせない」）
2. **各案の影響差** — 少なくとも **① mockup の全ページに載るか ② feature 間の導線と到達性がどう変わるか
   ③ 既存 UI の再現度**（ルート B では ③ を「ヒアリングで表明された方針との整合」に読み替える）
3. **推奨案と、その理由**（skill が推す 1 案を明示する。「判断できません」で返さない）
4. **人が選ぶまで §4 に書かない**こと

種類ごとの扱い:

| 種類 | 扱い |
|---|---|
| **§4 の必須項目**（§4-10 のグローバルナビ・ナビ項目の現在地 / 無効・パンくずなど、本書が「必ず含める」と定めたもの） | 【MUST】**上の原則のとおり、選択肢 + 推奨を添えて停止する**（→「出力」の報告） |
| **§4 のその他の部品・§5 レイアウト**（ルート B で決まらないもの） | 同上。**「業務画面の汎用的な既定」を skill の判断で置かない**（雛形の `{{ }}` は記入欄であって既定値ではない） |
| **状態色**（error / success / warning / info の 文字 + 面 + 枠） | 【MUST】**補完する。** 既に在る状態色と**同じ出どころ・同じ体系**から残りを取り、`sources.note` と §2 に**補完した旨と出どころ**を書く。既存 UI の他の色（装飾色・用途が決まった色）を流用しない — 流用すると色に意味が二重になる（ガードレール）。<br>**逆向きも封じる**: 既存 UI が状態色相当の色を構造・装飾に使っていても**状態色として抽出せず、役割名で別のトークンに分ける**。そのうえで §2 と §7 に**「状態色を状態以外に使わない」**を禁止として書く（**古い UI では流用が頻発する** — ガードレール） |
| **雛形が持つ段・キー**（文字サイズの段・太さの段・余白の段・寸法の下限など） | **既存 UI に合わせて増減してよい。** 段が足りないときに**同値で埋めない**（段が無いことを段の数で示す）。減らした段・落としたキーを §1-1 に 1 行で書き、**いつ拾い直すかを添える** |
| **上記以外の部品**（Badge・タブ・通知の一部など） | **作らない。** §4 の該当小節に「部品を作らない」と理由つきで明記し、後の工程が追記候補として報告する（ガードレール） |

**いずれの場合も §1-1 に一覧を残す**（何が決まらず、選択肢として何を出し、人が何を選んだか）。
確定時に人が見る対象になる。**抽出元の方針の適用を変えたときは、雛形 §1-1 の類型を添える**（類型の正は雛形）。
**「方針からの離脱」と判定する前に抽出元を引く。**

## 業務状態と種別の割り当て

**Badge のように「業務状態を色で表す」部品は、状態名と種別（色）の対応が決まらないと描けない。**
ところが**状態名の正は画面マップ §5・部品名の正は画面設計書**で、どちらも**どの状態をどの色にするかを決めない**。
本書が形だけを持って対応を持たないと、**割り当ては mockup が決めるしかなく、
その記録が manifest にしか残らない**（再生成のたびに揺れる）。

【MUST】**状態を表す部品の小節に、割り当て表の器を置く。**

| 業務状態（正は画面マップ §5） | 種別 | class |
|---|---|---|
| {{状態名}} | {{neutral / info / success / warning / error}} | `.badge-{{...}}` |

- **状態名を本書が決めない**（列に写すだけ。増減は画面マップ §5 に従う）
- **値（どの状態をどの種別にするか）は案件が埋める**。埋まっていない行は
  `STYLEGUIDE-backlog.md` の `1-3. 未判断` に出す
- **種別の顔ぶれは §2 の状態色と 1:1**（状態色に無い種別を作らない）

## styleguide.css の生成規約

STYLEGUIDE.md の frontmatter `tokens` を **CSS 変数**に、**§4「部品の様式」**を**部品クラス**に落とした 1 ファイル。

1. **変数名は frontmatter のキーをケバブに落とす** — `color.brand.primary` → `--color-brand-primary`、
   `spacing.md` → `--spacing-md`。階層はハイフンで平坦にする（`_` は `-` にする）
2. **`tokens` に現れる全キーを出力する**（使用の有無で絞らない）。理由: 各 feature の
   `pages/tokens/styleguide.css` は**案件直下の正の複製**であり、**内容が 1 バイトでも違うと機械検査で落ちる**。
   キーを絞ると絞り方の差で割れる
3. **frontmatter 内の参照（`{spacing.md}` の形）は `var(--spacing-md)` に落とす**（値を展開しない — 層が読めなくなる）
4. **部品クラスの出どころは §4 だけ。** §5〜§7 からクラスを作らない。
   **§4 に `class:` で併記した名前と、CSS が定義するクラスを 1:1 にする**（片側にしか無いものを残さない）。
   **§4-10 のシェルのクラスを必ず含める** — シェルは全ページに載るため、欠けると全ページで検査に掛かる
5. **生値（hex / rgb / px）を書いてよいのはこのファイルだけ。** 部品クラスの中では
   トークンを `var(--...)` で参照し、§4 に無い値を新たに作らない
6. **冒頭コメントに版と出所を記録する** — STYLEGUIDE.md と**同じ `version`**・生成日・
   既存システムの CSS / トークン定義を流用した場合はその所在
7. **既存システムの CSS・トークン定義が手に入る場合は、それを元にしてよい**（忠実度が上がる。6 に記録する）
8. **画像は「装飾か内容か」で切り、本書が持つのは装飾だけである。**

   | | **装飾** — 本書が持つ | **内容** — 本書は持たない |
   |---|---|---|
   | 何の画像か | 全画面に載り、画面が変わっても変わらない（地紋・アイコン・区切り・ロゴ） | その画面固有で、意味を運ぶ（帳票の見本・添付のサムネ・業務データとしての画像） |
   | 正はどこか | **本書の `tokens.asset.*`** | **画面設計書**（どの画面にどの画像を置くか） |
   | 版の単位 | 本書の版 → 上げると全 feature の mockup を再生成 | 画面単位 |
   | 置き方 | **styleguide.css に data: URI**（下記） | **`<img src>` + `alt`**（`alt` は文言なので画面設計書が正） |

   **この 3 行が同じ向きに揃うのが判断基準の根拠**である。装飾画像は `alt` を持てず・意味を運ばず・
   全画面共通で・見た目に属する。内容画像はその逆で、**「装飾は CSS の背景・意味を運ぶ画像は `<img alt>`」
   という一般則が、本工程の正の分担（本書 / 画面設計書）とそのまま一致する**。
   **内容画像は本書に入れない**（【MUST NOT】画面の構成・項目・文言を書く、に触れる）。
   `<img src>` を使う場合の置き場と `presented/` 凍結時の扱いは**まだ決めていない**（設計書 §9 の未決）。
   目安として、**装飾でも 1 案件の `asset` 合計が数十 KB を超える**なら `<img src>` 側を検討する
   （data: URI は base64 で +33% になり、かつ **feature 数 + 1 箇所に複製される**）。

   **装飾画像は `tokens.asset.*` に出どころのパスで持ち、
   styleguide.css では `url("data:...;base64,...")` に埋め込む。** **相対パスの `url()` を書かない** —
   案件直下の正と `<feature>/pages/tokens/` の写しで解決先が変わり、**機械検査の同一性（複製の一致）が壊れる**。
   冒頭コメントに**埋め込んだファイルと元のパス**を記録する。
   **ブランドマークの類は「持っていない」ものとして扱い**、`none` を入れて差し替え点にし、
   **必要であれば用意して差し替える**旨を §4 と §1 に書く（別案件の既存 UI から抽出した場合はとくに）。
   画像を使う場合は **§7 の「グラデーション・イラストを使わない」を「新しく作らない（既存 UI のものは流用する）」に
   直す**（雛形の既定のまま残すと本文が自己矛盾する）
9. **素の要素セレクタの節を置いてよい**（`body` / `a` / `h1`〜`h3` など）。
   **§3 タイポグラフィと §2 のリンク色は部品ではなく地の規定**なので、部品クラスに落とすと
   **mockup が地の文に一切適用できない**（ページ側でクラスを振って回ることになり、§5「クラスを生まない」に反する）。
   ページの下地（`background` / `font-family` / `font-size`）と既定のリンク色は、
   **`:root` の直後に「地の規定」の 1 ブロックとして素のセレクタで書く**。
   **クラスを増やさないので検査に影響しない** — パレット検査の未定義クラス検出は
   *HTML の `class=` 属性*と *CSS のクラス集合*の突合であり、素の要素セレクタを見ていない（実測）。
   **値は §2 / §3 のトークンを `var(--...)` で参照する**（ここでも生値を作らない）
10. **レイアウトの器は §4 の部品として置く。** 段組み（`.form-grid`）とアクション行（`.actions`）、
    表の横スクロールの器は、話としては §5 レイアウトだが **§5 はクラスを生まない**ため、
    **置かないと mockup が生値でレイアウトを書き、全ページがパレット検査 A-1 で落ちる**。
    §4 に**まとまりを作る部品**として小節を立て、`class:` を併記する。
    **段組みには列数を指定する手段を持たせる**（等分の格子だけだと、幅の段を足しても空白が残る）

**検算用のサンプル**（形の見本。クラスの顔ぶれは §4 が決める）:

```css
/* styleguide.css — <製品・案件名>
   STYLEGUIDE.md version: 0.1.0（同版。STYLEGUIDE.md を直したら再生成する）
   生成: 2026-01-01 / 流用元: src/styles/tokens.css, src/styles/components.css */

:root {
  /* frontmatter tokens を全キー。役割名のまま平坦にする */
  --color-brand-primary: #1a4f8a;
  --color-surface-card: #ffffff;
  --color-text-body: #1f2933;
  --spacing-md: 16px;
  --radius-sm: 2px;
  --control-height: 40px;
}

/* §4-1 Button（§4 の class: 併記と 1:1） */
.btn-primary {
  background: var(--color-brand-primary);
  height: var(--control-height);
  border-radius: var(--radius-sm);
  padding: 0 var(--spacing-md);
}

/* §4-10 アプリシェル（全ページに載る。欠けると全ページで検査に掛かる） */
.app-nav-item { color: var(--color-text-body); }
.app-nav-item-current { color: var(--color-brand-primary); }

/* 地の規定（生成規約 9 — 素の要素セレクタ。クラスを増やさないので検査に影響しない） */
body { background: var(--color-surface-page); font-family: var(--font-family-base); font-size: var(--font-size-body); }
```

## 改訂モード

**「開始時の宣言」の 3 分岐で改訂と判定した場合の手順。** 本書の他のハード制約・ガードレール・
生成規約・自己確認 8 項目は**すべてそのまま効く**（改訂はそれを緩めない）。

### 改訂の起点（4 つ。増やさない）

| # | 起点 | 根拠の所在 |
|---|---|---|
| ① | mockup の目視・顧客提示で出た**見た目**の指摘 | `mockup-manifest.json` の `viewed.findings` / `missing[]`、および案件の `STYLEGUIDE-backlog.md` |
| ② | 画面設計書の確認で出た**部品の語彙の不足**（本書に無い部品が要る） | 画面設計書 §5-3「STYLEGUIDE.md への追記候補」、および `STYLEGUIDE-backlog.md` |
| ③ | 実装からの申告 | 申告の記録（所在は案件裁量） |
| ④ | **本 skill の規約が改訂された**（配布物の版が上がり、雛形・生成規約が変わった） | 配布ワークスペースの改訂記録 |

**①②は案件直下の `STYLEGUIDE-backlog.md` に集約されている**（→「STYLEGUIDE-backlog.md」）。
起点として最初に読むのはこの台帳でよい。**④ のときは、直す節を規約の差分から導く**（案件側の申告は無い）。

### 開始時の宣言（改訂・MUST）

- **改訂であること**と、**現行の `version`** と**上げ先**
- **改訂の起点**（①〜④のどれか）と、**根拠の所在**（上表のファイルと項目名まで）
- **直す節の一覧**（§ 番号と、何を足す・直すか）。**ここに挙げた範囲を超えて触らない**
- **影響**: `styleguide.css` を再生成すること / **全 feature の mockup の再生成が要る**こと
  （見た目は全 feature に同じ版で効く）
- **改訂者**（案件で 1 人・既定は開発リード — →「完了後」）

> **【MUST】宣言の一覧には、規約が常に要求する節をあらかじめ含める。**
> 起点から導けるのは「直したい節」だけだが、本書の MUST は**それ以外の節も必ず要求する** —
> **§1-2（改訂履歴）/ frontmatter `version` / `styleguide.css`** の 3 つは、起点が何であれ毎回変わる。
> これを宣言に入れておかないと、**宣言の範囲外の差分**として自己確認 #10 に落ちる（実測）。

### 入力（本体の入力に足すもの）

| 入力 | 使い方 |
|---|---|
| 現行の `STYLEGUIDE.md` / `styleguide.css` | 直す対象。**節を減らさない・既存キーを消さない** |
| 改訂の起点の記録（`STYLEGUIDE-backlog.md` / `missing[]` / `viewed.findings` / 画面設計書 §5-3） | **部品・様式の不足の申告としてだけ**読む |

**読む範囲の限定（MUST NOT）**: 起点の記録のうち読んでよいのは上表の範囲だけで、
**画面の構成・項目・操作・状態・文言は読まない**（本体の「読まないもの」がそのまま効く）。
**mockup の HTML も読まない**（見た目の正は本書側であり、生成物から逆流させない）。

### ハード制約（改訂モードで足すもの）

- 【MUST】**指摘された箇所だけを直す。** 宣言した節の外にある節・値を触らない
- 【MUST】**節を減らさない。** frontmatter `tokens` の**既存キーを消さない・改名しない** —
  各 feature の `pages/tokens/styleguide.css` は**内容一致**で検査されるため、
  キーを消すと**全 feature の mockup が同時にパレット検査で落ちる**
- 【MUST】**`version` を上げる**（改訂は確定済みの版に対して行うため、草案の同一版据え置きは適用されない）
- 【MUST】**`styleguide.css` を再生成し、冒頭コメントの版を合わせる**
- 【MUST】**改訂の記録を §1-2 に 1 行積む**（→「改訂の記録と確定の担体」）
- 【MUST】**部品クラスを消す・改名するときは、§4 の本文 / `styleguide.css` /
  使う側（画面設計書の部品指定・mockup）の 3 方向で影響範囲を数え上げ、報告で下流に通知する**
  （`tokens` の既存キーと違い部品クラスは消せるが、黙って消すと画面設計書の名指しが宙に浮く）
- 【MUST NOT】**起点の申告に無い部品を足す**（本体のガードレール「あったほうが便利だから足す」に同じ）
- 【MUST NOT】**確定を代行する**

### 申告の 2 分類（手順 1 で必ず分ける）

申告は 2 種類あり、**直す場所が違う**。

| 分類 | 申告の形 | 直す場所 |
|---|---|---|
| **A. 部品が無い** | §4 に部品そのものが無い | **§4 に部品を足す**（`class:` の併記 + `styleguide.css` にクラス） |
| **B. 規定はあるが CSS に器が無い** | §2〜§5 に規定文はあるのに `styleguide.css` に実体が無く、mockup が規定を守れない | **§4 か frontmatter `tokens` に段を足す**（規定文は既にあるので原則増やさない） |

**B を A として扱うと部品が増えて §4 が膨らむ。** B は器を足すだけで済む。
**自己確認 #8（実体の無い規定）が拾うのは B 類型**である。

**B 類型の直し方**（誤ると目視が 2 巡し、1 巡ごとに全 feature の再生成が要る）:

- 【MUST】**器はコンテナに持たせる。個々の部品に方向つきの値（上だけ・下だけの余白など）を持たせない。**
  器の候補は §4 の**まとまりを作る部品**（`.card` / `.section` / `.dialog` / `.app-main`）。
  理由: 個々の部品に持たせると、**「下だけを持つ部品」と「上だけを持つ部品」が隣り合ったときに効かない** —
  組み合わせの数だけ穴が空き、目視で 1 組ずつ潰すことになる
- 【MUST】**同じ規定に触る他の部品を洗い出してから直す**（部品の横断確認）。
  申告は 1 箇所で出るが、**規定が効く範囲は §4 の全部品**である。
  申告のあった部品だけ直すと、次の目視で同じ規定の別の組み合わせが出る
- 【MUST】**段を足したら、その段が既存の器と噛み合うかを確かめる。**
  例: 入力欄の幅の段を足しても、並べる器が等分の格子なら空白は残る（幅と並べ方は対で見る）

> **機械検査も自己確認も「規定と器が対応しているか」を数えるだけで、器が組み合わせで壊れるかは見ない。**
> 全項目 pass のまま誤った直し方が通る（実測）。この 3 点は人の判断の代わりではなく、
> **目視を 2 巡させないための下限**である。

### 改訂の記録と確定の担体

**本書は他の成果物の `confirmed` / `status` / `viewed` に相当する確定の担体を持たない。**
版を上げた後に人が確定したかを機械判定できないため、**§1-2 の表が担体である。**

【MUST】改訂のたびに §1-2 の表に 1 行積む（**消さない・上書きしない**。**書式の正は雛形 §1-2**）:

| version | 日付 | 起点 | 直した節 | 確定（by / recorded_by） |
|---|---|---|---|---|
| `<version>` | `<日付>` | `<①〜④ / 初回>` | `<直した節>` | `未` |

- **`未` を書くのは skill、`済` に直すのは人**（確定の代行は MUST NOT）。
  **`by` = 判断した人、`recorded_by` = 記入した主体**（人が直接書けば `by` と同じ。
  エージェントが代筆したら skill 名を書く。**判断そのものは代行しない**）
- **`未` の行が在る版は「人が見ていない版」である。** 次の改訂を重ねる前にこの行を確認する
- **確定の前に、§1-2 の要約と本文を 1 回突き合わせる**
- 初回も同じ形で 1 行目を置く（起点 = `初回`・直した節 = `全節`。ルート C は → 手順 3C）
- **確定後に再検討が要るものは、次の改訂の起点として台帳に起こす**（確定済みの行は書き換えない）

## STYLEGUIDE-backlog.md（案件の追記候補の台帳）

**本書への追記候補を案件全体で束ねる台帳。** 案件直下（本書と同じ場所）に 1 枚置く。

**なぜ要るか**: 追記候補の置き場は本来 ① 各 feature の `mockup-manifest.json` の `missing[]`
② 各 feature の画面設計書 §5-3 の 2 か所だが、**① は mockup の再生成で書き直され、
② は feature 単位に分散する**。**案件全体で何件残っているかを見る場所が無く**、
とくに**本書が仮運用で後から差し替わる場合、差し替えの時点で未処理が失われる**。

**書式**（skill が起こし、以後は追記する。雛形は持たない）:

```markdown
# STYLEGUIDE への追記候補（案件の台帳）

> 本書への追記候補を案件全体で束ねる。反映しても行を消さず、状態を書き換える。
> **next_id: {{SGB-1}}** ← 次に振る番号（**総数から数えない**）

## 1-1. 直す（次の改訂で反映する）

| # | 申告 | 分類 | 起点 | 宛先の節 | 優先度 | 関連 | 状態 |
|---|---|---|---|---|---|---|---|
| SGB-1 | {{申告の内容}} | A / B | {{feature}} の `missing[]` / §5-3 / 目視 / **他案件からの予見（出どころ）** | §4-x | 高 / 中 / 低 | {{#n を上書き / #n に上書きされた}} | 未 / 反映済・起草（0.3.0） / 反映済・確定（0.3.0） / 使わなくなった |

## 1-2. 現状で可（直さない）

| # | 申告 | 判断の理由 |
|---|---|---|

## 1-3. 未判断（人が決める）

| # | 申告 | 選択肢と推奨 | 推奨の根拠を読んだか |
|---|---|---|---|

## 1-4. 保留（判断は付いたが今は直さない）

| # | 申告 | 判断 | 乗せる条件 | 宛先 |
|---|---|---|---|---|
```

- **採番は `SGB-<連番>` で案件を通して一意**。**反映しても番号を再利用しない**
- **分類は「申告の 2 分類」の A / B**（改訂モードの手順 1 の入力になる）
- **`1-3. 未判断` は「決められない項目の扱い」の返し先**でもある（選択肢と推奨を書いて人に渡す）。
  **推奨の根拠を実際に読んだかを列に残す**
- **`1-4. 保留` は「版が上がるなら乗せる」ものと、番号を振れない論点（上流に正が無いもの）の置き場**でもある
  （宛先を書く。落とすと滞留する）
- **【MUST NOT】反映した行を消す**（消すと「なぜその形になったか」が失われる）

**誰が書くか**: MU が `missing[]` を出したとき / 目視で見た目の指摘が出たとき / SD-1 が §5-3 に
追記候補を書いたときに、**その工程が 1-1〜1-4 のいずれかに行を足す**。
SG は改訂モードで**起点として読み、反映した行の状態を「反映済・起草（version）」に直す**
（人の確定後に「反映済・確定」にする）。
**【MUST】本台帳は案件で共有するため、書き込むのは 1 スレッドずつ。**

## ガードレール

- 【MUST NOT】**部品を「あったほうが便利だから」で §4 に足す**。§4 は既存 UI から読み取れたもの・
  ヒアリングで決まったものだけを書く。足りない部品は、後の工程が**追記候補として報告する**
- 【MUST NOT】**§4 に無い部品クラスを `styleguide.css` に作る**（クラスの出どころは §4 だけ）
- 【MUST NOT】**色に意味を二重に持たせる**（ブランド色で状態の意味を表す / 状態色を装飾に使う）
- 【MUST NOT】**既存 UI が状態色相当の色を構造・装飾に使っていても、それを状態色として抽出する。**
  **古い UI ではこれが頻発する** — error / warning 相当の色（赤系・黄系・橙系）が表のセルの面・ラベル・
  ページの背景・用途別ボタンに流用されていることが多い。**役割が違う色は役割名で別のトークンに分ける**
  （`surface.*` / `brand.*` 等）か、出どころが framework の画面だけなら**落とす**。
  そのうえで **§2 と §7 に「状態色を状態以外の面・文字・装飾に使わない」を禁止として書く**（逆向きも封じる）
- 【MUST NOT】**状態色を文字色だけで持つ**（error / success / warning / info は**面色とペア**で持つ）。
  既存 UI に一部しか無い場合は**同じ体系から補完する**（→「決められない項目の扱い」）
- 【MUST】**本文の最小サイズを決め、それを下回る段を作らない**
- 【MUST NOT】**キャプチャに無い装飾**（グラデーション・写真・イラスト・独自の装飾色）を足す
- 【MUST NOT】**確定済みの版の内容を、版を上げずに変える**（未確定の草案は同一版で直してよい — ハード制約）

## 完了後

- **確定は人**（開発者。デザイン担当がいれば確認役に立つ — 任意・非ブロッキング）。
  **人がキャプチャと突合して確定する。** skill は確定を代行しない。
  **人は §1-2 の行の `確定` を `済` に直す**（`by` / `recorded_by` つき — →「改訂の記録と確定の担体」）。
  **ルート C の突合先は案件の既存画面のキャプチャ**（無ければプリセットの抽出元）。
  **確定なしに画面マップ（SD-0）へ進めない**
- **改訂者を案件で 1 人決める**（既定は開発リード）。誰でも書き足せる状態にしない（版の意味が失われる）
- **2 feature 目以降は本 skill を初回として実行しない。** 版の確認だけを行う
  （改訂が要る場合は**本 skill を改訂モードで実行する** — →「改訂モード」）
- **改訂の起点は 4 つ**（→「改訂モード」）。いずれも**版を上げ、`styleguide.css` を再生成し、
  全 feature の mockup を再生成する**（見た目は全 feature に同じ版で効く）。
  **本文の入力（画面設計書・画面マップ）は不変なので、再生成後の目視は見た目の変化だけでよい**
- **案件に 1 枚を保つ。** 改訂は追記で積もる。文書が莫大になりエージェントが読み切れなくなる兆候
  （追記候補が消化しきれず溜まる / 改訂のたびの全 feature 再生成が重い / 記述の読み落とし・矛盾を拾う）が出たら、
  **分割ではなく DS（構造化データ — トークン・部品仕様・ブランド原則）への落とし込みを判断する**。
  方向は **STYLEGUIDE.md → DS の一方向**で、その時点で工数をかけて行う（先回りして DS を作らない）
