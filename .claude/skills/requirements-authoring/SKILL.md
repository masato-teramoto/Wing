# requirements-authoring（Phase 4: requirements 作成）

各 feature について「**何を作るか / 完了の判定基準は何か**」を確定する。

- 成果物: `specs/<feature-name>/requirements.md`
- テンプレート: `Templates/specs/_template/requirements.md`

---

## 入力

| 項目 | 内容 |
|---|---|
| 要求一覧 | `.aidd/requirement-list.md`（**`approved`**） |
| steering | `steering/` 一式（全文） |
| feature-list | `.aidd/feature-list.md`（**`approved`**。生成順の参照元） |

---

## 生成単位（守らないと修正が feature 数分に膨らむ）

- **1 feature ずつ**、`feature-list.md` の **優先度順**に生成する。全 feature を 1 回の生成で出力しない。
- **品質ゲートは生成単位と同じ粒度で通す。** 1 feature 分を書き終えるたびに feature スコープのゲートを通し、**`approved` まで進めてから次の feature に移る**。
  - 生成を分割しながらゲートを一括にすると、1 本目の誤り（要件の粒度・AC の書き方・要求IDの紐づけ方）が 2 本目以降にもそのまま繰り返される。
- 全 feature が `approved` になり、**横断スコープのゲートの指摘に対する ③ の判断が済むまで Phase 5 へ進まない**。

---

## 手順

### 1. 対象 feature を選ぶ

`.aidd/feature-list.md` の優先度順に 1 つ選ぶ。

### 2. テンプレートを埋める形で作成する

- **要件ID は数値のみ**（`1`, `1.1`）。要求ID（`REQ-` 接頭辞付き）とは名前空間を分ける。アルファベット ID を使わない。
- 受入基準は **EARS 形式**で記述する。パターンはテンプレートの早見表を正とする。
- **各要件に、由来する要求ID を紐づける。**
- **`feature-list.md` の当該 feature の「対応要求ID」を分母とし、取りこぼしが無いか自己確認する。**

### 3. 壁打ちで未記入箇所を埋める

下記 §未記入箇所の質問化 に従う。

### 4. feature スコープの品質ゲートを通す

`requirements-check-subagent` を **別コンテキストで**起動し、スコープに `成果物単位（<feature 名>）` を指定する（起動時の制約は `.claude/skills/aidd-flow/SKILL.md` §5 Step 3）。**指摘の要約は呼び出し元へ返す。③ の提示と人間の判断の反映は呼び出し元が行うため、本 Skill が人間へ承認を求めない。**

### 5. 繰り返す

1〜4 を feature の数だけ繰り返す。**当該 feature が `approved` になるまで次の feature の生成に進まない。**

### 6. 横断スコープの品質ゲートを通す

全 feature が `approved` になったら、`requirements-check-subagent` を **スコープ `横断`** で起動する。**指摘の要約は呼び出し元へ返す。** 引き下げ・差戻しの要否は ③ が判断する。

- 横断スコープは **承認対象の文書を持たないため status を遷移させない**。
- 引き下げられた requirements は修正後、**feature スコープのゲートから通し直す**。

---

## 壁打ちで出た内容の切り分け（最重要）

壁打ちで出た内容は、**既存要求の詳細化か新規要求かを必ず切り分ける。**

| 判定 | 条件 | 行うこと |
|---|---|---|
| **詳細化** | 要求一覧のいずれかの要求に **含まれると読める** | 要件として書き、その要求IDに紐づける。要求一覧は変えない |
| **新規要求** | **どの要求にも属さない** | **Phase 1 へ戻す** |

- **本フェーズが要求一覧を書き換えることはない。** Phase 1 の壁打ちとして改めて確定され、出典種別 `壁打ち` で追記・再承認されたものを待つ。
- **要求一覧に無い要求を要件として書かない。** 書くと要件ID → 要求ID の突合が成立しなくなる。
- **既存要求の詳細化で足りるものを新規要求に昇格させない。** 昇格させるとフロー全体が巻き戻る。

## 未記入箇所の質問化

1. テンプレートから **`<UPPER_SNAKE>` 系統**のプレースホルダー（記法と扱いは `.claude/skills/aidd-flow/references/status-protocol.md` §7 を正とする）を抽出し、**セクション単位**で人間に提示する。`{{...}}` 系統は機械的に埋めるため質問化しない。
2. 提示は「この項目の根拠が要求一覧 / steering に無い」という形にする。**推測した候補を選択肢として並べない。**
3. 受入基準が **観測可能な書き方になっていない**箇所（何をどう確かめれば満たしたと言えるかが読み取れないもの）は、**その場で質問して確定させる**。本フェーズのゲート ② も同じ観点で検査するが（指摘のみ）、**書き方を決められるのは壁打ちの場だけ**である。ここで確定しないまま進むと Phase 7 で「検証不能」として差戻され、design / tasks を巻き込んで作り直しになる。
4. **埋める必要がないプレースホルダーは、人間が明記した不要理由を記載して保持する。削除しない。**
5. 未回答が残る場合は `phase-progress.json` の `waiting_for` を `human_answer`、`open_placeholders` を **不要理由が明記されていない未記入数**に更新して停止する。

---

## Dependencies / Adjacent の書き方

- 宣言する依存・隣接への期待は、**`feature-list.md`（依存の SSoT）の `依存` 列と食い違わせない。**
- 他 feature に期待する責務を書く場合、**受け手側の In Scope に存在するか**を意識する。存在しない期待は横断スコープのゲートで「受け手不在」として報告される。
- 依存関係そのものを本ファイルで新設しない。必要なら `feature-list.md` の更新（Phase 3）を人間に提案する。

---

## 禁止

- 全 feature を 1 回の生成で出力すること。
- 当該 feature が `approved` になる前に次の feature へ進むこと。
- 要求一覧を書き換えること。
- 要求一覧に無い要求を要件として書くこと。
- 要件ID にアルファベットを使うこと、要求IDと同じ名前空間で採番すること。
- プレースホルダーを削除すること。
- `approved` でない要求一覧・feature-list を入力にすること。
- 自ら `status: approved` にすること。
