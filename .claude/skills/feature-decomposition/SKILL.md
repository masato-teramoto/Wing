# feature-decomposition（Phase 3: Feature 分割）

> 出典: フロー設計 `03_Feature分割フェーズ設計書.md`。

要求一覧を満たすために必要な feature を洗い出し、**実装順序の根拠（優先度・依存）を確定**する。

- 成果物: `.aidd/feature-list.md`
- テンプレート: `Templates/Flow/feature-list.md`
- **`feature-list.md` は優先度・依存の SSoT である。** Phase 4 以降は本ファイルを正として参照する。

---

## 入力

| 項目 | 内容 |
|---|---|
| 要求一覧 | `.aidd/requirement-list.md`（**`approved`**） |
| steering | `steering/` 一式（**`approved`**。全文） |

---

## 手順

### 1. feature を洗い出す

Input から、要求を満たすシステム開発のために必要な feature を洗い出す。各 feature に **種別・実装優先度・feature 間依存・対応要求ID** を付与する。

- スキーマ項目はテンプレート（`Templates/Flow/feature-list.md`）を正とする。
- **対応要求ID の分母は、分類が `機能` の要求のみ**である。`非機能` / `制約` は feature ではなく steering に反映されるため、feature へ割り当てない。

### 2. 種別を判定する

判定は次の一問だけで行う。

> **この feature だけが出来上がった状態で、誰かが用事を済ませて終われるか。**
> 終われる → **User Feature** / 終われない（他の feature の中で使われる）→ **Platform Feature**

- 利用者には **運用者・管理者も含む**。社内向けの管理機能も User になりうる。
- **画面の有無では決めない。** 主目的で決める（ログインは操作を伴うが、用事はその先にあるため Platform）。
- 同じ題材でも切り口で変わる。監査ログを**記録する仕組み**は Platform、監査担当が**検索して確認を終えられる機能**は User。
- **「前提かどうか」は種別ではなく `依存` 列が持つ。** 先に作る必要があることを理由に Platform としない。

### 3. 大きすぎる feature の分割を提案する

次のいずれかに該当する feature について、AI が分割案を提示する。**分割の採否は人間が決める。**

- 想定規模が「大」
- 対応要求ID が **独立した複数目的**にまたがる

### 4. 優先度を付ける

次の順で決める。

1. **依存に基づく必須先行を機械的に決定する**（AI が算出）。
2. 必須先行で順序が決まらない範囲は、**`steering/product.md` の主要ユースケース・提供価値と要求一覧を根拠に AI が並べる**。根拠が無い場合は推測で並べず、**質問して停止**する。
3. Phase 4 以降の微修正は可。ただし **依存の逆転は禁止**。

**優先度は AI が決定する。** 人間による並べ替えは必須工程としない。異議はレビューで指摘され、修正して再承認する。

- 依存に **循環が無いこと**を確認する。循環がある場合は優先度を確定できないため、依存の見直しを人間に提示して停止する。
- 依存が複雑で表だけでは追えない場合のみ、テンプレートの依存関係図のスロット行を Mermaid のコードフェンスに置き換えて記述する。図の要件はスロット直前の注記に従う。不要な場合は**スロット行を残し、直後に HTML コメントで不要理由を書く**（削除しない）。

### 5. 品質ゲートを通す

`feature-check-subagent` を **別コンテキストで**起動する（起動時の制約は `.claude/skills/aidd-flow/SKILL.md` §5 Step 3）。**指摘の要約は呼び出し元へ返す。③ の提示と人間の判断の反映は呼び出し元が行うため、本 Skill が人間へ承認を求めない。**

## 本ファイルに書かないこと

| 内容 | 正の所在 |
|---|---|
| スコープ・完了条件 | `specs/<feature>/requirements.md`（`Boundary Context` / `Acceptance Criteria`） |
| 横断の方針・制約 | `steering/`（feature にしない） |
| 要求文・出典・分類 | `.aidd/requirement-list.md` |

- **要求一覧に「対応 feature」列を書き戻さない。** 対応関係の正は本ファイルの「対応要求ID」のみである。要求一覧は Phase 1 が所有し `approved` 済みであるため、Phase 3 が書き戻してはならない。

---

## 不足情報の質問化

1. feature の洗い出しで判断がつかない箇所を、**要求ID 単位**で人間に提示する。
2. 提示は「この要求をどの feature が担うか判断できない」「この要求の対象範囲が特定できない」という形にする。**推測した候補を選択肢として並べない。**
3. 優先度が根拠から決まらない箇所は、**どの feature 同士の順序が決まらないか**を明示して質問する。
4. **埋める必要がないプレースホルダーは、人間が明記した不要理由を記載して保持する。削除しない。**
5. 未回答が残る場合は `phase-progress.json` の `waiting_for` を `human_answer`、`open_placeholders` を **不要理由が明記されていない未記入数**に更新して停止する。

---

## 禁止

- `非機能` / `制約` の要求を feature に割り当てること。
- 要求一覧を書き換えること（Phase 1 の所有物）。
- 根拠なく優先度を並べること。
- 依存の逆転を含む優先度を出すこと。
- 分割の採否を自分で決めること（提案までが本 Skill の範囲）。
- 先に作る必要があることを理由に種別を Platform とすること。
- `approved` でない要求一覧・steering を入力にすること。
- 自ら `status: approved` にすること。

---

## 新規要求が判明した場合

feature の洗い出し中に、要求一覧に無い要求が必要だと判明した場合は **要求一覧を書き換えず Phase 1 へ戻す**。Phase 1 の壁打ちとして確定され、出典種別 `壁打ち` で追記・再承認されたものを待つ。
