# prohibition-authoring — 規範文（禁止・要求）の書き方

## 起動時に確定する項目（dispatch）

- **mode** — `authoring`（これから書く）／`review`（既存の規範文を判定する）。依頼者の明示を優先し、
  明示がなければ対象と操作から一意に判定できる場合のみ自動で決める。**一意に決まらないときは質問して停止する**。

本パックは project profile を読まない。

## ルールA: 文体

- **A-01 曖昧語を規範文に使わない**: 規範文は**命令形＋検証可能な述語**で宣言的に書く。強度の根拠が
  示されない "should"・"consider"・"prefer" 等の助言語を規範文の中心に置かない。
- **A-02 強度は標準語彙で明示する**: **MUST／SHALL**（絶対要件）・**SHOULD**（推奨・例外の余地あり）・
  **MAY**（任意）を使い、独自の強度表現を発明しない。
- **A-03 検出方法と実例を随伴させる**: 各規範に、**どう検出するか**（grep・検査手順・観測点）と、
  **違反形と準拠形の具体例**を添える。抽象的な禁止文だけを置かない。

## ルールB: 例外の扱い

- **B-01 例外は独立した条件文として書く**: 実在する例外は「**観測可能な条件をキーにした独立の条件文**」
  として本文の外に置く。禁止本文に「ただし〜の場合を除く」を差し込まない。
- **B-02 除外節で射程を切ろうとしない**: 「〜には適用しない」という除外節は**スコープを切らない**——
  除外したはずの対象まで規範が届き、抑制してしまう（実測）。出力の一部を規範の外に置く必要があるなら、
  **観測可能な条件をキーにした独立の条件文**にするか、**規範がそこへ届かないよう構造の側を分離する**
  （章・成果物・適用対象そのものを分ける）。

## ルールC: 失敗タイプに形式を合わせる

規範を書く前に、**対処したい失敗の型**を見極めて形式を選ぶ。

| 失敗の型 | 適した形式 |
|---|---|
| **規律違反**（知っていながら圧力下で破る） | 禁止事項＋検出方法＋ループホール封鎖（下記） |
| **形が悪い**（従うが出力の形状が誤り） | **禁止ではなく positive recipe**——出力が何であるかを部品と順序で宣言する |
| **要素欠落**（必要なものが書かれない） | **構造スロット**（テンプレートの REQUIRED フィールド） |
| **条件依存**（場合によって可否が変わる） | **観測可能な述語の独立した条件文**（B-01） |

**禁止を既定の形式にしない。**

### 規律違反型ではループホールを先回りして閉じる

規律違反型を選んだ場合は、禁止事項と検出方法に次を加える。

1. **既知の回避策を列挙する**: 「参考として残す」「一時的だから例外」「実質は同じ」など、対象の文脈で
   予想される抜け道を `No exceptions` の配下に具体化し、禁止がどこまで届くかを先に示す。
2. **letter と spirit を分離させない**: 文言上の違反は趣旨上の違反でもあると明記し、「趣旨は守った」という
   合理化で禁止を無効化できないようにする。
3. **言い訳と反駁を対にする**: 想定される合理化を `Excuse`、その誤りと取るべき行動を `Reality` とする
   rationalization table を置く。一般論ではなく、対象の規律で実際に起こり得る言い訳を書く。
4. **red flags を置く**: 違反の直前に現れやすい言葉・行動・状態を列挙し、見つけた時点で停止して規範を
   再確認できるようにする。

実在する条件付き例外は B-01 の独立条件文で扱う。ここで閉じるのは、その条件を満たさないのに例外として
扱おうとする回避策であり、正当な条件分岐まで `No exceptions` で消さない。

### 構造と判断規則を置き分ける

出力の節・順序・必須欄は template に置き、AI がいつ何を選ぶかという判断基準と MUST／NEVER は rules に置く。
構造要件を禁止文で代用したり、判断規則を template の見た目へ埋め込んだりしない。

## 落とし穴（実測に基づく注意）

- **形状の問題に禁止で対処すると、禁止した当のものが増えることがある**。「〜を書くな」という規範は
  対象を想起させるため、望ましい形を実例で示すほうが有効な場合がある。
- **本文に nuance の一節を足しただけで、それまで機能していた規範が劣化することがある**。条件を足すなら
  本文の外に独立させる（B-01）。
- **除外節はスコープしない**——「〜には適用しない」と書いても、規範は除外先まで届いて抑制する。
  守りたい部分があるなら構造を分ける（B-02）。
- **規律を守らせるために好意や返報性に訴えない**（同調的な追従を招き、規範の実効が下がる）。

## review 時の出し方

各規範文について、**対処したい失敗の型と採用された形式が適合しているか**（ルールC の表）、規律違反型なら
回避策・letter/spirit・rationalization table・red flags が対象に接地しているか、構造と判断規則の置き場が
分離されているか、曖昧語の有無・強度語彙の適否・検出方法と実例の随伴・例外の置き方を判定し、対象箇所を
引用して指摘する。規範文を書き換えない（判定と修正の分離）。**指摘は【SHOULD】として提示する。**

## 関連パックへの引き継ぎ

- **要求文書そのもの**（受入基準・NFR・スコープ）の記述は `requirement-authoring-core` の領分。
  規範文が要求文書の一部として書かれる場合は、そちらへ handoff する（任意）。
- **規範文の受入判定**は `acceptance-review` へ handoff する。

## 適用範囲外

- 規範の内容そのものの当否（何を禁止すべきか）— 人間と案件の決定事項
- 規範を適用した監査の実施 — 別パックの領分
- severity 語彙・違反時の運用（罰則・例外承認の手続き）— プロジェクトの決定事項
