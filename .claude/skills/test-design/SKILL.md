# test-design — テスト設計の品質とブラウザ E2E の規律

## 使い方

対象の要求・受入条件、影響する機能、既存テスト、既知の不具合を読み、何を観測できれば要求を確かめたと
言えるかを整理する。テストを書く・レビューするときは次の設計表を使い、ルールA（一般）と、
ブラウザを含む場合はルールBを照合する。未決の仕様や実行できない確認は未確認のまま残す。

## 挙動・テスト層・隔離する依存を決める

テスト方針を作る、または対象挙動をどの層で確かめるか検討するときは、次の用途から選ぶ。
一つの層で分からない境界を別の層で補い、同じ期待を理由なく重ねない。

| 層 | 主に確かめること | 実物で通す範囲と依存の扱い |
|---|---|---|
| 単体 | 関数・クラスの業務ロジック、条件分岐、境界の挙動 | 対象の実ロジックを動かし、その外の遅い・外部操作を必要に応じ隔離する |
| 結合 | モジュール間・サービス間の契約、DB・APIとの受渡し | 試験対象の境界を実際につなぐ。対象外の第三者依存は境界で隔離する |
| E2E | UIとバックエンドを通る重要な利用経路、最小限の動作確認 | 制御できる検証用環境で経路を通す。画面だけの応答処理を確かめる試験と分ける |

試験範囲や優先順位を決めるときは、重要な利用経路、複雑なロジック、過去に不具合があった箇所を挙げ、
対応するテストと未確認部分を照合する。件数やカバレッジ率が高いことだけを十分性の根拠にしない。
全案件共通の層別比率・件数や測定方式は置かない。

| 要求・リスク | 確かめる挙動 | テスト層 | 前提・入力データ | 期待する観測 | 実物で通す範囲／隔離する依存 |
|---|---|---|---|---|---|
| 受入条件、重要経路や過去の不具合 | 操作と条件 | 単体・結合・E2Eなど、選んだ理由 | 成立させる状態と与える入力 | 外から確認できる値・状態・表示 | 検証対象の接続、モックにする対象と理由 |

例えば画面が空の一覧応答を適切に表示することは、制御したAPI応答で画面の表示を確かめられる。
画面から作成したデータが自分たちのバックエンドへ保存されることを確かめる試験では、その接続を
モックで置き換えず、制御した検証用バックエンドと保存先まで通す。前者の成功を後者の証拠に代用しない。

## 前提状態と具体的な期待を準備する

- DB・ファイル・キャッシュ・認証状態・モックの呼出履歴など、テスト間に残る状態がある場合は、
  各テストの準備と後始末を決める。専用の状態に隔離するか、各実行後に元へ戻し、他テストの成功や実行順に依存させない。
  既存環境を不用意に初期化せず、対象テストが管理する範囲を明確にする。
- テストを単独で実行できることを確かめ、状態漏れが疑われる場合は順序変更・並列・繰返し実行の
  結果を比較する。結果が揺れたら前提状態や共有依存を調べる。実行していなければ確認済みとしない。
- アサーションや期待結果を書く・見直すときは、要求に対応する具体的な値・状態・表示を選ぶ。
  戻り値が存在する、例外が起きない、といった確認だけで要求を示せるかを確かめる。
  例えば「一覧が返る」だけでは指定件数や内容は示せないため、今回の条件で期待する件数や項目との一致を確認する。
  要求にない数値を発明せず、未決の期待は確認事項として残す。特定のmatcherやエラー文言の全文一致は一律に求めない。

次に、選んだ各テストをルールA/Bとpitfallsに照らして見直す。

## ルールA: テスト設計の品質（工程非依存）

- **A-01 決定性＝タイミング推測の排除**: テストは毎回同じ結果を返す。ランダム性・タイミング依存・共有可変状態を排除する。
  タイミングを推測する任意の待機は「速いマシンで通り CI/負荷下で落ちる」レース条件そのもの。
- **A-02 sleep/固定待機でなく条件ベース待機**: 非同期を待つときは、関心のある実条件（要素状態・イベント・状態遷移）を
  明示的に待つ。例外はタイミング挙動そのもの（debounce/throttle 等）のテストのみで、(a) 先にトリガ条件を待機し
  (b) 既知タイミングに基づき (c) WHY をコメントで文書化する。
- **A-03 mock 挙動をテストしない＝実挙動をテストする**: 検証するのはコードの実挙動であって mock の存在・挙動ではない。
  mock 要素へのアサーション・実装詳細（内部状態・CSS クラス等）へのアサーションを避け、
  ユーザ／呼び出し側から観測可能な挙動を検証する。
- **A-04 mock は境界で・依存理解の上で最小限に・構造は完全に**: mock するのは境界（HTTP クライアント・DB アダプタ・
  キュー等）のみで、純粋関数や業務ロジック内部は実物を使う。mock する前に実メソッドの副作用と当該テストの依存を
  理解する（不明なら先に実装のまま走らせて観測する）。mock データは実 API の**完全な構造**を鏡写しにする
  （使うフィールドだけの部分 mock は下流依存で沈黙故障する）。mock の理由が非自明なら文書化する。
- **A-05 テスト名は挙動を記述する文**: テスト名はシナリオ・操作・期待結果を含む、独立して読める文にする
  （様式の選択—GWT / should_doX_whenY 等—はプロジェクトで決める）。`test1`・`check user` 等の曖昧名を避ける。
- **A-06 1テスト1挙動・1論理アサーション**: 各テストは単一の挙動を検証する。名前に "and" が要るなら分割する。
  1テスト内で無関係な複数事項をアサートしない。

## ルールB: ブラウザ E2E 固有

- **B-01 ユーザ視点のセレクタ**: 要素選択はテスト専用属性または意味的属性（role / label / text）で行い、
  CSS クラス・DOM 構造（nth-child チェーン等）・XPath への結合を避ける（スタイル変更で壊れる brittle selector の排除）。
  具象の属性名・API 名はプロジェクトのフレームワークで確定する。
- **B-02 検証用バックエンドと第三者依存を分ける**: 画面の応答処理を確かめるUI試験では、第三者や不安定な
  バックエンドの応答をネットワーク境界で制御する。UIから自分たちのバックエンドまでの接続を確かめるE2Eでは、
  起動・状態・データを管理できる検証用バックエンドを使い、検証対象の接続をモックで置き換えない。
  どこを実物で通し、何を隔離したか記録する。制御不能な外部オリジンは直接自動化せず、必要なら専用の分離機構を使う。
- **B-03 固定時間待機でなく準備完了条件を待つ**: 操作・検査の前に、要素の可視/有効状態・network idle・
  自動リトライするアサーション等の実条件を待つ。固定タイムアウトを待機手段の既定にしない。
  動的アプリでは**準備完了前の DOM 検査も避ける**（描画前の状態から誤ったセレクタを掴む）。例外の扱いは A-02 と同じ。
- **B-04 成功系・失敗系の両検証**: クリティカルユーザフローに対し、成功シナリオとエラーシナリオ
  （誤入力→エラーメッセージ表示等）の両方を検証する。ナビゲーション・状態更新・エラーハンドリングが検証の三本柱。
- **B-05 観測してから操作（recon-then-action）**: 操作の前に描画後の実状態を観測（snapshot / screenshot / DOM 検査）して
  セレクタ・要素参照を取得し、その観測結果に基づいて操作する。ナビゲーション・モーダル開閉・タブ切替・
  大きな DOM 変化の後は参照が stale になるため**再観測してから続行**する。
- **B-06 失敗診断アーティファクトの捕獲と保存先規律**: trace・screenshot・video・console ログ等の診断証拠を
  捕獲できるよう構成する（失敗時/リトライ時に自動記録）。保存先は「指定パス > 規定の成果物ディレクトリ、
  自己検査用は temp」に従い、任意の場所に新規トップレベルフォルダを作らない。保存したパスは必ず報告する。

## pitfalls（失敗知。規範ではなく「どう失敗するか」の記録）

**mock 濫用の失敗知**:

- 症状「mock の存在を検証して通ったと信じる」— アサーション対象に mock 由来の識別子が現れたら停止。
  mock があれば通り外せば落ちるテストは、実挙動について何も語らない
- 症状「テスト専用メソッドが production クラスに生える」— 追加前に「このメソッドはテスト以外から呼ばれるか」を問う
  （呼ばれなければ test-utils 行き）
- 症状「依存を理解せずに mock して、テストが依存していた副作用ごと消す」—「念のため mock」「遅そうだから mock」は
  red flag。不明なら実装のまま走らせて観測してから最小限に mock する
- 症状「部分 mock の沈黙故障」— mock 作成前に実 API のレスポンス構造を docs/実例で確認したか自問する
- 症状「実装完了・テストはこれから、という完了報告」— 採用したTDDの手順は `test-driven-development` で扱い、ここでは証拠が欠けた兆候として捉える
- 症状「mock がテストより大きくなる」— mock setup が本体より長い・外すと落ちる・必要な理由を説明できない・
  mock が実コンポーネントにあるメソッドを欠いていて mock の変更でテストが壊れる、は「そもそも mock すべきか」を
  疑うサイン。複雑な mock より実コンポーネントの integration テストの方が単純なことが多い

**期待値の現在状態依存**:

- 症状「作成時に通る期待値が、時間経過・データ変化で腐る」— テスト・評価の期待値が生きたデータや環境状態に
  依存していないかを確認する。質問・期待値文中の「currently」「now」等の現在時制語彙が兆候。
  closed な概念（完了した事象）への接地か、固定時間窓での絶縁かを問う

## 自己確認に使う検査候補

- sleep 系 API の grep（候補抽出は機械・例外該当の判定は文脈判断）
- アサーション内の mock 由来識別子（`-mock` 系）の grep
- テスト名の様式照合と名前中の `" and "` 検出
- **順序シャッフル実行・並列実行・複数回実行での結果一致検査**（状態漏れや実行条件への依存を実際に確かめる）
- セレクタ禁止側（nth-child / XPath / CSS クラス直参照）の grep・固定待機 API の grep・両系検証の構造的存在

具象の API 名・パターンは言語／フレームワーク依存のため、プロジェクトで確定してから検査に使う。
検出した候補は、タイミング自体のテストなどの文脈と照合する。パターンへの一致だけで正式な合否を決めない。

## プロジェクトで決める項目（本パックは値を持たない）

- **test pyramid の比率・カバレッジ目標値・1ファイルのテスト数上限** — 文脈依存の数値であり本パックは既定を持たない
- **テスト名の様式**（GWT / should_doX_whenY 等）— 1系に固定して記録する
- **具象のセレクタ属性名・待機 API・モック API** — フレームワーク確定後に決定的検査へ落とす

## 設計したテストを自己確認する

設計表とルールA/Bを照合し、選んだ層で要求の挙動を確かめられるか、状態を隔離できるか、期待が具体的かを見直す。
重要経路・複雑箇所・過去の不具合の確認漏れと、pitfallsの兆候を残す。本パックの助言から正式なPASS/FAILや採点を
作らない。実際のテスト実行の成功・失敗は実出力どおりに記録し、未実行を成功へ置き換えない。

## 設計結果と未確認事項を引き渡す

- 設計表、選んだ層の理由、実物とモックの境界、前提状態の準備・後始末を示す。
- 各確認の期待と実結果を分け、未実行なら予定する方法・必要な環境・確認できない理由を記す。
- 要求や期待が未決の部分、重要なのに未確認の経路、必要な追加確認を引き渡す。件数や率だけで完了を主張しない。
- TDDの進め方は `test-driven-development`、追加で列挙する条件の探索は `edge-case-enumeration` を参照できる。
  別パックの自動呼出しや、常時の併用を本手順から要求しない。

## 適用範囲外

- テスト先行のプロセス規律（RED/GREEN/REFACTOR）— `test-driven-development` の担当範囲
- テスト設計技法の体系（境界値分析・状態遷移・デシジョンテーブル等）— 供給薄・外部源泉が必要
- エッジケースの探索 — `edge-case-enumeration` の担当範囲
- 評価 QA セット設計の規範本体 — 別テーマの資産・現在未供給
- テストデータ管理全般（本番データ・PII の扱い等）— 今回の供給外。ここで扱うのは試験の前提と状態の隔離
