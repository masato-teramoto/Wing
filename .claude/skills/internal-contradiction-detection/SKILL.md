## 概要

同一成果物の異なる項目・セクション間で、内容が両立しない記述になっていないかを検出する。
`ssot-consistency` の「二重定義」（同じ事実の重複）とは異なり、こちらは「異なる事実同士が
論理的に両立しない」ケースを扱う。呼び出し元が対象を指定することで、Phase 1（要求間矛盾）・
Phase 6（system-overview内の矛盾）に使い回せる。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象 | 矛盾を検査する成果物 | `.aidd/requirement-list.md` 全行 / `docs/architecture/system-overview.md` |
| 突合単位 | 何と何を突き合わせるか（任意。無ければ全項目の総当たり） | `要求ID同士` / `セクション間` |

## 手順

1. `対象` から個別の事実・制約・記述を項目単位で抽出する。
2. `突合単位` に従って項目同士を突き合わせ、同時に成立し得ない組（例: 「同期処理のみ」と
   「非同期キューを使用」が両方書かれている）を検出する。
3. 明示的な矛盾（数値・条件が食い違う）だけでなく、前提が食い違う記述（例: 対象ユーザーの
   定義が箇所によって異なる）も対象とする。
4. 矛盾が見つかった場合、両方の記述箇所と引用を `evidence` に書く。どちらが正しいかは断定しない
   （上流で決まっていればそれに合わせる修正案、決まっていなければ選べる案と `質問：…`）。

## この工程で指摘しない事項

- `.claude/skills/finding-rules/SKILL.md` の工程の境界の表・`confirmed_answers`・`learned` に当たる事項
- `TBD（<工程> で確定）` と書いてある値

当たるものは指摘にせず、除外として返す（除外の出典を付ける。書き方は finding-rules）。

## 出力の形

指摘ごとに次を返す。書き方は `.claude/skills/finding-rules/SKILL.md`（検査の最初に読む）に従う。重大度は出さない（L3 が `kind` から決める）。

```
{ location, subject, kind, summary, evidence, suggestion, recommendation, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `location` | 矛盾する一方の記述箇所（もう一方は `evidence`）。`<案件相対パス> § <節見出し> / <ID>` の形。複数箇所なら代表 1 か所＋「ほか n か所」（全件は `evidence`） |
| `subject` | 対象の語（例: `REQ-003`） |
| `kind` | `.claude/skills/finding-rules/SKILL.md` の種類から 1 つ選ぶ。迷ったら上の行。通常 `業務の欠落・矛盾` |
| `summary` | 60 字以内。結論を先に、何が・どこで（例: 「`REQ-003` と `REQ-011` で同期／非同期の前提が食い違う」） |
| `evidence` | 矛盾する両方の記述箇所と引用 |
| `suggestion` | 修正案（差分・書き換え文）。業務の新しい事実が要るときは、修正案ではなく「何を決めればよいか」と選べる案 |
| `recommendation` | `修正：理由` / `差戻し：理由` / `対応せず進める：理由` / `質問：理由` のどれか。業務の新しい事実が要るときは `質問：…` |
| `is_rollback_candidate` | 通常 `false`（同一フェーズ内での調整で解消できるため） |

## 禁止

- 対象成果物を書き換えない（どちらが正しいかを決めて統合しない）
- 合否を出さない
- 業務の新しい事実が要る値を自分で決めない。`suggestion` に「何を決めればよいか」と選べる案を書き、`recommendation` を `質問：…` にする
