## 概要

`steering/non-functional.md`（および関連する `steering/architecture.md`）が、この配布資材が採用する8つの観点（機能適合性・性能効率性・互換性・使用性・信頼性・セキュリティ・保守性・
移植性）それぞれについて、方針の記述を持っているかを検証する網羅性検証である。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象 | 検証する成果物 | `steering/non-functional.md` / `steering/architecture.md` |
| 特性一覧 | 網羅を確認する基準（既定はこの配布資材の8観点。採用規格の版・特性は案件の指定を優先する） | 機能適合性・性能効率性・互換性・使用性・信頼性・セキュリティ・保守性・移植性 |
| 突合元 | 各特性の検討の起点（任意） | `.aidd/requirement-list.md` の非機能/制約要求 |

## 手順

1. `対象` を通読し、`特性一覧` の各特性に対応する記述が、次の判定基準を満たすかを1特性ずつ確認する。

   | 特性 | 判定基準 |
   |---|---|
   | 性能効率性 | 応答時間・スループット・キャパシティ等の目標が記述されているか |
   | 信頼性 | 可用性目標・障害復旧（DR）・事業継続（BCP）方針が記述されているか |
   | セキュリティ | `steering/security.md` に認証・認可・暗号化・監査ログ等の方針があるか（詳細は STRIDE 網羅性で担保するため、ここでは有無のみ） |
   | 保守性 | コーディング規約・テスト方針・ドキュメント方針が記述されているか |
   | 移植性 | インフラ・実行環境の移植性要件が（該当する場合）記述されているか |
   | 互換性 | 既存システム・外部システムとの共存・相互運用性要件が（該当する場合）記述されているか |
   | 使用性 | UI/UX 方針が（該当する場合）記述されているか |
   | 機能適合性 | 非機能 / 制約要求の反映突合（traceability）で担保済みのため、ここでは重複して検査しない |

   `突合元` が指定されていれば、要求一覧の非機能/制約要求と対応づけて検討済みかを特性ごとに見る。
2. 記述が全く無い特性、または名前だけ触れられていて具体的な方針を持たない特性を洗い出す。
   データガバナンス（保持期間・削除・越境移転）は信頼性/セキュリティの下位観点として含める。
3. 該当しない特性（例: UI を持たないバッチの使用性）は、「不要」とその理由が明記されていれば指摘しない。
   理由の無いまま抜けている特性だけを指摘する。
4. セキュリティ特性については `steering/security.md` に方針がある場合、二重管理を避けるため
   `non-functional.md` 側は参照で足りるとみなす（実体があれば網羅とみなす）。
5. 非機能反映突合（traceability）で既に未反映と指摘された要求IDは、同じ記述箇所を理由に重ねて指摘しない。

## 出力の形

```
{ id, location, finding, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `id` | この Skill 内で一意な通し番号 |
| `location` | 記述が欠落している特性名 |
| `finding` | 欠落の事実（例: 「ISO/IEC 25010の『移植性』に対応する方針が `non-functional.md` に無い」） |
| `is_rollback_candidate` | 通常 `false`（同一フェーズ内での追記で解消できるため） |

## 禁止

- 対象成果物を書き換えない（方針を自動で追記しない）
- 合否を出さない
- 記述の質（妥当性）までは判断しない（有無の網羅性のみ。妥当性は `evidence-guard` 等が扱う）

この観点表による記述の有無の確認を、ISOの最新版への適合性認証として報告しない。規格の版や適用範囲が未指定なら、使用した観点一覧を明示する。
