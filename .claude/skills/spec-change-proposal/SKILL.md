# spec-change-proposal — 仕様変更提案の作成とレビュー

## 使い方

まず依頼が重大な仕様変更の提案・レビューに当たるかを確認する。意味・範囲・受入条件・公開契約を変えない誤字や表記の訂正は、案件の既存の変更管理と依頼の承認範囲で `requirement-authoring-core` に渡す。本Skillの方言設定や独立提案を要求しない。意味を変えるが重大ではない変更も、案件の既存の変更管理へ渡す。意味の変化・重大度・適用する手続きが不明なら、その判断を名指しして確認する。軽微か不明な修正を黙って適用しない。

以下は、本Skillの対象となる重大な変更の提案・レビューに適用する。

**必須入力**（不足したまま始めない・不足時は何が足りないかを名指しして停止する）:

- **authoring**（提案をこれから書く）: **現行基線**（変更対象の確定済み仕様・要求）＋**変更要求**（何をなぜ変えたいか）
- **review**（提出済み提案を見る）: **現行基線**＋**既存提案**（判定対象の変更提案文書）

変更は本体仕様への黙った上書きではなく、**独立した提案として起草し、レビューと明示承認を経てから本体へ反映する**
（二段構造）。承認前に本体を書き換えない。提案文書の中では、各変更を分類マーカーの配下に置き、分類なしの散文変更を作らない。

## 起動時に確定する項目（dispatch）

依頼者の明示指定を優先し、明示がなければ下記の順で解決する。**一意に決まらないときは質問して停止する**
（推測で走らない）。

- **mode** — `authoring`（これから作る）／`review`（提出済みを判定する）。対象と操作から一意に判定できる
  場合のみ自動で決める。
- **change_format_profile**（authoring）— ① 明示 → ② project profile → ③ 質問して停止。値は
  `generic` / `openspec` / `bmad` のいずれか。
  **review では project profile を使わず、提出物の構造から決める**——各方言の必須マーカーを照合し、
  **1方言だけ一致したときのみ採用**する。2方言以上が一致したら停止。どれも完全一致しないが方言の
  マーカーが残っている場合も停止（壊れた方言を中立形式に落とさない）。マーカーが一切なく中立形式の
  条件も満たさない場合も停止する。
- **deferred_slots_extended** — `effective` は「project profile が true」または「明示が true」。
  **project profile が true のときに明示 false で緩めることはできない**——人間の緩和承認がある場合に
  限り、**当該成果物のみ** `effective = false` とし、**承認者・日時・対象**を成果物に記録する。
  3点のいずれかを欠く承認は無効として停止する。

project profile が**設定されているのに読めない**場合（ファイル欠落・権限・書式不正・型不正）は、
「設定されていない」と同じ扱いにせず、読めなかった旨を明示して停止する。

## 変更の分類（change kind）

各変更に次の6種のいずれかを付す。**分類の境界**:

- **ADDED** — 新しい要求・仕様項目の追加。
- **MODIFIED** — 対象の**同一性と基本目的を維持した**変更。
- **REMOVED** — 項目の廃止。**理由（なぜ廃止か）と移行先（利用者はどこへ移るか）を必須**で随伴させる。
- **RENAMED** — 参照名の変更（実体は維持）。
- **DEFERRED** — 今回は実施せず先送り。**基本スロット＝変更前の状態と理由**。project profile の
  `deferred_slots_extended` が effective のときは、**deferral 先と再開条件の2欄が必須**（案件制約）。
- **REDEFINED** — 同じ追跡対象を**根本的に置換**する（同一性は保つが目的・内容が入れ替わる）。

同一性も維持しない変更は、`REMOVED` と `ADDED` に**分解**する。**`BREAKING` は6種と直交する属性**であり、
破壊的な変更にのみ付す（分類の代わりに使わない）。

**変更の書き方（分類によらず共通）**:

- `MODIFIED` / `REDEFINED` 相当は **変更後の完全な内容**を示す。断片だけの差分にしない（マージ時に情報が失われる）。
- **すべての変更に理由を添える**。理由なき変更・黙った変更を作らない。

## 方言別の描画

`change_format_profile` の値に従って描画する。**分類の意味は方言に依存しない**（描画だけが変わる）。

**6種 × 3方言の対応（固定）**——**畳む場合は、項目内に `change_kind: <CANONICAL>` を必ず併記する**
（畳んだ先のラベルだけでは元の分類が復元できず、レビュー時に案件制約〔DEFERRED 拡張2欄〕の要否を
判定できなくなるため）:

| change kind | `generic` | `openspec` | `bmad` |
|---|---|---|---|
| `ADDED` | `change_kind: ADDED` | `## ADDED Requirements` | `Add new` |
| `MODIFIED` | `change_kind: MODIFIED` | `## MODIFIED Requirements` | `Modify existing` |
| `REMOVED` | `change_kind: REMOVED` | `## REMOVED Requirements` | `Remove or defer` ＋ **`change_kind: REMOVED` 併記** |
| `RENAMED` | `change_kind: RENAMED` | `## RENAMED Requirements` | `Modify existing` ＋ **`change_kind: RENAMED` 併記**（この方言に改名ラベルは無い） |
| `DEFERRED` | `change_kind: DEFERRED` | **表現不能 → 停止** | `Remove or defer` ＋ **`change_kind: DEFERRED` 併記** |
| `REDEFINED` | `change_kind: REDEFINED` | `## MODIFIED Requirements` ＋ **`change_kind: REDEFINED` 併記** | `Completely redefine` |

- `openspec` の **DEFERRED は表現不能につき停止**する——例外は、依頼者が分類自体を人間の判断で変更した
  場合と、新しい種別スロットを合意のうえ導入して再検証した場合のみ。
- `bmad` の `Remove or defer` は2つの分類を畳むラベルであるため、**併記された `change_kind:` が
  `REMOVED` か `DEFERRED` かで区別する**。review 時に `DEFERRED` を見つけたら、`deferred_slots_extended`
  が effective なら**拡張2欄（deferral 先・再開条件）の有無を必ず検査する**。
- `BREAKING` は破壊的な場合のみ付す（`generic`・`openspec` とも分類とは別の属性として置く）。
- `bmad` では**各項目に `OLD:` と `NEW:` の対**と**対象 ID または節名**を必ず持たせる。

### OpenSpec profile の追加規則

`change_format_profile = openspec` のときだけ、次を適用する。

- Scenario 見出しは `#### Scenario: <name>` の形にし、`#` はちょうど4個にする。3個や箇条書きへ
  変えない。`MODIFIED` に置く requirement の
  見出しは現行基線の見出しと厳密に一致させる（空白差は無視してよい）。タスク一覧も同時に作る場合は、
  各タスクを `- [ ] X.Y` の checkbox 形式にする。
- 既存挙動を変えずに新しい関心事を足すなら `ADDED` を使う。`MODIFIED` は、現行基線に存在する requirement の
  挙動を変える場合だけに使う。
- 名前だけを変える変更は `RENAMED` に置き、`FROM:` と `TO:` の対で旧名と新名を示す。挙動も変わるなら
  名前だけの変更として扱わず、該当する変更を別に分類する。
- delta spec に含めるのは要求・仕様レベルの挙動が変わる項目だけにする。実装方法だけが変わり、外部から
  観測できる挙動が変わらない項目は delta spec へ入れない。

### BMAD profile の経路評価

`change_format_profile = bmad` のときは、推奨案を選ぶ前に次の3経路をすべて評価する。

1. **Direct Adjustment** — 現行計画の中で直接修正する
2. **Potential Rollback** — 完了済み作業を巻き戻して単純化する
3. **MVP Review** — スコープ縮小または目標修正を行う

各経路に工数とリスクを付け、`Viable`／`Not viable` を明示してから推奨経路を選ぶ。組合せが最善なら
Hybrid を選んでよい。選定理由は、工数・時期、技術リスク・複雑性、チームの士気・勢い、長期保守性、
stakeholder の期待・事業価値の5軸を走査し、触れない軸は対象外と理由を示す。

**形式の判定規律（review 時に方言を見分けるとき）**:

- マーカーとして認めるのは**上表の canonical な有限集合のみ**。大文字小文字を区別せず、**行の完全一致**で
  照合する（行中の部分一致は取らない）。
- `## Impact` `## Rationale` `## Business Requirements` のような**通常見出しは無視**する（変更区分の
  見出し・ラベルだけを見る）。
- **`change_kind:` を伴わない裸の `ADDED` 等は中立形式と認めない**（形式不明として停止する）。
- `bmad` は**各ラベルから次のラベル直前までを1項目ブロック**とし、**ブロックごとに** `OLD:`／`NEW:`／
  対象 ID または節名を検査する（文書全体に1つずつあれば足りる、とはしない）。

## 変更の重大度（significance）

本手順は**プロジェクトの方向性に影響する重大な変更**のためのものであり、軽微な修正には使わない。
重大度が判定できない場合は **UNKNOWN として扱い、そのまま進めない**（推測で軽微側に倒さない＝停止する）。
判定には**具体的な証拠**（エラー・stakeholder の申し入れ・技術制約の実測）を要求し、証拠が無い状態で
影響分析へ進まない。

## 影響分析（impact inventory・5面）

変更提案には影響分析の節を置き、次の5面を**列挙的に**カバーする。触れない面がある場合は「対象外」と
明示する（沈黙で飛ばさない）。

1. **計画単位**（epic / マイルストーン）— 現行計画の完遂可否・将来計画の見直し要否・順序と優先度への影響
2. **要求文書**（PRD 相当）— コア目標との衝突・要求の増減・最小スコープの達成可否
3. **アーキテクチャ** — コンポーネント／パターン／技術選定／データモデル／API 契約／連携点
4. **UI・UX** — 対象画面と体験への影響
5. **二次成果物** — デプロイ手順・IaC・監視・テスト戦略・ドキュメント・CI/CD

必須入力（現行基線）が部分的にしか無い状態で影響分析を始めない。**必要な文書が見つからなければ停止する。**

## 提案文書の構成

1. **課題の要約** — 問題文・発見された文脈・証拠
2. **影響分析** — 上記5面（計画単位／要求／技術／成果物の4象限に整理してもよい）
3. **推奨する対処** — 選定した経路と理由、工数・リスク・時期の見積り
4. **具体的な変更提案** — 成果物ごとの編集提案（要求文書＝対象節の特定とスコープへの影響／アーキテクチャ＝
   影響コンポーネントと波及／UI・UX＝対象画面と体験への接続）
5. **次の一手** — 承認後に誰が何をするか

影響評価のチェックは **完了／対象外／要対応**の3値で記録し、要対応が残るまま「完了」と宣言しない。
完遂できない場合はブロッカーを特定して止まる。

## 関連パックへの引き継ぎ

- **要求・受入基準・NFR・スコープの記述そのもの**を書き直す作業は `requirement-authoring-core` が所有する。
  本パックは変更提案の形式と影響分析を扱い、要求本文の規範はそちらへ handoff する。未導入の場合は、
  必要な記述変更を提案として示すにとどめ、要求本文の代筆はしない。
- **禁止事項の記述**が変更に含まれる場合は `prohibition-authoring` へ handoff する（任意）。
- **被覆への影響**（変更により写像が壊れる・未被覆が生じる）は `traceability-audit` へ redirect し、
  変更承認後の**再監査**を handoff する。本パックは被覆率や被覆状態を確定しない。
- **提案の受入判定**（承認／差し戻し）は `acceptance-review` へ handoff する。本パックの成果物は変更提案と
  影響分析であり、承認そのものではない。**人間が最終決定者**である。

## 適用範囲外

- 変更内容の是非そのもの（採否の意思決定）— 人間と受入判定の領分
- 承認後の本体仕様への反映・台帳同期の実施 — 本パックは提案までを扱う
- 変更に伴うタスク分割・実装計画 — `implementation-planning` の領分
- 軽微な修正の手続き — 本手順は重大な変更専用
- レビュー進行の UI 様式 — 案件の決定事項
