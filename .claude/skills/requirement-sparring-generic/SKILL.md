# requirement-sparring-generic — 要件壁打ちの generic 観点パック

## 使い方

対象の要求文書を以下の観点で走査し、ギャップを指摘する。指摘は必ず**対象箇所（節・行・引用句）を引用**し、
何が欠落・曖昧・違反かを名指しし、実行可能な修正方向を1行添える。抽象批判・網羅的チェックボックス列挙はしない。
文書を直接修正しない（判定と修正の分離）。未確定と思われる箇所は推測で補完せず、質問として表面化する。

## 観点1: 受入基準の品質

- 各受入基準は自動テスト可能／明示的に検証可能な具体性を持つか。検証不能な願望記述を指摘する。
- 受入基準は観測可能な振る舞い（入力・出力・エラー条件）か。実装内部詳細（tech stack・内部クラス/関数名・
  ライブラリ選定・内部処理手順）の混入を指摘する（公開 API シグネチャは What 側＝違反でない）。
- 各機能要求／ユーザーストーリーに受入基準が最低1件紐づいているか。宙に浮いた要求を指摘する。
- 各受入基準は「条件／トリガ → 期待される応答」の構造（GWT / EARS 相当）か。素の散文を指摘する（特定方言は強制しない）。
- 測定可能な境界で書かれているか。境界なしの曖昧形容詞（"fast" / "user-friendly" / "reasonable"・
  「高速」「使いやすい」等）を全件指摘する。
- 未確定事項が明示マーカー（NEEDS CLARIFICATION / Open Questions / [ASSUMPTION] 等）で表面化されているか。
  推測による断定・仮定の無断混入を指摘する（マーカー語彙は固定しない。存在と回収可能性を見る）。
- 要求強度の助動詞（shall / must / should、RFC 2119 相当）で強度が明示されているか（Requirement レベルの被覆で可）。
- happy path だけでなく境界・エラー条件・異常系（edge cases）が受入基準に含まれるか。正常系のみの集合を指摘する。
- 生成者の仮定が確認済み要求のように混入していないか。複数解釈の余地は質問で解消し、残す仮定は Assumptions 節へ
  隔離されているかを確認する。

## 観点2: 非機能要求（NFR）

- 主要4カテゴリ（Performance / Security & Privacy / Reliability & Availability / Compliance）のそれぞれに
  「対象」または「対象外」の明示宣言があるか。無宣言の欠落（silent omission）を指摘する。
  他カテゴリ文中の傍論的言及は宣言と数えない。
- 対象カテゴリの記述が数値閾値または具体的なユーザ/オペレータ観測可能な期待に変換されているか。
  閾値なきボイラープレート（「スケーラブル/セキュア/高信頼であること」のコピペ＝NFR theater）を指摘する。
- NFR の数値はドメイン固有の単位ファミリ（req/s・p95 レイテンシ・SLA/RTO/RPO 等）で書かれているか。
- 「NFR が指定されているか」自体が文書のチェック項目・レビュー対象になっているか（存在検査）。

## 観点3: スコープ境界

- 対象外（out of scope / Non-Goals 相当）が明示宣言され、配下に実質的な項目が1件以上あるか。
  沈黙は下流が勝手に埋める——宣言欠落・全項目無内容（「特になし」「TBD」のみ）を指摘する。
- スコープは in/out 対の**専用構造スロット**（独立の節・欄・リスト）に置かれているか。散文への埋没を指摘する。
- スコープが誤読されうる場合・隣接システム/外部仕様に触れる場合、「隣接に何を期待し、何を所有しないか」まで
  宣言されているか。
- 省略が「意図的除外」か「単なる書き漏れ」か判別可能か。判別不能な省略（silent de-scoping / silent gap）を
  要求品質の欠陥として指摘する。将来対応を含意する対象外項目に行き先（deferral 先）または理由があるか。
- 対象外項目は下流の判断材料になる実質（機能・ユーザー群・ユースケース単位の特定可能性）を持つか。

## 観点4: 完成度・実質性

- 文書のどこにでも差し替え可能な定型文（furniture / theater）を実質不合格として指摘する——閾値なき品質形容詞・
  どの製品にも入る Vision 文・未解決 placeholder（TODO / TBD / ???）の残存。
- 次工程に進んでよいかの判定を下す文書（ゲート系）なら: 明示的判定語（GO/NO-GO 相当＋根拠）があるか、
  所見に重大度ラベルが付くか、CRITICAL 相当の未解決所見を残したまま合格を宣言していないか。
- 機械的に検査できる事項（構造・スロット存在）と文脈判断を要する事項が区別されているか。

## 観点5: トレーサビリティ・被覆

- すべての要求（FR / AC / シナリオ）が最低1つの下流項目（タスク・実装・テスト・受入基準）に
  **安定 ID の明示参照**で対応づくか。tangential な言及・暗黙の含意を被覆と数えない。
- 逆方向: どの要求にも対応しない下流項目（孤児）がないか。
- 被覆の主張が散文でなく、対応表（要求 ID × 下流 ID）として物質化されているか。被覆率・未被覆件数が
  数値で報告され実態と一致するか。
- 未被覆を埋め草（要求に接続しない filler 項目の発明）で塞いでいないか。未被覆は最高重大度で正直に報告する。

## 関連パックへの引き継ぎ（redirect / handoff）

本パックは**検出専用**であり、文書を直接修正しない。指摘の先にある作業は次のパックが持つ。各 redirect 先が
未導入の場合は、本パックの所見として当該欠落を報告するにとどめ、代筆・代行はしない。

- **受入基準・NFR・スコープの記述そのものを書く／直す作業**は `requirement-authoring-core` が持つ。観点1〜3 で
  検出した欠落の修正は、そちらへ redirect する。未導入の場合は、欠落の所在と修正方向を1行で示すところまでを
  本パックの成果物とし、requirements 本文の代筆はしない。
- **被覆マトリクス・被覆報告を成果物として作る／判定する作業**は `traceability-audit` が持つ。観点5 は壁打ち
  時点での被覆の欠落検出に限られ、監査成果物の生成・被覆状態（COMPLETE／INCOMPLETE／UNDETERMINED）の確定は
  そちらへ redirect する。未導入の場合は、未被覆・孤児の疑いを所見として挙げるにとどめ、被覆率の確定値や
  遷移可否は宣言しない。
- **完成度ゲートの判定レポート**（GO/NO-GO 相当の判定語と根拠を伴う文書）の観点は本パックが持つ（観点4）。
  他パックが完成度ゲートに言及する必要が生じたときは、本パックへ redirect される側である。
- **レビュー結果を受けた受入判定（承認／差し戻し）**は `acceptance-review` へ handoff する。本パックの成果物は
  ギャップ指摘であり、受入 verdict ではない。未導入の場合は、判定に必要な材料（指摘・重大度・位置引用）を
  揃えて明示的に引き渡し、承認の可否は依頼元の人間に委ねる。
- **正式な採点**（0/5/10・Critical Fail・合格閾値）が必要で、判定ハーネス（verifier）と Contract 本体が
  未導入の場合は、採点を代行せず導入要求を出して停止する。

## validation（紐づく Contract の INV/DEV チェックリスト）

成果物の自己チェックに使う。詳細な採点規則（0/5/10・Critical Fail・PASS≥70%）は各 Contract 本体
（factory/contracts/）を参照。

**CT-REF-002（受入基準）**: INV-01 テスト可能性／INV-02 実装詳細の不混入（公開APIシグネチャは可）／
INV-03 要求↔受入基準の紐付け／INV-04 条件→応答の構造化／INV-05 曖昧形容詞禁止／INV-06 未確定の明示マーカー／
INV-07 強度助動詞／INV-08 edge case 被覆。**DEV**: 実装詳細混入・境界なし曖昧形容詞・推測断定＝Critical Fail。

**CT-REF-008（NFR宣言）**: INV-01 4カテゴリの採否明示宣言（傍論的言及は不可）／INV-02 曖昧形容詞→数値閾値・
観測可能期待／INV-03 未確定マーカーの回収可能性（soft hedge「想定」「程度」は正規マーカーでない）／
INV-04 in/out 境界と隣接期待の宣言／INV-05 意図的除外の判別可能性。**DEV**: カテゴリの silent omission・
全面 NFR theater・推測充填＝Critical Fail。

**CT-REF-009（スコープ境界）**: INV-01 対象外の明示宣言＋実質項目≥1／INV-02 in/out 対の独立構造スロット／
INV-03 隣接への期待と非所有の宣言（隣接言及がある場合のみ適用）／INV-04 対象外項目の実質性／
INV-05 将来含意項目の行き先・理由。**DEV**: 宣言の完全欠落/全項目無内容・隣接依存があるのに境界宣言が実質を
欠く・黙ったデスコープ＝Critical Fail。

**CT-REF-010（完成度ゲート判定レポート）**: INV-01 明示判定語＋根拠／INV-02 severity ラベルの一貫付与／
INV-03 theater の flag（該当がある場合のみ適用）／INV-04 位置引用＋実行可能な remediation／INV-05 判定専用
（修正の実施を含まない）／INV-06 機械/判断検査の区別明示。**DEV**: 判定語欠落・CRITICAL 未解決のまま合格宣言・
theater 見逃し・判定と修正の混合＝Critical Fail。

**CT-REF-011（トレーサビリティ成果物）**: INV-01 全要求の安定 ID 写像／INV-02 孤児検査の実施と結果明示
（「点検した」等の曖昧な言明は方法の明示に当たらない）／INV-03 被覆マトリクスの物質化／INV-04 数値報告と
実態の一致（比率は分母を再計算して突合）／INV-05 実質被覆のみ計上（tangential 不可）／INV-06 未被覆の
正直報告・埋め草禁止。**DEV**: 形式的ゼロ写像の虚偽報告・意味的虚偽（被覆偽装）・マトリクス不物質化＝
Critical Fail。複数 edge を束ねた成果物の集約規則（検査項目ごとの最小値・非適用の扱い・重大逸脱の波及）と
verdict の優先順（重大逸脱→不合格 ＞ 全項目非適用→非適用 ＞ 7.0 以上→合格 ＞ その他→**警告**）は
Contract 本体が持つ。被覆監査の成果物そのものを作る・判定する作業は `traceability-audit` の領分。
