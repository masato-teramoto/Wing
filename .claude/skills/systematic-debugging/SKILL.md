# systematic-debugging — 根拠から原因を特定して直す

## 調査の対象と反復の上限を確認する

- 症状、期待する挙動、関連タスク・仕様、修正できる範囲を確認する。
- 案件に定められた修正試行の上限と、上限到達時の引渡先・経路を確認する。
  既存の停止規則がある場合はそれに従う。上限が未設定なら、有限の上限を案件の運用に沿って決めてから修正反復を始める。
  上限が決まらないまま修正を繰り返さない。症状や証拠の読み取りは進められる。
- これまで同じ症状に試した修正と結果を確認し、試行回数に含める。
  仮説や担当が変わっただけで失敗回数をリセットしない。

## 1. 証拠を集めて再現する

- エラーメッセージとスタックトレースを全文読む。発生箇所だけでなく、直前の入力・設定・実行状態を確認する。
- 元の症状を再現する最小の手順を実行し、正確な手順、入力、期待、実際の結果を記録する。
  再現が毎回起きるか、条件によって変わるかも確認する。
- 再現できない場合は、発生時の情報と現在との差を集める。再現不能を推測した修正で埋めない。
- 直近の差分・履歴・依存・設定の変更を調べ、発生時期と照合する。
  緊急時や単純に見える障害でも、この調査を飛ばして修正案を出さない。

### 症状が複数のコンポーネントを通る場合

API→サービス→DB、CI→ビルド→実行環境など、症状が複数のコンポーネントを通る場合は、
処理の経路を並べ、各境界で次の証拠を集める。

1. コンポーネントへ入る値と出る値、必要な環境・設定が次の層へ伝わっているか、各層の状態を観測する。
   既存の診断手段を使い、観測点が足りなければ調査範囲内で必要な計装を加える。原因を直す変更とは分ける。
   秘密値をログへ出さず、設定の有無や期待との差を確認できる情報を残す。
2. 観測点を揃えて同じ再現手順を一度実行し、境界ごとの結果を並べる。例えば次の表を使える。

   | コンポーネント境界 | 入力と出力 | 環境・設定の伝播 | 状態・期待との差 | 観測結果の所在 |
   |---|---|---|---|---|
   | 呼出元→呼出先 | 実際に観測した値 | 必要な設定が届いたか | どの状態から期待を外れたか | 同じ再現実行のログなど |

3. 上流から順に照合し、期待どおりだった境界と、最初に期待から外れた境界を絞る。
   その層を次の原因調査の対象にする。まだ観測できていない層は未確認とし、推測した値で表を埋めない。

### 依存・ランタイムに関わる障害の場合

依存の読込み、ビルド、実行環境の互換性などに関わる障害では、エラー全文に加えて、実際に失敗した
環境のランタイム・依存バージョンを確認する。宣言された版と実際に動いた版を区別し、不明な版は不明と記す。

- webを使える場合は、正確なエラー文言、技術と症状の組合せ、判明した実バージョンで調べる。
  公式ドキュメント、公式リポジトリのissue、対象版のリファレンスや移行情報を優先する。
  検索に秘密値や案件固有情報を含めない。
- 得た情報は適用版・成立条件とローカルの観測を照合する。最新版の説明だけで原因を断定せず、
  原因候補と、それを確かめる次の観測を分けて残す。
- webを使えない場合は利用できるローカル資料と実行環境の調査を進め、外部情報が未確認であることを記す。
  実バージョンが不明な場合も、資料との版一致を確認済みとは扱わない。

## 2. 発生源を追って一つの仮説にする

- エラーが見えた場所から、値・状態を渡した呼出し元を順に遡る。
  各段で「何が入力され、どこで期待から外れたか」を調べ、最初に不正な値・状態を作った箇所を特定する。
- 調査結果を「原因は何か、それを支持する観測は何か」の一組で書く。
  原因と症状のつながりを説明できなければ調査を続ける。
- 一度に検証する仮説を一つにする。仮説が正しければどの観測が変わるかを定め、
  それだけを確かめる最小の変更・実行を選ぶ。複数候補を同時に変更しない。
- 仮説が外れたら結果を残して調査へ戻る。効かなかった修正の上に別の修正を積み増さない。

### 原因が分かったら、対応できる範囲を分ける

環境・タイミング・外部サービスが原因だと観測で裏付けられた場合は、コード修正へ直行せず、
調べたこと・原因を支持する観測・残る不明点と、誰が何を変更できるかを整理する。
単に再現できない、原因がまだ分からないという理由では外部起因と確定せず、証拠収集へ戻る。

| 観測で確かめた状態 | 次に行うこと | 残す情報 |
|---|---|---|
| リポジトリ内で直せ、既存の依頼・編集範囲に収まる | 手順3の最小修正と手順4の検証へ進む | 原因、対象箇所、確認する期待。直せる問題を早々に外部へ渡さない |
| 外部サービス・認証情報・機器などに必要な変更権限がない | 権限のある担当・既存の対応経路へ必要な対応を引き渡す | 発生条件、証拠、必要な権限・前提、依頼する対応、再確認する条件 |
| 確定した環境・タイミング要因に、案件範囲内の対処や観測の追加が必要 | 対処の目的と観測する結果を定め、既存の権限内で実施する。コード変更を伴う場合は手順3・4で確かめる | 原因への対応関係、実施内容・結果、観測手段と未確認事項 |

引き渡したことと問題が解決したことを分ける。権限・前提の不足が残るなら対応待ちとして記録し、
未実施の修正や回帰確認を完了扱いにしない。再試行・タイムアウト・エラー表示・監視を自動で足さず、
判明した原因に必要な対処か、今回の範囲で扱えるかを確認して選ぶ。
例えば外部サービスの停止が観測で確認され、復旧権限がない場合は、無関係なコード変更で隠さず、
証拠と復旧後に再実行する元手順を渡す。復旧確認前に「修正済み」と報告しない。

## 3. コード変更で対応する場合は最小修正を行う

- 修正前に、元の症状を再現する失敗テストを作って実行する。
  原因とテストの失敗理由が対応していることを確認する。
- 不正な値・状態の発生源を直す。症状が現れた箇所だけでエラーを抑えたり、
  無関係な複数領域をまとめて直したりしない。
- 変更が関連タスクの範囲に収まるか確認する。原因がタスク分割・順序・仕様そのものの欠陥なら、
  コードで迂回せず、その問題と必要な計画修正を案件の判断経路へ引き渡す。

## 4. 修正したら元の症状と回帰を検証する

- 修正前と同じ再現手順を実行し、元の症状が消えたことを確かめる。
- 追加・更新した回帰テストを実行し、同じ問題を再発させない確認として残す。
- 周辺を含む既存テストスイートを実行し、別の機能を壊していないことを確かめる。
  元の症状だけ消えても、回帰が残る状態を修正完了とは記録しない。
- 実行コマンドと結果を残す。実行できなかった検証は対象と理由を明記し、成功した検証と区別する。

## 修正が効かない場合

- その修正を止め、試行内容、結果、回数、新たに分かったことを記録する。
- 案件の停止条件に達していなければ、新情報を持って証拠収集・原因分析へ戻る。
  同じ根拠のまま追加修正を続けない。
- 規定上限または案件のより早い停止条件に達したら、それ以上の修正を止める。
  根本の設計・境界・前提が適切かを論点にし、既定の引渡先へ試行履歴と必要な判断を渡す。
  上限を自分で延長して次の修正へ進まない。

## 調査・修正の結果を残す

| 項目 | 記録する内容 |
|---|---|
| 症状と再現 | 期待・実際・入力・再現手順、再現できなかった条件 |
| 多層の観測を行った場合 | 境界ごとの入出力・設定伝播・状態、最初に期待を外れた層、未観測の層 |
| 依存・ランタイムを調べた場合 | 実バージョン、参照資料と適用版、症状との対応、web利用不可・版不明など未確認の範囲 |
| 原因 | 発生源、そこまでの値・状態の追跡、原因を支持する観測 |
| 試行 | 仮説ごとの最小変更、実行結果、試行回数、適用した停止条件 |
| 対応範囲を分けた場合 | 外部・環境起因を裏付ける観測、変更権限、必要な対処・引渡先・再確認条件 |
| 修正と検証 | 実施した変更、元手順と回帰テストのコマンド・結果。変更していない場合はその旨 |
| 残っていること | 未解決・未検証の範囲、計画側へ戻す論点、引き渡した判断 |
