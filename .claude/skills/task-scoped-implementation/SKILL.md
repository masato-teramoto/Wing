# task-scoped-implementation — 確定タスクの範囲内で変更を作る

## 着手前に編集境界を宣言する

1. 今回の要求、承認済みタスク・サブタスク、完了を確かめる条件を読む。
   タスクや要求が不明確なら、何が未確定かを示して先に範囲を確定する。
2. リポジトリの構造と現状の差分を確認し、今回編集するファイル・領域を限定して記録する。
   既存の変更と今回加える変更を区別できる状態にしておく。
3. 既存ファイルは実在するパスと編集箇所を確認する。新規ファイルは置き場所と親ディレクトリを確定する。
   パスが未確定なら推測で書き始めず、計画へ戻して決める。
4. 完了条件ごとに、今回の新規・変更挙動をどう観測するかを決める。
   既存テストがその条件を直接確かめていれば利用し、不足があれば変更に適したテストや確認を選ぶ。
   文書・設定などの変更では、該当する内容照合や手動確認も含め、対象・入力・期待する結果を明らかにする。
5. 既存機能を確かめるテストスイートと実行方法を確認する。
   今回の達成を示す確認と、既存機能を保全する回帰確認を区別する。

| 着手時の記録 | 書く内容 |
|---|---|
| 対応する要求・タスク | 今回満たす要求と作業単位 |
| 編集してよい範囲 | ファイルと必要な領域。新規作成・削除が含まれるならその対象 |
| 各変更の目的 | その変更がどの要求・タスクに必要なのか |
| 達成の検証 | 完了条件ごとの観測対象・入力・期待結果、用いる既存／追加テストまたは手動確認 |
| 既存機能の保全 | 影響する既存機能、既存テストスイートと実行方法 |

## 要求に必要な変更だけを作る

- 各変更を要求・タスクに対応づける。対応先を説明できない変更は加えない。
- 具体的な必要のない抽象化、不要な依存、仕様外の機能、起こり得ない条件へのエラー処理を加えない。
  小さな変更のためにファイル全体を書き換えない。
- 無関係なコード・機能・構造を保つ。「ついでに便利になる」という理由で変更対象を増やさない。
- 編集の途中でも実際の差分を確認し、必要な変更が宣言範囲に収まっているか確かめる。

### 隣接する責務に関わる変更を自己確認する

変更が呼出し先・データの受渡し・共有状態などを通じて隣接する責務に関わる場合は、設計とタスクに
記された責務の分担を確認する。編集ファイルが宣言範囲内でも、次のような越境がないか差分を追う。

| 確認すること | 差分で確かめる対象 |
|---|---|
| ローカルなタスクに隠れた越境調整が入っていないか | 変更の成立に別の境界の同時変更や調整を暗黙に要求していないか |
| 下流固有の挙動を便宜のため上流へ押し込んでいないか | 共通処理や上流側へ足した条件分岐が、本来下流が担う判断を引き受けていないか |
| 隣接する境界に隠れ依存・共有所有・未宣言結合を作っていないか | 新しい呼出し、共有データや状態、その管理責任が設計・タスクで説明できるか |
| 明示的な統合タスクでない作業が統合作業へ変わっていないか | 複数の境界をつなぐ責任が、今回のタスクへ黙って追加されていないか |

該当する差分があれば、関係する責務とタスク上の対応先を記録する。既に計画された連携と、今回新たに
持ち込む連携を分け、範囲や所有権が不明な部分は次の境界確認へ戻す。連携があるという理由だけで、
承認済みの統合作業まで範囲外と扱わない。

## 境界の外に出る必要が生じたら

- 宣言外ファイル、新しい依存、不明確な要求、責任の所在が分からない変更が必要なら、
  その変更を止め、現在のタスクだけでは足りない理由を具体的に示す。
- 既存の要求・承認記録で既に許可されている範囲を確認する。
  その範囲を超える部分だけ、案件の既存の判断・承認経路で扱う。
  境界変更の理由と必要な承認の記録、編集境界を更新してから進める。
- 仕様やタスクを黙って変えて成立させない。計画の修正が必要なら、未確定の箇所と変更が必要な理由を計画側へ返す。
  新しい共通承認手続きを本パックを理由に追加しない。

## 納品前に変更集合・達成・回帰をそれぞれ確認する

1. 今回の実変更集合を差分から取り出し、宣言した編集範囲と照合する。
   既存の未commit変更を今回の変更と混同したり、範囲外という理由だけで削除したりしない。
2. 宣言外への接触があれば、明示的な正当化・必要な承認と境界更新があるか確認する。
   記録のない逸脱は未解決として扱い、黙って納品しない。
3. 差分の各まとまりについて、要求・タスクとの対応を再確認する。
   無関係な削除、追加機能、抽象化、依存、ファイル全体の不必要な書換が混じっていないか調べる。
   隣接する責務に関わる変更では、上の自己確認と実際の差分が一致しているかも確かめる。
4. 完了条件ごとに、今回の新規・変更挙動を予定した方法で確かめ、期待と実結果を照合する。
   既存テストが直接示していない挙動を、回帰テストが成功しただけで達成済みとしない。
   不足に応じて追加・更新テストや適切な手動確認を行う。すべての変更に新規テストやTDDを要求しない。
5. 既存テストスイートを実行し、既存機能の回帰がないことを確認する。
   失敗があれば原因を確認し、回帰が残った状態を完成として扱わない。
   実行できない確認は対象と理由を明示し、達成未確認・回帰未確認を分けて残す。

達成確認は、例えば次の表で完了条件とのつながりを示す。

| 完了条件 | 新規・変更した挙動／内容 | 確認方法と入力 | 期待する観測 | 実際の結果と証拠 | 未確認・不足 |
|---|---|---|---|---|---|
| 今回満たす条件 | 変更で成立させること | 既存／追加テストの実行、または適切な手動照合 | 達成を示す具体的な結果 | 実出力・観測内容・その所在 | 未実行の理由や満たせない条件 |

例えば入力拒否を追加するタスクでは、既存の正常系が通ることだけで完了とせず、対象の入力を与えて
指定の拒否結果が返ることを別に確かめる。同じテストが達成と回帰の両方を示す場合も、その対応を記す。

## 実装結果を引き渡す

- 要求・タスクと変更の対応、宣言範囲との照合結果、境界を更新した場合の理由と記録を示す。
- 新規作成・変更・削除したファイルがある場合は、今回の全対象をリポジトリルートからの相対パスで列挙する。
  各パスに新規・変更・削除の別と対応する要求・タスクを添え、実変更集合と照合して記載漏れを確かめる。
  既存の作業変更を今回の成果として数えず、今回変更していないファイルを混ぜない。
  次のように記録できる。案件に既存の様式がある場合は、その中で同じ情報を示す。

  | リポジトリ相対パス | 新規・変更・削除 | 対応する要求・タスク |
  |---|---|---|
  | 今回変更したファイル | 変更の種類 | 変更を必要とする作業単位 |

  今回変更したファイルがなければ、その旨を記す。

- 完了条件ごとの達成確認と、既存機能の回帰確認をそれぞれ示す。実行方法・入力・期待・実結果と証拠、
  未解決の差分、失敗・未検証の範囲を添える。変更範囲に収まることだけを要求達成の証拠にしない。
- 実装計画を作り直す場合は利用可能なら `implementation-planning`、コード変更の受入レビューは
  `acceptance-review`、完了主張と証拠の照合は `completion-verification` の担当範囲を参照する。
  本パックの実行を、それらのレビューや検証を終えた証拠にはしない。
