## 概要

検査役（check-runner）は合成 check の手順に入る前にこのルールを読み、全観点の指摘をこのルールで出す。観点 Skill の手順と食い違うときは、このルールを優先する。重大度・同一性キー・節ハッシュ・同一性キーが同じ指摘のまとめは L3 が機械で行うので、検査役は書かない。

## 1. 指摘の書き方

| 項目 | 中身 |
|---|---|
| `location` | `<案件相対パス> § <節見出し> / <ID>`（節見出し・ID は分かる範囲で）。複数箇所なら代表 1 か所＋「ほか n か所」とし、全件は evidence に書く |
| `subject` | 対象の語。指摘している対象を表す短い語（例：`貸出期間の上限`、`AC-3`）。同じ対象には同じ語を使う |
| `kind` | 種類。§2 の 6 つから 1 つ |
| `summary` | 要約。**60 字以内**。結論を先に、「何が・どこで」を 1 文で |
| `evidence` | 根拠・引用・出典（上流の該当箇所、steering の節、意味判定の内容、全箇所）。観点 Skill が「引用して示す」「根拠を添える」「明示する」と指示する内容はここに書く |
| `suggestion` | 修正案（差分や書き換え文）。業務の新しい事実が要るときは修正案を作らず、「何を決めればよいか」と選べる案を書く（質問） |
| `recommendation` | AI の推奨。`修正：理由` / `差戻し：理由` / `対応せず進める：理由` / `質問：理由` のどれか。業務の欠落・矛盾と業務のあいまい・不足には必ず付ける |
| `is_rollback_candidate` | 原因が上流にあれば true |

軽微の種類（§3）は修正案を付ける（修正案があれば AI が直す）。

## 2. 種類（6 つ）

指摘ごとに 1 つ選ぶ。**迷ったら上の行を選ぶ**（業務に寄せる）。

| 種類 | 定義 |
|---|---|
| 業務の欠落・矛盾 | 業務ルールが抜けている・食い違っている。上流（steering・要求）と食い違う。セキュリティ・法令。差戻しの候補 |
| 業務のあいまい・不足 | 業務の記述があいまい。その工程で決める値・境界値・異常系が足りない |
| 工程・文書の分担 | 書くべき文書・工程が違う |
| 文書間の参照 | ID・参照が切れている、対応が取れていない |
| 出典・根拠 | 出典・根拠の書き方が足りない |
| 書式 | 表・見出し・記法の不備 |

機械の検査の指摘（findings_path の行）は検査の種類で決まる。format-conformance → 書式（ID の重複・参照の不整合なら文書間の参照）、revision-diff-validity／sequence-consistency → 文書間の参照、dependency-cycle-detection → 業務の欠落・矛盾。観点の名前は機械検査が findings_path に書いた名前のまま。本文は改変しない。

## 3. 種類から重大度

AI は重大度を出さない。L3 が種類から次の対応で決める。

| 種類 | 重大度 | 扱い |
|---|---|---|
| 業務の欠落・矛盾 | 重大 | 1 件ずつ人に出す。判断が済むまで承認できない |
| 業務のあいまい・不足 | 要判断 | 観点＋種類ごとに束ねて人に出す |
| 工程・文書の分担／文書間の参照／出典・根拠／書式 | 軽微 | 人に出さず、修正案で AI が直す（承認時に一覧） |

## 4. 出さない事項

次に当たる指摘は出さず、`除外` に `観点 / 対象箇所 / 要約 / 除外の出典` を記録する（黙って捨てない）。
L3 は除外の出典を確かめる。`rule:` は下の表の id か `TBD`、`answer:` は `confirmed_answers` の key、`learned:` は `learned` の行に実在しなければならず、無い出典の除外は受け付けない。

| 当たるもの | 除外の出典 |
|---|---|
| 工程の境界の表（下） | `rule:<id>`（例 `rule:B-02`） |
| `TBD（<工程> で確定）` と書いてある事項（後の工程で決める） | `rule:TBD` |
| `confirmed_answers`（人が確定した回答）で決まっている事項 | `answer:<confirmed_answers の key>` |
| `learned`（却下から学んだ扱い）と同じ扱いの事項（同じ工程の却下だけ。ほかの工程の却下は当てない） | `learned:<phase> <scope> <回数>-<番号>` |
| 確かめ役が根拠なし・重複として外した指摘 | `verify:<理由>` |
| 形式不備のため意味検査から外した節（§7。指摘ではなく、検査していない節の記録） | `unchecked:形式不備` |

工程の境界の表（全案件で共通）

| id | 工程 | この工程で決めない事項（決める工程） | この工程の対象外 |
|---|---|---|---|
| B-01 | steering | — | 会議体・議事録・体制・スケジュールなどプロジェクト管理の進め方 |
| B-02 | requirements | 桁数・形式・項目の対応・テーブル・カラム・画面遷移・画面項目の配置（design） | — |
| B-03 | feature | 画面・API・データ項目の詳細（requirements／design） | — |
| B-04 | design | タスクの分割・実装の順番（tasks） | — |

## 5. 重ねない決まり

- 同じ箇所・同じ原因の指摘は、観点をまたいで 1 件にする。ほかの手順で指摘済みの箇所は重ねない。機械の検査が出した箇所・原因も重ねない。
- 原因が上流（steering・要求など）にある指摘は、原因の場所で 1 件だけ出す（`is_rollback_candidate: true`）。下流の各要件・各 feature では出さず、影響箇所は evidence に書く。
- 次の問題は、表の観点だけが出す。ほかの観点は出さない。

| 問題 | 持ち主の観点 | feature／横断 |
|---|---|---|
| 上流に根拠のない追記 | evidence-guard | feature |
| 要求 ID・要件 ID の対応の抜け | traceability | feature |
| steering の規則（業務コード・DB 規則など）への違反 | steering-conformance | 横断（design は design-cross-check） |
| 二重定義 | ssot-consistency | 横断（feature 内の重複要件は feature） |

例：traceability の下流→上流の「要求IDに紐づかない要件」、steering-conformance の「逸脱（無断の拡張）」は、evidence-guard が出すので出さない。表にない問題は、各観点の手順どおりに出す。

## 6. 差分の検査

`snapshot.changed_sections` があるとき（前回の検査がある再検査）は、意味検査を「変わった節」と「それを参照する節」に絞る。`*` はファイル全体を検査する（新規、または前回形式不備で外した対象）。空（`{}`）なら何も変わっていないので意味検査をやり直さない。変わっていない節の前回の指摘（`previous_findings`）は L3 が引き継ぐので、出し直さない。`changed_sections` が無い（初回・前回の snapshot が無い・`snapshot.full_inspection` がある＝上流の入力が前回から変わった）ときは全体を検査する。横断の検査は、変わった feature の成果物と、それと関係する feature の成果物を見る。

## 7. 形式不備でも意味検査を止めない

format-conformance やステージに形式不備があっても、意味検査（②）を省略しない。形式不備のある節だけを意味検査から外し、層は `①②` と記録する。
外した節は、`除外` に 1 行ずつ記録する（観点＝外した観点、対象箇所＝`<パス> § <節見出し>`、要約＝「形式不備のため意味検査から外した」、除外の出典＝`unchecked:形式不備`）。
L3 は、外した節を持つ対象を「意味検査が終わっていない」と扱う。そこでは前回の指摘を自動で解消せず、形式を直して再検査するまで承認を止める（検査していないことを、指摘が無くなったことと取り違えないため）。
