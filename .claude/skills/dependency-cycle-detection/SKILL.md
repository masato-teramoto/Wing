## 概要

対象成果物に記述された依存関係のグラフに閉路（循環依存）が無いかを、トポロジカルソートで
機械的に検証する。呼び出し元が「依存列」の抽出元を指定することで、Phase 3（feature間の依存
循環）・Phase 5（横断・API呼び出し循環依存）・Phase 7（タスク依存循環）に使い回せる。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象 | 依存関係が記述された成果物 | `.aidd/feature-list.md` の依存列 |
| 依存の単位 | 何を1ノードとするか | `feature 名` / `タスク番号` / `API/Event Contract` |
| 依存の向き | どちらから読むか（`依存元→依存先` 等、必須。不明なら入力不足として返す） | `依存元→依存先` |

## 手順

1. `対象` から `依存の単位` ごとにノードを列挙する。
2. 各ノードの依存先（または依存元）を抽出し、有向グラフを構築する。
3. トポロジカルソートを試みる。ソートできない（閉路が残る）場合、閉路を構成するノード列を
   特定する。
4. 自己参照（ノードが自分自身に依存する記述）も閉路として扱う。
5. 呼び出し元が既検出の閉路（例: feature-list の依存列で検出済みの組）を示した場合、同じ根本原因の
   閉路は、新たな閉路を構成していない限り重ねて指摘しない。

## この工程で指摘しない事項

- `.claude/skills/finding-rules/SKILL.md` の工程の境界の表・`confirmed_answers`・`learned` に当たる事項
- `TBD（<工程> で確定）` と書いてある値
- 呼び出し元が示した既検出の閉路と同じ根本原因の閉路

当たるものは指摘にせず、除外として返す（除外の出典を付ける。書き方は finding-rules）。

## 出力の形

指摘ごとに次を返す。書き方は `.claude/skills/finding-rules/SKILL.md`（検査の最初に読む）に従う。重大度は出さない（L3 が `kind` から決める）。

```
{ location, subject, kind, summary, evidence, suggestion, recommendation, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `location` | 閉路を構成するノードの一つ（全ノードは `evidence`）。`<案件相対パス> § <節見出し> / <ID>` の形。複数箇所なら代表 1 か所＋「ほか n か所」（全件は `evidence`） |
| `subject` | 対象の語（例: `login`） |
| `kind` | `.claude/skills/finding-rules/SKILL.md` の種類から 1 つ選ぶ。迷ったら上の行。通常 `業務の欠落・矛盾` |
| `summary` | 60 字以内。結論を先に、何が・どこで（例: 「`login → payment → login` が循環依存になっている」） |
| `evidence` | 閉路を構成するノード列と、各依存が書かれた箇所 |
| `suggestion` | 切る依存の案（どの依存をどう変えるか）。業務上の順序が要るときは「何を決めればよいか」と選べる案 |
| `recommendation` | `修正：理由` / `差戻し：理由` / `対応せず進める：理由` / `質問：理由` のどれか。業務の新しい事実が要るときは `質問：…` |
| `is_rollback_candidate` | 通常 `false`（同一フェーズ内の依存記述の修正で解消できるため） |

## 禁止

- 対象成果物を書き換えない（依存関係を自動で並べ替えない）
- 合否を出さない
- 業務の新しい事実が要る値を自分で決めない。`suggestion` に「何を決めればよいか」と選べる案を書き、`recommendation` を `質問：…` にする
