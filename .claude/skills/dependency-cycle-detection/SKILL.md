## 概要

対象成果物に記述された依存関係のグラフに閉路（循環依存）が無いかを、トポロジカルソートで
機械的に検証する。呼び出し元が「依存列」の抽出元を指定することで、Phase 3（feature間の依存
循環）・Phase 5（横断・API呼び出し循環依存）・Phase 7（タスク依存循環）に使い回せる。

## 入力

| 項目 | 内容 | 指定例 |
|---|---|---|
| 対象 | 依存関係が記述された成果物 | `.aidd/feature-list.md` の依存列 |
| 依存の単位 | 何を1ノードとするか | `feature 名` / `タスク番号` / `API/Event Contract` |
| 依存の向き | どちらから読むか（`依存元→依存先` 等、必須。不明なら入力不足として返す） | `依存元→依存先` |

## 手順

1. `対象` から `依存の単位` ごとにノードを列挙する。
2. 各ノードの依存先（または依存元）を抽出し、有向グラフを構築する。
3. トポロジカルソートを試みる。ソートできない（閉路が残る）場合、閉路を構成するノード列を
   特定する。
4. 自己参照（ノードが自分自身に依存する記述）も閉路として扱う。
5. 呼び出し元が既検出の閉路（例: feature-list の依存列で検出済みの組）を示した場合、同じ根本原因の
   閉路は、新たな閉路を構成していない限り重ねて指摘しない。

## 出力の形

```
{ id, location, finding, is_rollback_candidate }
```

| フィールド | 内容 |
|---|---|
| `id` | この Skill 内で一意な通し番号 |
| `location` | 閉路を構成するノードの一覧 |
| `finding` | 検出した閉路の事実（例: 「`login → payment → login` が循環依存になっている」） |
| `is_rollback_candidate` | 通常 `false`（同一フェーズ内の依存記述の修正で解消できるため） |

## 禁止

- 対象成果物を書き換えない（依存関係を自動で並べ替えない）
- 合否を出さない
- 閉路の解消方法（どちらの依存を切るべきか）を提案しない（事実の指摘のみ）
