# SD-1: 画面設計書の起草（feature に 1 つ）

> フロー内の位置・実行順・人間停止点の概要は **入口 skill `aidd-system-design`（配布ワークスペースの `.claude/skills/aidd-system-design/SKILL.md`）が正**。単独で呼ぶときは「単独起動時の前提」を満たすこと。
> **本 SKILL.md が工程内の起草規約と手順の正**（実行規約は本書で自己完結する）。
> 書式の正は雛形 **本 skill の `templates/screen-spec.md`**（読み取り専用）。

## 位置づけ（起草規約の前提）

- 画面設計書は **`design.md`（approved）の下位文書**で、**画面の構成・項目・操作・状態・文言の正**
- **design.md は画面を列挙しない**（「Components and Interfaces」は責務と契約の節で、画面の印を持たない）。
  **画面の切り出し・所有・feature 間の繋ぎは画面マップが決め、各画面に何を置くかを本書が決める**
- **本書が書くのは、画面マップで本 feature が所有と決まった画面だけ。** 他 feature の画面は**参照行**として置く
- **見た目は書かない**（正は STYLEGUIDE.md）。**シェルは書かない**（正は画面マップ §4、様式は STYLEGUIDE.md §4-10）
- **確定文書であり、再生成しない**（mockup は再生成する）

## ハード制約

- 【MUST NOT】**他 feature の `requirements.md` / `design.md` を入力にする**（越境が増える）。
  他 feature の情報は**画面マップ経由でだけ**入る
- 【MUST】**本 feature の画面マップ行が `confirmed` になってから起草を始める**
  （frontmatter `features[]` の該当行の `confirmed.at` が null なら停止して報告する）
- 【MUST NOT】**requirements / design.md に根拠の無い画面・項目・挙動を足す。**
  各画面は受け入れ基準か System Flows に紐づく
- 【MUST】**操作は 3 種に切り分ける**（→「操作の切り分け」）。
  **サーバーとの契約・業務ルールを伴う操作**は design.md の契約にあるものだけを置き、
  **画面内で完結する操作**と**他画面へ遷移するだけの操作**は本工程が決めてよい
- 【MUST NOT】**requirements にも steering にも無い制約・採番規則・書式を画面で確定させる**（仕様の先取り）
- 【MUST NOT】**画面マップに無い画面を自書で足す・所有を自書で移す**（画面マップの改訂に回す — §5-5）
- 【MUST NOT】**視覚仕様（色・余白・書体・影）を書く**。部品は **STYLEGUIDE.md §4 の名**で指す
- 【MUST NOT】**シェル（グローバルヘッダ・ナビ・パンくず）の様式・並び・ナビ項目を書く**（レイアウトの領域表にも行を置かない）。
  **ただし STYLEGUIDE.md §4-10 が画面設計書に委ねた値（画面名など）は §3-x-6 に書く**
- 【MUST】**§3-x-6 には実文言を置く**（design.md のメッセージ例を**エラーコード付きで転記し、転記元を書く**。正は design.md のまま）。
  **§3-x-3 の制約列はエラーコードの参照形**で書く（条件文を転記しない）
- 【MUST NOT】**確定を代行する**（frontmatter `status` / `confirmed` は開発者が記入する）
- 【MUST NOT】**requirements.md / design.md / steering / 画面マップを書き換える**
- 【MUST NOT】**wireframe 工程の成果物のうち manifest 以外（HTML・CSS・`tokens/`）を読む**
  （見た目の正は STYLEGUIDE.md。DS のクラス・変数名を部品名・領域表に持ち込まない — →「wireframe-manifest の使い方」）
- 【MUST NOT】**wireframe-manifest を画面・項目・操作・状態の根拠にする**
  （根拠は AC / design.md / steering。manifest は**種と突合先**であり、「wireframe に在るから」で項目・状態を足さない）
- 【MUST】**ダミーの識別子は汎用的な数値のみ**（独自プレフィックスを創作しない。案件の書式が steering にあれば画面マップ §5 に従う）
- 【MUST】Markdown・表示文言は ja で記述する

## 開始時の宣言（MUST）

- **初回か改訂か。** 出力先の `screen-spec.md` の有無と、**改訂の起点**の有無で 3 分岐する:

  | 状態 | 挙動 |
  |---|---|
  | `screen-spec.md` が**無い** | **初回**として続行する（本節の以下の項目を宣言する） |
  | `screen-spec.md` が**在り、改訂の起点が特定できる** | **改訂**として続行する（→「改訂モード」。宣言の項目が違う） |
  | `screen-spec.md` が**在るが、起点が示されない** | 起草せず、`status` と `confirmed` を報告して**停止する** |

  > **【MUST NOT】既存の `screen-spec.md` を全文で作り直す。** 確定文書であり、作り直すと
  > **`status: confirmed` と確定者・日時が消える**。**上の分岐を最初に通す**（在ることに気づかない失敗が最も重い）。

- 対象 feature と、**画面マップの該当行の `confirmed.at`**（null なら起草しない）
- 入力の所在（自 feature の `design.md` の `updated_at` と `status: approved` / `requirements.md` /
  `steering/` / 画面マップの `revision` / STYLEGUIDE.md の `version` / あれば wireframe-manifest〔**その `confirmed_at`**。HTML・CSS は読まない〕）
- **本 feature が所有する画面の一覧**（画面マップ §2 から。これが本書の対象のすべて）と、**参照行**の一覧
- 出力先 `.aidd/screen-design/<feature>/screen-spec.md` と雛形の所在

## 状態の下限

**下限は「まず疑う型」であって、無条件に置く一覧ではない。**
一律に求めると、**裏づけの無いまま「下限を満たすため」だけの状態がページになる**。

**型**（ここから数え始める）:

| 画面の型 | 状態 |
|---|---|
| 全画面 | 通常 / 空 / ローディング / エラー（取得失敗） |
| フォーム | + 入力エラー / 送信中 / 完了 |
| 一覧 | + 絞り込み結果なし |
| 共通画面: 入口 / システムエラー / 権限なし | **通常のみ** |
| 共通画面: お知らせ | **通常 / 空** |

- 表示が変わる長文・大量件数は品質状態として 1 行足す。型に無い機能固有の状態は行を足す
- **モーダル・印刷ビュー・確認ダイアログは親画面の「状態」として行を置く**（画面にしない）。
  基準: **閉じると必ず親画面に戻り、ナビ・パンくず上の位置を持たず、他 feature から直接遷移されない**表示は状態。
  逆の 3 つのどれかを満たせば画面（自書で足さず画面マップの改訂に回す）
- 【MUST】**型の各状態について、発生条件を requirements / design.md から裏づけられるかを判定する。**
  判定は 4 通り:

  | 判定 | 扱い |
  |---|---|
  | **起こる**（裏づけがある） | 行を置く。**発生条件列に根拠を書く** |
  | **起こりえない**（裏づけがあり、かつ起こらないと言い切れる） | **行を置かない。** §5-1 に「置かなかったもの」として**理由つきで記録する** |
  | **判断できない**（裏づけが無い） | **行を置いて残す。** 発生条件列に `—（根拠なし）` と書き、**§5-4 に確認事項として記録する** |
  | **起こるが、表示先が別画面に移った** | **行を置かない。** §5-1 に**移った先の画面 ID**を書く（共通のシステムエラー画面へ出した場合など。落としたのではない） |

- **迷ったら残す**（「判断できない」の側に倒す）。**削るには裏づけが要り、残すには要らない**
- **同じ器で中身だけが変わるもの**（参照ダイアログの対象違い・外部照会の失敗の種類）は
  **1 状態に畳んでよいかを判断し、§5-1 に記録する**（畳むと mockup では見せられない）
- 【MUST】**落とした数が 0 のときも、型の各状態の判定の内訳を §5-1 に表で残す**（判定したことが証跡に出ない）
- **擬似 feature（`_app-shell` など）は requirements / design.md を持たない。**
  **画面マップ §4（入口とシェル）が確定している事項から言い切れるものは判定し**（型は共通画面の型で見る）、
  言い切れないものだけ「判断できない」として残す。§5-4 の代わりに
  **steering の該当節を根拠として §5-1 に書く**（→「擬似 feature の扱い」）

## 操作の切り分け（§3-x-4 の操作表）

**「根拠の無い操作を足さない」は、すべての操作を上流に要求するという意味ではない**。
次の 3 種で扱いが違う。

| 種類 | 例 | 根拠 | 契約列の書き方 |
|---|---|---|---|
| **A. 契約・業務ルールを伴う操作** | 登録 / 更新 / 承認 / 差戻し / 検索 / CSV 出力 / 外部照会 | 【MUST】**design.md の契約にあるものだけ。** 無ければ置かず §5-4 に記録する。**ただし AC が画面挙動を明記していれば置き、§5-4 に記録する**（落とさない） | 契約名 / **`契約なし（§5-4 #n）`** |
| **B. 画面内で完結する操作** | 条件のクリア / 並べ替えの切替 / 折りたたみの開閉 / ページ送り / タブの切替 / ダイアログを閉じる | **本工程が決めてよい。** サーバーに触れず業務状態を変えないため、上流に根拠が要らない | **`—（画面内）`** |
| **C. 他画面へ遷移するだけの操作** | 新規作成へ / 詳細を開く / 一覧へ戻る / 入口へ戻る | **遷移の正は §2 の遷移表**（= System Flows と画面マップ §3）。契約は要らない | **`—（遷移のみ）`** |

**判定は「サーバーに要求を出すか」「業務状態を変えるか」の 2 点。**
どちらかが yes なら A、両方 no で他画面へ移るだけなら C、両方 no で同じ画面に留まるなら B である。
**迷ったら A として扱い §5-4 に記録する。**

**優先順**: **① 落とさない ＞ ② 契約に無い A 種を置かない**
（② は AC が画面挙動を明記していない場合の規定。**明記されていれば ① が勝つ** — A 種の 1 段目）。

- 【MUST】**B・C の操作にも §3-x-4 の行を置く**（契約列は `—（画面内）` / `—（遷移のみ）`）。
  操作表に無い操作は mockup が描かないため、**行を置かないと画面から消える**
- 【MUST】**§3-x-5 の「表示内容・文言」に導線を書いたら、§3-x-4 の操作表にも必ず行を持たせる。**
- 【MUST NOT】**B を口実に A を置く**（「画面内の操作だから」で検索・保存を足さない）

## 記入規約

- **状態は「起こりうるもの」を網羅する。下限は型として持つが、一律には求めない**（→「状態の下限」）
- **状態表は 4 列**（状態 / 発生条件 / 表示内容・文言 / **受け入れ基準 ID / NFR**）。表示内容は
  **機能固有のものだけ**を書き、部品が既定で持つ枠・見出しは書かない。
  **UI に関わる NFR は同じ列に書き、§4 の別掲枠にも載せる**（要件被覆の分母には入れない）
- **§3-x-6 には実文言を置く** — design.md の「メッセージ例」を**エラーコード付きで転記し、出どころ列に転記元の行を書く**
  （**正は design.md のまま**。mockup は design.md を読まないので参照形では画面に文言が出ない）。
  **§3-x-3 の制約列はエラーコードの参照形**で書く。表に行が無い状態（空・取得失敗）の文言は §7 の文言トーンで起草する
- **ボタン名・アクセスキーが AC に無い場合は本書が起草し、§5-4 に記録する**（案件内でキーが衝突しないかも見る）。
  **部品が既定で持つラベルは起草せず §5-3 の追記候補にする**
- **AC の「受け口の仕様」と「画面の要求」を分ける** — API のクエリ書式（「カンマ区切りで複数可」等）は
  受け口の仕様であって、複数選択の器を画面に要求するとは限らない。**どちらとして読んだかを §5-1 に書く**
- 【MUST】**STYLEGUIDE.md が画面設計書に委ねた決定**（列幅の段の割り当て・本文幅を広げる画面など）は
  **本書が名指しで宣言する**（宣言しなければ様式の側だけを直しても 1 ページにも効かない）
- **版番号は突合される欄（frontmatter `inputs`）にだけ書き、散文に書かない。**
  確定文書に工程の通し番号を書かず、工程名で書く
- **requirements / design.md に根拠の無い項目・操作・挙動を足さない**（各画面は受け入れ基準か System Flows に紐づく）。
  **requirements にも steering にも無い制約・採番規則・書式を画面で確定させない。** 判断が要った箇所は §5-1 に記録する
- **部品名は STYLEGUIDE.md §4「部品の様式」の名で書く。** §4 に無い部品が要る場合は**近い名で代用せず**、
  「STYLEGUIDE.md への追記候補」として §5-3 に挙げる。
  【MUST】**あわせて案件ルート直下の `STYLEGUIDE-backlog.md` にも行を足す**
  （§5-3 は feature 単位に分散するため。書式は `styleguide-authoring` の SKILL.md が正）
- 【MUST】**部品名は書いたあとに §4 の見出しと 1 件ずつ、意味ではなく字面で突き合わせる**
  （一字違う名は §4 に無い部品として扱われ、描かれずに `missing[]` へ回る）

### feature 横断の画面（正は画面マップ）

- **所有は画面マップ §2 で決まっている 1 feature。** 本書は所有画面だけを 6 小節で書く。
  画面マップに無い画面が要る・所有を移したいと分かったら、**自書で足さず・書き換えず、
  画面マップの改訂（行の追加・修正 → 差分確認）に回してから**書く（§5-5 に改訂依頼として記録する）
- **他 feature の画面は `<feature>:S-xx` の修飾形で指す**（自 feature 内は `S-xx` のまま）。
  画面一覧には**参照行**として置き（所有 feature・画面 ID・自 feature からの用途だけ。型・項目・状態は写さない）、
  遷移表の遷移先にも修飾形で書く。**参照行は画面ごとの小節を持たず、mockup の画面 × 状態の数に入れない**
- **共有画面に項目・操作・状態を足すときは、所有 feature の画面設計書を改訂する**
  （足した行の根拠に自 feature の受け入れ基準 ID を書く。所有側は `status: draft` に戻し差分だけ再確定）。
  **後の feature の画面設計書には足した内容を書かない**（正を 2 つにしない）。要件被覆では自 feature の AC を
  修飾形の画面 ID に紐づけ、その確認 #1 は**所有側の再確定の後**に通す
- **要求側の AC と所有側の AC が矛盾したら、所有側の AC を優先する**（どちらも承認済みでも同じ）。
  要求側は自書に書かず、**§5-4 に宛先 `requirements` として記録し、requirements の変更管理へ返す**
- **入口・出口は画面マップ §1 の該当行を転記する**（本 feature に入るナビ項目 / 終端画面から次工程への行き先 1 つ）。
  出口のリンク先は所有側の画面。**画面マップ §3 に無い feature 間リンクを遷移表に書かない**
- 【MUST】**§2 の遷移表には、画面マップ §3 のうち「自 feature の画面が遷移元または遷移先になる行」をすべて載せる。**
  **自画面へ入ってくる遷移（inbound）も載せる** — 遷移元列に**他 feature の修飾形**（`<feature>:S-xx`）を書き、
  **備考に `inbound` と明記する**（載せないと「どこから来られるか」がどの文書にも無くなる。
  **1 本の遷移が 2 つの画面設計書に現れるのは重複ではない** — 正は画面マップ §3）
- **遷移元は `S-xx（状態）` で書いてよい**（「1 つ前へ戻る」の行き先が状態で変わる場合。画面単位では表せない）。
  **共通画面（システムエラー・権限なし等）の inbound は、遷移元列に `全画面（画面マップ §3 ④）` と 1 行で書く**
  （全画面から 1 つの画面へ向かう遷移。**入口画面自身は入口へ戻る行を持たない**）
- **§2 の図には feature 間遷移も描く**（他 feature 側を `subgraph` で囲んで参照であることを示す）。
  **図と表は対で置き、正は表**（表に無い矢印を描かない）

## wireframe-manifest の使い方（wireframe 工程を実施した案件のみ）

wireframe 工程（要件定義工程のワイヤーフレーム）は **DS を正にして描かれ、顧客が型・構成・情報量・状態の顔ぶれを確認している**。
本工程は見た目の正を STYLEGUIDE.md に置くので、**wireframe の見た目を持ち込まない**。持ち込むのは manifest の**語彙と記録**だけである。

- 【MUST】**読むのは自 feature の `wireframe-manifest.json` だけ。** HTML・CSS・`tokens/` を読まない
  （DS のクラス・変数名が部品名・領域表に流れ込む）
- 【MUST】**使い方は 2 つ — 種と突合先。根拠にしない。** 画面・項目・操作・状態の根拠は AC / design.md / steering のまま。
  **「wireframe に在るから」で項目・状態を足さない。** 突合は**転記・起草の後**に行う（先に読むと wireframe が根拠になる）
- 【MUST】**様式と配置は STYLEGUIDE.md が正。** wireframe が持つのは顧客が確認した**型・構成・情報量・状態の顔ぶれ**で、
  ラベルの位置・必須の示し方・エラーの出し方・名前と値の組み方・段組み・アクション行の位置は **STYLEGUIDE.md §4 / §5 / §7** に従う。
  wireframe と違う形になった箇所は **§5-2 に差分として書く**（顧客提示のときの説明材料になる）
- **wireframe は design 承認前の産物である。** `notes` の判断は要件定義時点のもので、design.md の契約・Data Models と
  食い違えば **design.md が正**（食い違いは §5-2 に書く）
- **翻訳は近似で当てない。** DS の部品名・状態名をそのまま書かず、対応が無いものは無いと書いて §5-2 / §5-3 に落とす
- **manifest には表示文言・画面名・項目の並びが無い**（`screen` は英字の slug）。これらは従来どおり
  requirements / design.md / steering から起こす

| ② | **画面マップの改訂**（所有の移動・遷移の追加・ナビ項目の追加・§5 語彙の変更） | 画面マップ §6-3 改訂履歴の「影響 feature」列 |
| ③ | **design.md の変更管理**（契約・データ・バリデーションが変わった） | design.md の `updated_at` と変更履歴 |
| ④ | **自書の §5-4 / §5-5 に出した確認事項・改訂依頼が解決した** | design.md / 画面マップの該当箇所 |
| ⑤ | **STYLEGUIDE.md の改訂が本書に決定を委ねた**（幅の段の割り当てなど。**宣言しないと様式が 1 ページにも効かない**） | STYLEGUIDE.md §1-2 と、委ねた節 |

### 開始時の宣言（改訂・MUST）

- **改訂であること**と、**現行の `status`**（`confirmed` なら誰がいつ確定したか）
- **改訂の起点**（①〜⑤）と、**根拠の所在**（ファイルと項目名まで）
- **直す小節の一覧**（§ 番号と、何を足す・直すか）。**ここに挙げた範囲を超えて触らない**
- **影響**: `status` を `draft` に戻すこと / **mockup の再生成が要る**こと

> **【MUST】宣言の一覧には、規約が常に要求する小節をあらかじめ含める。**
> **起点が何であれ毎回変わるのは §5-1（改訂の記録）/ §6（参照の版）/ frontmatter `status`** の 3 つ。
> さらに**連鎖して要求されるもの**があり、宣言の時点では見えない:
>
> | 直した小節 | 連鎖して要求される小節 | 理由 |
> |---|---|---|
> | §3-x-3 項目定義 / §3-x-4 操作 | **§4 要件被覆** | AC と画面の紐づけが変わる |
> | §3-x-4 操作 | **§5-3 追記候補** | 新しい部品が要るかを確認 #5 が見る |
> | §3-x-5 状態 | **§3-x-6 文言**・**§3-x-4 操作** | 状態を足すと文言の出どころと導線が要る |
> | どれでも | **§5-1 / §6 / frontmatter** | 常に |
>
> **宣言を守れなくなったら、範囲を広げて宣言し直す**（黙って超えない）。

### ハード制約（改訂モードで足すもの）

- 【MUST】**宣言した小節だけを直す。** 全文を作り直さない
- 【MUST】**`status` を `draft` に戻し、`confirmed` を空にする**（人の確認をやり直す）。
  **確定を代行しない**のは本体のまま
- 【MUST】**§5-1 に改訂の 1 行を積む**: `- 改訂 <連番>（<日付>）: 起点 <①〜⑤> — <直した小節> / 根拠: <所在>`
- 【MUST】**§6 参照の版・時点を更新する**（design.md の `updated_at` / 画面マップの `revision` と
  本 feature 行の `confirmed.at` / STYLEGUIDE.md の `version`）
- 【MUST NOT】**画面を足す・所有を移す**（画面マップの改訂に回す — 本体の MUST NOT）

### 手順（改訂）

```
- [ ] 0. 開始宣言（→「開始時の宣言（改訂・MUST）」）。起点が特定できなければ status を報告して停止する
- [ ] 1. 起点の記録を読み、**指摘 → 小節の対応表**を作る。
        上の連鎖表で、要求される小節を宣言に足す
- [ ] 2. **小節を直す。** 宣言した範囲だけ
- [ ] 3. **§5-1 に改訂の 1 行を積み、§6 参照を更新する**
- [ ] 4. **frontmatter の status を draft に戻し、confirmed を空にする**
- [ ] 5. 自己確認（**確認【人】の全項目 + 下記 3 項目**）。落ちたら直してから報告する
- [ ] 6. status: draft のまま報告して停止する。**確認と確定は開発者**。
        報告に **mockup の再生成が要る**ことと、**変わった画面 × 状態の数**を明示する
```

## ガードレール

- 【MUST NOT】**契約に無い A 種の操作を「業務上あって自然だから」で置く**（§5-4 に記録して置かない。
  **AC が画面挙動を明記しているものは例外** — 置いて `契約なし（§5-4 #n）` と書く）
- 【MUST NOT】**B 種・C 種の操作を「根拠が無いから」で落とす**（→「操作の切り分け」）。
  落とすと**状態表が求める導線が画面に出ない**
- 【MUST NOT】**型の状態を「下限だから」で無条件に置く / 「根拠が無いから」で黙って落とす**
  （→「状態の下限」。4 通りに判定して記録する）
- 【MUST NOT】**画面マップに無い画面を作る**（§5-5 の改訂依頼へ。改訂と差分確認の後に小節を足す）
- 【MUST NOT】**共有画面の項目・操作・状態を自書に書く**（所有側の画面設計書を改訂する）
- 【MUST NOT】**他 feature の操作 UI を自 feature の画面として起こす**（越境）
- 【MUST NOT】**STYLEGUIDE.md に無い部品を近い名で代用する**（追記候補に挙げる）
- 【MUST NOT】**転記元を書かずに文言を置く**（§3-x-6 は実文言 + エラーコード + 転記元。**正は design.md のまま**）
- 【MUST】**足りないと分かったものは記録する**（黙って落とさない・埋め合わせをひねり出さない）
- 【MUST NOT】**wireframe の HTML・CSS を読む / DS の部品名・状態名をそのまま書く / wireframe を根拠に項目・状態を足す**
  （manifest は種と突合先。翻訳表で写し、差分は §5-2 に。→「wireframe-manifest の使い方」）

## 完了後

- **確認と確定は開発者**（数え上げ — 上の確認【人】の全項目）。skill は代行しない。
  確定は frontmatter `status: confirmed` + 確定者・日時（**記入を代筆したら `recorded_by` に代筆した主体を残す**）
- **`status: confirmed` になってから MU（`mockup-authoring`）を実行する**
- **§5-5 の改訂依頼のうち区分「改訂を要する」が残っているうちは mockup に進まない**
  （切り出し・所有・遷移が動くと mockup を作り直すことになる）。
  区分「上流が既に扱うと記録済み」はブロックしない（0 件に数えず別枠で報告する）
- design.md が変更管理で変わったら、切り出し・所有・遷移に影響があれば**画面マップの差分改訂が先**。
  無ければ本書を**改訂モードで**直して mockup を再生成する
- **確定後に本書を直す経路は改訂モードだけ**（→「改訂モード」）。
  在るファイルに対して初回として実行すると `confirmed` が消える
