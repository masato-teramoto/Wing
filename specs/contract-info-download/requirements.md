## Introduction（概要）

> このフィーチャーが何のために、誰のためにあるかを 2〜3 段落で書く。`背景` はなぜ今このフィーチャーが必要か、`対象ユーザー` は想定する利用者像、`期待する変化` はこのフィーチャーがあると何が変わるか。

契約情報ダウンロードは、契約情報を CSV として取り出すための画面・機能を新規に作成する機能である（REQ-044）。検索画面は既存の [GWTG004] 契約情報検索／一覧と**同一の検索条件・表示項目**とし（REQ-045）、出力する CSV は契約情報取込で使える形式とする（REQ-047）。

「既存と同一」と「取込で使える形式」という 2 つの制約が本フィーチャーの性格を決めている。検索の側は既存機能に合わせるため本フィーチャーで新たに定めるものがなく、出力の側は `contract-info-import` が定める取込形式に従う。したがって本フィーチャーは**両者をつなぐことが仕事**であり、独自の条件や形式を作らない。

担当者が契約情報を検索して CSV を取得し終えられるため User Feature である（`.aidd/feature-list.md`）。取込で使える形式（REQ-047）の前提となる `contract-info-import` に依存するため、優先度 7 に置かれている。

- **背景**: 外部で作成された契約情報を WiNG に反映する取込（REQ-040〜REQ-043）に対して、WiNG 側の契約情報を取り出して外部で扱う手段が要る（`steering/product.md` の主要ユースケース 5）
- **対象ユーザー**: 契約情報を扱う社員（`steering/product.md` の対象ユーザー）、および権限制御の対象となるベンダー・施工会社（REQ-046）
- **期待する変化**: 契約情報を既存の検索と同じ操作感で絞り込み、取込にそのまま使える CSV として取得できるようになる（REQ-044 / REQ-045 / REQ-047）

> プロダクトレベルの目的・価値は steering の `product.md` を参照。ここではこのフィーチャー固有の文脈を書く。

## Boundary Context（境界文脈）

> スコープの誤読が起こりやすい場合や、隣接するシステム / スペックに影響する場合は必ず記述する。
> `_N` の行を項目の数だけ増やす。`Out of Scope` は扱わない振る舞いに加えて理由または委譲先を書く。`Adjacent` は前提として動いている他フィーチャー / API / バッチ、およびこのフィーチャーが依頼している外部側の責務を書く。

- **In Scope（このフィーチャーで扱う）**:
  - 契約情報を CSV 出力するための画面・機能を新規に作成する（REQ-044）
  - 検索条件と表示項目を既存の [GWTG004] 契約情報検索／一覧と同一にする（REQ-045）
  - 絞り込んだ契約情報を一覧に表示する（REQ-044。CSV に出す対象を利用者が確認できるようにするために必要）
  - 契約情報取込で使える形式の CSV をダウンロードする（REQ-047）
  - ログインユーザーの会社コードによるデータ範囲の絞り込みと、ベンダー／施工会社に対するデータ範囲の制御（`steering/security.md` の所有権・エンティティ境界 / 認可。REQ-046 は `制約` 分類のため feature 割当の分母外だが、方式への準拠は本フィーチャーが負う）
- **Out of Scope（扱わない）**:
  - **既存の [GWTG004] 契約情報検索／一覧そのものの改修**。本フィーチャーは既存機能に手を入れず、**同一の条件・項目を持つ画面を新規に作る**（REQ-044 の区分は「新規」/ REQ-045）。既存機能に手を入れない方針は `steering/tech.md` の新規機能の追加方針（既存クラス・既存 SQL を書き換えず新規に追加する）に従うものである。**なお REQ-052 が列挙するデグレード対象に [GWTG004] が含まれるかは要求文からは読み取れないため、本書は REQ-052 を根拠としない**
  - 取込のファイル形式そのものの定義。`contract-info-import` が定める（REQ-042）。**本フィーチャーはその形式に従うだけで、形式を決めない**
  - 契約情報の取込・洗替更新。`contract-info-import` が持つ（REQ-040〜REQ-043）
  - 契約情報の登録・変更。既存 WTG 機能（契約情報変更・参照）が持ち、本プロジェクトの改修対象外である（REQ-052 / REQ-073）
  - 物件契約情報申請状況の検索・一覧・CSV 出力。`contract-application-status` が持つ（REQ-012〜REQ-014）。本フィーチャーが出力するのは契約情報であり、申請状況ではない
  - 権限制御の方式そのものの定義。方式の正は `steering/security.md` であり、本フィーチャーはそれに従う（REQ-046 は `制約` 分類のため feature 割当の分母外 — `.aidd/feature-list.md`）。**「既存 WTB と同様の方式」の実体は steering にも要求一覧にも無いため、準拠すべき内容は基本設計で確定する**（未確定事項 ④）
- **Adjacent（隣接システム / 隣接スペックへの期待）**:
  - `contract-info-import`: 取込で使えるファイルの形式を定める。**形式の外延は「文字コード・区切り・引用符・項目の並び・ヘッダの有無・種別の表し方」の 6 要素とし、本書はこの 6 要素すべてを同 feature の定めに合わせて出力する**（REQ-047 / `.aidd/feature-list.md` の `依存` 列。形式の正は同 feature の未確定事項 ②）。**取込側が受け付けるファイル名の条件があればそれにも従う**（未確定事項 ⑤）
  - 既存の [GWTG004] 契約情報検索／一覧: 本フィーチャーが同一とすべき検索条件と表示項目の**現物**である。改修対象ではなく、参照する対象である（REQ-045 / REQ-073）
  - 既存 WiNG の共通基盤: 認証・セッション（`LoginService` / `SessionCheckInterceptor`）と権限制御（`AccessControlInterceptor` + `@FuncID`）を提供する（Requirement 1 の受入基準 4・5）。コードマスタ取得（`CodeMstService`）は選択式の検索条件の区分値を提供する（Requirement 2 の受入基準 5）。ファイルダウンロード（`DownLoadFileInfo`）は CSV の出力経路を提供する（Requirement 3 の受入基準 6）。**いずれも既存 WiNG の構成要素であり、本フィーチャーで作らない**（`steering/architecture.md` の共通基盤 / `steering/security.md`）

## Requirements（要件）

> 要件 ID は **数値**（`1`, `1.1`, `2`, `2.1` ...）のみ。`A`, `B` などのアルファベット ID は使わない。
> 各要件は **User Story** + **Acceptance Criteria（EARS 形式）** で構成する。

### Requirement 1: 契約情報ダウンロード画面の新規作成

> 由来する要求ID: REQ-044

**User Story**: 契約情報を扱う社員として、契約情報を CSV として取り出す画面がほしい。なぜなら WiNG の外で契約情報を扱う場面があるから。

#### Acceptance Criteria（EARS 形式）

> 1 項目 = 1 基準。`_N` の行を基準の数だけ増やす。下の早見表のいずれかのパターンに当てはめて書く。

1. The system shall 契約情報を CSV 出力するための画面を新規に作成し、画面ID・PGID を既存の体系（`GWTG` + 3 桁 / `PWTGO` + 3 桁）に従って採番する（REQ-051 / `steering/tech.md` の命名規則）。採番の具体値と、画面を何本のプログラムに分割するかは基本設計で確定する（未確定事項 ①）。
2. The system shall 既存の [GWTG004] 契約情報検索／一覧の画面ID・PGID・実装を変更せず、**別の画面として**新規に作成する（REQ-044 の区分は「新規」/ `steering/tech.md` の新規機能の追加方針「既存クラス・既存 SQL を書き換えず、新規の Controller / Service / Mapper / Form を追加する」）。
3. When 担当者が検索を実行したとき、the system shall 条件に合致する契約情報を一覧として画面に表示する。
4. If ログインしていないセッションから本画面のリクエストが行われた場合、then the system shall 画面を表示せずログイン画面へ遷移させる（`steering/security.md` の認証フロー）。
5. If ログインユーザーが本画面の機能ID（PGID）に対する権限を持たない場合、then the system shall 画面を表示せずエラー画面にメッセージIDに対応する文言を表示する（`steering/security.md` の認可 / `InvalidAccessErrorException`）。
6. The system shall 検索の SQL の `WHERE` 条件に、ログインユーザーの会社コードを必ず含める（`steering/security.md` の所有権・エンティティ境界 / `steering/database.md` のクエリパターン）。
7. The system shall ベンダー／施工会社に対するデータ範囲の制御を、既存 WTB（計画・工程管理）と同様の方式に従って行う（REQ-046 / `steering/security.md` の認可）。「既存 WTB と同様の方式」の実体は要求一覧・steering のいずれからも決まらないため、基本設計で確定する（未確定事項 ④）。
8. The system shall 契約情報を参照のみで扱い、本画面から契約情報を更新しない（`## Boundary Context` の `Out of Scope`）。
9. The system shall 一覧の表示件数の上限と並び順を SQL 側で確定させ、全件をメモリに読み込んでからの絞り込みを行わない（`steering/database.md` のクエリパターン）。上限値と既定の並び順は基本設計で確定する（未確定事項 ②）。**それらが Requirement 2 の受入基準 8 が言う「同一」の範囲に含まれるかは未確定事項 ③ で確定する**。
10. The system shall 出力・表示する「契約情報」の 1 行が表す単位と、その単位を識別するキーを、既存の [GWTG004] 契約情報検索／一覧の一覧の単位に合わせる（REQ-045）。**単位とキーの具体は既存機能の現物から確定する**（未確定事項 ②）。**既存の単位が `contract-info-import` が取り込む単位（同 feature の未確定事項 ③）と食い違う場合の優先関係は未確定事項 ⑤ で確定する**。

### Requirement 2: 既存の契約情報検索／一覧と同一の検索条件・表示項目

> 由来する要求ID: REQ-045

**User Story**: 契約情報を扱う社員として、既存の契約情報検索と同じ条件・同じ項目で絞り込みたい。なぜなら画面ごとに条件や項目が違うと使い分けの負担が増えるから。

#### Acceptance Criteria（EARS 形式）

1. The system shall 本画面の検索条件を、既存の [GWTG004] 契約情報検索／一覧と**同一**にする（REQ-045）。
2. The system shall 本画面の一覧の表示項目を、既存の [GWTG004] 契約情報検索／一覧と**同一**にする（REQ-045）。
3. The system shall 既存に無い検索条件・表示項目を本フィーチャーで新たに追加しない（REQ-045 の「同一の検索条件、表示項目とする」）。追加が必要と判明した場合は要件の変更として扱う。
4. The system shall 既存の [GWTG004] の検索条件・表示項目の現物を、付録A の現行システム機能一覧を前提資料として確認する（REQ-073）。**付録A から条件・項目の一覧まで確認できるとは限らないため、入手元を含めて基本設計で確定する**（未確定事項 ②）。
5. The system shall 選択式の検索条件のうち区分値にあたるものを、コードマスタ（`CodeMstService` が参照するコードマスタ）から取得し、ソースに区分値を直書きしない（`steering/database.md` の業務コード・区分値・採番の設計ルール / `steering/tech.md` のコード規約）。
6. If 検索条件の入力チェックでエラーが検出された場合、then the system shall 検索を行わず元の画面を再表示し、`BindingResult` に積んだ全件のエラーを該当項目の近くに表示する（`steering/api-standards.md` のエラーハンドリング）。
7. The system shall 検索条件を Form のフィールドとして POST で受け取る（`steering/api-standards.md` の一覧取得の注記）。
8. The system shall 「同一」の範囲（条件・項目の名称と並びまで一致させるか、条件・項目の集合が一致していれば足りるか）を、基本設計で確定した内容に従う（未確定事項 ③）。

### Requirement 3: 取込で使える形式の CSV ダウンロード

> 由来する要求ID: REQ-047

**User Story**: 契約情報を扱う社員として、取り出した CSV をそのまま取込に使いたい。なぜなら形式を人手で変換するのは手間であり、変換の誤りが取込の失敗につながるから。

#### Acceptance Criteria（EARS 形式）

1. When 担当者が CSV ダウンロードの操作を行ったとき、the system shall 契約情報を CSV ファイルとして出力する（REQ-047）。
2. The system shall 出力する CSV の**文字コード・区切り・引用符・項目の並び・ヘッダの有無・種別の表し方**（形式の 6 要素）を、**`contract-info-import` が定める取込ファイルの形式に一致させる**（REQ-047 / `contract-info-import` の未確定事項 ②）。**形式の正は `contract-info-import` にあり、本フィーチャーで独自に定めない**。
3. The system shall 出力した CSV が `contract-info-import` の取込でそのまま受け付けられる状態にする（REQ-047 の「契約情報取込で使える形式」）。
4. The system shall CSV を**一覧と同じ SQL の結果**から出力する（`steering/database.md` のクエリパターンの「CSV 出力」。出力のためだけに別条件の SQL を作らない）。
5. The system shall CSV の出力にも**一覧と同じ表示件数の上限と並び順を SQL 側で適用する**（`steering/database.md` のクエリパターン「CSV 出力は一覧と同じ SQL の結果を用いる」/ `steering/non-functional.md` の性能・容量運用「一覧・CSV 出力は表示件数の上限と並び順を SQL 側で確定させる」）。**上限を超える件数を取り出す必要がある場合の扱い（CSV のみ上限を別に設けるか、絞り込みを促すか）は基本設計で確定する**（未確定事項 ②）。取込に使う CSV であることから件数の制約が問題になる場合は、`contract-info-import` 側の受け入れ単位とあわせて検討する。
6. The system shall CSV を `Content-Disposition` を付けたレスポンスとして返し、ファイルの出力を既存のファイルダウンロードの仕組み（`DownLoadFileInfo`）に載せる（`steering/api-standards.md` のリクエスト/レスポンス形式 / `steering/tech.md` の共通処理の再利用）。**ファイル名の規約は、取込側が受け付けるファイル名の条件（あれば）に従う。条件が無い場合の規約は基本設計で確定する**（未確定事項 ⑤）。
7. The system shall CSV 出力を Requirement 1 の受入基準 5・6・7 と同じ権限判定・会社コードの絞り込み・データ範囲の制御の対象とする（`steering/security.md` の機密データ「帳票・CSV の出力も同じ権限判定に従う」）。
8. The system shall 大量件数の CSV 出力をレスポンスのストリームで返す（`steering/api-standards.md` のパラメータ配置の「大量データ」）。
9. The system shall ダウンロードのアクション名に共通処理が効く既定の名前（`download` / `downLoad` / `executeDownLoad`。CSRF トークン生成の除外対象）を用いる。**別の名前を用いる場合は `servlet-context.xml` の interceptor マッピングとの整合を確認する**（`steering/api-standards.md` のエンドポイントのパターン）。
10. The system shall CSV に出力する項目を、基本設計で確定した内容に従う（未確定事項 ⑤）。**受入基準 2 が定める「取込形式に合わせる」対象は区切り・引用符・項目の並び・ヘッダの有無であり、出力する項目の集合そのものは本基準で扱う。表示項目（既存と同一 — REQ-045）と取込形式が要求する項目（`contract-info-import` が定める — REQ-047）が食い違う場合の優先関係も未確定事項 ⑤ で確定する。**

## Out of Scope（明示的に対象外）

> Boundary Context だけで誤読を防ぎきれないとき、追加でここに書く。
> 1 項目 = 1 件。`_N` の行を件数だけ増やす。対象外にするものと、なぜ対象外か、どこで扱う予定かを書く。

- 既存 WTG 機能（契約情報変更・参照、支払実績データ作成／変更／参照、電力会社直受支払実績変更、契約支払情報インポート、契約基本情報インポート、インボイス情報インポート）の仕様変更。デグレードを発生させない対象であり、新規の Controller / Service / Mapper / Form を追加する形で実装する（REQ-052 / REQ-073 / `steering/tech.md` の新規機能の追加方針）
- 契約情報を保持するテーブルの追加・変更。本フィーチャーは既存の契約情報を参照して出力する参照系であり、テーブルを持たない
- ダウンロードした CSV を外部システムへ受け渡す処理。連携はファイルの受け渡しを境界とし、相手システムのプロセスを直接呼び出さない（REQ-008 / `steering/architecture.md` の外部 API / 外部システム）

## Dependencies / Assumptions（前提と依存）

> `前提` はこのフィーチャーが成立するために真でなければならない事項、`依存` は他フィーチャー / 既存システム / 外部 API / データ、`未確定事項` は調査・確認待ちのトピック（design に進む前に解消する）。

- **前提**: 既存 WiNG の認証・セッション・権限制御の仕組み（`LoginService` / `SessionCheckInterceptor` / `AccessControlInterceptor`）がそのまま利用できること（REQ-009 / REQ-053）。既存の [GWTG004] 契約情報検索／一覧の検索条件と表示項目が確認できること（REQ-045）。**付録A の現行システム機能一覧は前提資料として用いるが（REQ-073）、条件・項目の一覧まで確認できるとは限らないため、入手元は未確定事項 ② に含める**。`contract-info-import` が取込ファイルの形式を定めていること（REQ-047）
- **依存**: `.aidd/feature-list.md` の `依存` 列は `contract-info-import`。出力する CSV の形式が同 feature の定める取込形式に従うため、形式が確定する側が先行する必要がある。既存 WiNG の共通基盤（認証・セッション・権限制御・コードマスタ・ファイルダウンロード）と、既存の [GWTG004] 契約情報検索／一覧の仕様にも依存する
- **未確定事項**: 次の 5 件は **いずれも基本設計で確定する**（REQ-010。Phase 4 の共通の扱いとして人間が確定 / 2026-09-11）。
  - ① **画面ID・PGID の採番の具体値**と、画面を何本のプログラムに分割するか（REQ-010 / REQ-051）
  - ② **既存の [GWTG004] 契約情報検索／一覧の検索条件と表示項目の現物**、**一覧の 1 行が表す単位と識別キー**、および**それらの入手元**（付録A で足りるか、既存実装の調査や発注者への確認を要するか）（REQ-045 / REQ-073）。一覧の表示件数の上限と既定の並び順が「同一」の範囲に含まれるか、および **CSV の出力件数に上限を設けるかどうか**もここで確定する
  - ③ **「同一」の範囲**（条件・項目の名称と並びまで一致させるか、条件・項目の集合が一致していれば足りるか。**一覧の表示件数の上限と既定の並び順を「同一」の対象に含めるかを含む**）（REQ-045）
  - ④ **「既存 WTB（計画・工程管理）と同様の権限制御方式」の実体**（ベンダー／施工会社に対してどのデータ範囲をどう制御するか）（REQ-046 / `steering/security.md` の認可）。要求一覧は方式を既存 WTB に合わせるとだけ述べ、steering も同じ表現に留まっているため、既存 WTB の実装を調査して確定する（REQ-073）
  - ⑤ **CSV に出力する項目**（Requirement 2 の表示項目と一致させるか、取込形式に合わせて増減するか）、**CSV のファイル名の規約**（取込側が受け付けるファイル名の条件があればそれに従い、無い場合の規約）、および **REQ-045 側（既存 [GWTG004] と同一）と REQ-047 側（`contract-info-import` が定める取込形式）が食い違う場合の優先関係**（REQ-047）。優先関係は**出力項目だけでなく、1 行が表す単位と識別キー（受入基準 1-10 と同 feature の未確定事項 ③）についても定める**。**本項は `contract-info-import` の未確定事項 ②・③ の確定を待つ**（形式と単位の正は同 feature にあるため）
