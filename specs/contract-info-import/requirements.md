## Introduction（概要）

> このフィーチャーが何のために、誰のためにあるかを 2〜3 段落で書く。`背景` はなぜ今このフィーチャーが必要か、`対象ユーザー` は想定する利用者像、`期待する変化` はこのフィーチャーがあると何が変わるか。

契約情報取込は、外部で作成された契約情報を WiNG に反映するための機能である（REQ-040）。担当者が取込バッチの実行画面から取込を指示し（REQ-041）、バッチが契約情報の新規・変更・削除を取り込み（REQ-042）、洗替更新を行う（REQ-043）。

取込のような時間のかかる一括処理は画面で同期実行せず、オンライン画面からタスクを登録してバッチエンジンが実行する非同期方式を採る（`steering/architecture.md` の通信パターン / `steering/non-functional.md` の性能・容量運用）。したがって本フィーチャーは**オンラインの画面（実行指示と状況の確認）とバッチ（取込処理）の 2 つの構成要素**を持つ。

担当者が取込を実行して契約情報の反映を終えられるため User Feature である（`.aidd/feature-list.md`）。依存を持たず、`contract-info-download` が「取込で使える形式」の CSV を出力する（REQ-047）ため、取込の形式が確定する本フィーチャーを先に置いて優先度 6 としている。

- **背景**: 契約情報は UQ 様社内システム群を含む WiNG の外でも作成されており（REQ-006）、それを WiNG に反映する手段が要る（`steering/product.md` の主要ユースケース 5）
- **対象ユーザー**: 契約情報の取込を担当する社員（`steering/product.md` の対象ユーザー）、および権限制御の対象となるベンダー・施工会社（REQ-046）
- **期待する変化**: 外部で作成された契約情報を、画面からの指示で WiNG に反映できるようになる（新規・変更・削除の取込と洗替更新 — REQ-042 / REQ-043）

> プロダクトレベルの目的・価値は steering の `product.md` を参照。ここではこのフィーチャー固有の文脈を書く。

## Boundary Context（境界文脈）

> スコープの誤読が起こりやすい場合や、隣接するシステム / スペックに影響する場合は必ず記述する。
> `_N` の行を項目の数だけ増やす。`Out of Scope` は扱わない振る舞いに加えて理由または委譲先を書く。`Adjacent` は前提として動いている他フィーチャー / API / バッチ、およびこのフィーチャーが依頼している外部側の責務を書く。

- **In Scope（このフィーチャーで扱う）**:
  - 契約情報取込機能（契約情報インポート画面／契約情報インポートバッチ）を新規に作成する（REQ-040）
  - 取込バッチの実行画面を設ける（REQ-041）
  - 契約情報の新規・変更・削除を取り込む（REQ-042）
  - 契約情報の洗替更新を行う（REQ-043）
  - 取込の対象となるファイルの形式（文字コードを含む）を定めること（REQ-042 の「新規、変更、削除を取り込む」を成立させるために必要。**取込機能そのものの一部として本フィーチャーが定める**）。定めた形式は、`contract-info-download` が REQ-047 を満たすための前提になる（同 feature 側の要件であり、本フィーチャーは REQ-047 を自らの `対応要求ID` として扱わない — `.aidd/feature-list.md`）
  - ログインユーザーの会社コードによるデータ範囲の絞り込み（`steering/security.md` の所有権・エンティティ境界）
- **Out of Scope（扱わない）**:
  - 契約情報の CSV ダウンロード（検索画面と出力）。`contract-info-download` が持つ（REQ-044 / REQ-045 / REQ-047）
  - 既存の契約支払情報インポート・契約基本情報インポート・インボイス情報インポートの仕様変更。既存 WTG 機能であり、デグレードを発生させない対象である（REQ-052 / REQ-073）
  - バッチ実行基盤そのものの実装。JavaKit バッチエンジンとタスク登録の仕組み（`BatchCommonService`）は既存 WiNG の構成要素であり、本フィーチャーはその上にタスクを載せる（REQ-053 / `steering/architecture.md` の共通基盤・バッチ）
  - 取込元となる契約情報を外部側で作成する処理。UQ 様社内システムは改修対象外である（REQ-008）
  - 物件基本情報・発行依頼書の登録・変更。`property-basic-info` / `issue-request` が持つ（REQ-015〜REQ-034）
  - 権限制御の方式そのものの定義。方式の正は `steering/security.md` であり、本フィーチャーはそれに従う（REQ-046 は `制約` 分類のため feature 割当の分母外 — `.aidd/feature-list.md`）
- **Adjacent（隣接システム / 隣接スペックへの期待）**:
  - `contract-info-download`: 本フィーチャーが定める取込の形式に合わせた CSV を出力する（REQ-047 / `.aidd/feature-list.md` の `依存` 列で同 feature が本 feature に依存する）。**形式の正は本フィーチャーにある**
  - 外部システム（UQ 様社内システム群を含む WiNG の外）: 取込対象の契約情報を作成する。連携はファイル（CSV）と DB 上のテーブルを境界とし、相手システムのプロセスを直接呼び出さない（REQ-006 / REQ-008 / `steering/architecture.md` の外部 API / 外部システム）
  - 既存 WiNG の共通基盤: 認証・セッション（`LoginService` / `SessionCheckInterceptor`）と権限制御（`AccessControlInterceptor` + `@FuncID`）を**オンライン側に**提供する（Requirement 2 の受入基準 6・7）。ファイルアップロード（`FileUploadService`）は取込対象を画面から受け取る構成を採る場合の受付経路を提供する（Requirement 2 の受入基準 9）。バッチのタスク登録（`BatchCommonService`）は画面からバッチへの実行指示の経路を提供する（Requirement 2 の受入基準 3・11）。**いずれも既存 WiNG の構成要素であり、本フィーチャーで作らない**（`steering/architecture.md` の共通基盤 / `steering/security.md`）

## Requirements（要件）

> 要件 ID は **数値**（`1`, `1.1`, `2`, `2.1` ...）のみ。`A`, `B` などのアルファベット ID は使わない。
> 各要件は **User Story** + **Acceptance Criteria（EARS 形式）** で構成する。
> **`### Requirement` のブロックを要件の数だけ複製する。** 要件領域名は、その要件がどの範囲を扱うかが分かる名前にする。

### Requirement 1: 契約情報取込機能の新規作成

> 由来する要求ID: REQ-040

**User Story**: 契約情報の取込を担当する社員として、外部で作成された契約情報を WiNG に反映する手段がほしい。なぜなら WiNG の外で作られた契約情報を手で入力し直すのは現実的でないから。

#### Acceptance Criteria（EARS 形式）

> 1 項目 = 1 基準。`_N` の行を基準の数だけ増やす。下の早見表のいずれかのパターンに当てはめて書く。

1. The system shall 契約情報インポート画面と契約情報インポートバッチを新規に作成し、画面ID・PGID を既存の体系（画面 `GWTG` + 3 桁 / オンライン `PWTGO` + 3 桁 / **バッチ `PWTGB` + 3 桁**）に従って採番する（REQ-051 / `steering/tech.md` の命名規則）。採番の具体値と、画面・バッチを何本のプログラムに分割するかは基本設計で確定する（未確定事項 ①）。
2. The system shall 取込の処理をバッチ側に置き、画面側では実行の指示と状況の確認のみを行う（`steering/architecture.md` の通信パターン / `steering/non-functional.md` の性能・容量運用「時間のかかる処理」）。
3. The system shall 画面とバッチの境界をタスク登録テーブルと処理対象データ（DB / ファイル）とし、バッチからオンラインのクラスを直接呼び出さない（`steering/architecture.md` のバッチの境界）。
4. The system shall 取込の対象となるファイルの形式（**文字コード・区切り・引用符・項目の並び・ヘッダの有無・種別の表し方**）を定める（REQ-042 を成立させるために必要）。具体値は基本設計で確定する（未確定事項 ②）。**文字コードについては、`steering/security.md` が定める `wing-web.properties` の `CHARSET` はオンラインの CSV ダウンロードに対する規定であり、Linux 環境で動くバッチの取込に及ぶかが steering から読み取れない。`contract-info-download` が出力する CSV をそのまま取り込めること（REQ-047）を満たすため、両者の文字コードが一致する形で基本設計で確定する**。定めた形式は `contract-info-download` が REQ-047 を満たすための前提になる。
5. The system shall 取り込む「契約情報」の 1 件の単位と、既存データとの**同一性を判定するキー**を定める（新規・変更・削除の判別と洗替の対象特定に必要）。単位とキーは基本設計で確定する（未確定事項 ③）。
6. The system shall 取込によって更新するテーブルを既存の命名規則と共通カラム（`CompanyCD` / `RegisteredPerson` / `RegisteredDT` / `UpdatedPerson` / `UpdatedDT` / `ExclusiveFG`）の規約に沿って扱う（`steering/database.md` の命名規則）。既存テーブルを使うか新規テーブルを追加するかは基本設計で確定する（未確定事項 ③）。
7. The system shall 既存の契約支払情報インポート・契約基本情報インポート・インボイス情報インポートの処理を変更せず、新規の Controller / Service / Mapper / Form とバッチを追加する形で実装する（REQ-052 / REQ-073 / `steering/tech.md` の新規機能の追加方針）。

### Requirement 2: 取込バッチの実行画面

> 由来する要求ID: REQ-041

**User Story**: 担当者として、取込を画面から指示して結果を確認したい。なぜなら取込のたびに運用担当へ依頼するのでは業務が回らないから。

#### Acceptance Criteria（EARS 形式）

1. The system shall 契約情報の取込バッチを実行するための画面を設ける（REQ-041）。
2. The system shall 本画面で、取込を実行するために必要な指定（取込の対象と、実行する処理の種類）を利用者から受け取る。**何をどこまで画面で指定させるか（取込対象のファイルまたはその所在、Requirement 3 の取込と Requirement 4 の洗替更新を別々に指示させるか同一タスクとするか、洗替の対象範囲を画面で指定させるか）は基本設計で確定する**（未確定事項 ④・⑨。⑨ は取込と洗替を同一タスクとするか別タスクとするかを扱う）。
3. When 担当者が実行の操作を行ったとき、the system shall 取込処理を同期実行せず、バッチのタスクとして登録する（`steering/api-standards.md` のパラメータ配置の「大量データ」/ `steering/non-functional.md` の性能・容量運用）。
4. When タスクの登録が完了したとき、the system shall 登録を受け付けたことを利用者に知らせ、**タスクを識別できる情報**を画面に示す（`steering/api-standards.md` の「実行状況を別画面で確認させる」）。
5. The system shall 取込の結果（少なくとも**正常に取り込んだ件数とエラーの件数**）を利用者が確認できる手段を設ける。**確認の手段（本画面で表示するか、既存のバッチ状況確認の仕組みに載せるか）と、件数以外に提示する項目（種別ごとの内訳・エラーの明細など）は基本設計で確定する**（未確定事項 ④）。
6. If ログインしていないセッションから本画面のリクエストが行われた場合、then the system shall 画面を表示せずログイン画面へ遷移させる（`steering/security.md` の認証フロー）。
7. If ログインユーザーが本画面の機能ID（PGID）に対する権限を持たない場合、then the system shall 画面を表示せずエラー画面にメッセージIDに対応する文言を表示する（`steering/security.md` の認可 / `InvalidAccessErrorException`）。
8. The system shall 実行の操作を更新系リクエストとして扱い、`CSRFTokenCheckInterceptor` によるトークン検証の対象にする。**共通処理が効く既定のアクション名（`execute` / `upload` を含む）以外を用いる場合は、`servlet-context.xml` の interceptor マッピングとの整合を確認する**（`steering/api-standards.md` のエンドポイントのパターン）。
9. Where 取込対象のファイルを画面から受け取る構成を採る場合、the system shall 既存のファイルアップロードの仕組み（`FileUploadService`）を通じてファイルを受け取り、機能側で独自の保存先・独自の受付処理を作らない（`steering/security.md` の共通ルール 4）。取込対象を画面からのアップロードで受け取るか、所定の配置場所から読むかは基本設計で確定する（未確定事項 ⑤）。
10. The system shall ベンダー／施工会社に対するデータ範囲の制御を、既存 WTB（計画・工程管理）と同様の方式に従って行う（REQ-046 / `steering/security.md` の認可）。「既存 WTB と同様の方式」の実体は要求一覧・steering のいずれからも決まらないため、基本設計で確定する（未確定事項 ⑧）。
11. When タスクを登録するとき、the system shall **セッションの AuthContext（`LoginUserUtils.getLoginUserInfo()` が返す `LoginUserInfo`）から取得した会社コードを、タスクのパラメータとしてバッチへ引き渡す**。**画面からのリクエストパラメータで受け取った会社コードを用いない**（`steering/security.md` の所有権・エンティティ境界「画面からの受け取り値に依存しない」/ 認証 → 認可の契約）。バッチは HTTP セッションを持たずオンラインの共通処理に依存できないため（`steering/architecture.md` のバッチの「しないこと」。`steering/security.md` の AuthContext の消費側にバッチは挙げられていない）、**認可の判定は本画面（オンライン側）で行い、バッチはその結果として渡された値を処理範囲として使う**。**引き渡す情報が会社コードだけで足りるかは、REQ-046 の制御方式（未確定事項 ⑧）の確定に伴って決まる**（ベンダー／施工会社の制御に別の識別子が要る場合は引き渡す項目が増える）。
12. The system shall バッチのタスク・ジョブの開始と終了を、メッセージIDとともに `info` レベルでログに出力する（`steering/non-functional.md` のログレベル・出力する）。

### Requirement 3: 契約情報の新規・変更・削除の取込

> 由来する要求ID: REQ-042

**User Story**: 担当者として、外部で追加・修正・廃止された契約情報をまとめて反映したい。なぜなら差分の種別ごとに別の手段を使うのは手間だから。

#### Acceptance Criteria（EARS 形式）

1. The system shall 取込データに含まれる契約情報を、**新規・変更・削除**の 3 つの種別として取り込む（REQ-042）。
2. When 新規の契約情報を取り込んだとき、the system shall 当該の契約情報を登録し、以降の参照の対象にする。
3. When 変更の契約情報を取り込んだとき、the system shall 既存の契約情報を更新する。
4. When 削除の契約情報を取り込んだとき、the system shall 当該の契約情報を以降の参照・更新の対象から外す。**外し方を論理削除とするか物理削除とするかは基本設計で確定した内容に従う**（未確定事項 ⑥。`steering/database.md` の設計思想は物理削除を既定とせず、画面に表示して編集だけを制御する必要があるデータは論理削除で扱うと定めている）。
5. The system shall 種別をどのように判別するか（データ中の区分の値で判別するか、既存データとの突合で判別するか）を、基本設計で確定した内容に従う（未確定事項 ②）。区分の値で判別する場合は、コードマスタ（`CodeMstService` が参照するコードマスタ）で管理しソースに直書きしない（`steering/database.md` の業務コード・区分値・採番の設計ルール）。
6. If 取込データに不正なもの（形式の誤り・必須の欠落・参照先の不存在）が含まれる場合、then the system shall **対象（何行目のどの項目か）と理由が分かる形で**、(a) バッチのログにメッセージIDとともに出力し（`steering/non-functional.md` のログ方針。出力先は `log4j2.xml` が定めるアプリケーションログ）、(b) **エラーの件数をタスクの実行結果として残す**（Requirement 2 の受入基準 5 が求める確認の最低限）（`steering/api-standards.md` の分類の外部エラー）。**エラーの明細を件数に加えて利用者に見せるかどうかは未確定事項 ④ に従う**。
7. The system shall 不正なデータを検出したときに取込全体を中止するか、当該の 1 件のみを飛ばして継続するかを、基本設計で確定した内容に従う（未確定事項 ⑦）。**取込全体を中止する場合はバッチのタスクを異常終了させ、タスクの状態とメッセージIDをログに残す**（`steering/tech.md` の例外処理フローのバッチの行）。1 件を飛ばして継続する場合はタスクを異常終了させず、受入基準 6 の記録をもって利用者に伝える。
8. The system shall 大量件数の取込についてコミット単位を決めて分割する（`steering/database.md` の接続 / トランザクションの「バッチの単位」）。単位は基本設計で確定する（未確定事項 ⑦）。**この単位は Requirement 4 の洗替更新にも同じく適用する。**
9. When 既存の契約情報を更新・削除するとき、the system shall 排他フラグ（`ExclusiveFG`）を `WHERE` 条件に含めて更新件数を確認する（`steering/database.md` のクエリパターンの排他制御 / 整合性「オンラインとバッチが同じテーブルを更新する場合の競合は、排他フラグと更新件数の確認で検出する」）。更新件数が 0 件だった行の扱い（受入基準 6 の形でエラーとして記録するか、取込全体を中止するか）は未確定事項 ⑦ に従う。
10. The system shall **Requirement 2 の受入基準 11 でタスクのパラメータとして引き渡された会社コード**を、取込のすべての DB アクセスに適用する。すなわち (a) 既存データの検索・更新・削除の `WHERE` 条件に含め、(b) 新規に登録する行の `CompanyCD` に設定し、(c) **取込データに当該の会社コードと異なる会社コードのレコードが含まれる場合は取り込まず、受入基準 6 の形でエラーとして記録する**（`steering/security.md` の所有権・エンティティ境界 / `steering/database.md` のクエリパターン）。バッチは HTTP セッションからログインユーザー情報を取得しない。

### Requirement 4: 契約情報の洗替更新

> 由来する要求ID: REQ-043

**User Story**: 担当者として、対象範囲の契約情報を取込データの内容で置き換えたい。なぜなら差分ではなく全量で受け渡される場合があるから。

#### Acceptance Criteria（EARS 形式）

1. The system shall 契約情報の洗替更新（対象範囲を取込データの内容で置き換える処理）を行う（REQ-043）。
2. The system shall 洗替の**対象範囲を明示してから置き換える**（`steering/database.md` の整合性「取込による洗替更新は、対象範囲を明示してから置き換える」）。対象範囲の決め方（会社コード単位・契約単位・取込データに含まれるキーの範囲など）は基本設計で確定する（未確定事項 ⑨）。
3. The system shall 洗替更新と、Requirement 3 の新規・変更・削除の取込との使い分け（同一のタスクで行うか別のタスクとするか、どちらを既定とするか）を、基本設計で確定した内容に従う（未確定事項 ⑨）。
4. The system shall 洗替によって対象範囲から外れた契約情報を以降の参照・更新の対象から外す。**外し方は Requirement 3 の受入基準 4 と同じく未確定事項 ⑥ で確定した内容に従う**（`steering/database.md` の設計思想）。
5. The system shall オンラインとバッチが同じテーブルを更新する場合の競合を、排他フラグ（`ExclusiveFG`）と更新件数の確認で検出する（`steering/database.md` の整合性 / クエリパターンの排他制御）。
6. When 洗替更新が完了したとき、the system shall 置き換えた件数と対象範囲をログに残す（`steering/non-functional.md` のログ方針）。

## Out of Scope（明示的に対象外）

> Boundary Context だけで誤読を防ぎきれないとき、追加でここに書く。
> 1 項目 = 1 件。`_N` の行を件数だけ増やす。対象外にするものと、なぜ対象外か、どこで扱う予定かを書く。

- 既存 WTG 機能（契約情報変更・参照、支払実績データ作成／変更／参照、電力会社直受支払実績変更、契約支払情報インポート、契約基本情報インポート、インボイス情報インポート）の仕様変更。デグレードを発生させない対象であり、新規の Controller / Service / Mapper / Form とバッチを追加する形で実装する（REQ-052 / REQ-073 / `steering/tech.md` の新規機能の追加方針）
- **稼働開始前の既存契約情報データの移行**。本フィーチャーが提供するのは稼働後の運用としての取込であり、移行そのものは本フィーチャーの機能として扱わない。移行に本フィーチャーの取込を用いるかどうかは基本設計で判断する（未確定事項 ⑩）。データ移行のテストは発注者にて実施する前提である（REQ-054）

## Dependencies / Assumptions（前提と依存）

> `前提` はこのフィーチャーが成立するために真でなければならない事項、`依存` は他フィーチャー / 既存システム / 外部 API / データ、`未確定事項` は調査・確認待ちのトピック（design に進む前に解消する）。

- **前提**: 既存 WiNG の認証・セッション・権限制御の仕組み（`LoginService` / `SessionCheckInterceptor` / `AccessControlInterceptor`）がそのまま利用できること（REQ-009 / REQ-053）。JavaKit バッチエンジンとオンラインからのタスク登録の仕組み（`BatchCommonService`）が、新規の取込バッチにも利用できること（REQ-041 / `steering/architecture.md` のバッチ）。テスト用の取込データは発注者から提供される前提である（REQ-069）
- **依存**: `.aidd/feature-list.md` の `依存` 列は「なし」。本フィーチャーは他 feature の完成を前提としない。既存 WiNG の共通基盤（認証・セッション・権限制御・ファイルアップロード・バッチ実行基盤）には依存する。なお `contract-info-download` は本フィーチャーが定める取込の形式に依存する側であり、本フィーチャーからの依存ではない
- **未確定事項**: 次の 10 件は **いずれも基本設計で確定する**（REQ-010。Phase 4 の共通の扱いとして人間が確定 / 2026-09-11）。
  - ① **画面ID・PGID（オンライン `PWTGO` / バッチ `PWTGB`）の採番の具体値**と、画面・バッチを何本のプログラムに分割するか（REQ-010 / REQ-051）
  - ② **取込ファイルの形式**（文字コード・区切り・引用符・項目の並び・ヘッダの有無・種別の表し方）と、**新規・変更・削除の種別の判別方法**（REQ-042）。要求一覧は形式に触れていない。**文字コードについては、`steering/security.md` の `wing-web.properties` の `CHARSET` がオンラインの CSV ダウンロードに対する規定であり Linux 環境で動くバッチの取込に及ぶかが steering から読み取れないため、`contract-info-download` の出力と一致する形で本項に含めて確定する**。**本項の確定内容は `contract-info-download` が REQ-047 を満たすための前提になる**
  - ③ **取り込む「契約情報」の 1 件の単位と、既存データとの同一性を判定するキー**、**取込が更新する対象のテーブル**（既存テーブルを使うか新規テーブルを追加するか）、および対象となる契約情報の項目（REQ-040 / REQ-042）
  - ④ **実行画面で利用者に指定させる項目**（取込対象のファイルまたはその所在、取込と洗替のどちらを行うか、洗替の対象範囲を画面で指定させるか）、**取込の実行状況と結果を利用者が確認する手段**（本画面で表示するか、既存のバッチ状況確認の仕組みに載せるか）、および**結果として提示する項目**（処理件数・種別ごとの内訳・エラーの件数と内容）（REQ-041）
  - ⑤ **取込対象を画面からのアップロードで受け取るか、所定の配置場所から読むか**（REQ-041 / `steering/security.md` の共通ルール 4）
  - ⑥ **削除・洗替で対象から外れた契約情報を参照・更新の対象から外す方法**（論理削除か物理削除か）（REQ-042 / REQ-043 / `steering/database.md` の設計思想は物理削除を既定とせず、画面に表示して編集だけを制御する必要があるデータは論理削除で扱うと定めている）
  - ⑦ **不正なデータを検出したときの扱い**（取込全体を中止するか 1 件を飛ばして継続するか）と、**コミット単位**（REQ-042 / `steering/database.md` の接続 / トランザクション）
  - ⑧ **「既存 WTB（計画・工程管理）と同様の権限制御方式」の実体**（ベンダー／施工会社に対してどのデータ範囲をどう制御するか）（REQ-046 / `steering/security.md` の認可）。要求一覧は方式を既存 WTB に合わせるとだけ述べ、steering も同じ表現に留まっているため、既存 WTB の実装を調査して確定する（REQ-073）
  - ⑨ **洗替更新の対象範囲の決め方**（会社コード単位・契約単位・取込データに含まれるキーの範囲など）と、**新規・変更・削除の取込との使い分け**（同一タスクか別タスクか、どちらを既定とするか）（REQ-043）
  - ⑩ **稼働開始前の既存契約情報データの移行の要否と方式**（本フィーチャーの取込を移行に用いるかを含む）（REQ-054 は移行テストの実施主体を定めるに留まり、移行そのものの要否を定めていない）
