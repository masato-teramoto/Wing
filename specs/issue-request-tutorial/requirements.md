# 要件定義書

> このファイルは **「何を作るか」「完了をどう判定するか」** を確定させる文書である。\
> _分担_: `status: approved` になるまで `design.md` に進まない。`approved` は人間が付ける（エージェントは付けない）。

> _書き方_: 確定した要件だけを書き、作成の手順やレビューの記録は残さない。

## 概要（Introduction）

> このフィーチャーが何のために、誰のためにあるかを示す節。\
> _分担_: プロダクト全体の目的は `steering/product.md` の `## 開発物の概要・背景`、価値は同ファイルの `## 提供価値`。

> _書き方_: このフィーチャー固有の事情だけを書き、経緯や検討過程は書かない。

発行依頼書チュートリアル設定は、発行依頼書の入力を誘導するチュートリアルの設定を作るための画面である（REQ-036）。チュートリアルは選択肢により順番に入力欄と例が表示される仕組みであり、その表示内容と順序をここで定義する（REQ-035）。

現行は設定用ウインドウが 26 フォーム（画面）に分かれており、これに相当する画面を新規に実現する（REQ-036。RFP の区分は「新規」）。何本のプログラムに分割するかは基本設計で決定する（REQ-010）。

設定という用事がこの画面で完結するため User Feature である（`.aidd/feature-list.md`）。依存を持たないが、`issue-request`（優先度 4）のチュートリアルが動作するには設定が先に存在する必要があるため、優先度 3 に置かれている。

- **背景**: 契約書発行依頼業務は入力項目が多すぎるとの指摘があり（REQ-002）、誤入力による不備指摘のやり取りが契約書発行までの納期を延ばしている（REQ-003）。システム側の入力補助で入力の負担を下げる手段の一つがチュートリアルである（REQ-002 / REQ-035）
- **対象ユーザー**: チュートリアルの設定を担当する利用者（`.aidd/feature-list.md` の種別の判定）。設定されたチュートリアルを使うのは発行依頼書を登録・変更する担当者である（`steering/product.md` の対象ユーザー）
- **期待する変化**: 発行依頼書の入力時に、選択肢に応じて必要な入力欄と記入例が順番に提示されるようになり、入力項目の多さに起因する負担と誤入力が減る（REQ-002 / REQ-003 / REQ-035）

## スコープの境界（Boundary Context）

> このフィーチャーで**何を作り、何を作らないか**を確定させる節。スコープの誤読が起きやすい場合や、隣接するシステム・スペックに影響する場合は必ず書く。\
> _分担_: 扱わない理由と引き継ぎ先は `## 対象外`。無いと成立しない依存は `## 前提と依存（Dependencies / Assumptions）`。実装として何を所有するかは `design.md` の `## 責務境界（Boundary Commitments）`。ここには利用者から見た機能の範囲だけを書き、理由や実装の話は書かない。

> _書き方_: **確定した境界だけ**を書き、検討中のものは書かない。1 項目 1 行で列挙する。

- **扱う範囲（In Scope）**:
  - チュートリアル設定画面を新規に作成する（REQ-036）
  - 現行の設定用ウインドウ 26 フォーム（画面）に相当する設定項目を扱えるようにする（REQ-036）
  - 選択肢と、選択肢に応じて表示する入力欄・例を設定として定義する（REQ-035）。**表示順序をどう決めるか（設定として順序を保持するか、項目の定義順に従うか）は本項では確定させず**、受け入れ基準 3.4・未確定事項 ⑤ に従う
  - **選択肢が選ばれたときに、対応する入力欄と例が順番に提示されるという振る舞いそのものの定義**（REQ-035）。何をどの順で提示するかを本フィーチャーが決める
  - 設定内容を保存し、発行依頼書登録変更画面のチュートリアルから参照できる状態にする（REQ-035）
  - 設定の削除の扱い（削除の方式は未確定事項 ⑧）
  - ログインユーザーの会社コードによるデータ範囲の絞り込み（`steering/security.md` の所有権・エンティティ境界）
- **扱わない範囲（Out of Scope）**:
  - 発行依頼書の登録・変更・発番。`issue-request` が持つ（REQ-026 / REQ-028）
  - **発行依頼書登録変更画面への組み込み（画面側の実装）**。本フィーチャーが定義した振る舞いに従って画面部品を描画し、利用者の選択に反応させる実装は `issue-request` が担う（`.aidd/feature-list.md` の `依存` 列。`issue-request` の目的に「チュートリアルによる入力補助」が含まれる）。**振る舞いの定義そのものは本フィーチャーの 扱う範囲（In Scope）である**
  - 設定内容をサンプルより入力できるボタン。`issue-request` が持つ（REQ-029）
  - バーコード生成（REQ-037 / REQ-038 / REQ-039）、単独局／複数局の切替（REQ-030）、金額の自動計算（REQ-031）。いずれも `issue-request` が持つ
  - 現行の設定用ウインドウ（26 フォーム）そのものの改修。RFP の区分は「新規」であり、相当する画面を新たに作る（REQ-036）
  - 権限制御の方式そのものの定義。方式の正は `steering/security.md` であり、本フィーチャーはそれに従う（REQ-046 は `制約` 分類のため feature 割当の分母外 — `.aidd/feature-list.md`）
- **隣接する仕組みへの期待（Adjacent）**:
  - `issue-request`: 本フィーチャーが定義したチュートリアルの設定内容と振る舞いの定義を読み取り、発行依頼書登録変更画面へ組み込む（画面側の実装）。**何を表示するか・どの順で表示するかは本フィーチャーの定義に従い、`issue-request` 側で新たに決めない**（REQ-035 / `.aidd/feature-list.md` の `依存` 列で同 feature が本 feature に依存する）
  - 既存 WiNG の共通基盤: 認証・セッション（`LoginService` / `SessionCheckInterceptor`）、権限制御（`AccessControlInterceptor` + `@FuncID`）を提供する（`steering/architecture.md` の共通基盤 / `steering/security.md`）

> _書き方_: 1 項目に「扱わないこと / 理由 / どこで扱う予定か」をまとめて書く。

- 既存 WTG 機能（契約情報変更・参照、支払実績データ作成／変更／参照、電力会社直受支払実績変更、契約支払情報インポート、契約基本情報インポート、インボイス情報インポート）の仕様変更。デグレードを発生させない対象であり、新規の Controller / Service / Mapper / Form を追加する形で実装する（REQ-052 / REQ-073 / `steering/tech.md` の新規機能の追加方針）

## 要件（Requirements）

### 要件 1: チュートリアル設定画面の提供

> 由来する要求ID: REQ-036

**利用者ストーリー（User Story）**: チュートリアルの設定を担当する利用者として、チュートリアルの設定を行う画面を使いたい。なぜなら発行依頼書の入力を誘導する内容を自分で用意する必要があるから。

#### 受け入れ基準（Acceptance Criteria）

1.1. システムはチュートリアル設定画面を新規に作成し、画面ID・PGID を既存の体系（`GWTG` + 3 桁 / `PWTGO` + 3 桁）に従って採番しなければならない（REQ-051 / `steering/tech.md` の命名規則）。採番の具体値と、画面を何本のプログラムに分割するかは基本設計で確定する（未確定事項 ①）。\
1.2. ログインしていないセッションから本画面のリクエストが行われた場合、システムは画面を表示せずログイン画面へ遷移させなければならない（`steering/security.md` の認証フロー）。\
1.3. ログインユーザーが本画面の機能ID（PGID）に対する権限を持たない場合、システムは画面を表示せずエラー画面にメッセージIDに対応する文言を表示しなければならない（`steering/security.md` の認可 / `InvalidAccessErrorException`）。\
1.4. システムは設定の検索・更新の SQL の `WHERE` 条件に、ログインユーザーの会社コードを必ず含めなければならない（`steering/security.md` の所有権・エンティティ境界 / `steering/database.md` のクエリパターン）。\
1.5. 入力チェックでエラーが検出された場合、システムは元の画面を再表示し、`BindingResult` に積んだ全件のエラーを該当項目の近くに表示しなければならない（`steering/api-standards.md` のエラーハンドリング）。

### 要件 2: 現行の設定用ウインドウ 26 フォーム相当の設定項目

> 由来する要求ID: REQ-036

**利用者ストーリー（User Story）**: チュートリアルの設定を担当する利用者として、現行の設定用ウインドウで行っていた設定を新しい画面でも行いたい。なぜなら現行でできていた設定ができなくなると業務が成り立たないから。

#### 受け入れ基準（Acceptance Criteria）

2.1. システムは現行の設定用ウインドウ 26 フォーム（画面）に相当する設定項目を、本フィーチャーの画面で設定できるようにしなければならない（REQ-036）。\
2.2. システムは現行の 26 フォームそれぞれが持つ設定項目を、基本設計で洗い出した内容に従わなければならない。洗い出しの前提資料として付録A の現行システム機能一覧を用いる（REQ-073）。**各フォームの設定項目と、その入手元（付録A で足りるか、現行システムの調査や発注者への確認を要するか）は基本設計で確定する**（未確定事項 ②）。\
2.3. システムは 26 フォーム相当を 1 画面に集約するか複数画面に分けるかを、基本設計で確定した構成に従わなければならない（REQ-010 / 未確定事項 ③）。\
2.4. 設定が登録・変更されたとき、システムは入力された内容を保存し、以降の表示・変更の対象にしなければならない。\
2.5. 既存の設定を変更して保存したとき、システムは排他フラグ（`ExclusiveFG`）を `WHERE` 条件に含めて更新し、更新件数が 0 件の場合は排他エラー（`ExclusiveException`）として処理しなければならない（`steering/database.md` のクエリパターン）。\
2.6. システムは設定を保持する新規テーブルを、既存の命名規則と共通カラム（`CompanyCD` / `RegisteredPerson` / `RegisteredDT` / `UpdatedPerson` / `UpdatedDT` / `ExclusiveFG`）の規約に沿って追加しなければならない（`steering/database.md` の命名規則）。\
2.7. 登録済みの設定に対して削除の操作が行われたとき、システムは当該設定を以降のチュートリアルの参照対象から外さなければならない。**このとき受け入れ基準 2.5 と同じく排他フラグ（`ExclusiveFG`）を `WHERE` 条件に含めて更新し、更新件数が 0 件の場合は排他エラー（`ExclusiveException`）として処理しなければならない**（`steering/database.md` のクエリパターン）。**削除を論理削除で扱うか物理削除で扱うかは基本設計で確定した内容に従わなければならない**（`steering/database.md` の `## 設計思想` は物理削除を既定とせず、画面に表示して編集だけを制御する必要があるデータは論理削除で扱うと定める / 未確定事項 ⑧）。

### 要件 3: 選択肢に応じた入力欄と例の順次表示の定義

> 由来する要求ID: REQ-035

**利用者ストーリー（User Story）**: チュートリアルの設定を担当する利用者として、選択肢とそれに対応する入力欄・記入例・表示の順番を定義したい。なぜならチュートリアルは選択肢により順番に入力欄と例が表示される仕組みだから。

#### 受け入れ基準（Acceptance Criteria）

3.1. システムはチュートリアルの設定として、**選択肢**と、選択肢に対応して表示する**入力欄**および**例**を定義できるようにしなければならない（REQ-035）。\
3.2. システムは選択肢が選ばれたときに、対応する入力欄と例が**順番に**提示されるという振る舞いを、チュートリアルの設定として定義できるようにしなければならない（REQ-035）。順序の持ち方（設定として順序を保持するか、項目の定義順に従うか）は受け入れ基準 3.4 に従い、本基準では確定させない。\
3.3. システムは選択肢の種類と、選択肢ごとに表示する入力欄・例の対応を、基本設計で確定した内容に従わなければならない（未確定事項 ④）。\
3.4. システムは表示順序の決まり方（設定として順序を持たせるか、項目の定義順に従うか）を、基本設計で確定した内容に従わなければならない（未確定事項 ⑤）。\
3.5. システムは定義した設定内容と振る舞いの定義を、発行依頼書登録変更画面のチュートリアルから参照できる形で保存しなければならない（REQ-035）。**画面への組み込み（画面側の実装）**は `issue-request` が行う（`## スコープの境界（Boundary Context）` の 扱わない範囲（Out of Scope）／隣接する仕組みへの期待（Adjacent））。\
3.6. システムは設定内容の適用範囲（会社単位・利用者単位のいずれか）を、基本設計で確定した内容に従わなければならない（未確定事項 ⑥）。いずれの範囲であっても、会社コードによる絞り込みは受け入れ基準 1.4 に従わなければならない。
