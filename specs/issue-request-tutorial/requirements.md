## Introduction（概要）

> このフィーチャーが何のために、誰のためにあるかを 2〜3 段落で書く。`背景` はなぜ今このフィーチャーが必要か、`対象ユーザー` は想定する利用者像、`期待する変化` はこのフィーチャーがあると何が変わるか。

発行依頼書チュートリアル設定は、発行依頼書の入力を誘導するチュートリアルの設定を作るための画面である（REQ-036）。チュートリアルは選択肢により順番に入力欄と例が表示される仕組みであり、その表示内容と順序をここで定義する（REQ-035）。

現行は設定用ウインドウが 26 フォーム（画面）に分かれており、これに相当する画面を新規に実現する（REQ-036。RFP の区分は「新規」）。何本のプログラムに分割するかは基本設計で決定する（REQ-010）。

設定という用事がこの画面で完結するため User Feature である（`.aidd/feature-list.md`）。依存を持たないが、`issue-request`（優先度 4）のチュートリアルが動作するには設定が先に存在する必要があるため、優先度 3 に置かれている。

- **背景**: 契約書発行依頼業務は入力項目が多すぎるとの指摘があり（REQ-002）、誤入力による不備指摘のやり取りが契約書発行までの納期を延ばしている（REQ-003）。システム側の入力補助で入力の負担を下げる手段の一つがチュートリアルである（REQ-002 / REQ-035）
- **対象ユーザー**: チュートリアルの設定を担当する利用者（`.aidd/feature-list.md` の種別の判定）。設定されたチュートリアルを使うのは発行依頼書を登録・変更する担当者である（`steering/product.md` の対象ユーザー）
- **期待する変化**: 発行依頼書の入力時に、選択肢に応じて必要な入力欄と記入例が順番に提示されるようになり、入力項目の多さに起因する負担と誤入力が減る（REQ-002 / REQ-003 / REQ-035）

> プロダクトレベルの目的・価値は steering の `product.md` を参照。ここではこのフィーチャー固有の文脈を書く。

## Boundary Context（境界文脈）

> スコープの誤読が起こりやすい場合や、隣接するシステム / スペックに影響する場合は必ず記述する。
> `_N` の行を項目の数だけ増やす。`Out of Scope` は扱わない振る舞いに加えて理由または委譲先を書く。`Adjacent` は前提として動いている他フィーチャー / API / バッチ、およびこのフィーチャーが依頼している外部側の責務を書く。

- **In Scope（このフィーチャーで扱う）**:
  - チュートリアル設定画面を新規に作成する（REQ-036）
  - 現行の設定用ウインドウ 26 フォーム（画面）に相当する設定項目を扱えるようにする（REQ-036）
  - 選択肢と、選択肢に応じて表示する入力欄・例を設定として定義する（REQ-035）。**表示順序をどう決めるか（設定として順序を保持するか、項目の定義順に従うか）は本項では確定させず**、Requirement 3 の受入基準 4・未確定事項 ⑤ に従う
  - **選択肢が選ばれたときに、対応する入力欄と例が順番に提示されるという振る舞いそのものの定義**（REQ-035）。何をどの順で提示するかを本フィーチャーが決める
  - 設定内容を保存し、発行依頼書登録変更画面のチュートリアルから参照できる状態にする（REQ-035）
  - 設定の削除の扱い（削除の方式は未確定事項 ⑧）
  - ログインユーザーの会社コードによるデータ範囲の絞り込み（`steering/security.md` の所有権・エンティティ境界）
- **Out of Scope（扱わない）**:
  - 発行依頼書の登録・変更・発番。`issue-request` が持つ（REQ-026 / REQ-028）
  - **発行依頼書登録変更画面への組み込み（画面側の実装）**。本フィーチャーが定義した振る舞いに従って画面部品を描画し、利用者の選択に反応させる実装は `issue-request` が担う（`.aidd/feature-list.md` の `依存` 列。`issue-request` の目的に「チュートリアルによる入力補助」が含まれる）。**振る舞いの定義そのものは本フィーチャーの `In Scope` である**
  - 設定内容をサンプルより入力できるボタン。`issue-request` が持つ（REQ-029）
  - バーコード生成（REQ-037 / REQ-038 / REQ-039）、単独局／複数局の切替（REQ-030）、金額の自動計算（REQ-031）。いずれも `issue-request` が持つ
  - 現行の設定用ウインドウ（26 フォーム）そのものの改修。RFP の区分は「新規」であり、相当する画面を新たに作る（REQ-036）
  - 権限制御の方式そのものの定義。方式の正は `steering/security.md` であり、本フィーチャーはそれに従う（REQ-046 は `制約` 分類のため feature 割当の分母外 — `.aidd/feature-list.md`）
- **Adjacent（隣接システム / 隣接スペックへの期待）**:
  - `issue-request`: 本フィーチャーが定義したチュートリアルの設定内容と振る舞いの定義を読み取り、発行依頼書登録変更画面へ組み込む（画面側の実装）。**何を表示するか・どの順で表示するかは本フィーチャーの定義に従い、`issue-request` 側で新たに決めない**（REQ-035 / `.aidd/feature-list.md` の `依存` 列で同 feature が本 feature に依存する）
  - 既存 WiNG の共通基盤: 認証・セッション（`LoginService` / `SessionCheckInterceptor`）、権限制御（`AccessControlInterceptor` + `@FuncID`）を提供する（`steering/architecture.md` の共通基盤 / `steering/security.md`）

## Requirements（要件）

> 要件 ID は **数値**（`1`, `1.1`, `2`, `2.1` ...）のみ。`A`, `B` などのアルファベット ID は使わない。
> 各要件は **User Story** + **Acceptance Criteria（EARS 形式）** で構成する。
> **`### Requirement` のブロックを要件の数だけ複製する。** 要件領域名は、その要件がどの範囲を扱うかが分かる名前にする。

### Requirement 1: チュートリアル設定画面の提供

> 由来する要求ID: REQ-036

**User Story**: チュートリアルの設定を担当する利用者として、チュートリアルの設定を行う画面を使いたい。なぜなら発行依頼書の入力を誘導する内容を自分で用意する必要があるから。

#### Acceptance Criteria（EARS 形式）

> 1 項目 = 1 基準。`_N` の行を基準の数だけ増やす。下の早見表のいずれかのパターンに当てはめて書く。

1. The system shall チュートリアル設定画面を新規に作成し、画面ID・PGID を既存の体系（`GWTG` + 3 桁 / `PWTGO` + 3 桁）に従って採番する（REQ-051 / `steering/tech.md` の命名規則）。採番の具体値と、画面を何本のプログラムに分割するかは基本設計で確定する（未確定事項 ①）。
2. If ログインしていないセッションから本画面のリクエストが行われた場合、then the system shall 画面を表示せずログイン画面へ遷移させる（`steering/security.md` の認証フロー）。
3. If ログインユーザーが本画面の機能ID（PGID）に対する権限を持たない場合、then the system shall 画面を表示せずエラー画面にメッセージIDに対応する文言を表示する（`steering/security.md` の認可 / `InvalidAccessErrorException`）。
4. The system shall 設定の検索・更新の SQL の `WHERE` 条件に、ログインユーザーの会社コードを必ず含める（`steering/security.md` の所有権・エンティティ境界 / `steering/database.md` のクエリパターン）。
5. If 入力チェックでエラーが検出された場合、then the system shall 元の画面を再表示し、`BindingResult` に積んだ全件のエラーを該当項目の近くに表示する（`steering/api-standards.md` のエラーハンドリング）。

### Requirement 2: 現行の設定用ウインドウ 26 フォーム相当の設定項目

> 由来する要求ID: REQ-036

**User Story**: チュートリアルの設定を担当する利用者として、現行の設定用ウインドウで行っていた設定を新しい画面でも行いたい。なぜなら現行でできていた設定ができなくなると業務が成り立たないから。

#### Acceptance Criteria（EARS 形式）

1. The system shall 現行の設定用ウインドウ 26 フォーム（画面）に相当する設定項目を、本フィーチャーの画面で設定できるようにする（REQ-036）。
2. The system shall 現行の 26 フォームそれぞれが持つ設定項目を、基本設計で洗い出した内容に従う。洗い出しの前提資料として付録A の現行システム機能一覧を用いる（REQ-073）。**各フォームの設定項目と、その入手元（付録A で足りるか、現行システムの調査や発注者への確認を要するか）は基本設計で確定する**（未確定事項 ②）。
3. The system shall 26 フォーム相当を 1 画面に集約するか複数画面に分けるかを、基本設計で確定した構成に従う（REQ-010 / 未確定事項 ③）。
4. When 設定が登録・変更されたとき、the system shall 入力された内容を保存し、以降の表示・変更の対象にする。
5. When 既存の設定を変更して保存したとき、the system shall 排他フラグ（`ExclusiveFG`）を `WHERE` 条件に含めて更新し、更新件数が 0 件の場合は排他エラー（`ExclusiveException`）として処理する（`steering/database.md` のクエリパターン）。
6. The system shall 設定を保持する新規テーブルを、既存の命名規則と共通カラム（`CompanyCD` / `RegisteredPerson` / `RegisteredDT` / `UpdatedPerson` / `UpdatedDT` / `ExclusiveFG`）の規約に沿って追加する（`steering/database.md` の命名規則）。
7. When 登録済みの設定に対して削除の操作が行われたとき、the system shall 当該設定を以降のチュートリアルの参照対象から外す。**このとき受入基準 5 と同じく排他フラグ（`ExclusiveFG`）を `WHERE` 条件に含めて更新し、更新件数が 0 件の場合は排他エラー（`ExclusiveException`）として処理する**（`steering/database.md` のクエリパターン）。**削除を論理削除で扱うか物理削除で扱うかは基本設計で確定した内容に従う**（`steering/database.md` の `## 設計思想` は物理削除を既定とせず、画面に表示して編集だけを制御する必要があるデータは論理削除で扱うと定める / 未確定事項 ⑧）。

### Requirement 3: 選択肢に応じた入力欄と例の順次表示の定義

> 由来する要求ID: REQ-035

**User Story**: チュートリアルの設定を担当する利用者として、選択肢とそれに対応する入力欄・記入例・表示の順番を定義したい。なぜならチュートリアルは選択肢により順番に入力欄と例が表示される仕組みだから。

#### Acceptance Criteria（EARS 形式）

1. The system shall チュートリアルの設定として、**選択肢**と、選択肢に対応して表示する**入力欄**および**例**を定義できるようにする（REQ-035）。
2. The system shall 選択肢が選ばれたときに、対応する入力欄と例が**順番に**提示されるという振る舞いを、チュートリアルの設定として定義できるようにする（REQ-035）。順序の持ち方（設定として順序を保持するか、項目の定義順に従うか）は受入基準 4 に従い、本基準では確定させない。
3. The system shall 選択肢の種類と、選択肢ごとに表示する入力欄・例の対応を、基本設計で確定した内容に従う（未確定事項 ④）。
4. The system shall 表示順序の決まり方（設定として順序を持たせるか、項目の定義順に従うか）を、基本設計で確定した内容に従う（未確定事項 ⑤）。
5. The system shall 定義した設定内容と振る舞いの定義を、発行依頼書登録変更画面のチュートリアルから参照できる形で保存する（REQ-035）。**画面への組み込み（画面側の実装）**は `issue-request` が行う（`## Boundary Context` の `Out of Scope` / `Adjacent`）。
6. The system shall 設定内容の適用範囲（会社単位・利用者単位のいずれか）を、基本設計で確定した内容に従う（未確定事項 ⑥）。いずれの範囲であっても、会社コードによる絞り込みは Requirement 1 の受入基準 4 に従う。

## Out of Scope（明示的に対象外）

> Boundary Context だけで誤読を防ぎきれないとき、追加でここに書く。
> 1 項目 = 1 件。`_N` の行を件数だけ増やす。対象外にするものと、なぜ対象外か、どこで扱う予定かを書く。

- 既存 WTG 機能（契約情報変更・参照、支払実績データ作成／変更／参照、電力会社直受支払実績変更、契約支払情報インポート、契約基本情報インポート、インボイス情報インポート）の仕様変更。デグレードを発生させない対象であり、新規の Controller / Service / Mapper / Form を追加する形で実装する（REQ-052 / REQ-073 / `steering/tech.md` の新規機能の追加方針）
- 設定内容のデータ移行。現行の設定用ウインドウ 26 フォームが保持している設定を新しい画面へ移すかどうかを含め、データ移行のテストは発注者にて実施する前提である（REQ-054）
- チュートリアル以外の入力補助。設定内容をサンプルより入力できるボタン（REQ-029）は `issue-request` が持つ

## Dependencies / Assumptions（前提と依存）

> `前提` はこのフィーチャーが成立するために真でなければならない事項、`依存` は他フィーチャー / 既存システム / 外部 API / データ、`未確定事項` は調査・確認待ちのトピック（design に進む前に解消する）。

- **前提**: 既存 WiNG の認証・セッション・権限制御の仕組み（`LoginService` / `SessionCheckInterceptor` / `AccessControlInterceptor`）がそのまま利用できること（REQ-009 / REQ-053）。現行の設定用ウインドウ（26 フォーム）の仕様が確認できること（REQ-036）。付録A の現行システム機能一覧は前提資料として用いるが（REQ-073）、**各フォームが持つ設定項目まで付録A から確認できるとは限らないため、設定項目の入手元は未確定事項 ② に含める**
- **依存**: `.aidd/feature-list.md` の `依存` 列は「なし」。本フィーチャーは他 feature の完成を前提としない。既存 WiNG の共通基盤（認証・セッション・権限制御）には依存する。なお `issue-request` は本フィーチャーに依存する側であり、本フィーチャーからの依存ではない
- **未確定事項**: 次の 8 件は **いずれも基本設計で確定する**（REQ-010。Phase 4 の共通の扱いとして人間が確定 / 2026-09-11）。
  - ① **画面ID・PGID の採番の具体値**と、画面を何本のプログラムに分割するか（REQ-010 / REQ-051）
  - ② **現行の設定用ウインドウ 26 フォームそれぞれが持つ設定項目と、その入手元**（REQ-036）。要求一覧は「26 フォーム（画面）に相当する画面」までしか述べておらず、各フォームの中身は付録A を前提資料として基本設計で洗い出す（REQ-073）。付録A（現行システム機能一覧）は既存資産の把握のための資料であり、**各フォームの設定項目まで記載されているとは限らない**ため、付録A で足りるか、現行システムの調査や発注者への確認を要するかを含めて確定する
  - ③ **26 フォーム相当を 1 画面に集約するか複数画面に分けるか**（REQ-010 / REQ-036）
  - ④ **「選択肢」の種類と、選択肢ごとに表示する入力欄・例の対応**（REQ-035）
  - ⑤ **入力欄と例の表示順序の決まり方**（設定として順序を持たせるか、項目の定義順に従うか）（REQ-035）
  - ⑥ **設定内容の適用範囲**（会社単位・利用者単位のいずれか）（REQ-035 / REQ-036）。**「全社共通」は選択肢から外す** — `steering/security.md` の `#### 所有権・エンティティ境界` が会社コードを全テーブル共通のキーに含めログインユーザーの会社コードで絞り込むと定めており、Requirement 1 の受入基準 4 と両立しないため
  - ⑦ **設定内容の変更履歴を残すかどうか**。履歴管理の要求（REQ-034）は `issue-request` に割り当てられており本フィーチャーの `対応要求ID` に含まれないため、本書では履歴の要件を立てていない（`.aidd/feature-list.md`）
  - ⑧ **設定の削除の扱い**（削除を論理削除で扱うか物理削除で扱うか）（REQ-010 / REQ-036）。`steering/database.md` の `## 設計思想` は物理削除を既定とせず、画面に表示して編集だけを制御する必要があるデータは論理削除で扱うと定めている。削除の振る舞い自体は Requirement 2 の受入基準 7 で扱う
